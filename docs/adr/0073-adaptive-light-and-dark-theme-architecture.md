# ADR 0073: Adaptive Light and Dark Theme Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-16
- Scope: ECL 桌面应用的浅色/深色主题、语义颜色资源、主题运行时切换、系统主题偏好及主题相关窗口与控件适配
- Related: [ADR 0050: ECL UI Architecture and Design System Overhaul](0050-ecl-ui-architecture-and-design-system-overhaul.md)、[ADR 0021：WPF 交互反馈与轻量动效系统](0021-wpf-interaction-and-motion-system.md)
- Supersedes: [ADR 0050: ECL UI Architecture and Design System Overhaul](0050-ecl-ui-architecture-and-design-system-overhaul.md)（仅取代其中固定深色模式、禁止浅色模式的主题模式约束；不取代其余 UI 架构决策）

## 背景

ECL 当前以深色界面作为唯一品牌主题呈现。ADR 0050 将这一选择固化为全局约束：不提供浅色模式，也不允许用户切换主题模式。随着页面体系和使用场景逐渐成熟，需要重新评估这一限制。

深色界面可以突出 ECL 的紫色品牌元素，但深色背景与高亮紫色的大面积组合也可能形成较强的视觉重量。浅色主题能够为偏好明亮界面、长时间阅读或不同环境光条件下使用 ECL 的用户提供另一种呈现方式。增加浅色主题不意味着更换品牌，也不意味着必须重写页面。

代码初步检查发现，当前 `src/ECL.App/Themes/Theme.xaml` 已集中定义 Background、Sidebar、Surface、Input、Border、Text、Accent、Success、Warning、Danger、Scrim 等语义颜色资源；页面大量通过 `DynamicResource` 引用这些资源。该基础有利于扩展主题，但当前 `App.xaml` 仅合并一套 `Theme.xaml`，尚未确认完整的运行时切换实现。

同时，`SplashWindow.xaml` 存在直接写入 XAML 的深色背景、紫色装饰和文字颜色。主题适配不能只覆盖主窗口，也必须识别启动窗口、独立窗口、弹窗、图表、图例、阴影及其他非标准绘制路径。

本 ADR 是对 ADR 0050 主题模式约束的局部修订提案。它不改变 ECL 的品牌身份，不要求重新设计 Application Shell、导航、页面信息架构、排版、DPI 策略或现有页面布局。

## 决策

### 1. 同一品牌设计系统提供浅色与深色两种主题

ECL 提供两种一等主题：

- **ECL Dark**：保留现有深色视觉作为默认基准，继续使用紫色品牌强调。
- **ECL Light**：采用低刺激的中性浅色表面与深紫色交互强调，维持与 ECL Dark 相同的品牌识别和信息层级。

两种主题是同一套 Design System 的不同颜色方案，不是两套独立 UI。页面结构、组件尺寸、字体、间距、圆角、动效、图标和交互语义必须保持一致。不得为浅色主题复制页面或建立另一套控件模板。

品牌紫色仍是 ECL 的固定产品身份色，不提供用户自定义品牌色或任意颜色编辑器。允许主题根据背景亮度使用不同明度和饱和度的紫色变体，以满足可读性和对比度要求；这些变体必须属于同一品牌色阶，不得形成互不相关的第二品牌色。

### 2. 主题模式与用户偏好

主题模式至少支持：

- `Light`：始终使用浅色主题。
- `Dark`：始终使用深色主题。
- `System`：跟随 Windows 当前应用主题偏好；无法可靠读取系统偏好时回退到 ECL Dark。

首次安装或没有用户设置时，默认采用 `System`。用户可以在外观设置中选择模式。不得在每次启动时无条件覆盖用户明确选择的 Light 或 Dark。

主题模式是表现层偏好，不得影响实例、账户、下载、启动、Addition、持久化数据或业务规则。切换主题不得触发应用重启、页面导航、数据重载或正在运行任务的中断。

设置值应使用稳定且可迁移的枚举/字符串语义（`System`、`Light`、`Dark`），不得将当前解析出的主题结果当作用户偏好持久化。系统模式下系统偏好发生变化时，应更新当前主题；显式 Light/Dark 模式不跟随系统变化。

### 3. 使用语义令牌，不允许页面直接选择主题颜色

所有主题相关颜色必须由统一语义令牌提供。页面、ViewModel 和控件模板不得根据当前主题自行判断并写入 HEX/RGB 值，也不得通过条件分支维护两套页面颜色。

至少覆盖以下令牌类别：

- 背景与层级：`Background`、`Sidebar`、`Surface`、`SurfaceAlt`、`Input`、`SurfaceHover`、`SurfacePressed`。
- 边界：`Border`、`BorderSoft`、`BorderStrong`。
- 文本：`TextPrimary`、`TextSecondary`、`TextMuted`、必要时提供适用于反色/特殊表面的文本令牌。
- 品牌强调：`Accent`、`AccentHover`、`AccentPressed`、`AccentSoft`、`AccentGlow`、`AccentBorder`、`AccentText`。
- 状态语义：`Success`、`Warning`、`Danger` 及其 Soft、Border、Hover 等配套令牌。
- 其他界面资源：`ScrollThumb`、`Scrim`、图表/图例所需的语义色，以及实际代码中发现的其他主题相关颜色。

状态色、加载器识别色、存储分类色等具有独立语义的颜色不应被错误地全部替换为品牌紫色；但其在浅色与深色背景上的可见性必须分别验证。

控件的正常、悬停、按下、选中、焦点、禁用、错误和只读状态都必须通过语义令牌表达。复选框、开关、选中导航项和主操作按钮可以使用主题对应的 Accent 变体，但同一交互语义在两种主题中必须一致。

### 5. 主题资源组织与运行时切换

建议将主题颜色值与共享控件样式分离：

- 共享 Design System 保留字体、字号、间距、控件模板、圆角、动效和非主题布局资源。
- ECL Dark 与 ECL Light 分别提供完整且键名一致的主题资源字典。
- 两套主题字典必须定义相同的必需语义令牌；不得在切换后出现缺失资源或静默回退到另一主题的颜色。
- 应用级主题服务负责解析用户偏好、监听系统主题变化、选择主题资源字典并通知界面刷新。
- 主题切换应通过统一入口完成，禁止页面或 ViewModel 直接操作资源字典。

WPF 资源切换必须经过实机验证。所有需要随主题变化的消费者应使用适当的动态资源引用；需要检查 `StaticResource` 的间接引用、控件模板、转换器、代码创建的 Brush、缓存画刷和第三方控件是否会保留旧颜色。

运行时切换应避免短暂显示错误颜色、资源缺失异常或局部区域未更新。若第三方控件无法使用语义资源，应通过统一适配层处理；不得将不兼容控件作为忽略主题一致性的理由。

本 ADR 不预先规定具体 ThemeService 类名、设置存储键或资源字典文件名；这些实现细节应在代码审查后确定。

### 6. 窗口、弹窗与特殊绘制区域必须纳入主题

主题覆盖范围包括但不限于：

- 主窗口 Shell、主导航、Right Auxiliary Rail、Workspace 与所有页面。
- 统一 Dialog Engine、独立对话框、菜单、ContextMenu、ToolTip、Popup、ComboBox 下拉列表及浮层。
- SplashWindow、首次启动向导、独立工具窗口和其他非主窗口 UI。
- 图表、进度可视化、状态徽标、图例、空状态、错误状态和加载占位。
- 滚动条、焦点环、选中项、拖放反馈、遮罩和阴影。
- 自绘控件、Drawing/Geometry、代码生成的 Brush、位图资源及第三方控件。

阴影、遮罩和透明度必须按主题分别校准。深色主题中常见的黑色阴影不能原样套用到浅色主题；浅色主题应优先使用边界和表面层级表达结构，避免过重投影。SplashWindow 可以保留品牌图形与启动识别，但不得继续把整套深色背景作为唯一不可切换的主题实现；若启动发生在主题偏好尚未加载前，应使用稳定且无闪烁的启动策略，并在进入主界面前正确应用最终主题。

### 7. 保持品牌与可读性，不以主题切换牺牲可访问性

- 品牌紫色是固定身份色；两套主题允许使用不同明度的紫色变体，以保证在各自表面上的可读性。
- 正文、辅助文本、按钮文字、图标、边框、焦点环和状态色必须分别验证，不得仅验证主背景与主文字。
- 正常文本目标对比度至少为 WCAG 2.2 AA 的 4.5:1；大号文本至少为 3:1。非文本控件边界、图形信息和必要状态指示至少达到 3:1 的适用对比度要求。
- 禁用状态可以降低视觉强调，但不得让仍需理解的状态信息完全不可辨认；若法律/标准对特定禁用元素有例外，也不能据此降低普通信息的可读性。
- 不能只依赖颜色区分成功、警告、危险、选中和错误状态；应同时使用图标、文字、形状或其他可识别信号。
- 两种主题均需检查色觉差异、灰度显示、系统高对比度偏好及键盘焦点可见性。

### 8. 主题偏好不改变其他用户界面偏好

主题模式应与字体、缩放、语言、动效等外观偏好保持独立。不得因选择浅色主题而重置字体、缩放、语言或动效设置。主题切换不得修改页面信息架构、控件尺寸、文字内容或功能可用性。

## 备选方案

### 方案 A：继续只提供深色主题

实现成本最低，也能保持当前 ECL 的既有视觉。但它把产品的视觉选择限制为单一偏好，无法适应不同用户和环境；当前语义资源基础也没有得到充分利用。

### 方案 B：提供两套独立 UI

为 Light 和 Dark 分别实现页面、控件模板或视觉分支，短期可以自由调整每套界面，但会造成双倍维护成本、页面行为漂移和持续回归风险。该方案不采用。

### 方案 C：共享 UI + 语义令牌 + 可切换主题资源（采用）

共享页面、控件与交互行为，只切换完整的语义颜色资源。它可以保留现有页面体系，集中控制颜色，并为未来系统主题适配提供明确边界。代价是必须认真治理资源引用和运行时切换行为，因此采用该方案。

## 后果

### 正面影响

- 用户可以根据环境与偏好选择浅色、深色或跟随系统。
- ECL 保留紫色品牌身份，不需要为了浅色模式更换品牌。
- 页面结构和控件只维护一套，避免主题分支导致的二次页面重写。
- 当前语义资源体系可以继续复用，改造重点集中在资源组织、运行时切换和漏网的硬编码颜色。
- 主题模式可以独立演进，不影响实例、启动、下载和 Addition 领域。

### 代价与风险

- 需要盘点 XAML、C#、转换器、自绘控件、图表和第三方控件中的硬编码颜色与静态资源引用。
- WPF 资源字典切换涉及 DynamicResource/StaticResource 行为差异，必须通过真实窗口和控件验证。
- SplashWindow 与独立窗口可能在应用设置加载前创建，需要避免主题闪烁和主题状态不一致。
- 两套主题都需要视觉回归与对比度检查，增加 UI 验收矩阵。
- 浅色主题如果仅做机械反色，容易造成边框过重、紫色突兀、层级混乱或状态色不可读；必须按语义逐项设计。

## 验收标准

本 ADR 的 Implementation 只有在以下项目全部完成后才能标记为 Verified：

1. ECL 提供 System、Light、Dark 三种模式；首次使用默认 System，显式用户选择能够跨重启保留。
2. System 模式能够跟随 Windows 应用主题偏好变化；系统偏好无法读取时按决策回退到 Dark。
3. Light/Dark 切换无需重启，不触发页面导航、数据重载或后台任务中断。
4. 两种主题的必需语义令牌完整且键名一致；不存在切换后资源缺失、主题混色或未更新区域。
5. 页面和控件没有因主题模式增加重复实现或按主题分支的业务逻辑。
6. 完成全仓库颜色来源盘点，覆盖 XAML、C#、转换器、自绘控件、图表、启动窗口、弹窗、菜单、Popup、ToolTip 和第三方控件；每个例外都有明确理由。
7. 主窗口、所有主要页面、SplashWindow、独立窗口、统一弹窗、菜单、下拉列表、滚动条、图表和状态徽标在两种主题下均正确显示。
8. 正文与大号文本达到 WCAG 2.2 AA 对比度要求；非文本控件边界和必要图形信息达到适用的 3:1 要求。提供可复核的对比度测试记录。
9. 主按钮、次按钮、悬停、按下、焦点、选中、禁用、错误、警告和成功状态在两种主题下均有一致语义且可辨认。
10. 浅色主题没有大面积纯白刺眼区域、过重阴影或高饱和紫色背景；深色主题没有因迁移产生明显色差和层级退化。
11. 完成 100%、125%、150%、175% DPI 下的主题切换与跨显示器测试；主题切换前后布局、字体和命中区域保持正确。
12. 完成构建、自动化测试与实机视觉回归；账户、实例、启动、下载、弹窗、Addition 加载及长时间运行任务不因切换主题回归。
13. 记录 System 模式下系统主题动态变化、用户显式选择、应用重启、启动窗口首次呈现和运行中切换的验证证据。
