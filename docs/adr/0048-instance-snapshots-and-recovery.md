# ADR 0048：实例快照与恢复架构

- Decision: Accepted
- Implementation: Implemented
- Date: 2026-11-03
- Scope: 用户主动快照、事务前态保护、内容寻址存储、差异识别、恢复与保留策略
- Related: [ADR 0018：Minecraft 工作区与实例存储位置](0018-minecraft-workspace-and-instance-storage.md)、[ADR 0027：原生 C# 世界分析与编辑引擎](0027-native-world-engine.md)、[ADR 0045：原生 Instance Engine 架构与能力边界](0045-native-instance-engine-architecture.md)、[ADR 0046：实例稳定身份与元数据模型](0046-instance-identity-and-metadata.md)、[ADR 0047：实例变更事务与并发控制](0047-instance-transactions-and-concurrency-control.md)

## 背景

实例更新、模组调整、配置修改和整合包变更可能导致原有环境无法启动或资源丢失。用户需要在操作前保存状态，并在之后比较或恢复。

事务系统也需要保留修改前状态，以便在操作失败或进程异常退出时恢复。但事务恢复与用户主动创建的长期快照目的不同：前者服务于一次操作的一致性，后者服务于用户跨时间点的备份与回退。

## 决策

### 1. 区分事务恢复材料与用户快照

两者可以共享底层内容存储、哈希、文件清单和恢复执行器，但必须拥有不同的逻辑类型、生命周期和保留策略：

- **Transaction Recovery Data：** 由 ADR 0047 的事务自动生成，短期保留，直到事务提交且恢复窗口结束，或 NeedsRecovery 被解决；
- **User Snapshot：** 用户主动或按用户配置创建，长期保留，用户可以查看、命名、比较、导出或恢复。

不得将事务临时备份直接显示成用户快照，也不得因用户清理旧快照而删除仍被未完成事务引用的恢复材料。

### 2. 快照内容以清单和内容指纹为基础

快照应记录实例身份、创建时间、快照格式版本、包含范围、排除范围、文件清单、文件元数据和内容哈希。实际文件内容可以采用内容寻址存储与去重，以减少重复快照的空间开销。

哈希用于识别内容和校验完整性，不代表来源可信。快照必须能够检测缺失对象、损坏对象和不完整创建状态。

### 3. 默认本地存储并明确存储位置

快照默认保存在 ECL 本地数据目录或用户明确选择的本地存储位置，不上传到 ECL 服务或第三方。存储位置应与实例目录分离，避免实例损坏或删除时同时丢失唯一备份。

用户选择外置磁盘或网络路径时，应提示离线、性能和可用性风险。快照空间占用、保留数量和清理规则必须可见；不得静默删除用户快照以腾出空间。

### 4. 快照范围必须明确，世界数据需要特殊保护

快照创建前应允许用户查看包含与排除范围，并按场景提供合理预设，例如：
- 完整实例快照；
- 游戏环境快照（版本、Loader、模组、配置和资源）；
- 指定世界存档快照。

世界存档可能在游戏运行时持续写入。无法获得一致性保证时，应提示关闭游戏后创建，或采用明确的只读/一致性策略；不得把跨文件复制得到的非一致状态标记为完整可恢复快照。

账户凭据、令牌、ECL 私有配置和不属于实例的用户数据默认排除。快照范围不得因目录名称模糊而擅自扩大。

### 5. 恢复必须是显式事务

恢复操作遵循 ADR 0047：
1. 检查快照完整性、实例身份与目标路径；
2. 展示将覆盖、创建、删除或保留的内容差异；
3. 检查磁盘空间、权限、游戏进程占用和目标状态；
4. 准备恢复前态材料；
5. 通过事务应用快照；
6. 验证恢复结果；
7. 成功后提交并更新 Inventory。

默认不直接覆盖当前状态而不留恢复点。恢复到原实例可保留 InstanceId；恢复为并行副本必须生成新的 InstanceId。快照身份冲突和格式不兼容必须明确处理。

### 6. 差异比较复用 Inventory 与内容指纹

快照与当前实例之间的比较应识别新增、删除、修改和未能比较的文件/资源。比较结果必须区分内容哈希一致、仅元数据变化、无法读取和扫描不完整；不得把无法访问的文件当作未变化。

模组、资源包、配置和世界等语义差异应复用 Inventory 的识别结果，不另建互不兼容的资源识别系统。

### 7. 保留策略由用户控制

ECL 可以提供数量、时间或空间上限建议，但默认不得静默删除用户创建的快照。自动快照若启用，必须允许用户配置触发时机、保留策略和存储上限，并在删除前明确说明受影响快照。

事务恢复材料可以按事务状态自动清理，但必须证明它不再被任何未完成事务引用。

## 备选方案

### 方案 A：只使用 ZIP/目录复制

优点是实现简单、文件容易被其他工具读取。

放弃原因：重复快照占用大、缺少可靠差异索引，且难以与事务恢复和 Inventory 统一。

### 方案 B：仅依赖事务前态备份

优点是无需额外用户快照功能。

放弃原因：事务恢复材料生命周期短，不能满足用户主动保存历史环境和跨时间点恢复的需求。

### 方案 C：共享底层存储、区分事务恢复与用户快照

选择原因：可复用内容寻址、哈希和恢复执行器，同时避免两种数据生命周期互相污染。

## 后果

### 正面影响

- 用户可以在重要变更前保存可恢复状态；
- 事务失败恢复与用户长期备份复用底层能力；
- 差异比较可复用 Inventory；
- 快照不会与实例原始目录绑定在同一故障域。

### 代价与风险

- 快照可能占用大量磁盘空间，需要去重、配额与清理策略；
- 一致性快照尤其是运行中的世界存档需要额外处理；
- 内容寻址存储需要垃圾回收与引用计数/可达性校验；
- 恢复操作本身也可能失败，因此必须依赖事务系统并保留恢复前态。

## 验收标准

1. 用户快照与事务恢复材料有独立类型、生命周期和 UI。
2. 快照包含实例身份、格式版本、文件清单、内容指纹和范围说明。
3. 快照默认本地保存，存储位置可识别，未经授权不会上传。
4. 创建不完整、损坏或无法一致读取的快照不会被标记为完整可恢复。
5. 恢复前展示差异、覆盖范围、空间和风险，并通过事务执行。
6. 恢复失败时保留恢复前态或明确进入 NeedsRecovery。
7. 恢复到原实例保留身份，恢复为并行副本生成新身份。
8. 快照差异比较复用 Inventory，并准确表示未知与未完成状态。
9. 用户快照不会被后台策略静默删除；事务恢复材料仅在不再被引用后清理。
10. 世界存档运行中一致性不足时明确提示，不宣称获得可靠快照。
