# ADR 0019：内存压力下的进程保活与诊断连续性

- Status: Accepted
- Date: 2026-11-01
- Scope: 游戏进程监督、日志采集进程、ECL 主 UI、内存压力与异常恢复

## 背景

ECL 同时管理 Minecraft 游戏进程并提供日志采集、会话追踪和诊断导出。游戏可能在高内存占用下运行；此时 ECL 主程序也可能持有日志缓冲、UI 状态、资源缓存和其他业务对象。系统内存或提交内存压力可能导致分配失败、进程崩溃、分页抖动，甚至使日志管道阻塞。

ECL 的日志采集能力是诊断体系的关键部分。若只保留游戏而终止唯一的 stdout/stderr 管道读取者，管道缓冲区可能填满并反过来阻塞游戏；若为了保留整个 ECL UI 而持续占用大量内存，又可能加剧游戏的资源压力。

因此，不能简单规定“永远保启动器”或“永远保游戏”。必须将游戏运行、日志采集和 UI 生命周期解耦，并明确各自的资源预算与降级行为。

本 ADR 与 [ADR 0015：按进程隔离游戏日志会话与诊断证据](0015-process-scoped-game-log-sessions-and-diagnostics.md) 配套：ADR 0015 定义日志会话与证据模型，本 ADR 定义资源压力下的进程生存与连续采集边界。

## 决策

### 1. 生存优先级按职责划分，而不是按产品进程名称划分

ECL 采用以下逻辑优先级：

1. **Minecraft 游戏进程：** 不得为了维持 ECL UI 或非必要诊断功能而主动终止游戏。内存压力时优先削减 ECL 非必要资源占用。
2. **最小化日志采集核心：** 对正在使用的 stdout/stderr 管道承担持续读取责任，必须尽可能保持读取与落盘；不得依赖主 UI 进程存活。
3. **ECL 主 UI 与非关键服务：** 可关闭高成本视图、丢弃可重建缓存、限制预览和扫描；必要时允许 UI 进程退出并在事后恢复。

上述顺序不是对 Windows 内核 OOM 处置顺序的保证，也不意味着采集进程可以无限占用资源。游戏运行与日志采集可能存在硬性耦合：若采集进程是管道唯一读取者，必须在其退出前完成管道交接或确保游戏写入端不会永久阻塞。

### 2. 日志采集必须与主 UI 的生命周期解耦

- ECL 不得把管道读取、日志持久化和关键进程状态记录仅实现为主 UI 的后台任务。
- 需要独立的轻量采集宿主（暂定名称 `ECL.LogHost`），或经验证具有等价隔离能力的独立进程边界。
- LogHost 只承担进程输出读取、会话日志写入、关键生命周期事件记录和与主程序的有限 IPC；不得加载 WPF UI、实例浏览器、账户系统或其他非必要业务模块。
- 主 UI 退出、崩溃或重启不得自动终止仍负责活动游戏会话的 LogHost。
- LogHost 必须能在没有主 UI 的情况下持续运行，并在游戏结束后完成会话收尾。
- LogHost 自身崩溃或退出时，必须留下可恢复的会话状态；不得将未确认的游戏退出伪装成正常结束。

### 3. stdout/stderr 管道必须有明确的所有权和背压策略

- 每条重定向管道在任意时刻必须有明确的读取者所有权。
- 读取与磁盘写入应采用有界缓冲，不允许无界内存队列积压日志。
- 读取管道与写入日志文件应尽量解耦：磁盘写入暂时变慢时，使用有界缓冲并触发可观测的降级，而不是无限增长内存。
- 不得在未完成交接的情况下关闭唯一读取端；否则游戏写入可能因管道缓冲区耗尽而阻塞。
- 若采集进程必须退出，应优先执行读取端交接；若平台与实现无法安全交接，应采用经过测试的明确降级策略，并记录日志可能不完整的事实。
- 对磁盘写入失败、磁盘空间不足、访问被拒绝和日志目标离线，必须分别记录状态；不得静默丢弃日志并报告采集成功。
- 文件日志与 stdout/stderr 双来源并存时，应登记来源与去重/关联策略，避免把同一行重复统计为独立证据。

### 4. 采集宿主采用严格的资源预算

- LogHost 不得在内存中长期保存完整日志；原始日志应流式写入会话文件。
- 管道读取缓冲、批量写入缓冲、IPC 消息队列和状态缓存都必须有明确上限。
- IPC 优先传递状态变更、计数、文件位置和小型控制消息；UI 不得要求 LogHost 将全部历史日志复制到内存。
- UI 日志视图应采用有界可视窗口或分页/增量读取，关闭视图不得停止采集。
- 内存压力下首先清理 UI 图片、预览、可重建缓存和非关键索引；再降低日志 UI 刷新频率与非必要后台任务。
- 不得通过提升 ECL 的 CPU 优先级或使用实时优先级来声称解决内存压力。CPU 调度优先级不等同于内存保留或 OOM 保护。
- 不得假设 Windows 会按 ECL 声明的逻辑等级选择终止进程；本 ADR 定义应用自身的降级策略，不控制系统级终止决策。

### 5. 内存压力检测与降级必须分级且可恢复

ECL 应实现可观测的压力状态，而不是仅凭单次分配异常判断系统状态。至少区分：

- Normal：正常运行。
- Elevated：可用物理内存或系统提交余量持续下降，开始削减非关键缓存与后台任务。
- Critical：内存/提交压力严重或关键分配失败，暂停非必要工作、限制 UI、停止新建高内存操作。
- Recovery：压力缓解后逐步恢复功能，避免一次性重建大量缓存。

检测信号、阈值和迟滞窗口应由实现阶段根据 Windows API 与实机数据确定；不得在本 ADR 中虚构固定阈值。压力等级变化必须写入诊断事件，但采样和记录本身不得造成显著内存开销。

进入 Critical 时：
1. 暂停非必要索引、扫描、预览、缩略图和预加载。
2. 释放可重建缓存，限制 UI 日志视图和历史记录驻留。
3. 保证 LogHost 读取活动管道并持续尝试落盘。
4. 阻止新的非必要高内存任务；对用户启动新游戏等操作给出明确提示。
5. 若主 UI 无法安全继续运行，允许其退出，不得连带杀死游戏或 LogHost。

退出压力状态时应分批恢复功能，避免缓存重建造成压力反弹。

### 6. 游戏退出与采集收尾有独立生命周期

- 游戏进程退出不代表日志采集已经完成；LogHost 应排空剩余管道数据、刷新文件并记录最终退出信息。
- 只有在管道 EOF/读取完成、文件写入成功或明确记录失败后，才能将会话标记为采集收尾完成。
- 主 UI 可以在游戏仍运行时退出；LogHost 应继续监督活动会话。
- 主 UI 重启后通过 SessionId 与 LogHost 重新建立连接，并从持久化状态恢复，而不是依赖旧 UI 内存对象。
- ECL 关闭操作必须区分“关闭窗口/退出 UI”与“结束游戏会话”；默认不得把退出 UI 等同于终止游戏。
- 若用户明确要求结束游戏，仍按独立的游戏终止流程执行，不得将其与内存压力处理混为一谈。

### 7. 失败边界与诊断诚实性

- LogHost 不得声称拥有操作系统级内存保护能力。
- 不保证在系统提交内存耗尽、磁盘不可写、文件系统故障、内核终止或突然断电时保存全部日志。
- 每个会话必须记录采集宿主状态、最后成功写入位置/时间、丢失或截断风险、收尾结果。
- LogHost 崩溃后，恢复流程必须区分“游戏进程仍运行”“游戏已退出但管道未确认排空”“进程状态未知”。
- 不得仅因 LogHost 消失就终止游戏；也不得仅因游戏进程消失就认定日志完整。
- 诊断导出应明确标记部分日志、采集宿主异常、磁盘写入失败和最后可确认的持久化位置。

## 后果

### 正面

- 主 UI 崩溃或退出不再必然中断活动游戏会话的日志采集。
- ECL 可以在不牺牲游戏运行的前提下削减自身非关键内存开销。
- 管道背压、日志落盘失败和采集不完整变成可观测状态，而不是隐性故障。
- 会话收尾与 UI 生命周期分离，支持主 UI 重启后恢复诊断视图。

### 代价与约束

- 引入 LogHost 进程、IPC 协议、进程监督和跨进程恢复逻辑。
- 需要明确 LogHost 与主 UI 的启动、重连、关闭、升级和版本兼容策略。
- 独立进程会增加少量固定内存与句柄开销，必须实测并设定预算。
- Windows 内存压力与进程终止行为受系统配置、提交限制和其他进程影响，应用层无法提供绝对保活保证。
- 管道交接、磁盘慢写、LogHost 崩溃和 UI 重启需要专门的压力与故障注入测试。

## 验收标准

1. 主 UI 被强制终止时，活动游戏进程不会因此被 ECL 主动终止。
2. 主 UI 退出或重启期间，LogHost 能持续读取活动游戏 stdout/stderr 并写入会话日志。
3. LogHost 不加载 UI 与非必要业务模块；内存占用、缓冲上限和队列上限有自动化或压力测试证据。
4. 在持续高频日志和磁盘慢写测试中，采集队列不会无界增长，游戏写入端不会因读取端停止而永久阻塞。
5. LogHost 退出/崩溃时，系统不会静默丢弃活动会话状态，也不会仅因此终止游戏。
6. 游戏退出后，LogHost 能排空可读取数据、刷新日志并记录收尾结果；无法完成时明确标记不完整。
7. 内存压力降级能暂停非必要任务、限制 UI 缓存，并在压力解除后分批恢复。
8. 诊断导出能显示采集宿主状态、最后成功持久化位置和日志完整性。
9. 不以 CPU 优先级调整冒充内存保护；不宣称应用可以控制 Windows 的系统级 OOM 终止顺序。
10. 在系统提交内存接近耗尽、磁盘空间耗尽、磁盘写入变慢、LogHost 崩溃、UI 崩溃和游戏崩溃等场景下完成故障注入测试。
