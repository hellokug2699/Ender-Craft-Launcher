# ADR 0042: Instance File Explorer and Crash Report Workflow

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-03
- Scope: 原生实例文件管理器、实例文件与资源清单、资源识别和依赖分析、受限文件操作、崩溃报告诊断联动及导出
- Related: [ADR 0015：按进程隔离的游戏日志会话与诊断证据](0015-process-scoped-game-log-sessions-and-diagnostics.md)、[ADR 0022：存储空间分析与安全清理中心](0022-storage-analysis-and-safe-cleanup-center.md)、[ADR 0026：实例工作台的存档、多人游戏与最近访问](0026-instance-workbench-worlds-servers-and-recent-access.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0033：本地 Minecraft 全面诊断与知识引擎](0033-local-minecraft-diagnostic-and-knowledge-engine.md)

## 背景

玩家经常需要进入 Minecraft 实例目录查看配置、模组、资源包、日志和崩溃报告。当前通常需要离开 ECL，使用 Windows Explorer 或其他文件管理器定位正确的实例目录。对不熟悉目录结构的玩家而言，这增加了查找成本，也容易误操作其他实例或启动器文件。

崩溃报告是诊断流程的重要入口。玩家往往需要先找到报告，再手动打开或复制内容，最后粘贴给社区或他人分析。ECL 已有按进程隔离的日志会话与本地诊断引擎方向，因此可以把文件浏览、报告识别、诊断和分享串成一个连续流程。

本 ADR 不打算在 ECL 中实现一个可访问整台计算机的通用文件管理器，而是提供以实例为安全边界的文件工作区。

## 决策

### 1. Instance File Explorer 是 ECL 原生功能，不是 Addition

Instance File Explorer 的基础浏览器必须作为 ECL 自身的原生功能交付，不应设计成需要单独安装的 Addition，也不应把基础文件浏览的可用性依赖于 Addition 运行时。

这里的“原生”指产品入口、基础交互和必要的文件浏览能力属于 ECL 主程序/Core 的正式组成部分；不要求所有文件格式解析器、预览器或高级编辑器都内置在主程序中。具体职责划分如下：

- **ECL 原生 UI：** 提供实例文件浏览页面、目录导航、文件列表、基础文件信息、上下文工具面板及操作反馈；
- **ECL Core：** 提供 Instance File Access Service、实例根目录安全边界、文件类型识别基础设施、处理器注册/发现/调度、文件操作授权和生命周期管理；
- **原生基础处理器：** 提供常见图片、文本、日志、JSON/XML 等低风险基础预览，以及未知格式的通用文件信息视图；
- **可选 Addition：** 提供 NBT/Region 语义浏览、复杂格式编辑、专用分析、转换等非基础能力，并通过统一处理器能力接口接入。

即使所有可选 Addition 均未安装，玩家仍必须能够打开文件浏览器、浏览实例目录、查看基础文件信息、预览受支持的常见文件，并完成被允许的基础文件操作。Addition 缺失只能影响其所提供的高级处理能力，不能使 Explorer 页面消失或无法使用。

因此，Explorer 本身不应出现在“需要安装的 Addition”列表中；但 Explorer 内部可以展示由 Addition 提供的文件处理器，并按安装、兼容性、依赖和授权状态显示可用性。

文件浏览器应支持：
- 目录树或面包屑导航；
- 文件名、类型、大小、修改时间等基础信息；
- 按名称排序及基础筛选；
- 文本类文件的安全预览；
- 打开受支持的文件类型；
- 复制文件或目录到用户明确选择的目标位置；
- 对允许的文件执行重命名、删除等操作（是否提供及具体范围由 Feature Spec 明确）。

界面应清楚显示当前实例名称和规范化后的根目录，避免用户误以为自己正在操作其他实例或全局文件系统。

### 2. 实例根目录是默认且强制的访问边界

文件浏览器默认只能访问当前实例的根目录及其后代路径。所有文件系统操作必须通过统一的 Instance File Access Service 执行，不允许 UI 层自行拼接路径后直接访问文件。

安全要求：
- 对根目录和目标路径进行规范化，并验证目标仍位于实例根目录之内；
- 拒绝 .. 路径穿越、绝对路径逃逸、盘符切换、UNC 路径逃逸及设备路径；
- 对符号链接、junction、reparse point 等可能跳出实例目录的路径进行显式处理；默认不得跟随到实例根目录之外；
- 对操作前后的路径进行检查，避免仅依赖字符串前缀判断目录归属；
- 对文件系统竞争条件和链接替换采取安全措施；无法可靠保证边界时拒绝操作；
- 隐藏文件、受保护文件和运行中被占用的文件按操作类型采取保守策略；
- 不向 Addition 或 UI 暴露任意文件系统访问能力。

用户可以通过系统文件选择器选择复制/导出目标目录，但这不意味着 ECL 文件浏览器获得该目标目录的持续浏览权限。目标路径只用于本次经用户确认的导出操作。

### 3. 默认以只读浏览为主，修改操作必须明确且可恢复

文件浏览不应隐式修改实例内容。删除、覆盖、移动、重命名等破坏性操作必须由用户明确触发，并在必要时显示目标路径、影响范围和覆盖提示。

对正在运行的实例：
- 日志、崩溃报告等可安全读取的文件可以在文件系统允许时读取；
- 对可能被游戏或 Loader 正在写入的文件，应采用共享读取或安全重试策略；
- 不应在游戏运行期间默认允许修改配置、模组、核心文件或其他可能影响运行的内容；
- 对无法确认安全性的写操作应提示关闭游戏后再操作。

文件管理器不负责替代实例安装、模组管理、世界编辑等专用功能。已由 ECL 专用工作流管理的对象，应优先跳转到对应功能，而不是提供容易绕过业务约束的通用编辑入口。

### 4. 崩溃报告与诊断引擎自动联动

ECL 应识别实例内常见的崩溃和诊断文件，例如：
- Minecraft crash-reports 中的崩溃报告；
- logs 中的日志及滚动日志；
- Loader 或模组生成的已知诊断报告；
- 后续由诊断引擎明确支持的其他报告格式。

当用户在文件浏览器中点击已识别的崩溃报告时，默认打开 ECL 内的报告详情并自动启动本地诊断流程，而不是仅调用外部文本编辑器。

自动诊断应：
- 先识别文件类型、大小、编码和可解析程度；
- 以只读方式读取原始文件，不修改原报告；
- 将报告关联到所属实例、对应游戏进程/日志会话（能够可靠关联时）；
- 将解析结果、证据位置、诊断规则版本和置信度交给 ADR 0033 的诊断引擎；
- 显示分析进度、结果和原始报告入口；
- 对不支持、损坏、过大或格式异常的文件给出明确说明，不得伪造分析结果。

文件被点击不应触发任何网络上传。自动诊断默认完全在本地完成。

### 5. 崩溃报告必须支持复制和导出

在诊断详情及文件浏览器中，用户应能将崩溃报告复制到其他位置，以便提交社区、发送给朋友或交给其他工具分析。

至少考虑以下操作：
- 复制原始文件到用户选择的目标目录；
- 通过系统保存对话框导出单个文件；
- 复制文件路径；
- 复制报告文本（适用于可安全解码的文本报告）；
- 未来可提供“打包诊断材料”，但必须单独选择并预览包含的文件。

导出必须保留原始报告，不应将脱敏后的内容覆盖原文件。复制时应检测源文件是否仍在写入、目标文件是否存在及是否需要覆盖确认，并在失败时保留清晰错误信息。

### 6. 分享与隐私保护

崩溃报告和日志可能包含用户名、磁盘路径、服务器地址、IP、模组列表、环境信息以及其他可能识别用户或其环境的内容。

因此：
- 本地复制原始文件属于用户明确发起的本地文件操作；
- ECL 不得自动上传报告或将其发送给第三方；
- 若未来提供一键分享、在线分析或远程诊断，必须在操作前显示实际将发送的文件/字段、接收方和用途，并获得明确授权；
- 脱敏副本必须与原始文件分开生成，展示脱敏规则和处理结果；
- 不得承诺脱敏能够移除所有敏感信息，用户应能在导出前预览内容；
- 不得默认把完整实例目录、账号数据、世界存档或凭据纳入诊断包。

### 7. 与日志会话及诊断引擎建立关联

实例文件浏览器是文件入口，不是另一套独立诊断系统。

- ADR 0015 的进程级日志会话用于关联游戏运行期间产生的日志；
- ADR 0033 负责统一解析报告、组织证据、应用规则和输出诊断结论；
- 文件浏览器负责定位和呈现原始文件，并发起诊断或导出；
- 若文件无法可靠关联到某次运行，应将其标记为实例级历史文件，不得猜测所属进程；
- 原始文件路径、文件标识、大小、修改时间及必要的内容哈希可作为本地证据元数据；是否持久化内容哈希由实现阶段评估。

### 8. 与 Addition 和 Core 的边界

实例文件浏览器作为 ECL 的原生基础能力提供，不要求用户额外安装文件管理 Addition。Core 提供受控的实例文件访问、路径边界验证、文件元数据和诊断入口；UI 负责浏览体验；诊断引擎负责内容分析。

Addition 只能通过受控 API 访问当前实例中明确授权的文件或文件流，不得借此取得任意磁盘访问权限。第三方 Addition 的权限应按能力声明授予，并在 UI 中可识别。


### 9. 文件类型识别与处理能力注册

文件浏览器必须区分文件类型识别、基础预览和高级处理能力，不能将文件扩展名直接硬编码绑定到某个 Addition。

ECL 应提供统一的 File Type Registry 与 File Handler Capability Registry：

- File Type Registry 负责识别文件类型，优先结合扩展名、已知文件签名及必要的内容探测；扩展名只能作为提示，不能单独作为可信格式证明；
- 文件类型标识应使用稳定、可版本化的语义 ID，例如 `image/png`、`text/plain`、`minecraft/nbt`、`minecraft/region`；
- File Handler Capability Registry 记录原生组件及 Addition 声明的处理能力，包括支持的文件类型、动作（例如 preview、view、inspect、edit、export）、兼容范围和所需权限；
- 同一文件类型允许存在多个处理器，用户可以按当前动作选择工具；例如 Region 文件既可由 Region Explorer 检查，也可由 NBT Explorer 读取其中的 NBT 数据；
- 处理器声明只代表其声称支持的能力，ECL 仍须检查安装状态、版本兼容性、依赖和权限，不能将声明视为安全证明；
- 对未知、冲突或无法可靠识别的文件类型，应回退到安全的文件信息视图，不得仅凭文件名执行专用解析器。

### 10. 原生基础预览与 Addition 高级处理分层

常见、低风险且普遍需要的预览能力由 ECL 原生提供，不应为了查看普通文件而强制安装 Addition。

原生能力至少考虑：
- 常见图片格式的只读预览；
- 文本与日志的只读预览；
- JSON、XML 等结构化文本的格式化只读查看；
- 未支持格式的基本元数据及安全文件信息。

NBT、Region 等复杂 Minecraft 数据可以先显示基本文件信息；完整语义浏览、编辑、区块分析等高级功能由对应 Addition 提供。原生预览必须限制文件大小、解码资源和解析时间；对超大、损坏或不可信文件采用可取消、受限的读取策略，不能阻塞文件浏览器主界面。

### 11. 上下文扩展工具面板与处理器发现

文件浏览器应提供与当前选中文件上下文相关的工具面板，并在右键菜单等入口复用同一份处理器发现结果。

工具状态至少区分：
- 已安装、兼容且可用：正常启用；
- 未安装：以弱化视觉状态展示，但仍可点击，点击后说明功能、所需 Addition 并进入安装/获取流程；
- 已安装但版本不兼容：不可执行，点击后说明兼容原因及可行的更新方向；
- 缺少依赖或权限：不可执行，点击后说明具体缺失项及授权要求；
- 正在安装、加载或初始化：显示明确进度/状态，避免重复触发；
- 加载失败或运行时不可用：显示失败原因，并提供重试或查看详情入口（若可恢复）。

未安装或不可用的工具不得伪装成可执行操作，也不应完全隐藏，否则用户无法发现 ECL 已提供的扩展能力。点击不可用工具只允许展示说明、安装或修复流程，不得在状态未满足时调用处理器。

处理器列表应根据文件类型、用户当前动作、Addition 声明的能力和权限动态过滤。默认处理器选择应可预测；当存在多个同等适用的处理器时，应提供明确选择，不得静默将文件交给不相关的工具。

### 12. 文件访问与 Addition 调用边界

Addition 处理文件必须通过 ECL 授权的文件访问接口获得受限句柄或文件流，而不是获得可任意访问磁盘的能力。

- 授权应绑定具体文件、实例、动作和必要的访问模式（只读/写入）；
- 默认只读，写入能力必须由用户动作触发并经过 ECL 的边界与风险检查；
- 处理器不得通过声明某个文件类型而自动获得该类型文件的写权限；
- ECL 应负责文件路径边界验证、文件句柄生命周期、取消、并发与写入提交策略；
- Addition 不得绕过授权接口访问实例之外的路径；
- 对文件写入应采用临时文件/原子替换等适当策略，失败时保留原文件并报告结果；具体策略按文件系统能力确定。

文件处理能力注册表是工具发现与调度机制，不是权限系统的替代品。能力声明、安装状态和实际授权必须分别验证。


### 13. 文件与目录元数据、统计及排序

Explorer 应提供足以承担日常文件管理工作的元数据，而不只是文件名列表。

文件条目至少展示名称、类型、文件大小、修改时间；目录条目至少展示目录大小、包含的文件数量与子目录数量、目录修改时间。目录统计应明确区分直接子项与递归统计结果。目录自身的修改时间不能代替其内容最近变更时间，若提供“最近内容变更时间”必须单独计算和标注。

统计状态必须可见，至少区分尚未计算、计算中、已完成、部分完成和失败。无法访问或无法统计的子树不得被静默当作零大小。大小展示应以逻辑文件大小为基础；若平台能够可靠取得实际磁盘占用，可作为独立字段呈现，不得混为一谈。

排序设置分为全局默认值和目录级覆盖值。目录级设置优先于全局设置，并应持久化；未设置目录级规则时继承全局规则。至少支持：
- 名称首字母升序与降序；
- 修改时间升序与降序；
- 文件大小升序与降序。

文件夹与文件的分组方式应稳定且与排序方向解耦，避免排序设置导致目录突然混入文件序列。排序只影响展示，不得改变文件状态、风险等级或业务处理结果。

### 14. Instance Inventory 与统一扫描服务

ECL 应提供共享的 Instance Inventory（实例资源清单）及 Instance Scanner（实例扫描服务），作为 Explorer、实例工作台和后续诊断/管理功能共同的数据基础。不得由 Explorer 和实例工作台分别实现互不兼容的全实例扫描器。

Inventory 不只是文件路径索引，还应记录可识别的实例资源实体及其关系，包括：
- 文件与目录的元数据、文件类型和扫描状态；
- 模组、资源包、光影包、投影/蓝图文件、世界存档等资源实体；
- 资源启用/禁用状态、版本与兼容性判断；
- 模组依赖关系及缺失依赖；
- 资源实体与其来源文件/目录的关联；
- 删除风险标记及其命中规则；
- 扫描时间、扫描器/规则版本、证据来源和判断可信度。

扫描至少分为三个可独立完成的阶段：
1. **快速文件扫描：** 枚举目录结构，统计文件/目录数量、大小、修改时间及基础元数据；
2. **资源识别扫描：** 识别模组、资源包、光影包、投影文件、世界等已知资源类型；
3. **深度分析扫描：** 解析模组元数据、依赖关系、目标 Minecraft/Loader 兼容性和可用性等信息。

扫描应支持取消、进度反馈、增量更新和缓存。打开 Explorer 后可以先展示快速扫描已有结果，再异步补齐资源识别和深度分析；深度扫描不得阻塞基本文件浏览。缓存必须记录适用实例、文件标识/修改时间或内容指纹、扫描器版本及规则版本；当文件、实例配置、Minecraft/Loader 版本或相关规则变化时，应使受影响结果失效并重新分析。扫描失败不得阻断普通文件浏览或游戏启动。

扫描器不得执行模组代码，不得为了验证资源而自动启动 Minecraft。对 JAR、ZIP 和其他压缩容器的解析必须限制文件大小、解压规模、条目数量、递归深度和处理时间，并支持取消，防止资源耗尽或恶意构造文件导致阻塞。

### 15. Minecraft 资源识别与状态判断

Inventory 应尽可能识别实例中的 Minecraft 专用资源，并提供数量、大小、状态和来源文件关联。首批资源类型至少包括 Mods、Resource Packs、Shader Packs、Schematic/Projection Files、Worlds，以及可识别的配置文件。

**模组状态必须采用多维证据，不得仅用一个“可加载”布尔值概括。** 至少区分：
- 元数据已识别/未识别；
- 当前实例中已启用/已禁用/状态未知；
- 依赖满足/缺少必要依赖/依赖关系未知；
- Minecraft 版本兼容/不兼容/未知；
- Loader 兼容/不兼容/未知；
- 文件格式和目标环境符合已知加载条件/不符合/未知；
- 曾在某次运行中成功加载/加载失败/没有运行证据。

界面可以汇总成“可加载条件满足”“已禁用”“缺少依赖”“版本不兼容”“无法识别”“状态未知”等便于理解的状态，但必须允许用户查看具体证据和未确定项。静态扫描只能判断已知条件是否满足，不能保证模组实际启动成功；只有可靠的运行日志或加载会话证据才能标记曾成功加载，且必须绑定到对应实例配置与运行会话。

模组依赖应形成可查询的依赖图，能够指出直接缺失依赖及因依赖链导致不可满足的上游模组。依赖解析应考虑依赖类型、版本范围、可选依赖、环境约束及 Loader 语义；不能把可选依赖缺失误报为必需依赖缺失。无法解析的元数据应标记未知，不得猜测。

Resource Packs 应识别数量、元数据、启用状态和可验证的版本适用信息。Shader Packs 应识别数量和格式，并结合当前 Minecraft、Loader、渲染模组及已知支持信息判断适用性；仅凭文件存在或扩展名不得宣称当前环境可用。Schematic/Projection Files 应识别已知格式、数量和大小；无法识别的文件仍保留为普通文件，不得仅凭扩展名伪造识别结果。Worlds 应复用实例工作台/世界引擎已有的世界识别能力，避免重复解析和互相矛盾的统计。

### 16. 删除行为与受保护路径规则

Explorer 应允许用户通过 ECL 删除其当前 Windows 用户账户本来就有权限删除的实例文件和目录。删除操作不得请求管理员权限、触发 UAC 提权、启动管理员进程，亦不得通过服务或其他方式绕过操作系统权限。遇到 Access Denied、文件占用或 ACL 限制时，应原样报告失败原因，不得尝试提权。

删除前应显示目标、递归影响范围及可获得的大小/数量统计。目录递归删除必须明确提示其包含内容；批量删除必须展示完整选择范围。默认不得静默永久删除；具体回收站/可恢复删除策略按 Windows API 能力和文件系统情况实现，无法保证可恢复时必须在确认界面明确说明。删除失败时应报告部分成功情况，不得声称整个操作已回滚。

ECL 应提供 Protected Path Rules（受保护路径规则集），识别不建议用户删除的目录和文件。规则可以依据相对路径、实例类型、Loader、Minecraft 版本、目录结构及内容特征匹配，并记录规则来源、适用范围、风险等级和解释。. fabric、.forge 等 Loader 内部目录，以及 versions、libraries、实例核心文件、世界存档和玩家数据等，应按具体上下文标记为高风险或强烈不建议删除；不得仅凭名称将所有同名目录一概视为相同内容。

风险标记是告知与保护机制，不应在一般情况下剥夺用户对自己实例的管理权。高风险删除应提供清晰原因、影响说明和额外确认；对于正在运行且可能被使用的文件、无法确认边界的链接目标或安全性无法保证的操作，可以直接拒绝并说明原因。规则未命中不代表文件一定安全，界面应区分“未发现已知风险”与“已确认安全”。

### 17. 实例工作台与 Explorer 共享资源清单

实例工作台和 Explorer 必须消费同一 Instance Inventory 数据源。实例工作台可以展示概览数字、资源异常摘要和快捷入口；Explorer 展示可浏览、可排序、可操作的文件与资源详情。

两者不得各自维护冲突的模组数量、实例大小、资源启用状态或扫描缓存。Inventory 应提供一致的实例级统计，例如文件/目录数量、实例总逻辑大小、模组数量及状态分布、资源包数量及状态、光影包数量及适用性、投影文件数量及大小、世界数量等。每项统计必须带有扫描时间、完成程度或未知状态，避免把未扫描结果显示为零。

Inventory 是本地派生数据，可在需要时重建；不得将缓存视为实例内容的权威来源。任何文件操作、实例配置变更或专用管理流程导致内容变化后，都必须使相关清单条目失效或触发增量更新。Explorer、实例工作台和诊断系统可共享 Inventory 的证据与实体标识，但各自保留其业务职责。


### 18. 从模组 JAR 提取嵌入式图标

Instance Scanner 的资源识别阶段应支持从模组 JAR 中提取嵌入式图标，并将其作为 Mod Inventory 条目的本地缩略图来源。该能力属于 ECL 原生资源识别与展示能力，不依赖专门的图片预览 Addition，也不要求网络访问。

图标来源按以下优先级确定：

1. 优先解析对应 Loader 元数据中明确声明的图标路径，例如 Fabric `fabric.mod.json` 的 `icon` 字段，以及 Forge/NeoForge `META-INF/mods.toml` 中的 `logoFile`；具体字段和路径语义由 Loader 专用 Recognizer 负责；
2. 元数据未声明图标或声明路径无效时，可尝试有限的常见约定文件名（例如 `icon.png`、`logo.png`）；
3. 不得从 JAR 中任意挑选一张图片作为模组图标。没有可靠候选图标时显示 ECL 默认占位图。

对于支持多尺寸图标的元数据，应选择适合当前缩略图目标尺寸的候选项；若无法解析尺寸映射，应按明确、稳定的回退规则选择，不得随机选择。

提取必须遵循安全约束：
- 只读取所需的 ZIP/JAR 条目，不得为了提取图标而完整解压 JAR；
- 对压缩包条目大小、解压后字节数、图片宽高、总像素数、解码时间和并发任务数设置上限；
- 校验实际文件签名和解码格式，不能只信任扩展名或元数据声明；
- 拒绝路径穿越、异常条目名和不符合预期的条目读取；不将条目路径映射为任意磁盘路径；
- 不执行 JAR 内代码，不加载模组类，不启动游戏；
- 解码失败、格式不支持或资源超限时，隔离该图标错误并回退占位图，不得影响模组元数据识别、其他模组扫描或 Explorer 浏览；
- 提取过程可取消，并受 Instance Scanner 的资源预算约束。

缩略图应由 ECL 在本地生成并缓存，不修改原始 JAR。缓存键至少应考虑 JAR 内容哈希、图标条目路径、目标缩略图规格及解码/提取器版本；缓存必须可失效和重建，不能仅以文件名或修改时间作为内容身份。原始提取图像与 UI 缩略图应区分管理，以便在缩略图规格或处理器版本变化时重新生成。

Mod Explorer 列表可展示缩略图；模组详情面板应在可获得时展示图标来源（元数据字段或回退规则）、JAR 条目路径及提取状态/失败原因。提取出的资源仅用于本地识别和展示，不得因此被重新打包、导出为模组资源包或作为 ECL 官方分发内容。

## 备选方案

### 方案 A：继续依赖系统文件管理器

优点是几乎没有开发成本，用户也熟悉现有工具。

放弃原因：用户需要离开 ECL 并自行定位实例；崩溃报告、日志和诊断流程无法自然衔接，也缺乏统一的实例范围安全约束。

### 方案 B：在 ECL 中嵌入通用文件管理器

优点是功能完整，可以访问各种路径。

放弃原因：超出实例管理场景所需权限，扩大路径穿越、误删和敏感文件暴露风险，也容易与系统文件管理器重复。

### 方案 C：仅提供崩溃报告列表，不提供文件浏览

优点是范围小，能快速完成诊断入口。

放弃原因：无法满足查看配置、日志、模组文件等日常实例管理需求；用户仍需要离开 ECL 完成复制和整理。

### 方案 D：采用实例范围文件工作区

以实例根目录为强制边界，默认只读浏览，通过统一服务执行受控文件操作，并与诊断引擎集成。

选择原因：在用户便利性、权限最小化和现有 ECL 架构之间取得更合适的平衡。

## 后果

### 正面影响

- 用户可以在 ECL 内完成常见实例文件查找；
- 崩溃报告从“一个文件”变成诊断流程的直接入口；
- 复制和导出功能降低社区求助与协作成本；
- 统一文件访问服务可被日志、诊断及后续实例功能复用；
- 明确的实例根目录边界减少误操作其他实例或启动器数据的风险。

### 代价与风险

- Windows 文件系统中的符号链接、junction、权限、共享锁和路径规范化需要认真处理；
- 大文件、持续写入的日志和损坏文件需要渐进式读取与错误恢复；
- 文件类型识别和自动诊断需要与 ADR 0033 的解析能力保持一致；
- 脱敏和诊断包功能涉及隐私风险，必须避免未经授权的远程传输；
- 通用文件操作可能与模组管理、世界管理等专用工作流产生重叠，需要明确职责。

## 验收标准

1. 用户能够从实例工作台打开指定实例的原生文件浏览器，并始终看到当前实例身份和根目录。
2. 文件与目录能够显示名称、类型、大小、修改时间；目录统计能区分直接子项与递归结果，并明确显示计算中、部分完成或失败状态。
3. 全局排序与目录级排序均可配置；目录级设置优先并持久化；名称、时间和大小均支持升序/降序。
4. Instance Scanner 支持快速扫描、资源识别和深度分析分阶段执行，支持取消、缓存和增量更新；扫描失败不影响基础浏览和游戏启动。
5. Explorer 与实例工作台读取同一 Inventory，实例级统计与资源状态保持一致，并显示扫描时间及完成程度。
6. 模组状态能够区分启用状态、依赖、Minecraft/Loader 兼容性和实际运行证据；未知信息不得被推断为可加载或已成功加载。
7. Resource Packs、Shader Packs、Schematic/Projection Files 和 Worlds 能按已验证的格式/元数据识别；无法识别的内容仍可作为普通文件浏览。
8. 删除操作只使用当前用户已有权限，不触发 UAC 或任何提权/绕过机制；拒绝访问时如实失败。
9. .fabric、.forge 等上下文相关的内部目录及世界存档等高风险内容能够显示删除风险、原因和额外确认；未命中规则不得被表述为绝对安全。
10. 对路径穿越、绝对路径逃逸、UNC 路径、符号链接和 junction 逃逸的测试均被安全拒绝。
11. 文件浏览器无法通过 UI 或 Addition API 访问实例根目录之外的文件。
12. 在游戏运行期间浏览日志和崩溃报告不会导致文件被修改或游戏进程被阻塞。
13. 点击受支持的崩溃报告能够自动进入本地诊断流程，并保留原始报告不变。
14. 对损坏、未知编码、超大或仍在写入的报告有明确、可恢复的处理结果。
15. 用户能够将原始崩溃报告复制/导出到自行选择的位置，并获得覆盖确认和失败反馈。
16. 复制文件、复制路径和复制可解码文本等操作不会隐式触发网络上传。
17. 任何未来的远程分享功能都必须在实际传输前展示数据范围并取得明确授权。
18. 可选 Addition 缺失时，Minecraft 正常启动和 Explorer 基础文件管理均不受影响；Addition 仅扩展其声明的高级处理能力。
19. Instance Scanner 能按 Loader 元数据优先级从模组 JAR 提取图标并生成本地缩略图；缺失或异常图标回退占位图，且不会影响其他扫描结果。\n20. JAR 图标提取不执行模组代码、不完整解压归档，具有条目大小、解压字节数、图片尺寸/像素数和解码时间限制；缓存可在 JAR 内容或提取器版本变化后正确失效。
2. 对路径穿越、绝对路径逃逸、UNC 路径、符号链接和 junction 逃逸的测试均被安全拒绝。
3. 文件浏览器无法通过 UI 或 Addition API 访问实例根目录之外的文件。
4. 在游戏运行期间浏览日志和崩溃报告不会导致文件被修改或游戏进程被阻塞。
5. 点击受支持的崩溃报告能够自动进入本地诊断流程，并保留原始报告不变。
6. 对损坏、未知编码、超大或仍在写入的报告有明确、可恢复的处理结果。
7. 用户能够将原始崩溃报告复制/导出到自行选择的位置，并获得覆盖确认和失败反馈。
8. 复制文件、复制路径和复制可解码文本等操作不会隐式触发网络上传。
9. 任何未来的远程分享功能都必须在实际传输前展示数据范围并取得明确授权。
10. 文件管理 Addition 或诊断组件缺失时，Minecraft 正常启动流程不受影响；基础文件浏览与诊断能力的依赖关系必须在产品规格中明确。
