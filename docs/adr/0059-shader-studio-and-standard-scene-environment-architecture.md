# ADR 0059: Shader Studio and Standard Scene Environment Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: Shader Studio Addition、光影包分析与预览、ECL 标准测试场景、场景资产交付、时间段取景及扩展协作边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0058](0058-resource-pack-studio-architecture.md)、[ADR 0060](0060-multi-addition-visual-preview-composition.md)

## 背景

ECL 计划提供独立的 Shader Studio，用于光影包浏览、结构分析、兼容性检查和视觉预览。光影效果依赖具体场景：水体、植被、地形、天空、远景以及不同时间和天气条件都会影响最终表现。没有统一场景，用户只能自行寻找或搭建测试环境，难以保证不同光影包之间的比较具有可重复性。

ECL 不应要求用户为预览自行搭建场景，也不应把完整 Minecraft 世界生成器作为 Shader Studio 的前置条件。更合适的方式是由 ECL 提供独立、固定、经过设计的标准测试环境，并在该环境中安排可重复的取景点和环境条件。

场景制作本身具有持续的美术与维护成本。基础自然环境需要覆盖水体、草地、树林和远处山脉等代表性元素；更丰富的原版生物群系需要额外地形、植被和环境资产。若进一步承诺第三方群系模组（例如 Biomes O' Plenty，简称 BOP），资产来源、模组版本、许可、资源兼容和场景维护范围都会显著扩大。因此必须明确标准场景与高级场景的内部规划边界，同时避免将其变成用户权益或功能限制。

## 决策

### 1. 建立独立 Feature Addition

建立候选 Addition：

- Name：Shader Studio
- Addition ID：`ecl.shader-studio`
- Type：`Feature`
- Registry Status：`Proposed`
- Implementation：尚未开始
- Release Assets：暂无

Shader Studio 负责光影包内容浏览、静态结构分析、兼容性信息呈现，以及在受支持的渲染环境中进行场景预览。它是可选专业工具，不进入 ECL 普通启动链；未安装、禁用、损坏或不兼容时，不得影响 ECL 主程序、实例管理和普通游戏启动。

### 2. 随 Addition 统一交付全部官方场景

ECL 官方标准场景和高级场景均属于 Shader Studio 的组成内容，随同一个 Addition 统一交付和管理：

- 不拆分为收费包、独立付费 Addition 或额外权益包。
- 不设置付费解锁、订阅限制、场景数量限制或人为功能锁定。
- 用户安装 Shader Studio 后，所有随扩展发布且与当前版本兼容的官方场景均可使用。
- 不得以 Standard / Advanced 标签向用户表达权限、等级或可用性差异。
- 场景资源可以按需读取、解码和加载，但不能因此将其变成需要额外购买或单独授权的内容。

Standard / Advanced 仅作为项目内部的制作规划、资产复杂度、覆盖范围和验收工作量分类。该分类不得影响实际用户体验。

### 3. 提供固定且可重复的 ECL Standard Environment

至少规划一个由 ECL 统一制作和维护的标准自然环境，作为光影预览的共同基准。其代表性内容包括：

- 河流或其他具有明确水面表现的水体；
- 草地及高低起伏的地表；
- 具有不同密度和遮挡关系的树林；
- 远处山脉或其他具有层次的远景；
- 天空、太阳及可用于观察大气效果的环境；
- 能体现材质、透明度、阴影和环境光差异的局部测试元素。

场景应具有明确的空间层次和视觉构图，而不是仅将若干测试方块随意摆放。场景资产、地形布局和材质应作为受控的基准内容维护；不应通过每次随机生成不同布局的方式构造默认测试环境。

### 4. 同一地点必须具备完整的时间段取景

标准场景的时间变化不能仅依赖一个时间滑块或一张白天截图。对同一地点，应规划并维护对应的代表性取景，至少覆盖：

- 日出；
- 白天；
- 黄昏；
- 黑夜。

每个时间段都应有对应的摄像机位置、观察方向和构图基准；若同一地点的同一机位无法充分展示该时段的关键效果，可以为该时段定义额外观察点，但必须保留可追溯的场景与取景身份。

这些取景用于观察太阳角度、天空颜色、阴影方向与长度、环境光、夜间照明及其他时段相关效果。具体时间参数、摄像机坐标和画面构图由场景制作与 Feature Spec 确定，不在本 ADR 中虚构数值。

场景应支持恢复标准取景和标准环境条件。用户可以调整时间、天气或观察位置进行探索，但临时调整不得覆盖官方基准配置；应能恢复到对应时段的标准取景。

### 5. 规划高级原版群系场景，但不将其限制为用户等级

在基础自然环境之外，可以逐步制作更多具有代表性的原版 Minecraft 生物群系场景。高级场景的规划目标是扩大光影效果覆盖，而不是制作完整世界或完整群系模拟器。

- 每个场景应体现其群系的代表性地形、植被、材质和环境特征。
- 优先通过可复用的地形模块、植被资产和环境组件降低重复制作成本，但不能以无差别随机拼装替代群系特征设计。
- 每个场景应具有可重复的取景点和环境条件；必要时覆盖不同时间段。
- 可以优先覆盖对光影效果具有不同测试价值的环境，例如雪地、沙漠、密林、洞穴或特殊植被环境。
- 场景数量和制作顺序由项目规划及资产验收决定，不在 ADR 中承诺固定数量。

高级场景与标准场景在用户可用性上完全平等，全部随 Shader Studio 统一交付。

### 6. 明确第三方模组群系的范围边界

当前官方场景规划以 ECL 自行制作和维护的标准环境及原版群系为基础，不承诺为 BOP 等第三方群系模组制作完整的官方场景资产。

原因包括但不限于：

- 第三方模组可能包含大量独有树木、植被、地表材质和地形特征；
- 仅复用原版资产或简单替换方块，无法真实体现模组群系的视觉特征；
- 不同模组版本、Minecraft 版本和资源包可能影响场景内容；
- 重新建模和维护所有代表性资产会形成持续且难以限定的工作量；
- 第三方资产的许可和再分发条件必须单独核实。

这不意味着 Shader Studio 永久禁止第三方场景。未来可以评估由模组作者或第三方提供场景资源、通过明确许可的场景包接入，或采用独立适配方案。但不得在当前提案中承诺 BOP 官方场景支持，也不得将其作为首期验收前提。

### 7. 场景、渲染环境和测试控制能力保持分离

架构上应区分：

- **Scene Assets**：场景几何、地形、模型、材质、植被、水体、环境资源和场景描述。
- **Render Environment**：光影包所需的渲染管线、Loader 适配、图形能力和运行环境。
- **Test Configuration**：时间、天气、摄像机、观察点及其他可重复测试条件。
- **Preview Controller**：场景选择、取景恢复、参数调整、预览任务与结果呈现。

固定场景不能被视为完整 Minecraft 渲染环境，也不能消除光影包对特定 Loader、渲染接口、游戏版本或 GPU 能力的依赖。场景资源应尽量与特定光影包和渲染后端解耦；渲染环境负责在其声明的兼容范围内消费场景资源。

### 8. 不承诺完整模拟所有光影包或游戏渲染管线

光影包可能依赖特定 Shader Loader、Minecraft 版本、渲染 Pass、缓冲区、Uniform、图形 API 和 GPU 能力。静态分析通过、GLSL 编译成功或场景资源可加载，均不能单独证明最终渲染效果正确。

- 应明确报告静态分析、语法检查、编译、Loader 兼容和实际预览是不同层次的结果。
- 只有在受支持的渲染环境中完成验证，才能宣称该组合可预览。
- 不支持的 Loader、渲染特性或 GPU 能力应明确标记，不得静默伪装成成功。
- 不得将 Shader Studio 宣称为能够运行所有光影包或完整复刻 Minecraft 客户端。
- 具体渲染后端、Loader 适配策略和兼容矩阵需要原型验证，不在本 ADR 中提前锁定。

### 9. 安全、资源预算与运行时边界

光影包包含外部代码和配置，处理过程可能触发编译、GPU 执行和高资源消耗。Shader Studio 必须遵循 ECL 的 Addition Runtime、权限授权和资源访问边界。

- 光影包分析和预览业务代码不得加载到 ECL 主进程。
- 对外部文件的读取遵循 ADR 0055 的 Resource Broker / Document Service 边界。
- 对 GLSL、配置文件、归档结构和资源引用进行有界解析；处理异常输入时不得发生无界递归或无界资源消耗。
- 编译和 GPU 执行应被视为独立风险面；进程隔离不等于 GPU 沙箱，也不代表 GPU 驱动或图形 API 已获得完整隔离。
- 必须提供任务取消、超时/资源预算、失败恢复和资源释放机制；具体阈值由实际设备与代表性光影包测试确定。
- 不得绕过 ECL 的权限、用户授权和安全策略来运行外部内容。

### 10. 场景资产治理与可复现性

官方场景是产品资产，不是临时截图或随意生成的演示内容。应建立可维护的场景描述与资产治理方式，至少能够追踪：

- 场景稳定身份、版本和资产来源；
- 场景所需资源及其许可/再分发条件；
- 适用的 Minecraft 资源版本或其他环境前提；
- 场景几何、材质和环境资源的变更；
- 标准取景点、摄像机和测试条件；
- 场景与渲染环境之间的兼容性限制。

场景资源可以按需加载并缓存，但必须有明确的版本和失效规则。相同场景版本与相同测试条件应产生可重复的基准输入；不同光影包的画面仍可能因渲染实现和 GPU 差异而不同，不得承诺跨设备逐像素一致。

## 备选方案

### 方案 A：让用户自行搭建或寻找测试场景

不需要 ECL 维护场景资产，但用户准备成本高，场景布局和测试条件不可控，难以进行有意义的横向比较。不采用。

### 方案 B：只提供单张固定白天场景

制作成本较低，但无法充分观察日出、黄昏、夜间光照和天空变化，也不足以作为完整光影测试基准。不采用。

### 方案 C：为每个群系和第三方模组提供完整世界

覆盖面可能很广，但会把 Shader Studio 推向世界生成和大型美术资产工程，维护成本不可控，也会引入大量第三方兼容与许可问题。不作为当前方案。

### 方案 D：将标准场景与高级场景拆成不同 Addition 或独立权益包

可以分别发布和维护，但会人为制造安装与可用性差异，增加版本协调和依赖管理成本，也不符合 ECL 工具与扩展统一免费提供的产品原则。不采用。

### 方案 E：单一 Addition 统一交付固定标准场景与逐步扩展的官方场景库

由 ECL 维护可重复的标准自然环境，并逐步增加更复杂的原版群系场景；所有官方场景随 Shader Studio 统一交付，内部规划分类不影响用户体验。该方案在可维护性、用户体验和覆盖范围之间更平衡，作为当前提议。

## 后果

### 正面影响

- 用户安装 Shader Studio 后即可使用官方场景，不必自行搭建测试世界。
- 固定场景、固定取景和标准测试条件提高不同光影包之间比较的可重复性。
- 同一地点的日出、白天、黄昏和黑夜取景能够覆盖不同时段的关键光照表现。
- 标准与高级场景统一交付，不产生收费、权限或额外安装差异。
- 场景资产与渲染环境分离，为未来支持不同 Loader 和渲染后端保留空间。
- 将第三方模组群系排除在首期官方资产承诺之外，可以控制制作和维护范围。

### 代价与风险

- 官方场景需要持续投入地形、模型、材质、植被和环境资产制作。
- 同一地点多个时间段的取景需要设计、校准和维护，不能只依赖单一截图。
- 场景资产可能与 Minecraft 版本、资源包或渲染后端存在兼容差异。
- 不同 GPU、驱动和渲染实现可能产生不同画面，限制自动化视觉比较的确定性。
- 光影包的 Loader 适配和 GPU 执行风险需要独立验证，固定场景本身无法解决。
- 高级群系场景的扩展速度受资产制作、许可和质量验收约束。

## 验收标准

本 ADR 当前为 Proposed。以下为后续实现评审与验收基线，不表示功能已经实现：

- Shader Studio 作为独立 Feature Addition 登记，具有独立版本和发布生命周期。
- 未安装、禁用、损坏或不兼容 Shader Studio 时，ECL 普通启动、实例管理和游戏启动不受影响。
- 标准场景与高级场景随同一 Addition 统一交付，不存在收费、权益、权限或额外下载区分。
- 用户安装 Addition 后，所有已随当前版本发布且兼容的官方场景均可使用。
- 至少提供一个包含水体、草地、树林和远处山脉的固定标准自然环境。
- 同一标准地点具有日出、白天、黄昏和黑夜的对应标准取景；每个时段均可恢复其基准摄像机与测试条件。
- 用户临时调整时间、天气或观察位置后，能够恢复官方标准取景，不会破坏基准配置。
- 场景布局和标准取景具有稳定身份及版本，不通过无约束随机生成改变基准场景。
- 标准与高级分类仅存在于内部规划和维护资料中，不向用户形成等级或可用性差异。
- 官方高级场景的规划以原版群系为主；BOP 等第三方模组群系不作为首期必需验收范围。
- 场景资产、渲染环境和测试配置在架构上保持可区分，不将固定场景误作完整游戏模拟器。
- 光影包静态分析、编译、Loader 兼容和实际渲染预览的结果能够分别表达，不以其中一项冒充全部验证。
- 不支持的 Loader、渲染特性或 GPU 能力能够明确报告，不静默显示为预览成功。
- 专业分析和预览业务代码不加载到 ECL 主进程；外部资源访问遵循 ECL 受控资源访问和授权边界。
- 编译、预览和场景资源加载具有资源预算、取消、失败恢复及资源释放机制。
- 官方场景的资产来源、版本、许可、取景和测试条件可追踪。
- 至少对代表性光影包、不同时间段取景和目标支持设备完成可复核的兼容性与性能验证。
