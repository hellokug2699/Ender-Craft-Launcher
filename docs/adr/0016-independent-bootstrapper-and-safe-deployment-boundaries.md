# ADR 0016：独立 Bootstrapper 与安全部署边界

- Status: Completed
- Date: 2026-11-01
- Scope: Windows 部署、版本切换、更新应用、启动与回滚

## 背景

ECL 是由多个程序集和资源组成的 .NET/WPF 应用。运行中的主程序无法可靠地覆盖自身正在使用的 EXE、DLL 和资源文件；若将更新、文件替换和启动逻辑全部放在主进程中，还会把网络输入、归档解包、文件系统变更与应用生命周期耦合在一起。

更新失败也不能让用户陷入无法启动的状态。部署需要可验证、可回滚，并且不得误删 Minecraft 实例、账户、配置等用户数据。

## 决策

### 1. Bootstrapper 是独立于 ECL 主程序的部署入口

- 使用独立进程 `ECL.Bootstrapper.exe` 执行安装目录的启动、更新应用和回滚。
- 主程序不得直接覆盖正在运行的自身文件。
- 当更新需要替换主程序文件时，由主程序请求退出，再由 Bootstrapper 完成部署与版本切换。
- Bootstrapper 不依赖主程序进程仍然存活，也不得把部署正确性建立在主程序内存状态上。
- Bootstrapper 应保持职责聚焦：部署目录管理、版本选择、更新包验证与应用、回滚，以及按当前指针启动目标版本；不承担 Minecraft 实例管理、账户管理或游戏启动流程。

### 2. 使用版本目录与原子指针切换

安装目录采用版本隔离布局：

```text
<install>/
├─ ECL.Bootstrapper.exe
├─ update-trust.json
├─ current.json
├─ versions/
│  ├─ <version-a>/
│  └─ <version-b>/
├─ staging/
└─ bootstrapper.log
```

- 每个已部署版本位于独立的 `versions/<version>/` 目录。
- 新版本先解包到独立 staging 目录，不得直接覆盖当前版本。
- 完成包校验、逐文件校验和必要的部署检查后，才可将 staging 提升为正式版本目录。
- `current.json` 是当前版本的权威指针，至少记录当前版本及其相对可执行文件名，并保留回滚所需的上一版本信息。
- 指针通过同目录临时文件写入并原子替换；切换失败时，旧指针必须保持有效。
- 旧版本在回滚保留期内不得被覆盖或自动删除。

### 3. 更新包必须先验证再部署

更新输入是不可信数据。部署前必须完成：

1. 限定并验证 Manifest schema、产品标识、版本、频道、平台和架构。
2. 使用受信任公钥验证 detached signature；签名算法和 keyId 必须符合信任策略。
3. 验证包大小与 SHA-256。
4. 安全解包，拒绝绝对路径、路径穿越、重复条目、符号链接及超出限制的归档。
5. 按 Manifest 逐文件验证大小与 SHA-256，并默认拒绝清单外文件。
6. 所有检查通过后才允许将版本提升并切换指针。

任何签名、信任、完整性、路径或部署验证失败都必须 fail-closed：不得切换到未验证版本，不得破坏当前可启动版本。

HTTPS 只保护传输通道，不替代发布者签名；SHA-256 用于完整性校验，不替代签名身份验证。

### 4. 部署操作必须可恢复并防止并发

- 使用安装根目录级锁（例如 `.update.lock`）阻止多个 Bootstrapper 同时修改同一安装目录。
- 锁必须在进程异常退出后可恢复，不得形成永久不可解除的逻辑锁。
- staging 目录与当前版本目录分离；异常中断后允许识别并清理未完成 staging，但不得误删 current 指针引用的版本。
- 切换前保留旧指针；切换后若启动失败，应提供明确的失败信息和回滚路径。
- 回滚只改变当前版本指针，不通过重新下载或修改旧版本文件来实现。
- 对所有文件系统操作进行路径规范化，并确保目标始终位于安装根目录之内。

### 5. Bootstrapper 的命令行协议必须稳定且可诊断

Bootstrapper 提供明确、可组合的命令行操作，包括：

- 使用当前指针启动 ECL；
- 应用已下载并签名的更新包；
- 仅执行部署而不启动主程序；
- 回滚到上一版本；
- 显式指定安装根目录、Manifest、签名、更新包和信任库。

参数缺失、冲突或非法时应拒绝执行，不得猜测路径或静默采用不安全默认值。

退出码是自动化与调用方的稳定接口。当前约定为：

| 退出码 | 含义 |
|---:|---|
| 0 | 成功 |
| 2 | 参数错误 |
| 3 | 信任、签名或公钥验证错误 |
| 4 | 部署失败 |
| 5 | 启动失败 |

日志写入安装目录中的 `bootstrapper.log`，不得记录私钥、访问令牌或其他秘密。

### 6. 安装程序、部署目录与用户数据必须隔离

- 安装目录只存放 Bootstrapper、程序版本、部署状态和公开信任材料。
- 用户数据目录独立于安装目录。
- 更新与回滚不得递归清理安装根目录以外的路径。
- 更新流程不得触碰账户、配置、日志、缓存、Minecraft 实例、用户导入目录或共享游戏目录。
- 未来卸载功能必须将程序卸载与用户数据清理分开；删除用户数据必须是独立、明确、展示具体路径与数据类别的操作。

### 7. 频道与版本元数据遵循统一发布决策

Bootstrapper 不自行推断或拼接发布频道、版本号。安装包、Manifest、Release 资产与主程序构建元数据遵循 [ADR 0013：分支驱动的版本与发布频道](0013-branch-based-versioning-and-release-channels.md)。

Bootstrapper 必须验证 Manifest 与当前支持的产品、平台、架构和最低更新器版本约束；遇到不支持的 schema 或最低版本要求时拒绝部署。

## 后果

### 正面

- 主程序不再承担替换自身文件的高风险操作。
- 更新在独立 staging 中完成，只有验证成功才切换当前版本。
- 指针切换失败时可以继续使用旧版本。
- 回滚不需要重新下载旧版本，也不需要修改旧版本文件。
- 部署安全边界与用户数据边界清晰，便于审计和测试。

### 代价与约束

- 需要维护 Bootstrapper 与主程序之间稳定的命令行协议。
- 需要额外磁盘空间暂存新版本并保留旧版本。
- 原子替换、文件锁和目录权限在 Windows 不同文件系统及权限环境下需要测试。
- Bootstrapper 自身升级、Authenticode 代码签名、首次安装 UI、卸载器和差分更新属于独立后续工作，不能假设当前已实现。

## 验收标准

1. 主程序运行期间不会直接覆盖自身文件；版本替换由独立 Bootstrapper 执行。
2. 更新包在签名、包哈希、路径和逐文件校验全部通过前，不会成为当前版本。
3. 部署失败或进程异常退出不会破坏原有 current 指针及其引用版本。
4. 回滚通过指针切换完成，旧版本内容保持不变。
5. 并发部署受到锁保护，异常遗留 staging 可安全恢复。
6. 所有部署文件系统操作均限制在安装根目录内。
7. 更新与回滚不触碰用户数据目录、实例目录和外部共享游戏目录。
8. CLI 参数与退出码有自动化测试覆盖；失败原因可从日志诊断且不泄漏秘密。
