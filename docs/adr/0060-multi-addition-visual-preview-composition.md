# ADR 0060: Multi-Addition Visual Preview Composition Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: Schematic Preview、Resource Pack Studio 与 Shader Studio 的可组合视觉预览模式，以及 Map Art Studio 与 Schematic Preview 的可选结构预览组合、Addition 能力协作、统一预览会话及降级边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0058](0058-resource-pack-studio-architecture.md)、[ADR 0059](0059-shader-studio-and-standard-scene-environment-architecture.md)、[ADR 0064](0064-map-art-studio-architecture.md)

## 背景

ECL 计划提供多种独立的视觉预览 Addition：

- Schematic Preview：投影/建筑结构预览。
- Resource Pack Studio：资源包内容、模型、材质、动画和状态变体预览。
- Shader Studio：光影包分析，以及在受支持渲染环境中的场景预览。

这三种能力具有不同的预览对象和专业职责，但在用户的实际工作流中存在有价值的组合关系。例如，用户可能希望将资源包的模型与材质应用到投影结构上，或在光影环境中观察投影结构，甚至同时使用资源包和光影效果。

如果每个 Addition 分别定义自己的联动协议、渲染器共享方式和生命周期规则，会造成重复规范、相互矛盾和紧耦合。ECL 需要一份集中定义组合预览总体规则的架构决策；各 Addition 的专属职责仍由各自 ADR 定义，并通过引用本 ADR 遵循统一规范。

## 决策

### 1. 建立统一的组合预览架构

ECL 采用由 Core 协调的 Multi-Addition Visual Preview Composition 模式。它不是一个新的 Addition，也不意味着将现有 Addition 合并为一个大型预览器。

本 ADR 使用以下字母作为组合关系的简写：

- **A — Schematic Preview**：投影结构与建筑内容预览。
- **B — Resource Pack Studio**：资源包解析及视觉资源预览。
- **C — Shader Studio**：光影分析与受支持渲染环境中的光影预览。

A、B、C 各自仍是独立 Addition，拥有独立安装、更新、启用、兼容性声明和生命周期。组合能力由 ECL Core 按需协调，不得使任意 Addition 成为其他 Addition 的强制安装依赖。

### 2. 明确受支持的预览模式

当前产品规划明确支持以下六种模式中的五种：

| 模式 | 组成 | 定位 |
|---|---|---|
| A | Schematic Preview | 独立投影预览 |
| B | Resource Pack Studio | 独立资源包预览 |
| C | Shader Studio | 独立光影与标准场景预览 |
| A+B | 投影 + 资源包 | 将受支持的资源包视觉资源应用于投影预览 |
| A+C | 投影 + 光影 | 在受支持的光影渲染环境中预览投影结构 |
| A+B+C | 投影 + 资源包 + 光影 | 在同一预览上下文中组合结构、资源包视觉资源与光影效果 |

**B+C 不属于受支持的产品预览模式。**

该限制是产品语义和功能范围决定的，而不是宣称技术上绝对无法组合。Resource Pack Studio 的独立资源预览对象通常是单个模型、材质或资源状态；Shader Studio 的主要价值依赖具有足够空间、环境和光照语义的场景。仅将单个资源对象交给光影环境，无法充分体现水体、天空、远景、植被、阴影和环境光等效果，因而不提供 B+C 独立组合入口或将其列为受支持模式。

B+C 的限制不得反向影响 B 或 C 的独立使用，也不得阻止 A+B+C 这一具有完整场景主体的组合模式。

### 3. 各 Addition 保持职责独立

组合预览应保留各 Addition 的专业边界：

- A 提供投影结构及其空间内容，并负责投影自身的读取、组织和预览语义。
- B 提供其支持范围内的资源包解析结果、模型/材质/动画/状态等视觉资源描述或受控资源访问能力。
- C 提供其支持范围内的光影分析能力、渲染环境能力及场景预览所需的环境信息。
- ECL Core 负责能力发现、授权、兼容性验证、服务路由、组合会话协调和资源访问中介。

消费者不得直接依赖提供方的内部类、私有对象、GPU 上下文、渲染器实例或未声明的实现细节。资源和能力应通过 ECL 受控且可版本化的协作边界提供。

### 4. 组合预览使用统一会话与一致的视觉上下文

A+B+C 必须作为一个协调后的组合预览会话运行，而不是将 A+B 和 A+C 两个互不知情的预览窗口简单叠加。

组合会话需要在架构层面协调：

- 投影结构及其空间范围；
- 目标 Minecraft 版本与资源格式语义；
- 用户选择的资源包及其可用视觉资源；
- 光影包、渲染环境和兼容性状态；
- 场景环境、时间、天气、摄像机与观察条件；
- 资源加载、缓存、失效和释放；
- 各 Addition 的可用状态、能力版本与任务生命周期。

具体上下文模型、数据结构、服务接口、渲染顺序和 UI 交互由 Core 与相关 Addition 在原型验证后确定，本 ADR 不预先规定具体协议。

### 5. 定义各模式的资源与场景语义

不同组合模式应使用符合其预览对象的场景语义：

- **A**：以投影结构本身作为预览主体。
- **B**：以资源包中的资源对象及其受支持的标准资源预览环境作为主体，不启动完整光影渲染组合。
- **C**：使用 Shader Studio 提供的 ECL 官方标准场景与已规划的官方扩展场景，作为光影预览的基准环境。
- **A+B**：以投影结构为主体，将 B 提供的受支持资源视觉结果应用于对应内容；不要求 C。
- **A+C**：以投影结构为主体，在 C 支持的渲染环境中观察其光影表现。C 的官方标准场景可作为环境或测试参照；投影与标准场景如何共同呈现，由实现验证确定，不在本 ADR 中强制规定具体合成方式。
- **A+B+C**：以投影结构为主体，同时消费 B 的资源视觉能力和 C 的光影渲染能力；应使用一致的目标版本、资源上下文和场景/摄像机条件。

组合预览不得将缺少的能力伪装成已经生效。例如，A+C 不得显示资源包已经应用；A+B 不得显示光影效果已经启用。

### 6. 组合按需成立，缺失能力不破坏独立模式

每种模式只要求其自身声明的 Addition 可用：

- A 只要求 A。
- B 只要求 B。
- C 只要求 C。
- A+B 要求 A、B。
- A+C 要求 A、C。
- A+B+C 要求 A、B、C。

用户主动选择某种组合时，宿主应检查所需 Addition 是否已安装、启用、兼容并获得必要授权。缺少依赖时，应说明缺失能力并提供扩展管理入口；不得静默安装、强制启用或擅自授予权限。

任何 Addition 未安装、禁用、崩溃、退出或版本不兼容时，其他 Addition 的独立预览仍必须可用。组合会话应能够取消、关闭或在适当情况下退回对应的独立预览模式，不得使投影文件、资源包或光影包本身无法访问。

### 7. 组合能力必须经过宿主授权和兼容性验证

跨 Addition 协作遵循 ADR 0053、ADR 0054 与 ADR 0055：

- Addition 必须声明提供和消费的能力、能力版本、兼容性要求及权限需求。
- Core 在建立组合会话前验证所需 Addition 的状态、能力版本、目标环境兼容性和用户授权。
- Addition 之间不得绕过宿主直接 IPC、共享任意内部对象或自行建立不受控的通信通道。
- Resource Broker、Service API、Event Bus 等宿主机制是否足以支撑具体组合，应由 Core 实现评审和验证；本 ADR 不假设某个尚未验证的接口已经存在。
- 能力缺失、版本冲突、授权撤销或提供方不可用时，宿主应停止受影响的组合能力，并保留可用的独立功能。

### 8. 资源、渲染与生命周期必须统一协调

组合模式会增加资源引用和渲染工作量。Core 与相关 Addition 必须明确组合会话内资源的所有权、引用关系、缓存边界和失效规则。

- 同一模型、材质、纹理或其他视觉资源应尽可能复用，避免因投影包含大量相同方块而重复解析、解码或创建 GPU 资源。
- 资源包切换、目标版本变化、光影包切换、场景切换或投影内容变化时，相关缓存必须按依赖关系更新或失效。
- 会话结束、Addition 退出或能力撤销时，必须释放不再使用的 CPU/GPU 资源、文件句柄和任务。
- 组合预览应具有任务取消、并发限制和经验证的资源预算；不能因为用户同时启用多个 Addition 就无界叠加资源消耗。
- 一个 Addition 的异常退出不得导致其他 Addition 或 ECL 主进程崩溃。
- 组合能力失败时，应提供可解释的状态和安全回退；不得静默显示过期资源或错误的组合结果。

### 9. 明确渲染一致性与能力边界

组合预览的目标是在受支持的资源格式、渲染环境和硬件条件下提供有价值的视觉近似，不承诺完全复刻 Minecraft 游戏内结果。

- A+B 的视觉结果受 B 的解析覆盖和 A 的投影渲染能力限制。
- A+C 的视觉结果受 C 的 Loader、渲染管线和 GPU 兼容范围限制。
- A+B+C 还受到资源包模型/材质语义与光影渲染环境相互兼容性的影响。
- 不支持的模型、状态、渲染 Pass 或 GPU 特性必须明确标记或回退，不得伪装成完整支持。
- 资源包优先级、光影与资源包的交互语义不得超出各自 ADR 和实际验证范围。
- 组合预览不等于完整 Minecraft 客户端，不负责执行游戏逻辑、方块更新、实体 AI、物理或世界模拟。

### 10. 本 ADR 作为组合预览的统一规范入口

本 ADR 定义 A/B/C 的组合关系及跨 Addition 协作的共同规则。各专项 ADR 应引用本 ADR，而不是重复定义整套组合协议：

- ADR 0058 负责 Resource Pack Studio 自身的资源发现、解析、状态变体、资源预览和安全边界；组合模式遵循本 ADR。
- ADR 0059 负责 Shader Studio、自身渲染能力、官方标准场景、时间段取景和场景资产治理；组合模式遵循本 ADR。
- Schematic Preview 的专项 ADR/Feature Spec 应定义其结构解析和独立投影预览能力，并引用本 ADR 规定组合行为。
- ADR 0064 定义 Map Art Studio 的二维地图画画布、颜色映射和材料规划；Map Art Studio 可独立运行，也可在经过验证后将地图画方案交由 Schematic Preview 进行三维结构预览。该组合属于 A（Schematic Preview）+ D（Map Art Studio）的独立组合方向，不改变本 ADR 第 2 节 A/B/C 既有模式矩阵，也不推导出 D 与 B、C 的其他组合受到支持。
- Map Art Studio 与 Schematic Preview 的组合必须遵循本 ADR 的宿主协调、授权、兼容性、资源生命周期和失败隔离原则；具体转换语义由 ADR 0064 及后续原型验证确定。
- 未来其他 Addition 若希望参与视觉预览组合，应先评估是否属于本 ADR 的适用范围；必要时通过后续 ADR 扩展组合模型，而不是自行建立旁路协议。

本 ADR 不重复各 Addition 的内部实现规范，也不规定具体 UI 布局、IPC 消息、接口签名、数据结构或渲染后端。

## 备选方案

### 方案 A：每个 Addition 自行定义联动规则

可以让各 Addition 快速实现局部协作，但会导致重复的能力发现、授权、版本协商、资源上下文和生命周期逻辑，长期容易产生互不兼容的协议。不采用。

### 方案 B：将 A、B、C 合并为一个大型 Addition

可以共享渲染资源和会话状态，但会破坏三个工具独立安装、独立更新和独立使用的目标，并使只需要其中一种能力的用户承担不必要的依赖。不采用。

### 方案 C：允许所有两两组合，不区分产品语义

实现上可以尝试任意组合，但 B+C 缺乏具有代表性的场景主体，无法充分体现光影预览的价值，也会增加测试矩阵和 UI 复杂度。不采用；保留 A、B、C、A+B、A+C、A+B+C 六种候选中的五种受支持模式。

### 方案 D：由一个 Addition 直接调用另一个 Addition 的内部渲染器

短期可能减少集成工作，但会形成内部实现耦合，绕过宿主授权和生命周期管理，并使 GPU 上下文与资源所有权难以协调。不采用。

### 方案 E：由 ECL Core 协调独立 Addition 的受控组合会话

各 Addition 保持专业职责和独立生命周期，Core 负责能力发现、授权、兼容性验证、会话协调和资源中介；产品只开放具有明确预览语义的组合模式。该方案符合 ECL 的 Addition 架构与长期扩展方向，作为当前提议。

## 后果

### 正面影响

- 三种专业预览能力可以独立交付，同时形成 A+B、A+C 和 A+B+C 的组合体验。
- 用户能够在不启动 Minecraft 的前提下查看投影结构在资源包与光影共同作用下的视觉效果。
- Addition 之间不形成强制安装依赖，用户可以按实际需求选择工具。
- 组合预览具有统一的能力发现、授权、兼容性和生命周期治理入口。
- 未来扩展其他视觉能力时，可以复用总体组合规范，减少重复设计。

### 代价与风险

- Core 需要协调多 Addition 能力、统一会话上下文和资源生命周期，架构复杂度高于单一预览。
- 三种 Addition 的版本、资源语义和渲染能力可能不一致，需要明确兼容矩阵与回退路径。
- A+C 和 A+B+C 中投影结构与 Shader Studio 标准场景的空间关系需要原型验证。
- 多 Addition 同时工作会增加 CPU、内存和 GPU 压力，需要统一预算与资源复用。
- 不同渲染后端之间的资源描述与视觉结果可能存在差异，无法保证与游戏内完全一致。
- 若 Core 的能力协作机制尚不具备所需能力，需要先补齐通用宿主机制，不能让 Addition 私自绕过边界。

## 验收标准

本 ADR 当前为 Proposed。以下为后续实现评审与验收基线，不表示功能已经实现：

- A、B、C 分别可以在不安装另外两个 Addition 的情况下独立运行。
- A+B、A+C、A+B+C 是明确支持的组合模式；B+C 不提供独立组合入口，也不列入受支持预览模式。
- A+B 能将 B 已支持的资源视觉结果应用于 A 的投影预览；B 不可用时 A 仍可独立预览。
- A+C 能在受支持的光影渲染环境中预览 A 的投影结构；C 不可用时 A 仍可独立预览。
- A+B+C 由统一组合会话协调，不是两个互不关联的预览结果简单叠加。
- 组合会话能够校验 Addition 状态、能力版本、目标 Minecraft 版本、渲染兼容性和用户授权。
- 用户未安装组合所需 Addition 时，系统明确提示缺失能力，不静默安装、启用或授权。
- 任何组合能力失败时，相关 Addition 的独立预览仍可使用。
- Addition 间不存在绕过 ECL Core 的直接通信、任意内部对象共享或渲染器内部调用。
- 组合资源具有明确所有权、缓存失效和释放规则；重复模型/材质资源能够合理复用。
- Addition 退出、资源切换、授权撤销或组合会话关闭时，相关任务与 CPU/GPU 资源得到正确清理。
- 组合预览具备取消、资源预算和失败回退机制，不因单一 Addition 故障导致 ECL 主进程崩溃。
- 不支持的资源、模型状态、渲染特性或 GPU 能力能够明确表达，不伪装成完整支持。
- 组合预览不执行完整 Minecraft 世界模拟或游戏逻辑。
- 相关组合模式具备可复核的兼容性、性能、资源生命周期和异常恢复测试。
