# ADR 0066: Non-Elevated Execution Requirement and Bootstrap Enforcement

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: ECL 在 Windows 上的非提权运行要求、Bootstrapper 最早期权限检查、主程序纵深防御与拒绝启动行为
- Related: [ADR 0051：统一安装、更新与恢复架构](0051-unified-installation-update-and-recovery-architecture.md)、[ADR 0065: OAuth Login Session Termination and Authentication Safety](0065-oauth-login-session-termination-and-authentication-safety.md)

## 背景

ECL 是面向普通桌面用户运行的启动器，不需要管理员权限完成正常启动、账户登录、实例管理或 Minecraft 启动。若 ECL 在提升后的管理员权限下运行，程序缺陷、恶意内容、扩展行为或误操作可能获得超出产品正常职责所需的系统访问能力，扩大意外影响范围。

Windows 管理员账户与提升后的进程权限并不是同一概念。启用了 UAC 的管理员账户通常可以使用未提升的标准访问令牌运行普通应用；只有在进程实际获得提升权限后，才应视为以管理员权限运行。仅检查当前用户名、账户类型或是否属于 Administrators 组，会错误拒绝大量正常使用场景。

因此，ECL 应明确拒绝以提升后的管理员权限运行，并在最早能够可靠检查进程令牌的启动阶段执行。该要求属于启动器整体的安全边界，而不只是某个业务功能的限制。

## 决策

### 1. ECL 必须以非提升权限运行

ECL 的 Bootstrapper、主程序及其正常启动的子进程不得要求或主动申请管理员权限。

- 正常启动、登录、实例管理、Minecraft 启动、更新检查及常规用户级文件操作不得要求管理员权限。
- ECL 不得通过 UAC 提示主动请求提升权限。
- 不得将“以管理员身份运行”作为解决文件访问、更新、实例管理或其他普通运行问题的通用建议。
- 如果未来某项独立能力确实涉及系统级操作，应优先重新评估该能力是否属于 ECL 职责；不得因此改变 ECL 主进程的默认权限模型，也不得让普通启动依赖提权。

### 2. 以当前进程的有效权限状态作为判定依据

拒绝条件是当前 ECL 进程实际处于提升后的管理员权限状态，而不是用户账户具有管理员身份。

- 管理员组成员以 UAC 未提升的普通令牌启动 ECL：允许运行。
- 标准用户以普通令牌启动 ECL：允许运行。
- 通过“以管理员身份运行”、提权父进程或其他方式使 ECL 获得提升权限：拒绝运行。
- 不得仅凭用户名、账户显示名称、Administrators 组成员身份或用户是否拥有管理员账户来拒绝启动。
- 实现应使用 Windows 提供的进程访问令牌信息判断实际提升状态，并正确处理 UAC split-token 场景；不得用不可靠的进程名称、环境变量或 UI 启动方式推断权限。

本 ADR 所称“提升权限”指进程实际持有的 elevated administrator token。它不等同于用户属于管理员组，也不试图禁止具有管理员账户的用户以普通令牌使用 ECL。

### 3. Bootstrapper 必须在最早阶段执行强制检查

Bootstrapper 是 ECL 正常启动、版本部署和恢复流程的入口，因此必须在执行任何需要改变安装状态或启动其他 ECL 组件的操作之前检查自身权限状态。

检查必须发生在以下操作之前：

- 启动 ECL 主程序或其他 ECL 子进程；
- 更新、替换、部署或删除 ECL 程序文件；
- 执行 Repair Mode、回滚或恢复操作；
- 启动需要读取或修改 ECL 安装状态的后续流程。

若 Bootstrapper 检测到当前进程已提升，必须拒绝继续执行并退出。不得先执行部分更新或部署，再显示警告。

### 4. 使用明确且一致的拒绝提示

检测到提升权限后，ECL 应向用户展示以下提示：

> ECL 不接受使用管理员身份启动  
> 过度授权可能会造成意外的后果  
> 请以正常形式启动 ECL

提示应提供明确的退出操作。该情况属于启动前安全拒绝，不应显示为普通可忽略警告，也不应提供“仍然继续”选项。

提示文字不应暗示用户必须更换 Windows 账户。用户应以当前账户的正常、未提升方式重新启动 ECL。

### 5. 不自动降权或重新启动

ECL 检测到自身处于提升状态后，不得尝试自动创建低权限令牌、借用其他用户令牌、调用系统降权机制或重新启动一个权限状态不明确的副本。

自动降权会引入令牌来源、用户会话、环境、工作目录、句柄继承和文件访问语义等额外复杂性，也可能掩盖用户明确选择的提权启动行为。

正确行为是拒绝本次启动、展示提示并退出；用户自行以正常方式重新启动。

### 6. 主程序保留纵深防御检查

Bootstrapper 的检查是主要强制入口，但不能假设主程序永远只会由 Bootstrapper 启动。

如果主程序被用户直接运行、通过其他程序启动或绕过 Bootstrapper 启动，也必须检查当前进程的实际提升状态。检测到提升时应拒绝进入正常应用流程，并展示相同的安全提示。

主程序检查是纵深防御，不得替代 Bootstrapper 的早期检查。其他 ECL 子进程也不得通过继承或重新申请提升权限绕过该原则。

### 7. Installer 与其他生命周期组件遵循相同原则

Installer、Bootstrapper、Uninstaller 及 ECL 官方辅助进程不得默认要求管理员权限，也不得主动申请提升权限。

安装和更新设计应优先采用当前用户可写的安装位置及用户级部署方式。若现有安装位置或历史部署方式要求管理员权限，应将其视为安装布局或迁移问题处理，不得通过静默提权绕过本 ADR。

本节不要求 Installer、Uninstaller 与 Bootstrapper 共用同一套 UI 或进程实现；它们只需遵循相同的非提权运行原则。

### 8. 拒绝启动不得破坏用户数据或安装状态

权限检查应在任何部署、修复、更新或用户数据操作之前完成。因提升权限而拒绝启动时：

- 不得修改 ECL 安装文件、版本指针或部署状态；
- 不得修改 Minecraft 实例、世界、账户凭据、配置或用户资料；
- 不得自动触发更新、修复、回滚或卸载；
- 只允许产生完成拒绝提示和必要诊断所需的最小副作用。

诊断记录不得包含认证凭据或其他秘密。

## 备选方案

### 方案 A：只在 ECL 主程序中检查

优点是实现入口较少。

缺点是 Bootstrapper 可能已经在提升权限下执行更新、部署或恢复操作；主程序检查发生得太晚，无法保护启动前生命周期。

不采用。

### 方案 B：只检查用户是否属于 Administrators 组

优点是检测逻辑表面上简单。

缺点是管理员账户在 UAC 未提升时可以使用普通令牌运行应用。按组成员身份拒绝会错误阻止合法的普通权限使用。

不采用。

### 方案 C：检测到提升后自动降权重启

优点是用户可能无需手动重新启动。

缺点是自动降权涉及令牌、用户会话、环境与句柄边界，可能产生不透明的权限切换和新的安全问题，也会掩盖用户主动选择的提权行为。

不采用。

### 方案 D：Bootstrapper 早期强制检查，主程序纵深防御，拒绝后退出

优点是覆盖正常启动入口与绕过入口；判定依据是进程实际权限，而不是账户身份；实现和用户行为都清晰。

采用。

## 后果

### 正面影响

- ECL 正常运行始终保持在普通用户权限边界内。
- Bootstrapper 不会在意外提权状态下执行更新、部署、修复或恢复。
- 管理员账户仍可在 UAC 未提升的状态下正常使用 ECL。
- 用户能够明确知道为什么启动被拒绝，以及如何恢复正常启动。
- 避免 ECL 自动降权带来的令牌和进程生命周期复杂性。
- 即使绕过 Bootstrapper 直接启动主程序，也仍有第二道权限检查。

### 代价与风险

- 需要在 Bootstrapper 最早阶段实现可靠的 Windows 进程令牌检查。
- 旧安装布局若要求写入受保护目录，可能暴露出安装位置与非提权运行原则之间的冲突，需要单独迁移或调整。
- 某些用户可能习惯以管理员身份启动应用，需要通过清晰提示引导其改为正常启动。
- 必须测试 UAC 管理员分离令牌、标准用户、提权启动、提权父进程启动及直接启动主程序等场景。

## 验收标准

本 ADR 当前为 Proposed。以下是未来实现评审的架构验收方向，不表示功能已经实现：

1. Bootstrapper 在启动任何 ECL 子进程、更新、部署、修复或恢复操作之前检查当前进程的实际提升状态。
2. Bootstrapper 检测到提升后的管理员令牌时，显示规定的拒绝提示并退出，不执行后续启动或部署操作。
3. Administrators 组成员使用未提升的普通 UAC 令牌启动时允许运行。
4. 标准用户使用普通令牌启动时允许运行。
5. 通过“以管理员身份运行”启动 Bootstrapper 时拒绝运行。
6. 通过提升权限的父进程启动 Bootstrapper 时，若子进程实际继承提升令牌，则拒绝运行。
7. 用户直接启动主程序并处于提升状态时，主程序仍会拒绝进入正常应用流程。
8. 拒绝启动不会自动降权、重新启动、请求新的 UAC 授权或提供忽略警告继续运行的选项。
9. 拒绝启动不会修改安装状态、版本指针、程序文件、Minecraft 实例、账户凭据或用户资料。
10. Installer、Uninstaller 和官方辅助进程不会主动申请管理员权限；常规生命周期操作不依赖提升权限。
11. 权限判定基于 Windows 当前进程令牌的实际提升状态，而不是账户名称或 Administrators 组成员身份。
12. 用户提示明确说明 ECL 不接受管理员权限启动，并要求以正常形式重新启动。
