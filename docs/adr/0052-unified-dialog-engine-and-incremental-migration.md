# ADR 0052: Unified Dialog Engine and Incremental Migration

- Decision: Accepted
- Implementation: Not Started
- Date: 2026-11-04
- Scope: ECL 主程序的弹窗基础设施、弹窗内容承载、窗口模态关系、遮罩与背景强调、生命周期、交互结果及旧弹窗迁移
- Related: [ADR 0021：WPF 交互反馈与轻量动效系统](0021-wpf-interaction-and-motion-system.md)、[ADR 0050: ECL UI Architecture and Design System Overhaul](0050-ecl-ui-architecture-and-design-system-overhaul.md)、[ADR 0051：统一安装、更新与恢复架构](0051-unified-installation-update-and-recovery-architecture.md)

## 背景

ECL 当前的 UI 布局与既有弹窗渲染实现，已经难以满足新页面对弹窗的内容结构、尺寸适配、动态状态和交互复杂度的要求。继续在旧弹窗上增加特例，会使弹窗实现与页面布局进一步耦合，也会导致不同业务页面重复处理窗口创建、遮罩、层级、关闭和结果返回。

新页面中的弹窗可能包含复杂表格、输入控件、动态列表、逐项进度、错误详情和持续更新的异步状态。它们不再只是固定尺寸的提示框，需要独立且可复用的内容承载和生命周期管理能力。

同时，弹窗出现时必须让用户明确感知当前交互焦点。仅将弹窗绘制在页面上方不足以建立清晰的视觉层级；弹窗外的 ECL 页面需要整体变暗，以突出当前弹窗并表达背景暂时处于非活动状态。该效果参考 Windows UAC 提示的视觉强调方式，但仅属于 ECL 应用内部的视觉与模态交互，不构成 Windows 安全桌面、系统级安全边界或权限提升机制。

因此，ECL 需要引入统一的 Dialog Engine，独立承担弹窗呈现和通用交互管理，并以渐进方式取代旧弹窗逻辑。

## 决策

### 1. 引入独立 Dialog Engine

ECL 主程序新增统一的 Dialog Engine，作为弹窗的基础 UI 基础设施。

引擎统一负责：

- 创建、呈现和关闭弹窗；
- 弹窗内容承载与布局约束；
- 弹窗尺寸、位置和可用空间适配；
- 弹窗与所属窗口之间的模态关系和层级；
- 背景遮罩及背景页面的视觉弱化；
- 弹窗生命周期、交互结果和关闭原因；
- 动态内容与异步状态更新；
- 通用焦点、键盘访问和可访问性语义；
- 动画、异常退出和资源释放。

业务页面通过统一接口请求显示弹窗，并提供业务内容、必要配置和操作处理。业务页面不得自行重复实现通用窗口管理、背景遮罩、模态输入控制或弹窗生命周期。

引擎应与具体业务领域解耦，不得将删除、安装、恢复、安全扫描等业务规则写入通用弹窗核心。

### 2. 弹窗与普通页面布局解耦

弹窗拥有独立于普通页面内容区域的布局和内容承载能力。

- 弹窗不得仅作为普通页面卡片或页面内容树中的固定区域实现。
- 弹窗不得依赖某个具体页面的布局结构、滚动容器或局部渲染状态才能正确显示。
- 弹窗内部可以组合文本、表格、输入控件、列表、进度、错误详情及业务自定义视图。
- 弹窗可以根据内容需要采用不同布局，不强制所有弹窗使用同一内容模板。
- 弹窗尺寸应受所属窗口可用区域约束，并在内容较多时通过弹窗内部滚动、内容折叠或其他明确布局策略处理。
- 弹窗不得因主页面滚动、导航切换或重新布局而发生意外裁切、漂移或状态丢失。
- 弹窗内容的布局职责与弹窗外壳的窗口管理职责分离；复杂业务内容不应迫使引擎核心不断增加业务专用分支。

引擎应提供稳定的宿主/内容接口。具体采用 UserControl、DataTemplate、ViewModel、ContentPresenter 或其他 WPF 机制属于实现选择，须在实现阶段结合现有 MVVM 架构验证，不在本 ADR 中预先锁定某一种具体 API。

### 3. 采用 UAC 风格的应用内背景暗化与模态强调

每当 ECL 主程序显示模态弹窗时，弹窗之外的 ECL 页面整体进入暗化状态，以凸显弹窗并明确当前交互焦点。

具体约束：

- 暗化范围覆盖所属 ECL 主窗口中弹窗之外的页面内容，包括主导航、主内容区及其他可见的 ECL 页面区域；不得只暗化弹窗背后的一小块局部卡片。
- 弹窗本身保持前景显示，不得被背景遮罩覆盖或一并变暗。
- 暗化效果应由 Dialog Engine 统一管理，不允许各业务页面自行叠加不同遮罩实现相同功能。
- 遮罩必须覆盖弹窗所属窗口的有效客户区，并随窗口尺寸变化正确调整；不得出现未覆盖区域、错位或因 DPI 变化产生的缝隙。
- 模态弹窗显示期间，遮罩后的背景页面不得接收普通鼠标或键盘业务输入。焦点应进入弹窗，并在关闭后按合理规则返回原焦点位置。
- 暗化程度应足以清楚区分前景弹窗和背景页面，同时保留背景布局轮廓，避免背景完全不可辨认。具体不透明度和颜色由 Design System 统一定义并通过实机校准，不在 ADR 中硬编码未经验证的数值。
- 弹窗进入和退出时可以使用克制的淡入/淡出或其他轻量过渡；动画不得延迟模态输入锁定、用户取消或业务操作，也不得导致背景短暂可交互。
- Windows 减少动态效果偏好生效时，应减少或跳过非必要动画，但仍保留明确的背景暗化和模态状态。
- 如果弹窗属于非模态辅助窗口，则不得无条件暗化并锁定主页面；是否模态由调用方通过明确配置声明，默认业务确认、警告、输入和进度弹窗采用模态方式。

该设计只模拟 UAC 提示的视觉层级和应用内模态体验。它不创建或模拟 Windows Secure Desktop，不改变系统权限，不要求用户输入 Windows 凭据，也不得向用户暗示弹窗具有系统级安全保护能力。

### 4. 模态、非模态与弹窗层级

引擎应明确区分模态弹窗与非模态弹窗。

- **模态弹窗**：在所属 ECL 窗口内阻止背景页面的普通交互，显示背景暗化，用户需要先处理或明确关闭弹窗才能继续操作背景页面。
- **非模态弹窗**：不锁定背景页面，不默认触发全窗口暗化；适用于确实需要与主页面并行操作的辅助内容。
- 弹窗默认采用模态方式；只有存在明确交互需求时才使用非模态。
- 弹窗必须归属于明确的 ECL 所属窗口，避免失去所有者、被其他窗口遮挡或出现在错误显示器。
- 多个弹窗同时存在时必须由引擎管理层级和所有者关系，不允许各业务页面任意设置窗口 Topmost 或自行争抢焦点。
- 允许受控的父子弹窗关系，例如父弹窗中的特殊操作确实需要进一步确认；子弹窗关闭后应返回父弹窗，并恢复合理焦点。
- 默认不鼓励深层嵌套。可以在父弹窗内部完成的交互，不应为了拆分控件而不断打开新弹窗。
- 无关业务弹窗不得随意堆叠。引擎应能够识别当前活动弹窗，并确保遮罩、焦点和关闭行为与层级一致。
- 关闭父弹窗时，必须按明确的生命周期策略处理仍然打开的子弹窗，不得留下失去所有者的孤立窗口。

### 5. 统一弹窗入口与配置模型

新弹窗必须通过 Dialog Engine 的统一入口创建和呈现。

统一接口至少需要表达以下概念（具体类型和命名由实现阶段确定）：

- 内容或内容提供者；
- 所属窗口；
- 模态模式；
- 标题及可选语义类型；
- 尺寸约束或尺寸策略；
- 允许的关闭方式；
- 初始焦点与关闭后的焦点恢复策略；
- 业务上下文及结果类型；
- 取消、关闭和操作完成之间的语义区别。

引擎应返回可供调用方观察的弹窗结果，而不是要求业务页面依赖窗口控件本身的内部状态。

不得将任意业务对象、业务服务或文件操作逻辑塞入通用弹窗配置。弹窗内容和业务处理应保持清晰边界。

### 6. 生命周期、异步状态与关闭语义

弹窗引擎必须管理清晰且可观察的生命周期，至少区分：

1. 请求创建；
2. 正在显示；
3. 已显示并可交互；
4. 正在执行异步操作；
5. 操作成功、失败、部分成功或结果未知；
6. 用户取消或关闭；
7. 正在关闭；
8. 已关闭并释放资源。

具体弹窗不一定经过全部状态，但不得将用户点击确认、业务开始执行和业务成功混为同一状态。

约束：

- 弹窗内容可以在显示期间动态更新，不应因更新而重新创建窗口或丢失用户输入。
- 异步业务操作不得在 UI 线程执行；引擎负责安全地将状态更新呈现到 UI。
- 重复提交必须由业务命令和交互状态共同防护，不能仅依赖按钮动画或视觉禁用。
- 关闭弹窗不等于自动取消后台任务。只有业务明确提供取消能力且用户触发了相应取消操作时，才请求取消任务。
- 若操作正在执行且不允许关闭，弹窗必须明确限制关闭方式并给出适当反馈；不得静默吞掉系统关闭请求。
- 若允许关闭但任务继续运行，必须确保任务生命周期不依赖弹窗窗口存活，并由其他适当 UI 承接后续状态。
- 动画中断、窗口失焦、页面导航或 UI 资源释放不得改变业务结果。
- 弹窗异常关闭不得伪造成功结果；调用方必须能够区分取消、关闭、失败和结果未知。

### 7. 内容布局、尺寸与滚动

引擎为不同内容提供可靠的可用空间管理，但不强制固定弹窗宽高。

- 弹窗尺寸必须受当前所属窗口和显示区域约束。
- 默认优先采用适合内容的尺寸，并设置合理最大尺寸，避免小内容弹窗无故占据整个窗口。
- 内容较长时，滚动区域应位于弹窗内部，标题、必要操作区和关闭入口应保持可发现。
- 表格、列表和错误详情等高密度内容应能在有限空间内使用，不得导致整个 ECL 主页面滚动。
- 动态扩展错误原因、进度状态或列表项时，应保持可预测的布局，不得使弹窗突然超出屏幕。
- 窗口缩放、显示器切换和 DPI 变化时，弹窗及遮罩必须重新适配。
- 对极端长内容应提供滚动、折叠或分页等合适策略，不要求无限增高。
- 具体弹窗页面的内容组织仍由对应页面规划定义；本 ADR 只约束引擎的通用承载能力。

### 8. 焦点、键盘与可访问性

- 模态弹窗打开后，键盘焦点进入弹窗。
- 模态期间 Tab 导航不得进入被遮罩的背景页面。
- 关闭后应尽可能恢复到打开弹窗前的有效焦点位置；若原控件已不存在或不可用，应回退到合理的所属窗口焦点。
- 默认按钮和危险按钮的焦点策略必须谨慎；破坏性操作不得因默认焦点而被意外触发。
- Enter、Escape 和系统关闭按钮的行为由弹窗语义明确规定，不得为所有弹窗设置同一套可能造成误操作的快捷键。
- 关键控件和状态应提供适当的 AutomationProperties、名称和屏幕阅读器语义。
- 背景暗化不能成为唯一的模态状态信号；键盘输入隔离、焦点和窗口关系也必须正确。
- 非模态弹窗必须保持可键盘访问，并清楚表达其与所属窗口的关系。

### 9. 动效与性能边界

弹窗动效遵循 ADR 0021 的统一动效令牌和减少动态效果策略。

- 优先使用 WPF 原生动画能力及适合合成的属性。
- 允许弹窗淡入/淡出、轻微缩放及背景遮罩透明度过渡。
- 动效应短促、克制，不得造成弹窗迟缓、夸张弹跳或影响高频操作。
- 输入隔离和模态状态必须在弹窗显示时及时生效，不得等待动画结束。
- 关闭和取消不得等待动画完整播放后才响应。
- 动画不得承载业务进度、决定业务成功或失败，也不得作为后台任务的生命周期。
- 不在动画帧回调中执行 IO、业务计算或高频 ViewModel 命令。
- 弹窗关闭后必须释放动画时钟、事件订阅和不再需要的内容引用，避免窗口或 ViewModel 被意外保留。
- 在大量列表、复杂表格、快速连续开关弹窗和低性能设备场景下验证响应性。

### 10. 业务安全与领域职责边界

Dialog Engine 只负责通用 UI 呈现、模态关系和交互结果，不拥有业务操作的安全授权权力。

- 删除确认不能绕过 ADR 0022 的文件所有权、白名单、路径边界、活动任务及引用关系检查。
- 安装和完整性确认不能绕过 ADR 0025、ADR 0051 的验证与部署边界。
- 安全中心的忽略、删除和风险接受不能由通用弹窗自行改变底层检测结论。
- 弹窗引擎不得根据显示文案自行推断用户已授权某项未明确提交的业务操作。
- 用户确认只代表对当前明确展示的操作意图作出选择；目标对象或影响范围变化时，业务层必须重新验证并在必要时重新确认。
- 操作失败、部分成功或结果未知必须由业务层提供真实结果；引擎不得将异常统一包装成成功或静默关闭。
- 业务页面负责提供目标、影响说明、风险、可恢复性和执行策略；Dialog Engine 负责按统一方式呈现并返回用户选择。

### 11. 旧弹窗渐进迁移与兼容策略

采用渐进式迁移，不进行一次性全量重写。

迁移规则：

1. 新增 Dialog Engine 和统一调用入口。
2. 新开发的弹窗全部使用 Dialog Engine。
3. 对现有弹窗进行盘点，记录调用位置、内容类型、模态行为、关闭语义和业务依赖。
4. 优先迁移高频、复杂、涉及破坏性操作或需要动态状态的弹窗。
5. 迁移期间允许旧弹窗和新弹窗短期共存，但必须明确标识旧实现，禁止新增业务继续依赖旧入口。
6. 旧弹窗迁移后应删除对应重复的窗口创建、遮罩、焦点和生命周期逻辑。
7. 迁移完成后，ECL 主程序弹窗统一由 Dialog Engine 管理。
8. 不得为了保持旧弹窗的实现限制而削弱新引擎能力；必要的兼容由受控适配层承担，并设置退出条件。
9. 每批迁移均应独立构建、测试和回归；出现回归时可以回滚该批迁移，不影响已完成的其他批次。

本 ADR 约束 ECL 主程序内的弹窗基础设施。Installer 和 Bootstrapper 是 ADR 0051 定义的独立应用与生命周期入口；它们可以复用经验证的通用实现或设计资源，但不得因本 ADR 而依赖 ECL 主程序、主窗口 Shell 或其运行时。其独立 UI 生命周期仍由 ADR 0051 约束。

### 12. 不预设具体实现技术

当前项目基于 WPF、XAML 和 MVVM，本决策优先在现有技术栈内实现 Dialog Engine。

本 ADR 不预先指定必须使用独立 HWND、Adorner、Popup、ContentControl 或某一种第三方库。实现阶段必须比较其在窗口所有者关系、全窗口遮罩、DPI、焦点隔离、键盘访问、内容裁切、自动化测试和生命周期方面的行为，选择最适合且可维护的方案。

不得为了实现视觉效果而引入新的 UI 框架或不必要的第三方依赖。若确有必要引入，应单独评估维护、许可证、兼容性和部署成本。

## 备选方案

### 方案 A：继续扩展现有弹窗实现

不采用。当前渲染和布局实现已难以承载新弹窗需求；继续增加特例会扩大耦合与维护成本。

### 方案 B：每个页面自行创建弹窗

不采用。该方案会重复实现窗口层级、遮罩、焦点、关闭和结果处理，导致交互与视觉不一致，也难以统一迁移。

### 方案 C：引入统一 Dialog Engine 并渐进迁移

采用。统一通用弹窗能力，同时让业务内容保持独立；渐进迁移可以控制回归风险，并允许新页面立即使用新能力。

## 后果

### 正面影响

- 弹窗拥有独立于普通页面布局的内容承载与尺寸管理能力。
- 全窗口背景暗化建立清晰的前景/背景层级，用户能够明确当前交互焦点。
- 模态输入隔离、焦点恢复和弹窗层级统一管理，减少各页面实现差异。
- 复杂表格、动态进度和错误详情等内容可以复用同一基础设施。
- 新功能不再受旧弹窗渲染能力限制。
- 旧弹窗可分批迁移，避免一次性重写造成大面积回归。
- 业务安全边界仍由领域引擎负责，UI 基础设施不会成为新的权限绕过路径。

### 代价与风险

- 需要维护新的弹窗宿主、生命周期、模态关系和焦点管理机制。
- 全窗口遮罩与不同窗口所有者、DPI、多显示器环境之间需要充分验证。
- 新旧实现共存期间需要维护迁移清单和兼容边界。
- 嵌套弹窗、异步操作和窗口关闭之间的状态关系更复杂。
- 自定义内容承载能力必须避免演变成任意业务逻辑注入通道。
- 如果遮罩、动画或焦点处理不当，可能造成背景残留可交互、焦点丢失或弹窗被遮挡等问题。

## 验收标准

1. ECL 主程序拥有统一 Dialog Engine 和统一弹窗调用入口；新开发弹窗不得新增旧实现依赖。
2. 弹窗可以独立承载不同业务内容，不依赖普通页面的局部布局、滚动容器或生命周期。
3. 弹窗尺寸受所属窗口和显示区域约束；复杂内容可在弹窗内部滚动或采用其他明确布局策略，不裁切主页面。
4. 模态弹窗出现时，所属 ECL 主窗口中弹窗之外的页面区域整体暗化，主导航和主内容区均包含在暗化范围内。
5. 弹窗前景不被遮罩覆盖；遮罩随窗口尺寸和 DPI 变化正确适配，不出现明显缝隙、错位或未覆盖区域。
6. 模态弹窗显示期间，背景页面不能接收普通鼠标或键盘业务输入；焦点进入弹窗，关闭后按规则恢复。
7. 非模态弹窗不默认暗化或锁定背景页面。
8. 模态与非模态模式有明确区分；默认业务确认、警告、输入和进度弹窗使用模态模式。
9. 支持受控父子弹窗关系；子弹窗关闭后正确返回父弹窗，关闭父弹窗不会留下孤立子窗口。
10. 弹窗可动态更新内容和异步状态，不因刷新而意外丢失输入、选择或执行状态。
11. 用户取消、窗口关闭、业务取消、执行失败、部分成功和结果未知能够被明确区分。
12. 弹窗关闭不会自动取消未明确授权取消的后台任务；任务不会依赖弹窗窗口存活。
13. 弹窗支持键盘导航、合理焦点顺序、可见焦点和屏幕阅读器语义；危险操作不会因默认焦点而被意外触发。
14. 减少动态效果策略生效时，动画可被缩短或跳过，但模态状态、背景暗化和输入隔离仍正确。
15. 快速连续打开/关闭弹窗、窗口缩放、跨 DPI 显示器移动和低性能设备场景下无明显卡顿、焦点残留或资源持续增长。
16. Dialog Engine 不执行领域业务操作，不绕过 ADR 0022、0025、0051 等相关安全与验证约束。
17. 旧弹窗迁移清单可追踪；每批迁移有构建和回归证据，迁移完成后旧弹窗管理逻辑已移除或有明确保留理由。
18. Installer 与 Bootstrapper 继续保持 ADR 0051 定义的独立 UI 生命周期，不依赖 ECL 主程序 Dialog Engine 才能启动或恢复。

## 实施阶段

- **P0：现状盘点与技术验证**：盘点现有弹窗、窗口所有者、焦点和关闭语义；验证 WPF 下全窗口暗化、输入隔离、DPI 和多显示器行为。
- **P1：引擎基础能力**：实现统一入口、弹窗宿主、内容承载、尺寸约束、模态/非模态、遮罩、焦点管理和结果返回。
- **P2：复杂内容与异步生命周期**：支持动态内容、复杂列表/表格、异步状态、父子弹窗和异常清理。
- **P3：新功能接入与旧弹窗迁移**：新弹窗统一接入；按优先级迁移旧弹窗，逐步删除兼容逻辑。
- **P4：全面回归与旧实现退出**：完成 DPI、多显示器、键盘访问、性能和业务回归验证；确认旧入口不再被使用后移除。

实施阶段描述目标顺序，不代表任何阶段已经完成。只有满足验收标准并提供可复核证据后，才能更新 Implementation 状态。
