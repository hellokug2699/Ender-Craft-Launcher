# ADR 0027：原生 C# 世界分析与编辑引擎

> 生命周期迁移说明：本次仅拆分决策与实施状态，不改变既有技术决策；尚未开始实施的提案保持原有阶段。

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-02
- Scope: Minecraft 世界存档解析、NBT 数据浏览与编辑、区块分析、地图渲染及语义定义查询
- Related: ADR 0026（实例工作台的存档、多人游戏与最近访问）、ADR 0030（世界诊断与区块异常定位联动）、ADR 0031（多维度世界架构与存储解析）

## 背景

ADR 0026 为实例工作台确定了存档发现、元数据读取和基础管理能力。进一步的产品方向是：让用户能够在不启动 Minecraft 的情况下浏览、分析并在明确授权后编辑世界区块，提供类似 MCA Selector 的能力，但不将 MCA Selector 作为 ECL 的运行时依赖或最终产品实现。

ECL 的主体采用 C# / .NET / WPF。引入 Java Runtime 会增加安装、分发、版本管理、进程启动和故障诊断成本，也会破坏现有技术栈的一致性。因此世界引擎必须以原生 C# 实现，不要求用户安装 Java，也不得通过后台启动 Java 工具完成核心功能。

兼容性不能只以原版世界为目标。Minecraft 模组和数据包能够引入自定义生物群系、方块状态、注册表条目及世界生成配置。以 Biomes O' Plenty 为代表的内容可能使仅按原版假设解释生物群系或绘制地形的工具产生严重失真。类似问题也可能出现在大型整合包和数据包世界中。

ECL 不能把“未知内容”简单映射为某个原版生物群系或地表类型，并将由此产生的错误地图当成真实世界。需要将原始数据解析、注册表解析、地形分析和视觉呈现分离，并在无法完整理解内容时保留信息、标记不确定性，提供不依赖生物群系识别的替代视图。

## 决策

### 1. 自研原生 C# 引擎，不引入 Java 运行时

ECL 将建设自己的 Native World Engine，使用项目现有的 C# / .NET 技术栈实现。

- 核心解析、分析和编辑能力不得依赖 Java Runtime、JVM 或外部 Java 程序。
- 不把 MCA Selector 作为 ECL 的必需组件、子进程或运行时后端。
- 可以研究公开格式、算法、兼容性行为和其他工具的测试案例；复用第三方代码或资产前必须单独审查许可证和归属要求。
- 不为追求功能完整而执行模组 JAR 中的任意代码。模组资源解析应是受限的静态读取。
- 核心库不得依赖 WPF，以便未来被实例工作台、CLI、测试工具或其他 ECL 组件复用。

### 2. 分层架构，隔离格式、语义、分析与 UI

建议划分以下职责边界，具体项目/程序集命名可在实施时按仓库约定调整：

- **World Storage / Format Layer：** Region / Anvil 文件访问、压缩解码、NBT 读写、Chunk 版本识别、文件边界与损坏检测。
- **World Schema Layer：** 不同 Minecraft 版本的 Chunk schema、字段迁移差异、DataVersion 处理及兼容性适配。
- **Registry & Resource Resolver：** 世界内注册表、数据包定义、可识别的模组资源和资源包资源解析。
- **World Analysis Layer：** 区块高度、表面方块、生物群系、区块状态、时间和数据异常分析。
- **Rendering Model：** 将分析结果转换为与 UI 无关的地图瓦片/像素数据、颜色和图层。
- **WPF Presentation：** 地图交互、缩放、平移、选择、筛选、图层开关和编辑工作流。

不得将 NBT 解析、Region 文件 I/O、模组资源扫描或地形算法直接写入 WPF ViewModel。UI 应消费可测试的领域模型和渲染结果。

### 3. 以真实保存的区块数据为依据

第一阶段以磁盘上已经生成并保存的世界数据为分析对象，不承诺在 ECL 中重现 Minecraft 的完整世界生成器。

解析至少应逐步覆盖：

- Region / Anvil 文件及区块定位；
- NBT 数据及 Minecraft 使用的压缩形式；
- Chunk 与 Section 结构；
- 方块状态 Palette 和对应索引数据；
- 生物群系 Palette / 数组及其版本差异；
- Heightmaps；
- Chunk 状态、DataVersion 和必要的元数据；
- 可能影响地图分析的地表方块信息。

必须区分“区块中实际保存的数据”和“根据规则推导的显示结果”。高度图、表面方块、生物群系和区块状态不得互相替代。遇到未知字段、未知版本或无法完整解码的数据时，应保留原始字节/数据或提供明确的不支持状态，不得静默丢弃后继续执行破坏性写入。

### 4. 建立注册表与资源解析机制，正面处理模组和数据包

生物群系和方块不能仅靠硬编码的原版 ID 列表识别。

Resolver 应按可用性逐步处理：

1. 读取世界保存的注册表信息及区块实际使用的标识符。
2. 解析世界所使用的数据包中可识别的生物群系、方块及相关定义。
3. 在安全、有限的范围内扫描实例模组 JAR 和相关资源，提取可静态识别的资源定义。
4. 解析可用的资源包色彩映射和相关资源。
5. 将无法解析的标识符保留为带命名空间的未知条目，并在 UI 中标明，而不是映射成错误的原版内容。

解析器必须记录信息来源、解析成功程度和缺失依赖。资源冲突、重复标识符和不兼容定义应产生可诊断结果。扫描 ZIP/JAR 等归档时应限制条目数、单项解压大小、总解压大小、递归深度和处理时间，防止恶意或异常资源耗尽内存与磁盘。

模组可以通过 Java 代码动态注册内容或实现自定义颜色计算。ECL 不执行模组代码，因此不能保证静态解析还原所有动态行为。遇到这种情况必须明确降级，不能声称完全兼容。

### 5. Biomes O' Plenty 是首批强制兼容性测试目标

Biomes O' Plenty 不得被视为普通的“未知 ID”边缘案例。它应进入早期测试矩阵，用于验证自定义生物群系识别和渲染链路。

测试至少应包含：

- 含有 Biomes O' Plenty 生物群系的真实世界存档；
- 同一世界在原始 Minecraft 环境中的可对照截图或数据；
- 自定义生物群系 ID 的识别与保留；
- 生物群系颜色及可用环境参数的解析；
- 缺少模组、模组版本变化或资源不完整时的降级表现；
- 不支持的自定义行为不会导致整张地图严重失真或程序崩溃。

除 Biomes O' Plenty 外，测试矩阵还应逐步纳入其他模组生物群系、数据包自定义生物群系、大型整合包和不同 Minecraft 版本。

兼容性验收应以真实世界数据为依据，不能仅凭人工构造的单个 NBT 样例宣称兼容。

### 6. 多种渲染模式，未知生物群系不得破坏地图可读性

地图不能只有一种依赖生物群系注册表的渲染方式。至少规划以下图层/模式：

- **高度图：** 依据区块高度或可用 Heightmap 展示地形起伏；不依赖生物群系着色。
- **生物群系图：** 依据区块保存的生物群系 ID 和可解析定义着色。
- **表面方块图：** 依据实际解析出的表面方块状态着色，不将生物群系颜色冒充表面方块。
- **区块状态图：** 展示已生成、缺失、异常、无法解析等状态。
- **分析叠加层：** 后续可增加时间、版本、结构或用户筛选结果等信息。

渲染结果必须能够表达未知、缺失和不确定状态。不能将未知生物群系静默替换成草地、海洋或其他原版生物群系颜色。

生物群系颜色应尽可能遵循对应 Minecraft 版本的数据驱动着色规则，包括可用的温度/降雨参数和资源包色彩映射（例如草地、树叶、水体相关映射）。不同版本规则应由版本适配层处理。若某模组使用只能通过执行代码获得的动态颜色逻辑，ECL 应标记为近似或未知，并允许切换至高度图或表面方块图。

高度图也不能被描述为绝对真实的地形重建：它只是依据实际保存的高度数据生成的视图，具体含义取决于对应版本和 Heightmap 类型。

### 7. 建立独立的 NBT 数据编辑器 Addition，复用自研 World Engine

ECL 将提供独立的官方 NBT Explorer Addition（建议 ID：`ecl.nbt-explorer`），定位为 Minecraft 数据文件的通用浏览、理解、编辑与校验工具。它是 ECL 自主设计和实现的产品，不以直接集成、嵌入或包装现有 NBTExplorer 等第三方应用作为最终实现，也不将其作为运行时依赖。可以研究公开文件格式、交互经验和测试样本；复用第三方代码、资源或数据前必须单独审查许可证与归属要求。

NBT Explorer Addition 负责面向用户的树形浏览、属性面板、搜索、差异比较、编辑工作流和本地化展示；Native World Engine 负责格式解析、版本适配、数据模型、语义解析、校验及安全读写。核心库不得依赖 WPF，Addition 通过受控接口调用引擎能力，不得自行实现另一套 NBT/Region 文件解析器，也不得将 UI 逻辑反向放入 World Engine。

能力按阶段提供，规划范围包括：

- 通用 NBT 树形浏览、展开/折叠、路径定位和类型识别；
- 标签值、名称、类型的添加、修改、删除和重命名；
- 按名称、路径、类型和值搜索，并支持结果定位；
- 两份 NBT 数据的结构和值差异比较；
- 适用格式的导入、导出和 SNBT 等文本表示；
- `level.dat`、玩家数据、实体数据、区块 NBT、Region/Anvil 等 Minecraft 常见数据载体的读取与编辑；
- 对未知标签、未知版本和未知命名空间保留原始数据，不因缺少语义定义而阻止通用 NBT 浏览。

具体文件格式支持必须逐项验证。扩展名相似不代表内部结构、压缩方式或写入规则相同；不支持或无法安全重建的容器必须保持只读或明确拒绝写入。

NBT Explorer 不得成为 World Engine 的唯一消费者。实例工作台、世界诊断、自动化测试及未来其他 Addition 可以直接使用稳定的引擎接口。Vanilla Toolkit 与 NBT Explorer 也不得形成强制依赖；两者可以通过共享的版本标识、Registry 查询接口或语义定义服务协作，但任一 Addition 未安装时，另一方仍须独立工作。

### 8. 为 NBT 建立版本化语义定义与本地化目录

NBT 本身只定义数据类型和结构，不天然包含字段的人类语义。相同标签名可能出现在不同文件、路径、Minecraft 版本或模组命名空间中，含义也可能不同。因此不得仅通过 `tag name → 中文译名` 的全局字典解释 NBT。

World Engine 应支持独立的、版本化的 **NBT Semantic Definition Catalog**。目录项应能根据文件类别、Minecraft 版本/DataVersion、完整标签路径、父级结构、命名空间及必要的上下文匹配定义。定义至少可以包含：

- 稳定定义 ID、适用 Minecraft 版本/DataVersion 范围及适用文件/对象类型；
- 原始标签名、路径匹配规则、NBT 类型及必要的父子结构约束；
- 多语言显示名称、简短说明和详细定义；
- 合法取值、枚举映射、单位、默认值或数值范围（仅在有可靠依据时提供）；
- 关联的 Registry ID、游戏对象或其他标签定义；
- 示例、常见用途、修改影响及风险说明；
- 来源、来源版本、验证状态、维护者和许可/归属信息。

界面必须同时保留原始标签名与路径。用户可以看到本地化译名和说明，但编辑、搜索复制、导出及写回始终以原始 NBT 名称和值为准；本地化目录不得改变文件内容，也不得把译名序列化进 NBT。

点击标签或选择值时，ECL 可以在内部定义面板中展示其定义、数据类型、取值含义、版本差异、关联对象和修改注意事项。用户还可以通过定义查询入口按原始名称、译名、路径、Registry ID 或关键词搜索。查询必须能区分同名但上下文不同的定义，并显示当前匹配依据；无法确定上下文时，应展示候选定义而不是武断选取一个。

语义目录与解析器、UI 分离，可独立更新和校验；无目录、目录不兼容或找不到定义时，NBT Explorer 仍须正常显示原始标签树，并回退到原始名称、类型和值。未知模组标签不得被错误翻译成原版标签。模组和数据包定义可以由独立目录扩展提供，但必须标记命名空间、来源和适用版本，不执行模组代码。

本地化文本与定义内容必须记录来源和许可。不得直接复制未获授权的 Wiki 文章或第三方数据库作为定义正文。可以编写自己的解释，并在许可允许时引用可追溯的事实、协议或公开定义；来源不明或许可不清的长篇说明不得进入官方目录。

目录应支持多语言回退：优先用户语言，其次项目指定的通用语言，最后回退原始标识符。缺少某种语言不能影响定义本身或编辑能力。初期可优先提供简体中文与英文，但数据模型不得将语言集合写死。

### 9. 编辑变更与数据校验必须在树形视图中持续可见

NBT Explorer 必须在编辑过程中明确呈现当前编辑会话相对于打开时基线的变更，以及数据校验结果。用户不应依赖记忆或逐项比较才能知道哪些内容已被修改。

- **直接变更标记：** 被新增、删除、重命名或修改值/类型的节点必须有明确标记；新增与删除节点应有各自可区分的状态。
- **父级路径标记：** 如果某个节点或其后代存在未提交变更，则从该节点到根节点的所有祖先都必须显示“包含变更”的聚合标记。父级聚合标记必须与节点自身被直接修改的标记区分，避免用户误以为父级值本身发生变化。
- **变更范围可追踪：** 用户可以查看变更摘要，并从摘要定位到具体节点；对删除、重命名和移动等操作，应能识别原位置与新位置。撤销/重做后标记必须与当前实际差异同步，已恢复到基线的节点不应继续显示为待提交变更。
- **非法值标记：** 不符合已知 NBT 类型约束、已匹配版本/文件结构定义或可靠语义规则的节点和值必须被标记，并提供原因、约束依据及定位信息。校验应覆盖值本身，也应覆盖必要的父子结构、必需字段、枚举取值和上下文约束。
- **错误与警告分级：** 确定违反格式或已验证约束的情况标记为错误；可能有风险、定义不完整或仅为建议的情况标记为警告。未知标签、缺少语义目录或尚未支持的模组字段不能仅因“无法识别”就判为非法。
- **实时与保存前校验：** 对可低成本判断的约束，在编辑时及时反馈；结构性或跨字段校验可异步执行，并在保存前重新执行。校验任务必须可取消且结果需绑定对应数据版本，避免旧结果覆盖新编辑状态。
- **保存策略：** 存在确定性错误时，默认阻止普通保存，并说明如何修复；对警告允许用户查看具体风险后显式确认继续。若用户选择导出原始/尽力恢复数据，应明确标注其校验状态，不得将其伪装为有效数据。
- **可访问性：** 状态不能只依赖颜色表达；必须同时提供图标、文本、工具提示或状态面板等可辨识信息，并支持键盘导航和屏幕阅读器获取。

变更跟踪和校验结果属于编辑会话状态，不得写入 NBT 文件。保存成功后应以新基线重新计算变更标记；保存失败时保留编辑状态、错误信息和恢复机会。

### 10. 分析与破坏性编辑分离

地图浏览和分析应默认只读。区块选择、筛选和统计不能隐式修改世界。

编辑能力应在只读分析稳定后分阶段实现。任何批量删除区块、清理区域或其他破坏性操作都必须具备：

- 清楚显示目标世界、Region、Chunk 范围和预计影响数量；
- 执行前预览，明确哪些区块会被修改；
- 检查世界是否正在被 Minecraft 或其他进程使用；无法可靠确认安全时拒绝写入；
- 在写入前创建可验证的备份或提供等效恢复保障；
- 写入期间采用临时文件、原子替换或经过验证的安全提交策略；
- 失败时尽可能保留原始文件，并提供恢复路径；
- 不支持或无法完整理解的 Chunk 不得进入批量破坏性操作；
- 对用户选择的操作再次确认，不得因地图框选或筛选而自动执行删除。

NBT Explorer Addition 可以提供通用 NBT 编辑能力，但这不意味着 World Engine 已经能够安全重建所有 Minecraft 容器。对 Chunk/Region 等复杂容器，必须在对应版本的解析、写回、压缩、偏移表更新和回滚流程经过验证后，才开放编辑；在此之前只提供只读浏览或明确标记为实验性的能力。应先实现可靠的只读分析，再逐步开放经过验证的编辑操作。

### 11. 性能、稳定性和资源限制

大型世界可能包含大量 Region 和 Chunk。引擎应采用异步 I/O、按需解析、可取消任务和有界并发；地图瓦片及解析结果可按世界文件状态进行缓存，但缓存失效必须可靠。

- UI 线程不得执行大规模 NBT 解析、全世界扫描或同步磁盘 I/O。
- 支持按视口/区域渐进加载，避免打开世界时一次性解析全部区块。
- 限制单文件、单 Chunk、NBT 嵌套深度、数组长度、资源包解压量和图像尺寸。
- 对损坏 Region、异常压缩流、无效 Palette、越界索引和未知 DataVersion 做隔离处理。
- 一个 Chunk 解析失败不得导致整个世界视图崩溃。
- 任务可取消，取消或失败不得留下被误认为完整的缓存或备份。
- 不得为了加速地图预览而修改原始世界数据。

### 12. 实例工作台集成

Native World Engine 作为独立核心能力，由实例工作台调用。存档发现、基本元数据、打开目录、备份和删除仍遵循 ADR 0026 的职责与安全要求；地图分析和区块编辑由 World Engine 提供。

主页只展示必要的最近访问摘要，不承载地图解析和编辑逻辑。世界引擎故障、未知模组内容或不支持的世界版本不得阻止用户启动 Minecraft 或使用实例工作台中的其他功能。

## 多维度世界模型与存储解析

World Engine 必须采用 **World → Dimension → Region → Chunk** 的基础对象层级。维度身份、发现规则、存储映射和跨维度隔离统一遵循 [ADR 0031：多维度世界架构与存储解析](0031-multi-dimension-world-architecture.md)。

引擎应实现独立的 Dimension Discovery & Storage Resolver，按版本和存档实际结构发现维度，并分别解析 Region、Entities、POI 等存储类别。不得将目录名直接当作 Dimension ID，也不得在解析失败时回退到主世界。

世界编辑器应提供维度选择器；地图、Chunk/Region、Biome、Heightmap、实体、诊断叠加层、缓存键和异步任务均必须绑定当前维度。相同坐标在不同维度中属于不同对象。自定义维度按可解析程度提供基础读取或明确降级，不执行模组代码，也不将未知语义伪装成原版结果。


## 后果

### 正面影响

- ECL 保持 C# / .NET 技术栈一致性，不增加 Java Runtime 安装和维护负担。
- 核心解析和分析能力可复用于 WPF、CLI、测试和其他工具。
- 原版、模组和数据包世界可以使用统一的解析与渲染架构逐步支持。
- 多种渲染模式降低对生物群系注册表和模组资源完整性的单点依赖。
- Biomes O' Plenty 等复杂模组成为明确的兼容性验收对象，而不是事后补丁。
- 只读分析与破坏性编辑分离，降低世界数据损坏风险。

### 代价与限制

- 不同 Minecraft 版本的 Chunk schema、NBT 和注册表机制需要持续维护。
- 模组可能通过代码动态注册内容或改变渲染行为，静态资源解析无法保证完全还原。
- 生物群系着色需要处理版本差异、数据驱动参数和资源包色彩映射。
- 大型世界的解析、缓存和地图渲染需要专门的性能设计。
- 自研引擎的范围明显大于简单调用外部 MCA 工具，必须分阶段交付。
- NBT 语义定义需要按版本、文件类型和路径持续维护；单纯标签名翻译无法覆盖上下文差异。
- 本地化定义可能存在来源、许可和准确性问题，必须提供来源、验证状态和未知回退。
- 对未知格式和不完整资源，ECL 必须接受显示降级，而不是猜测数据含义。

## 实施顺序建议

1. 建立纯 C# 的 Region / NBT 读取原型和版本识别测试，不接入 UI。
2. 读取 Chunk、Section、Block State Palette、Biome Palette 和 Heightmaps，建立统一领域模型。
3. 实现只读世界扫描、Chunk 状态分析和高度图渲染。
4. 实现表面方块图及多图层地图交互。
5. 建立注册表与资源解析器，支持数据包及静态可识别的模组资源。
6. 以 Biomes O' Plenty 真实世界为首批重点样本，完善自定义生物群系识别、颜色映射和降级策略。
7. 扩展到其他模组、数据包和整合包，并建立跨 Minecraft 版本的回归测试集。
8. 建立 NBT Semantic Definition Catalog，先覆盖 `level.dat`、玩家数据等高价值结构，提供中英文名称、定义和上下文查询。
9. 实现 NBT Explorer Addition 的只读树形浏览、搜索、定义面板和差异比较。
10. 实现编辑会话变更跟踪、祖先聚合标记和版本化语义校验，完成错误/警告分级及保存门禁。
11. 在通用 NBT 编辑与安全写回成熟后，逐步开放经过验证的文件和容器编辑能力。
12. 在只读解析和备份机制成熟后，再设计有限的区块筛选、删除和恢复能力。

## 验收要求

- 核心引擎可在没有 Java Runtime 的环境中独立运行和测试。
- 核心解析、分析和渲染模型不依赖 WPF。
- 能够读取受支持版本的 Region / Anvil、NBT、Chunk、Palette 和 Heightmap 数据。
- 未知或损坏的 Chunk 被隔离并给出明确状态，不导致整个世界视图崩溃。
- 高度图、表面方块图和生物群系图使用各自正确的数据来源，不互相冒充。
- 未知生物群系保留真实标识符，不得静默映射成错误的原版生物群系。
- Biomes O' Plenty 真实世界进入自动化/回归测试及人工对照验收；不能仅以原版世界测试通过代替。
- 数据包和可静态解析的模组资源能够被识别；无法静态还原的动态行为明确标记为近似或未知。
- 资源扫描、NBT 解析和图像解码具有明确的资源上限。
- 大型世界采用渐进加载、有界并发和可取消任务，UI 不因扫描或渲染而冻结。
- 只读浏览不会修改 Region、Chunk 或世界元数据。
- NBT Explorer 由 ECL 自主实现为独立 Addition，不依赖或直接包装第三方 NBT 编辑器。
- Addition 能浏览通用 NBT 结构，并在语义目录可用时按文件类型、版本和路径显示本地化名称与定义；目录缺失时仍可显示原始标签。
- 本地化定义面板和内部查询可按原始名称、译名、路径或 Registry ID 搜索，并能区分上下文不同的同名标签。
- 本地化显示不会改变原始 NBT 键、值或导出内容；未知标签和模组标签不会被错误映射为原版定义。
- 编辑会话中直接修改的节点有明确标记，所有包含变更后代的祖先节点有独立的聚合标记；撤销/重做后标记与实际差异一致。
- 不符合已知类型、版本结构或可靠语义约束的值/结构会显示错误或警告及原因；未知标签不会仅因缺少定义而被判为非法。
- 确定性校验错误默认阻止普通保存；警告需向用户说明风险并显式确认，校验结果不会因异步竞态而过期覆盖。
- 语义目录记录版本适用范围、来源和验证状态；未验证或来源/许可不清的说明不会伪装成权威定义。
- 复杂 Minecraft 容器只有在对应版本的安全写回、完整性校验和恢复流程通过验证后才允许编辑。
- 任何破坏性编辑在执行前提供目标预览、进程占用检查和可验证备份；不支持的数据拒绝写入。
- 世界引擎不可用时，不影响 ECL 的常规启动、实例管理和其他功能。
