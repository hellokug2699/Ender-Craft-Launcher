# ADR 0027：原生 C# 世界分析与编辑引擎

- Status: Accepted (implementation pending)
- Date: 2026-11-02
- Scope: Minecraft 世界存档解析、区块分析、地图渲染与编辑
- Related: ADR 0026（实例工作台的存档、多人游戏与最近访问）

## 背景

ADR 0026 为实例工作台确定了存档发现、元数据读取和基础管理能力。进一步的产品方向是：让用户能够在不启动 Minecraft 的情况下浏览、分析并在明确授权后编辑世界区块，提供类似 MCA Selector 的能力，但不将 MCA Selector 作为 ECL 的运行时依赖或最终产品实现。

ECL 的主体采用 C# / .NET / WPF。引入 Java Runtime 会增加安装、分发、版本管理、进程启动和故障诊断成本，也会破坏现有技术栈的一致性。因此世界引擎必须以原生 C# 实现，不要求用户安装 Java，也不得通过后台启动 Java 工具完成核心功能。

兼容性不能只以原版世界为目标。Minecraft 模组和数据包能够引入自定义生物群系、方块状态、注册表条目及世界生成配置。以 Biomes O' Plenty 为代表的内容可能使仅按原版假设解释生物群系或绘制地形的工具产生严重失真。类似问题也可能出现在大型整合包和数据包世界中。

ECL 不能把“未知内容”简单映射为某个原版生物群系或地表类型，并将由此产生的错误地图当成真实世界。需要将原始数据解析、注册表解析、地形分析和视觉呈现分离，并在无法完整理解内容时保留信息、标记不确定性，提供不依赖生物群系识别的替代视图。

## 决策

### 1. 自研原生 C# 引擎，不引入 Java 运行时

ECL 将建设自己的 Native World Engine，使用项目现有的 C# / .NET 技术栈实现。

- 核心解析、分析和编辑能力不得依赖 Java Runtime、JVM 或外部 Java 程序。
- 不把 MCA Selector 作为 ECL 的必需组件、子进程或运行时后端。
- 可以研究公开格式、算法、兼容性行为和其他工具的测试案例；复用第三方代码或资产前必须单独审查许可证和归属要求。
- 不为追求功能完整而执行模组 JAR 中的任意代码。模组资源解析应是受限的静态读取。
- 核心库不得依赖 WPF，以便未来被实例工作台、CLI、测试工具或其他 ECL 组件复用。

### 2. 分层架构，隔离格式、语义、分析与 UI

建议划分以下职责边界，具体项目/程序集命名可在实施时按仓库约定调整：

- **World Storage / Format Layer：** Region / Anvil 文件访问、压缩解码、NBT 读写、Chunk 版本识别、文件边界与损坏检测。
- **World Schema Layer：** 不同 Minecraft 版本的 Chunk schema、字段迁移差异、DataVersion 处理及兼容性适配。
- **Registry & Resource Resolver：** 世界内注册表、数据包定义、可识别的模组资源和资源包资源解析。
- **World Analysis Layer：** 区块高度、表面方块、生物群系、区块状态、时间和数据异常分析。
- **Rendering Model：** 将分析结果转换为与 UI 无关的地图瓦片/像素数据、颜色和图层。
- **WPF Presentation：** 地图交互、缩放、平移、选择、筛选、图层开关和编辑工作流。

不得将 NBT 解析、Region 文件 I/O、模组资源扫描或地形算法直接写入 WPF ViewModel。UI 应消费可测试的领域模型和渲染结果。

### 3. 以真实保存的区块数据为依据

第一阶段以磁盘上已经生成并保存的世界数据为分析对象，不承诺在 ECL 中重现 Minecraft 的完整世界生成器。

解析至少应逐步覆盖：

- Region / Anvil 文件及区块定位；
- NBT 数据及 Minecraft 使用的压缩形式；
- Chunk 与 Section 结构；
- 方块状态 Palette 和对应索引数据；
- 生物群系 Palette / 数组及其版本差异；
- Heightmaps；
- Chunk 状态、DataVersion 和必要的元数据；
- 可能影响地图分析的地表方块信息。

必须区分“区块中实际保存的数据”和“根据规则推导的显示结果”。高度图、表面方块、生物群系和区块状态不得互相替代。遇到未知字段、未知版本或无法完整解码的数据时，应保留原始字节/数据或提供明确的不支持状态，不得静默丢弃后继续执行破坏性写入。

### 4. 建立注册表与资源解析机制，正面处理模组和数据包

生物群系和方块不能仅靠硬编码的原版 ID 列表识别。

Resolver 应按可用性逐步处理：

1. 读取世界保存的注册表信息及区块实际使用的标识符。
2. 解析世界所使用的数据包中可识别的生物群系、方块及相关定义。
3. 在安全、有限的范围内扫描实例模组 JAR 和相关资源，提取可静态识别的资源定义。
4. 解析可用的资源包色彩映射和相关资源。
5. 将无法解析的标识符保留为带命名空间的未知条目，并在 UI 中标明，而不是映射成错误的原版内容。

解析器必须记录信息来源、解析成功程度和缺失依赖。资源冲突、重复标识符和不兼容定义应产生可诊断结果。扫描 ZIP/JAR 等归档时应限制条目数、单项解压大小、总解压大小、递归深度和处理时间，防止恶意或异常资源耗尽内存与磁盘。

模组可以通过 Java 代码动态注册内容或实现自定义颜色计算。ECL 不执行模组代码，因此不能保证静态解析还原所有动态行为。遇到这种情况必须明确降级，不能声称完全兼容。

### 5. Biomes O' Plenty 是首批强制兼容性测试目标

Biomes O' Plenty 不得被视为普通的“未知 ID”边缘案例。它应进入早期测试矩阵，用于验证自定义生物群系识别和渲染链路。

测试至少应包含：

- 含有 Biomes O' Plenty 生物群系的真实世界存档；
- 同一世界在原始 Minecraft 环境中的可对照截图或数据；
- 自定义生物群系 ID 的识别与保留；
- 生物群系颜色及可用环境参数的解析；
- 缺少模组、模组版本变化或资源不完整时的降级表现；
- 不支持的自定义行为不会导致整张地图严重失真或程序崩溃。

除 Biomes O' Plenty 外，测试矩阵还应逐步纳入其他模组生物群系、数据包自定义生物群系、大型整合包和不同 Minecraft 版本。

兼容性验收应以真实世界数据为依据，不能仅凭人工构造的单个 NBT 样例宣称兼容。

### 6. 多种渲染模式，未知生物群系不得破坏地图可读性

地图不能只有一种依赖生物群系注册表的渲染方式。至少规划以下图层/模式：

- **高度图：** 依据区块高度或可用 Heightmap 展示地形起伏；不依赖生物群系着色。
- **生物群系图：** 依据区块保存的生物群系 ID 和可解析定义着色。
- **表面方块图：** 依据实际解析出的表面方块状态着色，不将生物群系颜色冒充表面方块。
- **区块状态图：** 展示已生成、缺失、异常、无法解析等状态。
- **分析叠加层：** 后续可增加时间、版本、结构或用户筛选结果等信息。

渲染结果必须能够表达未知、缺失和不确定状态。不能将未知生物群系静默替换成草地、海洋或其他原版生物群系颜色。

生物群系颜色应尽可能遵循对应 Minecraft 版本的数据驱动着色规则，包括可用的温度/降雨参数和资源包色彩映射（例如草地、树叶、水体相关映射）。不同版本规则应由版本适配层处理。若某模组使用只能通过执行代码获得的动态颜色逻辑，ECL 应标记为近似或未知，并允许切换至高度图或表面方块图。

高度图也不能被描述为绝对真实的地形重建：它只是依据实际保存的高度数据生成的视图，具体含义取决于对应版本和 Heightmap 类型。

### 7. 分析与破坏性编辑分离

地图浏览和分析应默认只读。区块选择、筛选和统计不能隐式修改世界。

编辑能力应在只读分析稳定后分阶段实现。任何批量删除区块、清理区域或其他破坏性操作都必须具备：

- 清楚显示目标世界、Region、Chunk 范围和预计影响数量；
- 执行前预览，明确哪些区块会被修改；
- 检查世界是否正在被 Minecraft 或其他进程使用；无法可靠确认安全时拒绝写入；
- 在写入前创建可验证的备份或提供等效恢复保障；
- 写入期间采用临时文件、原子替换或经过验证的安全提交策略；
- 失败时尽可能保留原始文件，并提供恢复路径；
- 不支持或无法完整理解的 Chunk 不得进入批量破坏性操作；
- 对用户选择的操作再次确认，不得因地图框选或筛选而自动执行删除。

首期不承诺实现完整 Chunk NBT 编辑器，也不承诺任意修改区块内部数据。应先实现可靠的只读分析，再评估明确、有限的编辑操作。

### 8. 性能、稳定性和资源限制

大型世界可能包含大量 Region 和 Chunk。引擎应采用异步 I/O、按需解析、可取消任务和有界并发；地图瓦片及解析结果可按世界文件状态进行缓存，但缓存失效必须可靠。

- UI 线程不得执行大规模 NBT 解析、全世界扫描或同步磁盘 I/O。
- 支持按视口/区域渐进加载，避免打开世界时一次性解析全部区块。
- 限制单文件、单 Chunk、NBT 嵌套深度、数组长度、资源包解压量和图像尺寸。
- 对损坏 Region、异常压缩流、无效 Palette、越界索引和未知 DataVersion 做隔离处理。
- 一个 Chunk 解析失败不得导致整个世界视图崩溃。
- 任务可取消，取消或失败不得留下被误认为完整的缓存或备份。
- 不得为了加速地图预览而修改原始世界数据。

### 9. 实例工作台集成

Native World Engine 作为独立核心能力，由实例工作台调用。存档发现、基本元数据、打开目录、备份和删除仍遵循 ADR 0026 的职责与安全要求；地图分析和区块编辑由 World Engine 提供。

主页只展示必要的最近访问摘要，不承载地图解析和编辑逻辑。世界引擎故障、未知模组内容或不支持的世界版本不得阻止用户启动 Minecraft 或使用实例工作台中的其他功能。

## 后果

### 正面影响

- ECL 保持 C# / .NET 技术栈一致性，不增加 Java Runtime 安装和维护负担。
- 核心解析和分析能力可复用于 WPF、CLI、测试和其他工具。
- 原版、模组和数据包世界可以使用统一的解析与渲染架构逐步支持。
- 多种渲染模式降低对生物群系注册表和模组资源完整性的单点依赖。
- Biomes O' Plenty 等复杂模组成为明确的兼容性验收对象，而不是事后补丁。
- 只读分析与破坏性编辑分离，降低世界数据损坏风险。

### 代价与限制

- 不同 Minecraft 版本的 Chunk schema、NBT 和注册表机制需要持续维护。
- 模组可能通过代码动态注册内容或改变渲染行为，静态资源解析无法保证完全还原。
- 生物群系着色需要处理版本差异、数据驱动参数和资源包色彩映射。
- 大型世界的解析、缓存和地图渲染需要专门的性能设计。
- 自研引擎的范围明显大于简单调用外部 MCA 工具，必须分阶段交付。
- 对未知格式和不完整资源，ECL 必须接受显示降级，而不是猜测数据含义。

## 实施顺序建议

1. 建立纯 C# 的 Region / NBT 读取原型和版本识别测试，不接入 UI。
2. 读取 Chunk、Section、Block State Palette、Biome Palette 和 Heightmaps，建立统一领域模型。
3. 实现只读世界扫描、Chunk 状态分析和高度图渲染。
4. 实现表面方块图及多图层地图交互。
5. 建立注册表与资源解析器，支持数据包及静态可识别的模组资源。
6. 以 Biomes O' Plenty 真实世界为首批重点样本，完善自定义生物群系识别、颜色映射和降级策略。
7. 扩展到其他模组、数据包和整合包，并建立跨 Minecraft 版本的回归测试集。
8. 在只读解析和备份机制成熟后，再设计有限的区块筛选、删除和恢复能力。

## 验收要求

- 核心引擎可在没有 Java Runtime 的环境中独立运行和测试。
- 核心解析、分析和渲染模型不依赖 WPF。
- 能够读取受支持版本的 Region / Anvil、NBT、Chunk、Palette 和 Heightmap 数据。
- 未知或损坏的 Chunk 被隔离并给出明确状态，不导致整个世界视图崩溃。
- 高度图、表面方块图和生物群系图使用各自正确的数据来源，不互相冒充。
- 未知生物群系保留真实标识符，不得静默映射成错误的原版生物群系。
- Biomes O' Plenty 真实世界进入自动化/回归测试及人工对照验收；不能仅以原版世界测试通过代替。
- 数据包和可静态解析的模组资源能够被识别；无法静态还原的动态行为明确标记为近似或未知。
- 资源扫描、NBT 解析和图像解码具有明确的资源上限。
- 大型世界采用渐进加载、有界并发和可取消任务，UI 不因扫描或渲染而冻结。
- 只读浏览不会修改 Region、Chunk 或世界元数据。
- 任何破坏性编辑在执行前提供目标预览、进程占用检查和可验证备份；不支持的数据拒绝写入。
- 世界引擎不可用时，不影响 ECL 的常规启动、实例管理和其他功能。
