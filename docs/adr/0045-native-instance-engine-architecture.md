# ADR 0045：原生 Instance Engine 架构与能力边界

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-03
- Scope: Minecraft 实例身份、资源清单、文件访问、依赖分析、变更事务、快照恢复及 Addition 能力扩展
- Related: [ADR 0018：Minecraft 工作区与实例存储位置](0018-minecraft-workspace-and-instance-storage.md)、[ADR 0023：多实例来源目录登记与统一扫描](0023-multi-root-instance-discovery.md)、[ADR 0026：实例工作台的存档、多人游戏与最近访问](0026-instance-workbench-worlds-servers-and-recent-access.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0042：实例文件浏览器与崩溃报告工作流](0042-instance-file-explorer-and-crash-report-workflow.md)

## 背景

ECL 正从 Minecraft Launcher 扩展为围绕实例进行管理、分析和维护的工具。实例文件浏览、资源识别、模组依赖、迁移、快照、诊断和安全操作会共同访问同一组文件与状态。如果每个功能分别实现扫描器、路径访问、缓存、写入和恢复机制，容易出现身份不一致、重复扫描、互相覆盖、状态过期和不可恢复的部分写入。

ECL 已经通过 ADR 0032 确立原生功能入口与可选 Addition 的边界，也通过 ADR 0042 定义 Instance Inventory 与受控文件访问。需要进一步明确：这些跨功能基础能力应形成统一的原生 Instance Engine，而不是由各个 Addition 各自实现。

## 决策

### 1. 建立原生 Instance Engine

Instance Engine 是 ECL Core 的原生领域基础设施，负责对 Minecraft 实例进行识别、理解、追踪和安全变更。即使没有安装任何 Addition，实例身份、基础文件访问、资源清单、变更协调和恢复基础能力仍必须可用。

Engine 不等同于一个 UI 页面，也不是一个 Addition。ECL 原生页面和 Addition 都是它的消费者。

### 2. 核心职责

Instance Engine 按职责提供以下能力：

- **Identity & Registration：** 稳定实例身份、实例元数据、位置与来源登记关联；
- **File Access：** 实例范围的路径解析、访问授权、文件句柄和安全边界；
- **Inventory & Scanner：** 文件索引、资源识别、分阶段扫描、缓存与增量更新；
- **Dependency & Compatibility：** 资源依赖图、版本范围、环境约束和证据化判断；
- **Change Coordination：** 实例级写入协调、冲突检测、变更计划与事务生命周期；
- **Snapshot & Recovery：** 用户快照、事务恢复所需的前态保护、校验和恢复；
- **Evidence & History：** 扫描来源、规则版本、判断置信度、变更历史及可追溯结果。

这些模块应共享稳定的领域标识与数据模型，但可以独立演进；不得将 Engine 实现成一个包含所有业务逻辑的巨型服务。

### 3. 原生 UI 与 Addition 的边界

ECL 原生 UI 负责产品入口、页面、交互、确认流程和状态呈现。Instance Engine 负责领域规则、文件安全、状态一致性、操作协调和结果证据。

Addition 可以通过版本化 Core API：
- 读取经授权的实例与 Inventory 数据；
- 注册受限的资源识别器、分析器、预览器或处理器；
- 提供特定格式的领域分析结果；
- 请求 Engine 执行受控的变更计划。

Addition 不得直接绕过 Engine 修改受管理实例文件，不得自行维护与 Engine 冲突的实例身份、权威清单或事务状态。任何写入请求都必须由 Engine 验证目标、权限、并发冲突、影响范围和恢复策略。

### 4. 数据归属与本地优先

实例中的游戏文件仍由用户拥有；Engine 不应将派生缓存误认为实例内容的权威来源。

- 实例内只保存维持身份与必要恢复能力所需的轻量元数据；
- ECL 本地数据目录保存索引、扫描缓存、事务历史和可配置的快照存储；
- 派生 Inventory 可以重建，必须记录扫描时间、规则/解析器版本及证据来源；
- 实例身份元数据与本地数据库不一致时进入显式修复/重新关联流程，不得静默覆盖；
- 不上传实例清单、日志、路径、世界数据或诊断结果；任何未来外部传输均须另行明确授权。

具体身份与元数据策略由 ADR 0046 细化；事务与并发策略由 ADR 0047 细化；快照与恢复策略由 ADR 0048 细化。

### 5. 资源扫描与判断必须保留证据

Engine 输出的资源状态不应只有单一布尔值。扫描结果应区分已确认、推断、未知、未扫描、部分完成和失败，并附带适用时的来源、时间、规则版本和置信程度。

静态元数据只能证明静态条件，不得伪装成运行时加载成功或实际兼容性结论。Addition 提供的分析结果必须标明提供者及版本，并受相同证据模型约束。

### 6. 优先级与实施顺序

采用以下优先级，优先解决会造成数据损坏或跨功能冲突的基础能力：

| 优先级 | 能力 | 原因与交付边界 |
|---|---|---|
| P0 | 实例身份与元数据 | 所有实例操作的稳定锚点；先解决路径变化、重复识别和克隆语义 |
| P0 | 实例范围文件访问与安全边界 | 所有读取/写入的共同安全入口；复用 ADR 0042，不另造一套文件浏览器 |
| P0 | 实例级写入协调与事务基础 | 防止多个页面/Addition 并发修改导致覆盖、损坏或状态错乱 |
| P1 | Inventory 与分阶段扫描 | 统一 Explorer、Workbench、诊断和管理功能的资源事实来源 |
| P1 | 依赖分析与影响评估 | 支撑安全删除、更新计划和变更确认 |
| P1 | 事务恢复与基础快照能力 | 为中断恢复、更新回滚提供可靠底座 |
| P2 | 实例健康档案与变更历史 | 在已有身份、扫描和事务记录上汇总，不另建平行状态系统 |
| P2 | 实例迁移与克隆 | 依赖身份、文件操作、事务、验证和恢复成熟后实施 |
| P2 | 整合包/实例差异比较 | 复用 Inventory 与内容指纹 |
| P2 | 资源配置组合管理 | 复用 Inventory 和事务应用配置组合 |
| P3 | 性能分析与兼容性实验室 | 依赖运行时证据、隔离环境和较高测试成本 |
| P3 | 高级存档数据工具箱 | 复用现有 World Engine 与受控处理器能力，不重复实现 NBT/Region 基础设施 |

优先级表示架构依赖与实施顺序，不是用户价值评分，也不代表同一优先级内必须严格串行。P0 的并发控制与恢复边界未建立前，不应开放多个独立写入入口。

### 7. 与既有架构的关系

- ADR 0018 继续定义工作区、ECL 数据目录与实例存储边界；
- ADR 0023 继续定义来源目录登记与实例发现；本 ADR 的稳定身份决策由 ADR 0046 统一细化，必要时后续修订 0023 中旧的身份描述；
- ADR 0026 继续定义实例工作台的产品组织；
- ADR 0032 继续定义 Addition 生命周期与扩展边界；
- ADR 0042 继续定义 Explorer、Inventory、文件访问与处理器注册的功能要求，并逐步由 Instance Engine 承载共享实现；
- ADR 0033、0041、0043 等领域系统可消费 Engine 提供的本地证据，但保留各自诊断、性能与威胁判断职责。

## 备选方案

### 方案 A：每个功能自行实现实例管理逻辑

优点是局部开发简单、模块可以独立启动。

放弃原因：会产生重复扫描、不同身份规则、互不兼容缓存和互相竞争的文件写入路径，长期维护成本和数据风险更高。

### 方案 B：把所有实例能力放进某个 Addition

优点是主程序体积较小，能力可以独立发布。

放弃原因：实例安全、身份、文件访问和变更一致性是 ECL 的基础责任，不能因 Addition 缺失或损坏而失效；这也会迫使原生页面依赖可选组件。

### 方案 C：建立原生 Instance Engine

选择原因：把跨功能基础设施统一留在 Core，同时允许领域分析器和高级处理器通过受控接口扩展，符合 ADR 0032 的架构边界。

## 后果

### 正面影响

- 实例身份、资源事实和文件操作有统一来源；
- 并发写入可以在统一入口协调，而不是依赖 UI 自觉避免冲突；
- 新功能可复用扫描、依赖、事务和恢复能力；
- Addition 缺失不会破坏实例基础管理；
- 能逐步形成可追溯的实例生命周期模型。

### 代价与风险

- Core 的领域模型和 API 设计复杂度上升；
- Engine 需要处理文件系统权限、链接、外部修改、磁盘离线和进程占用等现实问题；
- 统一服务可能成为性能瓶颈，必须提供异步、取消、限流和增量能力；
- 需要避免把所有领域逻辑集中成不可维护的巨型模块；
- 旧功能迁移必须分阶段进行，不能一次性替换现有启动与管理流程。

## 验收标准

1. Instance Engine 位于 ECL 原生 Core，不要求安装 Addition 才能提供基础实例能力。
2. 原生 UI 与 Addition 均通过受控接口访问 Engine，不存在绕过 Engine 的实例写入路径。
3. Identity、File Access、Inventory、Dependency、Transaction、Snapshot/Recovery 的职责和 API 边界有独立定义。
4. Explorer 与实例工作台共享同一 Inventory，不维护冲突的资源数量和状态。
5. 写入请求经过实例级协调，能够识别并拒绝冲突操作。
6. 扫描结果保留证据、时间、规则版本和未知状态；扫描失败不阻断普通启动。
7. Engine 的缓存可重建，实例原始内容仍是资源事实的权威来源。
8. 没有 Addition 时，普通启动、基础实例浏览和 Engine 安全边界仍可用。
9. 各阶段按本 ADR 的优先级推进，并在后续 ADR/实施记录中提供可复核状态。
