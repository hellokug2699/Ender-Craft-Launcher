# ADR 0063: ECL Player Workspace Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: ECL Player Workspace 的产品定位、独立 Addition 边界、玩家数据自主权、通用组织能力、导入导出与跨 Addition 集成边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md), [ADR 0053](0053-addition-capability-permission-and-user-consent.md), [ADR 0054](0054-addition-registry-and-manifest-governance.md), [ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md), [ADR 0061](0061-ecl-ai-conversation-and-capability-architecture.md), [ADR 0062](0062-ecl-ai-agent-runtime-and-orchestration-architecture.md)

## 背景

ECL 已经拥有面向 Minecraft 机制、实例、世界、资源和联机等领域的工具与 Additions。玩家在使用这些能力时，也会产生大量不属于任何单一游戏功能的数据和事务：项目计划、任务清单、目标、材料表格、笔记、参考资料、文件附件以及长期进度记录。

如果将这些能力限定为 Minecraft 专用工具，就会人为限制玩家可以记录的内容、组织方式和用途。玩家可能希望用同一套工作空间管理其他游戏、学习计划、日常事务或完全无关的个人项目。ECL 不应判断这些内容是否与 Minecraft 有关，也不应要求玩家按预设的游戏目录组织自己的资料。

另一方面，将表格、任务、笔记等全部视为彼此无关的小工具，会削弱它们之间的组合价值。例如，项目目标可以关联任务，任务可以关联表格中的材料需求，项目还可以关联笔记、附件和外部资料。因此需要一个具有统一产品定位、又允许内部能力逐步扩展的独立 Addition。

## 决策

### 1. 注册独立 Feature Addition

建立 **ECL Player Workspace**，Addition ID 为 `ecl.player-workspace`，类型为 `Feature`。

它是面向玩家的通用个人工作空间，提供资料组织、项目管理和个人事务整理能力。它不是 Minecraft 专用工具，也不是 ECL 内部开发者工作区。

Player Workspace 可以作为一个完整产品组合交付。表格、目标与任务、笔记、项目组织、导入导出等属于其内部能力方向；本 ADR 不要求将这些能力分别拆成独立 Addition，也不预设未来永远只能有一个内部模块。

### 2. 用途不设限，Minecraft 只是重要使用场景

玩家可以使用 Player Workspace 管理任何自己希望整理的内容，包括但不限于：

- Minecraft 建筑计划、投影材料清单、整合包进度和多人项目。
- 其他游戏的攻略、收集目标、进度与项目资料。
- 学习计划、日常待办、个人项目和其他非游戏事务。
- 玩家自行定义的表格、笔记、资料集合和组织结构。

ECL 不得以内容与 Minecraft 无关为由拒绝创建、保存、导入、导出或组织资料。不得强制玩家将资料绑定到 Minecraft 实例、游戏、存档、服务器或其他 ECL 功能。

Minecraft 专用格式适配和 ECL 功能联动属于增强能力，不构成工作空间的用途限制或使用前提。

### 3. 玩家自主决定资料组织方式

Player Workspace 应支持玩家自主创建和组织内容。目标方向包括：

- 自定义项目、集合、分组及其层级关系。
- 通用表格与玩家自定义字段。
- 目标、任务、子任务及其关联。
- 笔记、说明、参考资料和附件。
- 模板以及可复用的组织结构。

以上是产品能力方向，不规定具体 UI、目录树、数据结构、字段类型、任务状态机或交互方式。不得强制采用固定的“游戏—实例—存档—项目”层级，也不得要求所有内容必须属于某个项目。

### 4. 表格与结构化资料

Player Workspace 应提供适合日常整理的结构化表格能力，支持玩家管理自定义列、分类、筛选和汇总等常见整理需求。

通用文本表格格式是数据交换的基础能力，至少将 CSV 与 TSV 纳入目标支持范围。导入和导出应尽可能保留可表达的数据；对格式本身无法表达的结构或元数据，应明确告知用户，不得静默丢弃或伪装成无损往返。

投影材料清单等游戏专用数据可通过格式适配能力接入。格式适配应保持可扩展，不将产品绑定到单一投影模组、单一导出版本或单一厂商格式。未知或未支持的格式不得仅因无法识别就被判定为损坏；应提供清晰的格式不支持反馈，并在适用时允许用户使用通用导入方式。

导入属于数据写入操作。导入前应让用户了解目标位置、数据范围及可能的覆盖、合并或重复项影响；不得在未经确认的情况下破坏现有资料。导入内容应视为不可信输入，解析过程需要遵守资源访问、安全处理和合理资源预算要求。导出时应考虑通用表格软件对公式内容的解释风险，避免将不可信文本意外变成可执行公式。

### 5. 目标、任务与项目之间的关联

Player Workspace 应允许玩家以适合自己的方式管理目标和任务。目标可以表达希望达成的结果，任务可以表达具体行动；任务可按需形成层级，并与项目、表格、笔记或附件建立关联。

例如，建筑项目可以关联一个目标、多个阶段任务和材料表格；材料表格中的收集进度也可以为相关任务提供参考。此类联动属于可选的组合能力，不应要求所有任务必须有目标，也不应要求所有目标必须拆分为任务。

由关联数据推导出的进度或完成状态，应保持来源可解释。是否自动更新、自动完成或仅提供建议，应由明确的产品行为和玩家控制决定，不得因导入数据或跨 Addition 事件而悄悄改变玩家的任务状态。

### 6. 玩家数据自主权与可迁移性

Player Workspace 中由玩家创建或导入的资料属于玩家数据。架构应遵循以下原则：

- 默认本地优先，不要求云服务才能创建、编辑、查询或导出基本资料。
- 不因使用 Player Workspace 就自动上传内容、附件、项目资料或使用行为。
- 不将云同步、远程协作或 ECL 账号绑定设为基本使用前提；未来如提供，必须作为独立且明确授权的能力。
- 提供合理的数据导出和迁移路径，避免玩家被 ECL 私有格式锁定。
- 对无法由通用格式完整表达的内容，提供可说明损失边界的原生数据备份或迁移方式。
- 卸载、禁用或更新 Addition 不得擅自删除玩家资料；资料生命周期应与 Addition 二进制/包体生命周期分离。
- 删除资料、覆盖导入或其他可能造成不可逆数据损失的操作，应遵循宿主已有的授权、确认、事务和恢复边界。

玩家拥有数据不代表其他 Addition、模型或外部服务自动拥有读取权限。数据访问仍须经过 Core 的资源中介和权限控制。

### 7. 附件、外部资料与实例关联

玩家可以按需将文件、图片、外部链接或 ECL 实例等关联到工作空间资料。关联不应被解释为自动上传、自动复制、自动解析或自动授予其他组件访问权限。

对于外部文件和实例资源，应区分引用与复制等不同语义，并考虑原始资源移动、删除、权限变化或实例不可用后的失效情况。外部链接默认作为玩家提供的引用，不应仅因保存链接就自动访问目标站点。

具体附件存储方式、引用模型和失效提示属于后续设计与实现评审范围。

### 8. 与 ECL 其他能力集成

Player Workspace 可以与 ECL 的其他原生能力和 Additions 协作，例如导入 Schematic Preview 或投影工具产生的材料数据、关联 Multiplayer 项目、由 ECL AI 辅助整理资料或生成任务。

这些集成必须遵守以下边界：

- Player Workspace 不依赖任何 Minecraft 专用 Addition 才能完成基本工作空间功能。
- 其他 Addition 不得直接访问其内部对象、私有存储或绕过 Core 读取玩家资料。
- 跨 Addition 协作通过宿主受控的能力、资源访问和授权机制进行。
- AI 对资料的读取、生成、修改或远程传输必须分别遵循适用的权限与用户授权；允许访问某项资料不等于允许将其发送给远程模型。
- 任何集成都不得将工作空间变成通用的隐式数据收集入口。

本 ADR 不要求 ECL AI、Agent Runtime、Multiplayer、Schematic Preview 或其他 Addition 成为 Player Workspace 的必需依赖。

### 9. 与 Bundle 和 Addition 的关系

面向玩家的 **Player Workspace** 是一个完整产品组合。其内部可以包含多个相互协作的能力模块，但对玩家应保持连贯、可理解的工作空间体验。

本 ADR 注册的是一个独立 Addition，而不是为表格、任务、笔记分别建立多个必须单独安装的 Addition。未来若出现具有独立生命周期、独立用户价值且确有独立分发必要的能力，再按 Addition 治理规则单独评估。

“Bundle”在本 ADR 中描述面向玩家的产品组合概念，不代表已经确定新的通用 Bundle Manifest、依赖解析或安装器机制。

### 10. 不在本 ADR 范围内

本 ADR 不规定：

- 页面布局、导航、具体交互、视觉设计和 UI 组件。
- 数据库、文件目录、序列化格式、内部对象模型或具体存储引擎。
- 表格公式语言、复杂数据分析、宏、脚本或电子表格软件的完整兼容性。
- 完整的文档编辑器、知识图谱、日历、邮件、即时通讯或多人协作平台。
- 云同步、账号体系、远程托管和商业化方案。
- 对任意第三方投影格式的首发兼容承诺。
- AI 自动操作的具体流程、Agent 计划格式或工具协议。
- 各项功能的首发范围、开发优先级和交付日期。

上述方向如需进一步明确，应通过产品规划、Feature Spec 或后续 ADR 处理，不应被解释为本 ADR 已经承诺交付。

## 备选方案

### 方案一：建设 Minecraft 专用项目管理工具

优点是初期场景明确，可以围绕投影材料、整合包任务和游戏实例做深度集成。

缺点是会限制玩家记录和组织其他事务的自由；随着能力增长，还可能出现与通用笔记、表格和任务管理重复建设的问题。

不采用。Minecraft 应是重要的默认场景，而不是产品的用途边界。

### 方案二：将表格、任务、笔记分别注册为独立 Addition

优点是各项能力可以独立发布和更新。

缺点是玩家需要分别安装和管理多个扩展，项目、任务、表格之间容易形成割裂的体验，也会增加跨 Addition 协作和依赖治理成本。

当前不采用。先以一个完整的 Player Workspace Addition 交付统一体验；未来只有在独立生命周期和分发价值充分明确时才重新评估拆分。

### 方案三：只提供若干互不关联的轻量工具

优点是实现边界简单，初期成本较低。

缺点是无法自然表达项目、目标、任务、表格和资料之间的关系，容易形成多个孤立工具。

不采用。统一工作空间应允许不同资料类型按需关联，但不强迫玩家采用复杂项目管理模型。

## 后果

### 正面影响

- 玩家可以用同一工作空间管理游戏内外的事务，不受 Minecraft 主题限制。
- 表格、任务、目标、笔记和项目资料能够形成组合价值。
- 通用导入导出和数据迁移降低长期锁定风险。
- Minecraft 专用格式与其他 ECL Addition 可以作为增强能力接入，而不污染通用核心定位。
- 以单一 Addition 提供连贯体验，避免初期过度拆分。

### 成本与风险

- 通用数据组织能力比单一游戏工具更复杂，需要避免过早建设成大型办公套件。
- 导入格式差异、字段映射、重复数据、无损导出和不可信文件解析会带来持续维护成本。
- 玩家数据具有长期价值，卸载、升级、迁移、损坏恢复和备份语义必须谨慎处理。
- 跨 Addition 集成可能扩大数据暴露面，需要严格遵守 Core 权限和数据最小化原则。
- 通用定位意味着不能依赖固定的 Minecraft 数据模型，需要在自由度与易用性之间持续权衡。

### 待验证事项

- CSV/TSV 与原生数据之间的字段、类型和元数据保留策略。
- 投影材料清单等候选格式的实际样本、版本差异、许可和适配成本。
- 玩家数据在 Addition 卸载、升级、迁移和恢复过程中的宿主生命周期支持。
- 表格、目标、任务、笔记和附件之间的关联需求及其实际复杂度。
- 大型表格、附件和批量导入场景下的性能与资源预算。

## 验收标准

以下为未来实现的架构验收方向，不代表当前已经实现：

1. Player Workspace 作为独立 Feature Addition 登记，稳定 ID 为 `ecl.player-workspace`，不声明 Minecraft 专用 Addition 为必需依赖。
2. 不关联 Minecraft 实例时，玩家仍能创建、编辑、组织、保存和导出工作空间资料。
3. 玩家可以管理自定义表格、目标、任务、笔记和项目资料；不强制固定的游戏目录或项目层级。
4. 通用 CSV/TSV 导入导出能够明确表达支持范围；无法无损表达的数据不会被静默丢弃。
5. 未知或不支持的专用格式不会仅因无法识别而被判定为损坏；导入写入具备清晰的影响说明和数据保护措施。
6. Addition 卸载、禁用或更新不会擅自删除玩家工作空间资料。
7. 基本资料管理不依赖云服务；远程传输和跨 Addition 数据访问必须经过适用的授权机制。
8. 关联实例、附件、外部资料或其他 Addition 不会绕过 Core 资源访问边界。
9. ECL AI 等能力缺失时，Player Workspace 的基本功能仍可独立使用。
10. 注册表、Addition README、Manifest 与本 ADR 对 Addition ID、名称、类型和状态的描述保持一致。
