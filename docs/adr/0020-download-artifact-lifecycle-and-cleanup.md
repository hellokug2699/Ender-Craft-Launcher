# ADR 0020：下载临时产物生命周期与失败清理

- Status: Accepted
- Date: 2026-11-02
- Scope: ECL 下载服务、下载缓存、断点续传与临时文件生命周期

## 背景

ECL 的下载任务可能涉及 Minecraft 客户端、Java Runtime、模组、整合包、资源包以及更新包等大量文件。下载过程中可能发生网络中断、HTTP 错误、进程退出、用户取消、磁盘错误或内容校验失败。

当前下载实现已经使用 `.part` 临时文件支持断点续传，并在下载完成后进行大小或 Hash 校验；校验成功后才将临时文件移动为最终文件。该机制能够避免将不完整内容直接暴露为最终文件，但如果没有明确的临时产物生命周期管理，长期失败或中断的下载仍可能在磁盘中持续堆积。

同时，`.part` 不能简单地在每次失败后立即删除：对于大型文件，保留可信的部分内容可以在下一次任务中继续下载，显著降低重复流量和等待时间。因此需要同时解决“失败下载可复用”和“无主临时文件最终必须回收”两个目标。

## 决策

ECL 采用**可恢复失败下载 + 有界生命周期清理**的下载临时产物策略。

### 1. 最终文件只能由已验证的临时文件产生

下载内容首先写入临时文件，例如 `<target>.part`。只有在满足预期大小、Hash 等完整性要求后，才能将临时文件原子移动为最终目标文件。

未完成、未验证或校验失败的内容不得被视为可用的最终文件。

### 2. 短期失败允许保留并复用

网络中断、可恢复的 HTTP 错误、进程异常退出或用户暂时取消等情况产生的 `.part` 文件，可以保留，以便后续任务进行断点续传。

复用 `.part` 前必须确认其与当前下载目标属于同一内容身份。至少应比较可获得的：

- 目标路径或逻辑资源身份；
- 预期文件大小；
- 预期 Hash 与 Hash 算法；
- 必要时的下载来源或来源集合版本。

关键身份不匹配时不得继续追加旧 `.part`，必须删除并重新开始。

### 3. 损坏或无效的临时文件必须删除

以下情况不得继续复用原 `.part`：

- `.part` 大于预期文件大小；
- Range 恢复后无法通过完整性校验；
- 已知内容 Hash 不匹配；
- 临时文件元数据与当前目标身份不一致；
- 无法可靠判断该临时文件属于当前下载目标。

删除失败本身不得阻塞整个下载流程，但应记录诊断信息，并在后续清理周期再次尝试。

### 4. 临时产物必须具有最终生命周期上限

ECL 必须提供临时下载产物的回收机制，使没有持续下载任务引用的 `.part` 最终能够被清理。

清理至少应覆盖：

- 长时间未使用的 `.part`；
- 不再对应任何当前资源或任务的孤儿 `.part`；
- 已知目标内容发生变化后留下的旧 `.part`；
- 下载任务取消或失败后超过保留期限的临时文件。

具体保留时长属于实现参数，可根据实际下载规模和用户体验调整，不在本 ADR 中固定具体数值。

### 5. 清理不得误删活动下载

清理器必须能够区分活动下载与孤儿临时产物。正在下载、暂停等待恢复或刚刚失败且仍在重试策略生命周期内的 `.part` 不得被后台清理任务删除。

必要时应通过任务状态、锁、元数据或其他可靠的活动标记完成保护，而不能仅依据文件修改时间进行粗暴删除。

### 6. 失败重试与临时文件生命周期分离

单次下载的短期重试次数与 `.part` 的长期保留期限是两个独立概念：

- 重试解决当前任务的瞬时网络问题；
- 临时文件保留解决跨任务的断点恢复；
- 清理解决长期无人使用产物的磁盘占用。

三者不得通过无限重试或无限保留其中任一项来代替其他机制。

### 7. 目标文件优先复用

开始下载前应先检查目标文件是否已经满足预期大小和 Hash。已验证的目标文件直接复用，不应重新下载。

这与 `.part` 复用属于不同层级：最终文件是稳定缓存，`.part` 是可恢复的临时缓存。

### 8. 用户取消与程序异常退出必须保持可恢复性

用户主动取消下载时，默认允许保留可验证的 `.part`，以便用户稍后继续；不得因为一次取消就无条件删除大型部分下载内容。

程序异常退出后，下次启动应能够识别并恢复合法的 `.part`，同时清理长期无主的临时产物。

### 9. 清理是容量保护机制，不是下载成功条件

临时文件清理失败不应使一个已经成功验证的下载失败；反之，清理机制也不得通过删除尚未验证的内容来伪造下载成功。

磁盘空间不足属于独立错误，应能够被下载任务识别并报告，而不能依赖“恰好清理了一些文件”来作为正常行为。

## 后果

正面影响：

- 大文件下载失败后可以继续利用已有数据，减少重复流量；
- 最终目录不会出现半成品文件冒充完整资源；
- 长期失败、取消和崩溃留下的临时文件不会无限堆积；
- 内容版本变化时不会错误复用旧版本的下载残片；
- 下载缓存和临时产物具有清晰、可测试的生命周期边界。

代价：

- 需要维护 `.part` 的身份信息或其他可靠的复用判断机制；
- 需要实现后台或启动时的清理流程；
- 需要处理文件被占用、删除失败以及清理过程中的并发竞态；
- 需要为断点续传、清理和异常恢复增加测试覆盖。

## 验收标准

1. 下载成功后不存在对应的 `.part` 残留。
2. 下载中断后，下一次相同内容的下载能够安全复用有效 `.part`。
3. `.part` 与当前目标的大小、Hash 或身份不匹配时不会被错误续传。
4. 校验失败或明显损坏的 `.part` 会被删除或标记为不可复用。
5. 用户取消下载后，符合恢复条件的 `.part` 可以保留并在后续任务中恢复。
6. 程序异常退出后重新启动，活动任务之外的合法 `.part` 能够被识别并处理。
7. 超过保留期限且不再被任何任务引用的 `.part` 会被自动清理。
8. 清理过程不会删除活动下载、暂停等待恢复的下载或正在进行验证的临时文件。
9. 大量连续失败下载不会造成临时文件无限增长；磁盘占用存在明确的生命周期上限。
10. 清理失败、磁盘不足、文件锁等异常能够进入诊断记录，而不会破坏已经成功完成的下载。
11. 至少覆盖网络中断、进程异常退出、用户取消、Hash 不匹配、目标版本变化、清理竞态和删除失败等故障注入场景。
