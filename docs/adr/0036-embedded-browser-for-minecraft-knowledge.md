# ADR 0036: Embedded Browser for Minecraft Knowledge Access

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-02
- Scope: ECL 内置浏览器、Minecraft 与模组资料访问、第三方网页呈现及浏览器安全边界
- Related: [ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0033：本地 Minecraft 全面诊断与知识引擎](0033-local-minecraft-diagnostic-and-knowledge-engine.md)、[ADR 0035：可选离线 Minecraft 知识库](0035-offline-minecraft-knowledge-library.md)
- Supersedes: [ADR 0035：可选离线 Minecraft 知识库](0035-offline-minecraft-knowledge-library.md)（仅取代以离线知识包作为主要知识访问方式的方向；授权内容、来源追踪和小型离线补充包仍可沿用）

## 背景

ECL 希望成为玩家查阅 Minecraft 与模组资料的统一入口。此前 ADR 0035 提出通过可选离线知识包提供百科式体验，但进一步讨论发现，真正困难的部分并非阅读器技术，而是合法、完整、准确且持续更新地获取大量第三方内容。

原版 Minecraft 和模组生态的资料分散在 Wiki、模组项目页面、作者文档、社区站点和代码仓库中。不同来源具有不同的内容许可、访问规则和更新节奏。若 ECL 试图全量抓取并离线分发，会带来较大的包体积、持续同步和审核负担，以及无法统一解决的再分发授权问题。即使完成一次性收录，也无法保证内容长期准确。

相比之下，内置浏览器可以让用户通过自己的网络直接访问资料来源，由原始网站负责托管和更新内容。ECL 负责提供统一入口、浏览体验和来源标识，而不把第三方网页复制成 ECL 自己的知识内容。

本 ADR 选择将内置浏览器作为知识访问的主要方式。它不意味着 ECL 能保证第三方页面准确，也不意味着使用用户自己的网络就自动免除网站条款、版权或安全责任。

## 决策

### 1. ECL 提供原生知识入口和内置浏览器容器

ECL 提供原生知识中心入口，允许用户搜索或打开 Minecraft、模组及相关技术资料。页面内容通过内置浏览器组件呈现，网页由其原始站点直接提供。

浏览器至少应支持地址导航、页面标题、后退、前进、刷新、停止加载、加载状态、失败提示、复制链接和通过系统浏览器打开当前页面，并清晰展示当前页面的来源域名。

首期不要求实现通用桌面浏览器的全部能力，也不承诺替代用户的主浏览器。功能范围应围绕 Minecraft 知识访问，避免无限扩展成完整浏览器产品。

### 2. 网页内容由原站直接提供，ECL 不建立内容代理或镜像

内置浏览器应通过用户设备的正常网络连接访问目标站点。ECL 不应为了展示第三方网页而默认建立服务器端抓取、代理、镜像或内容重发布服务。

ECL 不主动绕过登录、付费墙、访问控制、反自动化机制、地理限制或站点明确设置的嵌入限制。若站点拒绝在内嵌环境中显示，ECL 应提供在系统浏览器中打开的明确选项，而不是尝试规避站点限制。

“使用用户自己的网络”只说明网络请求由用户设备发起，不代表网站必须允许内嵌展示，也不自动解决版权、服务条款、Cookie、隐私或安全问题。

### 3. 第三方内容与 ECL 自有内容必须明确区分

浏览器页面应让用户能够识别当前内容由第三方站点提供。至少应提供当前页面标题、可检查的 URL、来源域名，以及复制地址和打开原始页面的操作。页面更新时间或版本信息只有在来源能够提供可靠信息时才显示。

界面应适当提示“第三方内容，由原始来源维护”。ECL 不得把第三方页面包装成 ECL 官方撰写、审核或背书的文章。导航分类、搜索建议和站点快捷入口也不应暗示内容已由 ECL 验证。

### 4. 不对第三方内容的正确性作无依据保证

第三方页面可能过期、错误、缺少版本条件或与当前 Minecraft / Mod 版本不匹配。ECL 不能仅因为页面可以打开，就将其内容标记为准确、官方或已验证。

当 ECL 自己提供摘要、版本提示或结构化说明时，必须区分原始网页内容、ECL 自己维护且有来源记录的资料、自动生成的摘要，以及用户提交但尚未审核的反馈。

自动摘要不能覆盖或替代原始页面，也不能在没有可靠证据时推断模组支持版本、配方、兼容性或机制。若未来增加 AI 摘要，应显示其生成性质、引用来源和生成时间，并提供回到原文的入口。

### 5. 提供来源选择，但不承诺全网搜索或全量覆盖

知识中心可以提供常用 Minecraft Wiki、模组资料站、模组作者文档、项目主页和技术文档的快捷入口。可支持用户输入 URL 或搜索关键词；搜索功能可以使用来源自身提供的搜索页面，或经过评估的公开搜索入口。

ECL 不应声称拥有全量模组目录，也不应把某个资料站当作唯一权威来源。同一模组存在多个来源时，可以并列提供项目主页、作者文档、社区 Wiki 等入口，并清晰显示来源差异。

站点列表和默认推荐属于可维护配置，应允许后续调整或移除，不应将某个第三方网站永久硬编码为唯一入口。

### 6. 浏览器安全边界由嵌入式浏览器能力和 ECL 导航策略共同保障

网页通过用户自己的网络加载，但网页内容仍属于不受 ECL 信任的外部输入。内置浏览器必须保留 WebView 运行时提供的沙箱和安全机制，不得为方便显示网页而全局关闭 Web 安全功能。

至少应评估和控制：

- 仅允许预期的网络协议；对危险或非预期协议的导航进行拦截或交由用户确认；
- 本地文件访问、任意脚本桥接和本机资源访问默认关闭；
- 网页 JavaScript 按正常网页需要启用，但不得向网页暴露任意 ECL/.NET 对象或本地文件系统能力；
- 新窗口、弹窗、下载和外部协议调用必须有明确处理策略；
- 摄像头、麦克风、地理位置、通知、剪贴板等权限不得静默授予；
- 不允许网页直接调用 ECL 的启动游戏、修改实例、读写配置或执行管理操作；
- 导航、下载和权限行为应有可审查的边界与日志，但不得记录不必要的浏览内容或敏感数据。

ECL 不需要自行实现网络过滤器或替代操作系统安全机制；应优先使用 WebView2 等成熟嵌入式浏览器运行时的安全默认值，并通过最小权限的宿主集成控制 ECL 自身暴露面。

### 7. 浏览器运行时和用户配置应独立管理

若采用 WebView2，应明确 Evergreen Runtime 或固定版本 Runtime 的部署策略、最低版本、更新策略和缺失时的提示。不能假定所有用户设备都已安装可用运行时。

浏览器用户数据目录、Cookie、缓存和会话数据应有明确生命周期和位置。首期应优先使用独立于 ECL 主程序的浏览器数据目录，避免与系统浏览器或其他应用共享登录状态。是否提供持久登录、清理缓存、无痕会话等能力由后续 Feature Spec 确定。

浏览器运行时缺失、初始化失败、网页崩溃或站点不可访问时，只影响知识浏览能力，不得阻塞 ECL 启动、实例管理和 Minecraft 启动。

### 8. 第三方网站的服务条款和嵌入策略必须被尊重

内嵌浏览不等于拥有该网站内容，也不意味着网站有义务支持 WebView。ECL 应尊重网站的访问规则、内容许可、嵌入限制和合理的反滥用措施。

如果网站明确禁止内嵌、要求使用特定客户端或其身份验证流程不兼容，ECL 应提供外部浏览器回退。不得伪造来源、移除归属信息、隐藏站点品牌或通过代理改变站点对用户的正常呈现。

### 9. 用户反馈可以帮助发现错误，但不能自动成为事实

ECL 可以允许用户报告页面过期、内容错误、链接失效或来源问题。反馈应关联页面 URL、来源域名和用户主动填写的说明。

用户反馈默认保存在本地或由用户主动选择提交；若未来提交至远端，应在提交前预览信息并取得明确确认。未经审核的反馈不得自动修改 ECL 自有知识库、诊断规则或站点可信等级。

对于第三方页面的错误，ECL 应优先引导用户向原始内容维护者反馈。ECL 可以记录用户反馈状态，但不能假装自己有权修改原站内容。

### 10. 保留小规模、明确授权的离线知识作为补充，而非主要交付方式

本 ADR 不禁止未来提供小型离线知识包。例如 ECL 自己撰写的帮助文档、经过授权的术语表、兼容性说明或特定诊断知识仍可离线分发。

这些内容应遵循 ADR 0035 中仍然有效的来源追踪、许可记录、版本管理和准确性要求。但不再以收录整个 Minecraft Wiki 或模组生态作为知识中心的目标，也不要求浏览器功能依赖离线知识包。

## 备选方案

### 方案 A：全量离线知识库

不作为主要方向。它需要长期解决内容授权、采集、转换、版本同步、包体积和人工审核问题。模组生态的规模与变化速度使其难以由 ECL 单独承担。小范围授权内容仍可作为补充。

### 方案 B：仅提供系统浏览器外链

作为回退方式保留，但不作为唯一体验。它实现简单且边界清晰，但用户需要离开 ECL，无法获得统一的导航、页面状态和知识入口体验。

### 方案 C：内置浏览器直接访问原始站点

采用。它让内容由来源方托管和维护，减少 ECL 的内容复制、同步和存储负担，并覆盖分散的原版与模组资料来源。其代价是依赖网络和第三方站点可用性，且 ECL 无法保证页面内容质量。

### 方案 D：ECL 服务器抓取并代理第三方网页

不采用。它会使 ECL 承担带宽、缓存、版权、隐私、内容责任和网站访问规则等额外负担，也会把用户原本直接访问网站的行为转变为 ECL 代为获取和转发内容。

## 后果

### 正面影响

- 不需要将大量第三方文章、图片和模组资料打包进 ECL。
- 内容更新由原始网站负责，减少 ECL 的同步和内容审核负担。
- 能访问多个分散的模组资料来源，不受单一知识库覆盖范围限制。
- 用户可以在 ECL 内完成搜索入口、页面浏览和来源切换。
- ECL 不需要建立内容代理服务器或承担大规模网页托管成本。
- 小型、明确授权的离线资料仍可独立存在，不被浏览器方案排斥。

### 代价与限制

- 浏览器访问依赖网络、目标站点可用性及其对内嵌浏览器的兼容程度。
- 某些站点可能拒绝 WebView、要求登录、限制 Cookie 或使用不兼容的验证流程。
- ECL 无法保证第三方文章正确、及时或适用于用户当前的游戏版本。
- WebView2 Runtime 的部署、更新、兼容性和用户数据管理会增加客户端维护工作。
- 内嵌浏览器引入网页内容攻击面，必须正确限制本地能力、权限和外部协议。
- 不同网站的页面布局、移动适配、广告和弹窗体验不一致，ECL 无法完全控制。
- 用户可能误以为内嵌页面是 ECL 官方内容，需要持续强化来源标识和内容责任边界。
- 内置浏览器仍然不是完整浏览器，复杂登录、下载或特殊网站可能需要回退到系统浏览器。

## 实施顺序建议

1. 检查当前 WPF/.NET 技术栈与 WebView2 Runtime 的兼容性、部署方式和最低系统要求。
2. 制作最小 WebView2 原型，验证常见 Wiki、mcmod.cn、Modrinth 项目页和 GitHub 文档的显示、导航与登录表现。
3. 明确浏览器宿主安全策略：协议、弹窗、下载、权限、文件访问、外部链接和脚本桥接。
4. 定义浏览器用户数据目录、Cookie 隔离、缓存清理和运行时更新策略。
5. 实现原生知识中心入口、地址/搜索输入、导航控件、来源域名和加载失败提示。
6. 建立可配置的常用资料来源列表，并为不支持内嵌的站点提供系统浏览器回退。
7. 增加第三方内容标识、页面错误反馈和隐私提示。
8. 只有在来源和事实验证机制明确后，才评估 ECL 自有摘要、结构化知识或 AI 辅助解释。

## 验收标准

- 用户可以从 ECL 原生知识中心打开常见 Minecraft 与模组资料页面。
- 页面内容由目标站点直接提供；ECL 不需要自建网页代理或镜像服务。
- 用户可以识别当前页面 URL、来源域名，并可复制链接或在系统浏览器打开。
- 对拒绝内嵌或无法正常工作的站点，ECL 能够明确提示并提供外部浏览器回退。
- WebView2 Runtime 缺失或初始化失败时，ECL 能提示处理方式，且不影响普通启动和 Minecraft 启动。
- 网页不能通过脚本桥接任意访问 ECL/.NET 对象、用户文件或启动器管理能力。
- 文件、本地资源、危险协议、弹窗、下载和权限请求具有明确策略，不会静默授予高权限。
- 浏览器不会将第三方网页内容标记为 ECL 官方撰写或已验证知识。
- 未经验证的页面内容或用户反馈不会自动写入诊断规则或 ECL 自有知识库。
- ECL 不绕过站点访问控制、嵌入限制或反滥用措施。
- 浏览器运行失败、网页崩溃或网络断开不会阻塞 ECL 的其他功能。
- 浏览器默认不向 ECL 自有服务器上传浏览历史、完整 URL、Cookie 或页面内容。
