# ADR 0033：本地 Minecraft 全面诊断与知识引擎

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-02
- Scope: Minecraft 日志、崩溃报告、运行环境、模组关系、故障模式与本地诊断知识库

## 背景

ECL 已经具备按进程管理游戏日志和诊断证据的基础能力，但传统的 Minecraft 日志查看方式主要解决“看到了什么”，不能稳定回答“为什么发生”和“下一步应该做什么”。现有的 mclo.gs 类服务主要擅长日志格式化、分享和阅读；ECL 更适合在本地结合实例环境、Java、Minecraft、Loader、模组关系和历史诊断记录进行全面分析。

该能力不应依赖 ECL 自建服务器，也不应默认上传用户日志、世界数据、Seed、服务器地址或其他诊断输入。与此同时，诊断规则和知识会持续增长，仅随启动器主程序发布会造成下载体积和发布耦合。因此诊断能力应与 ADR 0032 的 Additions 体系结合：ECL 原生提供分析中心页面和用户流程，诊断引擎及可持续更新的知识库按需安装。

## 决策

### 1. 定位为本地全面诊断，而不是日志转发服务

ECL 的诊断中心以本地分析为核心，不复制 mclo.gs 的在线日志托管和分享服务模型。诊断输入默认留在用户设备上。

分析对象至少包括：

- `latest.log`、历史游戏日志和 Crash Report；
- ECL 启动与下载阶段产生的相关诊断证据；
- Minecraft、Loader、Java 和操作系统运行环境；
- 实例中的模组、资源包及可读取的元数据；
- 模组依赖、冲突和版本兼容关系；
- Mixin、Class Loading、JVM、渲染和常见运行时故障模式；
- 与世界、维度、区块相关的诊断事件（在相关数据可用时）。

诊断结果应尽量回答：发生了什么、最可能的根因是什么、证据在哪里、哪些因素只是相关而不是根因、如何处理，以及当前结论的置信程度。

### 2. 采用“证据 + 规则 + 知识 + 关系分析”的混合模型

诊断引擎不以单一关键词命中作为最终结论。分析流程原则上包括：

1. 解析日志和崩溃报告为结构化事件；
2. 识别运行环境与实例上下文；
3. 使用确定性规则识别已知故障模式；
4. 查询版本化诊断知识库；
5. 分析模组、Loader、Java 和其他组件之间的依赖与关联；
6. 汇总证据并生成诊断候选；
7. 对候选按证据强度和置信度排序；
8. 输出可解释的结论和建议。

结论必须区分至少三类：直接证据、高度疑似、无法确定。日志中最后出现的模组、最后一个异常类或最接近崩溃位置，不得仅凭位置自动认定为根因。

未来可以允许用户自愿调用外部 AI 帮助解释复杂结果，但 AI 输出不能覆盖确定性证据，也不能在没有证据时伪装为确定结论。外部 AI 不是诊断系统的必需依赖。

### 3. 诊断知识库作为 Data Addition 独立分发

诊断知识不直接全部编译进 ECL 主程序。知识库作为 Data Addition 独立版本化和更新，并由 ADR 0032 的 Additions 管理机制负责下载、校验、安装、更新和回滚。

知识库可以包含：

- Minecraft 版本及 Java 要求；
- Fabric、Forge、NeoForge、Quilt 等 Loader 元数据；
- Mod ID、版本、依赖和兼容范围；
- 已知故障模式与诊断规则；
- Mixin、Class Loading 和常见 JVM 故障特征；
- 图形、渲染和环境问题的已知模式；
- 经过审核的解决方案和案例关联；
- 数据来源、版本、更新时间、许可和验证状态。

知识库不应成为一张不可解释的“错误字符串到答案”表，而应采用可版本化、可追溯的结构化模型。每条规则或知识记录应尽可能说明适用条件、证据模式、结论、置信度、来源及失效条件。

### 4. 诊断引擎与知识库解耦

Feature Addition 与 Data Addition 分离。诊断引擎负责解析、规则执行、证据组织和报告生成；知识库负责可持续更新的领域数据和规则。

因此可以出现以下状态：

- 仅安装诊断引擎：提供基础日志和环境分析；
- 安装诊断引擎及完整知识库：提供完整的知识增强诊断；
- 知识库版本过旧：继续提供允许的基础能力，同时明确标记知识库版本和可能的覆盖不足；
- 缺少某类数据：只禁用依赖该数据的分析，不阻塞整个诊断中心。

诊断中心不得因为知识库缺失而伪装成“全面诊断已可用”。

### 5. 诊断结果必须可解释并保留证据链

每个重要诊断结论应尽可能关联：

- 结论及严重程度；
- 置信度；
- 证据来源；
- 日志文件与行号或结构化事件位置；
- 使用的规则或知识记录版本；
- 相关环境对象，例如 Java、Minecraft、Loader 或 Mod；
- 建议操作；
- 建议是否已经在当前环境验证；
- 分析时间与知识库版本。

诊断报告不得只输出一个“罪魁祸首”。应展示推理依据，使用户可以检查结论，也方便未来修复错误规则。

### 6. 支持实例级诊断历史，但默认本地保存

ECL 可以为实例保存诊断摘要和历史结果，以便比较不同时间的环境变化，例如 Java、Loader、Mod 更新前后的故障变化。

历史记录默认不上传、不用于遥测，也不写入 Minecraft 的 `servers.dat`。记录应允许用户清理，并尽量避免保存不必要的原始日志副本。若保存原始证据，必须明确生命周期和存储位置。

诊断历史应记录分析所使用的知识库版本和实例环境摘要，以避免未来用新规则误解旧结论。

### 7. 与世界诊断和 World Engine 联动，但保持领域边界

诊断中心可以消费 ADR 0030 和 ADR 0031 提供的世界、维度、区块诊断事件。例如发现特定 Chunk、Dimension 或世界数据异常时，可以在诊断报告中提供进入对应世界分析视图的入口。

诊断中心不应自己重新实现 Region/NBT/Chunk/Dimension 解析。世界数据由 Native World Engine 提供结构化结果；诊断中心负责把这些结果纳入故障证据和用户解释。

当维度身份或目标位置无法可靠确认时，诊断中心不得伪造确定的世界地图定位，也不得自动执行修复。

### 8. 本地优先，不把服务器作为诊断前提

诊断中心必须可以在没有 ECL 自有服务器的情况下工作。知识库和功能包可以通过 ADR 0032 的静态发布渠道获取，但分析本身在本地执行。

未来可以增加用户主动分享诊断报告的能力，但应是独立功能：上传前提供内容预览、敏感信息检测和脱敏选项，并由用户明确确认。在线分享不是诊断中心的核心依赖。

### 9. 隐私与脱敏是诊断功能的一等要求

Minecraft 日志可能包含 Windows 用户名、文件路径、服务器地址、玩家名称、局域网地址、Token 或其他敏感信息。ECL 默认不上传诊断输入，并在未来提供导出/分享功能时执行结构化脱敏，而不是简单依赖字符串替换。

诊断 UI 应明确告诉用户哪些数据被分析、哪些数据会被保存，以及在主动分享前哪些字段将被移除或保留。不能因为用户点击“分析”就隐式同意上传。

### 10. 知识库必须允许错误修复、撤回和来源追踪

知识记录可能错误、过时或只适用于特定版本。每条重要规则应能够被版本化、停用或撤回，并保留来源和修订记录。

知识库更新不能覆盖本地诊断历史中的原始结论语义；历史记录应保留当时使用的规则/知识版本。发现错误规则后，可以标记受影响的历史诊断需要重新分析，而不是静默修改过去的结果。

## 备选方案

### 方案 A：直接使用 mclo.gs 类在线日志服务

不采用。它依赖远程服务，并不能天然访问 ECL 的本地实例环境、Java、Mod 关系和世界数据，也与 ECL 本地优先和无自有服务器的约束不一致。

### 方案 B：把全部诊断规则和数据库编译进 ECL

不采用。会增加主程序体积和更新耦合，也不利于知识库独立修复和快速更新。

### 方案 C：完全依赖外部 AI 分析日志

不采用。AI 对复杂上下文有价值，但不能作为唯一事实来源；网络、隐私、成本、可解释性和错误结论都不适合作为 ECL 基础诊断能力的唯一依赖。

### 方案 D：本地诊断引擎 + 可独立更新的知识库

采用。它兼顾本地隐私、可解释性、离线能力和长期知识积累，并与 ADR 0032 的 Additions 体系直接兼容。

## 后果

### 正面影响

- 不需要 ECL 自建诊断服务器即可提供完整的本地分析能力。
- 诊断知识可以独立于启动器快速更新。
- 能把日志、运行环境、模组关系和世界诊断统一到一个分析模型中。
- 诊断结果有证据链，便于用户理解和规则维护。
- 普通用户不安装诊断扩展时，不承担大型知识库和分析引擎的下载与运行成本。
- 未来可以持续积累已验证故障模式，而无需不断修改 ECL 主程序。

### 代价与限制

- 需要维护结构化诊断知识模型、规则版本和来源质量。
- Minecraft、Loader 和 Mod 生态快速变化，知识库需要持续维护。
- 复杂故障可能无法仅靠确定性规则解决，系统必须允许明确表示“不确定”。
- 诊断数据库会形成新的软件供应链，需要遵守 ADR 0032 的签名、哈希、依赖和撤回机制。
- 本地分析无法保证覆盖所有第三方模组内部行为，尤其是动态生成或依赖运行时环境的功能。

## 实施顺序建议

1. 定义诊断事件模型、证据模型和诊断结果模型。
2. 复用 ADR 0015 的进程级日志会话与诊断证据，不重复建立日志采集链。
3. 实现日志、Crash Report 和环境信息的结构化解析器。
4. 定义知识库 schema、规则模型、来源与版本字段。
5. 建立第一批高确定性的 Java、Loader、依赖缺失、Mixin 和常见启动故障规则。
6. 实现诊断引擎与知识库的独立加载及版本兼容检查。
7. 接入 Mod 依赖/兼容关系分析。
8. 接入 ADR 0030/0031 的世界与维度诊断事件。
9. 增加实例级诊断历史与差异分析。
10. 最后再评估可选的外部 AI 解释和用户主动分享能力。

## 验收标准

- 在无 ECL 自有服务器的情况下可以完成基础日志、Crash Report 和环境诊断。
- 未安装诊断 Addition 时，诊断中心页面仍可显示并明确提示所需扩展，不影响普通游戏启动。
- 诊断引擎和知识库可以独立更新，并能拒绝不兼容的知识库版本。
- 重要诊断结论能够关联可定位的日志/事件证据，并显示规则或知识版本。
- 系统不会仅凭最后一个异常类、模组名称或日志末尾位置就确定根因。
- 诊断结果能够区分直接证据、高度疑似和无法确定。
- 知识库可以停用或撤回错误规则，并保留版本历史。
- 历史诊断能够识别当时使用的知识库和规则版本。
- 默认不上传日志、Crash Report、Seed、世界数据或其他诊断输入。
- 用户主动导出/分享前可以预览并执行脱敏。
- 世界、维度和区块诊断结果遵守 ADR 0030/0031 的身份与隔离规则。
- 诊断引擎异常、知识库损坏或远程目录不可用时，不会阻塞 ECL 普通启动和游戏启动。
