# ADR 0043：Minecraft 威胁防护与安全分析架构

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-03
- Scope: ECL 管理的 Minecraft 文件、实例、整合包及由 ECL 启动的 Minecraft/Java 进程的本地安全分析与启动前风险提示
- Related: [ADR 0012：整合包归档提取安全边界](0012-modpack-archive-extraction-boundary.md)、[ADR 0015：按进程隔离的游戏日志会话与诊断证据](0015-process-scoped-game-log-sessions-and-diagnostics.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0033：本地 Minecraft 全面诊断与知识引擎](0033-local-minecraft-diagnostic-and-knowledge-engine.md)、[ADR 0034：ECL 自身完整性与可恢复安装架构](0034-ecl-self-integrity-and-recovery.md)、[ADR 0042：实例文件管理器与崩溃报告工作流](0042-instance-file-explorer-and-crash-report-workflow.md)

## 背景

Minecraft 模组、资源包、Shader、整合包及其附带脚本均来自多样的第三方来源。它们可能包含异常归档结构、可疑脚本、已知恶意内容、伪装文件或其他风险。Minecraft 运行时也可能通过 JVM 参数、Java Agent、类加载行为及进程模块加载暴露值得关注的异常。

ECL 已经负责下载、导入、安装、管理和启动这些内容，因此适合在 ECL 管理边界内提供本地威胁分析。该能力不应扩展为通用 Windows 杀毒软件，也不应复制 Windows Defender 的职责。

安全分析还必须考虑性能。Minecraft 实例可能包含大量文件，整合包可能包含数百个模组；若默认持续遍历、读取和分析所有文件，会造成不必要的磁盘 IO、CPU 和 RAM 消耗。因此安全扫描必须支持用户主动发起，并将后台自动检查限制在明确的工作流节点和必要范围内。

启动流程需要额外的风险门控：玩家点击启动后，ECL 应在创建 Minecraft 游戏进程前执行必要检查。发现需要告知的风险时，先暂停本次启动并展示证据与可疑资源；玩家可以自行处理、接受风险继续启动，或取消本次启动。安全系统负责告知和记录，不替玩家永久剥夺启动选择权。

## 决策

### 1. 产品边界：仅保护 ECL 管理的 Minecraft 生态

本能力暂定名称为 **ECL Threat Protection**，由 ECL 原生安全中心提供入口和工作流。

负责范围包括：

- ECL 管理的 Minecraft 实例及其目录内容；
- ECL 下载、导入、安装或更新的模组、资源包、Shader、整合包及相关脚本；
- 用户明确选择交由 ECL 扫描的文件或目录；
- ECL 启动的 Minecraft / Java 进程，以及能够可靠关联到该实例的运行时证据；
- 与上述对象直接相关的文件来源、哈希、归档结构、启动参数和可观测行为。

明确不负责：

- 对整个 Windows 文件系统进行通用杀毒扫描；
- 监控与 ECL/Minecraft 无关的进程或软件；
- 系统级实时防护、驱动级监控、内核注入检测或系统启动项治理；
- 取代、关闭、绕过或与 Windows Defender 等专业安全软件竞争；
- 为实现上述范围外的能力索取管理员权限或提升进程权限。

Java 运行时仅在其被 ECL 选为 Minecraft 启动运行时，或明确属于某个受管理实例时纳入检查；不扫描或监控用户电脑上的全部 Java 安装和其他 Java 程序。

ECL 自身程序、更新包和安装目录的完整性仍由 ADR 0034 负责。Threat Protection 可以消费 ECL 完整性验证结果，但不重复实现启动器自检与恢复系统。

### 2. 扫描策略：手动扫描优先，自动检查按需触发

手动扫描是安全中心的核心能力，至少支持：

- 单个文件扫描；
- 用户选择的目录扫描；
- 指定实例扫描；
- 整合包安装前扫描；
- 对运行中的指定实例执行受支持的运行环境检查。

用户应能够选择扫描范围，例如仅扫描某实例的 `mods/`、`resourcepacks/`、`shaderpacks/` 或指定 JAR，而不必每次扫描整个实例。

自动检查仅用于必要的工作流节点：

- ECL 下载或导入新内容后，对新进入管理边界的对象执行轻量检查；
- 整合包安装前，对待提取内容执行归档结构与安全边界检查；
- 每次启动 Minecraft 前，执行本 ADR 第 6 节定义的启动前检查。

默认不启用全实例实时扫描，不持续轮询目录，不在后台无条件周期性扫描全部文件。定时扫描如未来提供，必须由用户主动启用并选择范围和时间。

### 3. 分阶段扫描与资源预算

扫描引擎采用分阶段、按需深入的策略：

1. **Inventory / Metadata：** 获取扫描目标清单、文件类型、大小、路径、来源和可用元数据。
2. **Reputation：** 对适用文件计算内容哈希，并与本地已知威胁记录或可信来源信息匹配。
3. **Structure：** 检查 ZIP/JAR 等归档结构、路径异常、条目数量、声明大小、实际读取大小及资源消耗风险。
4. **Static Analysis：** 按文件类型执行脚本、字节码、元数据和其他静态特征分析。
5. **Contextual Analysis：** 结合实例、Loader、启动参数、依赖关系和可获得的运行时证据分析风险。

快速、标准、深度扫描可以作为用户可选的扫描配置；具体扫描器与覆盖范围必须如实显示，不得将未执行的分析暗示为已完成。默认配置应在资源消耗和覆盖率之间保持保守平衡。

扫描任务必须具备：

- 可配置的 CPU、内存、IO 和并发预算；
- 暂停、取消和任务状态查询；
- 对归档条目数、单条目读取量、累计解压量、图片/脚本/字节码分析输入等设置安全上限；
- 任务失败隔离，不因单个损坏文件导致整个扫描任务崩溃；
- 结果缓存与增量扫描；
- 扫描引擎或规则异常时释放资源并明确报告未完成状态。

缓存有效性不能只依赖文件修改时间。至少应考虑内容哈希、扫描器版本、规则/知识库版本及分析配置。相同内容可以复用静态分析结果，但实例路径、来源和运行上下文仍须单独评估。

### 4. 检测证据与风险判定

Threat Protection 应采用证据驱动的分层分析，不得仅凭文件名、模组名称、单个 API、反射、动态类加载、网络访问或日志关键词就认定恶意。

分析对象包括但不限于：

- 文件哈希、签名/来源信息及已知威胁匹配；
- JAR/ZIP 结构、异常路径、可疑嵌套内容和资源消耗特征；
- 模组元数据、脚本内容、字节码静态特征；
- 整合包内的安装脚本、下载/执行命令及外部文件引用；
- ECL 启动参数中的异常 Java Agent、额外 classpath 或非预期 JVM 参数；
- ECL 启动的 Minecraft 进程可观测到的模块、子进程、文件和日志行为。

日志提取器只能发现实际写入日志的信息，不能据此声称可以检测所有 DLL 注入、内存补丁或其他进程内篡改。运行时检测必须明确数据来源、可观测范围和盲区；不得把不可观测的行为报告为已检查或安全。

风险状态至少区分：

- `Clean`：在当前扫描范围、引擎和规则版本下未发现已知问题；不代表绝对安全；
- `Notice`：值得用户了解但证据不足以构成可疑威胁；
- `Suspicious`：存在需要关注的异常证据；
- `High Risk`：存在强风险证据，建议用户处理；
- `Confirmed Threat`：符合明确、可追溯的威胁判定条件；
- `Unknown` / `Scan Incomplete`：无法完成检查或证据不足，不能等同于 Clean。

每条重要发现应提供风险等级、受影响资源、证据摘要、证据来源、规则/知识版本、置信程度、检测时间和建议操作。静态特征推断、已知威胁匹配和运行时直接证据必须区分。

### 5. 隔离与处理：可恢复、透明且由用户发起

安全中心可以提供打开位置、查看详情、重新扫描、移入隔离区、恢复和删除等处理入口。隔离必须是可追溯、可恢复的受控操作，并遵循 ADR 0021 的统一操作确认与影响说明原则。

除非用户明确选择，不得自动删除、静默修改启动参数、擅自卸载模组或自动清理实例文件。不得因单个风险发现而自动封禁整个实例。隔离、删除和恢复操作必须明确展示目标、影响、可恢复性及失败结果。

### 6. 启动前安全检查门（Launch-time Security Gate）

玩家发起 Minecraft 启动时，ECL 必须在创建 Minecraft 游戏进程之前执行启动前安全检查。检查范围以当前实例及其本次启动所使用的 Java、启动参数和受管理资源为限，不进行全磁盘扫描或全实例深度扫描。

若发现需要用户注意的风险：

1. 暂停本次启动，不创建 Minecraft 游戏进程；
2. 展示风险等级、受影响资源、证据摘要及可疑资源定位；
3. 提供以下选择：
   - **自行处理：** 结束本次启动流程，保留风险状态和提示资格；玩家处理资源后可重新启动并重新检查；
   - **无视风险，继续启动：** 记录用户对当前风险的明确接受决定，并继续本次启动；
   - **取消：** 取消本次启动，不改变检测结果和风险接受记录。
4. 不得在玩家尚未作出选择时将本次启动静默放行。

风险接受记录必须与检测结果分离。用户接受风险只表示其选择继续，不会把资源的 `Suspicious`、`High Risk` 或 `Confirmed Threat` 状态改写为 `Clean`。

### 7. 风险接受记录与重复提示抑制

玩家选择“无视风险，继续启动”时，ECL 应建立明确的 Risk Acceptance Record。记录至少包含：

- 实例身份；
- 资源身份及内容哈希；
- 威胁规则/知识记录标识；
- 用户接受时的风险等级和证据版本；
- 接受时间；
- 扫描引擎及规则版本。

接受决定默认仅适用于当前实例和对应资源内容，不跨实例自动继承。资源内容哈希变化、资源身份无法可靠匹配、风险规则发生实质变化或风险等级升级时，旧接受记录不得直接覆盖新结论。

对于同一实例中内容未变化、风险等级未升级且关键证据未发生实质变化的已接受风险，后续启动不再重复弹出相同提示，但安全中心仍须保留并展示该风险。新出现的其他风险仍应正常提示。

若风险从先前接受的等级升级（例如从 `Suspicious` 升级为 `Confirmed Threat`），必须重新弹窗，并明确说明：

- 风险等级已经升级；
- 哪些新增证据或规则变化导致升级；
- 用户此前曾忽略/接受过该资源的风险；
- 此前的接受记录不覆盖本次升级后的风险。

用户仍可以选择继续启动。用户再次确认后，ECL 可以抑制同一风险等级和同一证据状态的重复提示；若以后再次发生实质升级，仍须重新提示。

“自行处理”和“取消”均不创建风险接受记录，不抑制后续相同风险提示。玩家处理后，下一次启动重新扫描；只有检测结果不再触发风险提示时，才正常启动。

### 8. 用户自主权与安全系统权限边界

Threat Assessment 负责检测、分级和提供证据；Launch Authorization 负责根据当前检测结果、风险接受记录和本次用户选择决定是否展示提示及是否继续启动。检测模块不得自行将风险结论转换成对用户的永久启动禁令。

即使风险等级为 `High Risk` 或 `Confirmed Threat`，ECL 仍须向用户提供明确的风险披露和继续启动选择。ECL 不负责替用户决定其是否应承担设备或数据风险，也不应通过隐蔽机制阻止用户执行已明确选择的启动操作。

此原则不代表 ECL 必须忽略自身无法履行的技术前置条件（例如文件无法读取、启动文件缺失或进程创建失败）；这些属于启动可用性错误，不得伪装成威胁拦截。

### 9. 与诊断、实例清单及 Additions 的边界

- ADR 0033 负责 Minecraft 故障诊断与根因分析；本 ADR 负责安全威胁判断。两者可以共享日志会话、文件清单和结构化证据，但诊断结论不能自动等同于安全结论。
- ADR 0042 的 Instance Inventory 可提供实例文件与资源清单；Threat Protection 不重复实现通用文件浏览和资源识别。
- ADR 0012 的归档提取安全边界继续负责安装时的路径与资源消耗防护；Threat Protection 可以复用其检查结果，但不能以威胁扫描替代归档安全校验。
- ADR 0032 的 Addition 可提供额外扫描器或知识数据，但安全中心原生入口、启动前检查协调、风险接受记录和用户决策流程不得依赖某个可选 Addition 才存在。
- ECL 自身完整性由 ADR 0034 负责。

可选扫描器缺失、知识库过期或某类文件格式不受支持时，必须明确标记覆盖缺口，不得显示为完整安全检查通过。

### 10. 本地优先与隐私

扫描、分析、风险接受记录和历史结果默认保存在本地。不得自动上传文件、哈希清单、日志、实例信息或威胁样本。未来如提供用户主动提交样本或分享报告，必须单独说明数据内容、接收方和用途，并由用户明确授权。

威胁知识库可以通过 ECL 已有分发机制更新，但本地扫描和启动检查不能依赖 ECL 自建在线服务持续可用。

## 备选方案

### 方案 A：不提供 ECL 内部威胁分析，完全依赖系统杀毒软件

不采用。系统杀毒软件仍然是系统级防护的主要职责方，但它不了解 ECL 的实例结构、模组上下文、启动参数和 Minecraft 生态证据，ECL 仍有必要提供面向自身管理对象的解释与工作流。

### 方案 B：默认实时扫描全部实例

不采用。大量实例文件和大型整合包会导致持续 IO、CPU 和 RAM 消耗，也会增加实现复杂度。手动扫描与明确工作流触发更符合 ECL 的性能和用户控制原则。

### 方案 C：发现高风险或确认威胁后永久禁止启动

不采用。ECL 应充分披露风险并记录用户决定，但不替用户承担最终风险选择。风险升级必须重新提示，但用户仍可明确选择继续。

### 方案 D：手动扫描优先、必要节点自动检查、启动前风险门控

采用。该方案在用户自主权、资源开销、可解释性和 Minecraft 工作流之间取得平衡，并保持 ECL 的本地优先边界。

## 后果

### 正面影响

- ECL 能针对其管理的 Minecraft 内容提供上下文相关的安全分析。
- 手动扫描成为明确、可控的主要入口，避免持续后台扫描造成资源消耗。
- 下载、导入、安装和启动等关键节点仍有必要的自动检查。
- 风险结论保留证据链，用户可以定位和处理可疑资源。
- 用户能够明确接受风险继续启动，且风险升级时会再次得到告知。
- 安全分析与诊断、文件管理、启动器自身完整性保持清晰边界。

### 代价与限制

- 需要维护文件类型分析器、威胁规则、知识库来源和误报处理流程。
- 静态分析无法证明任意第三方模组绝对安全；运行时可观测能力也存在平台和权限限制。
- 启动前检查会增加启动前置步骤，需要严格控制检查范围和延迟。
- 风险接受记录需要正确处理内容变更、规则更新、实例迁移和风险升级。
- 继续启动意味着用户可能承担真实风险；ECL 必须清楚记录用户决定，但不能保证其后果。

## 验收标准

- 安全中心仅处理 ECL 管理或用户明确选择的 Minecraft 对象，不执行全 Windows 扫描或无关进程监控。
- 用户可以分别发起单文件、目录、实例和整合包扫描，并选择合理的扫描范围。
- 默认不执行全实例持续实时扫描或后台目录轮询。
- 扫描任务具备资源预算、暂停、取消、增量缓存和失败隔离能力。
- 扫描结果能够区分 Clean、Notice、Suspicious、High Risk、Confirmed Threat 和 Unknown/Scan Incomplete，并提供可追溯证据。
- 日志分析不会宣称能够检测日志中不可见的所有注入或内存篡改。
- Minecraft 启动前检查在创建游戏进程前完成；发现需提示风险时，本次启动先暂停。
- 风险提示提供自行处理、无视风险继续启动和取消三种选择，三者行为符合本 ADR 规定。
- 选择继续启动会建立实例与资源范围内的风险接受记录，但不会修改威胁检测结果。
- 同一风险未发生实质变化时不重复提示；新风险仍会提示；风险升级时重新提示并披露此前忽略记录及升级原因。
- 用户始终可以明确选择继续启动，包括面对 High Risk 和 Confirmed Threat。
- 自行处理和取消不会创建风险接受记录，也不会抑制后续提示。
- 风险接受记录在资源内容变化、实例范围变化或风险实质升级时不会被错误复用。
- 隔离、删除和恢复操作由用户明确发起，并提供可恢复性及影响说明。
- 默认不上传扫描对象、日志、实例信息或风险接受记录。
- 扫描引擎、知识库或安全分析失败不会伪装成 Clean；失败状态和覆盖缺口清晰可见。
- Threat Protection 不重复实现 ADR 0033、0034、0042 已负责的能力。
