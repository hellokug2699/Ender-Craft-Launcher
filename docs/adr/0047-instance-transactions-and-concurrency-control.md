# ADR 0047：实例变更事务与并发控制

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-03
- Scope: 实例写入协调、并发冲突检测、变更计划、事务阶段、恢复记录及 Addition 写入边界
- Related: [ADR 0021：WPF 交互反馈与轻量动效系统](0021-wpf-interaction-and-motion-system.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0042：实例文件浏览器与崩溃报告工作流](0042-instance-file-explorer-and-crash-report-workflow.md)、[ADR 0045：原生 Instance Engine 架构与能力边界](0045-native-instance-engine-architecture.md)

## 背景

实例文件可能同时被模组管理、文件浏览器、整合包更新、Addition 处理器、迁移和恢复流程访问。若每个功能独立写入文件，可能发生更新覆盖删除、扫描读取到半成品、两个操作互相覆盖、旧结果覆盖新状态等问题。

并发修改异常不仅影响用户体验，还可能造成实例损坏。ECL 不能依赖页面按钮禁用或用户避免同时操作来保证一致性；必须在 Core/Engine 层提供实例级写入协调。

## 决策

### 1. 所有受管理实例写操作必须经过统一事务入口

对实例内容有持久化影响的操作，包括安装、更新、删除、重命名、配置写入、资源组合应用、迁移、克隆和恢复，必须通过 Instance Engine 的 Change/Transaction API。

Addition 可以提交变更计划，但不得直接写入实例路径。Engine 负责授权、目标验证、冲突检查、执行协调、恢复记录和最终状态。

### 2. 采用实例级写入互斥与读写协调

同一实例默认最多允许一个互相冲突的写事务处于 Apply 阶段。Engine 必须提供实例级协调器，防止两个写事务同时修改相同或相关资源。

- 同一实例的冲突写事务默认串行化；
- 对明确互不相交且可证明安全的操作，未来可以引入细粒度锁，但不得作为首期前提；
- 读取操作可并发，但必须明确读取一致性：读取正在变更的目标时，应等待、读取稳定快照或返回明确的 Busy/Changing 状态；
- 扫描、预览等读操作不得看到未提交的中间状态并将其缓存为稳定结果；
- 长时间事务必须提供进度、取消边界和占用说明。

实例级锁是逻辑协调，不应仅依赖 UI 状态或进程内单个按钮。若未来支持多个 ECL 进程同时管理同一实例，协调状态必须跨进程有效，并在进程异常退出后可检测和恢复。

### 3. 定义事务生命周期

标准事务阶段为：

1. **Inspect：** 读取目标、当前状态和必要证据；
2. **Plan：** 生成明确的变更计划、目标清单、影响范围和前置条件；
3. **Prepare：** 获取实例写入权、检查磁盘空间/权限/进程占用，准备临时文件和恢复材料；
4. **Apply：** 按计划执行写入、替换或删除；
5. **Verify：** 校验预期结果、文件完整性和关键元数据；
6. **Commit：** 将事务标记为成功并更新 Inventory/历史；
7. **Rollback / Recover：** 失败或中断时恢复前态，或进入需要用户处理的恢复状态。

事务状态必须持久化，至少区分 Planned、Preparing、Applying、Verifying、Committed、RollingBack、RolledBack、NeedsRecovery、Failed 和 Cancelled。状态迁移应受控，不能仅凭 UI 显示推断执行结果。

### 4. 不承诺文件系统 ACID，但必须提供可验证恢复语义

普通文件系统操作无法普遍保证数据库式 ACID，尤其涉及跨卷移动、外部进程写入、权限变化、磁盘故障和断电。

ECL 应采用暂存目录、临时文件、原子替换（平台/文件系统支持时）、内容校验、前态备份和持久化阶段日志等策略，尽可能保证单个变更步骤的安全性。

事务不得在尚未验证新状态时销毁唯一可恢复的旧状态。无法自动回滚时必须进入 NeedsRecovery，展示已完成步骤、失败步骤、可用恢复材料和用户可选操作，不得伪称回滚成功。

### 5. 取消、重试和重复提交必须有确定语义

- 用户取消只在安全检查点生效；进入不可中断的原子提交步骤后，应说明取消延后或不可用；
- 重复点击、重复 API 请求或 Addition 重试不得重复执行同一事务；应使用事务 ID/幂等键识别；
- 失败重试必须重新验证目标和前置条件，不得沿用过期的影响分析；
- 取消和失败均应保留必要的恢复记录，并明确是否已产生部分变更。

### 6. 处理外部修改与运行中实例

文件可能被游戏进程、其他启动器、用户或第三方程序直接修改。Engine 不能假定自己是唯一写入者。

事务计划应记录必要的前态指纹/文件标识；Apply 前重新验证关键目标，发现内容已变化则中止并重新规划。对于运行中的实例，按具体操作声明可读/可写范围；影响游戏运行或可能覆盖活动文件的写入应阻止、延迟或要求先关闭游戏。

Engine 的协调器只能协调经过 ECL 的操作，不能完全阻止外部程序写入。因此仍需通过文件身份、时间/内容指纹和提交后验证检测外部竞争。

### 7. 与统一操作确认规范集成

涉及破坏性或不可逆风险的事务应遵循 ADR 0021。影响分析必须区分已确认、可能和未知；扫描未完成或前态不可读取时不得显示“没有影响”。

UI 负责展示计划、风险、影响和结果；Engine 提供事实与证据，并负责执行策略。用户确认不能绕过路径边界、权限限制、身份冲突或并发一致性检查。

### 8. 扫描与缓存必须感知事务提交

事务提交后，Engine 应按变更目标使 Inventory、文件元数据和依赖分析缓存失效或执行增量更新。事务未提交期间，不能把中间状态发布为已确认的实例状态。

## 备选方案

### 方案 A：由 UI 禁用冲突按钮

实现成本低，能减少同一页面的重复点击。

放弃原因：无法覆盖多个页面、多个 Addition、后台任务、其他 ECL 进程和重试请求；UI 不是一致性边界。

### 方案 B：只对单个文件加锁

可以提高局部并发度。

放弃原因：实例变更常涉及多个文件和资源关系，文件级锁容易产生锁顺序、死锁和部分提交问题；首期难以证明安全。

### 方案 C：实例级写事务串行化

选择原因：实现和验证边界明确，优先保证数据安全；待有真实性能需求和可证明的非冲突模型后，再考虑细粒度并行。

## 后果

### 正面影响

- 多页面和 Addition 不会无协调地同时写入同一实例；
- 更新、删除、迁移和恢复共享事务状态与错误语义；
- 崩溃或断电后能够识别未完成操作；
- Inventory 不会把事务中间态当成已提交事实。

### 代价与风险

- 同一实例的写操作可能排队，长任务会降低并行吞吐；
- 事务日志、恢复材料和临时文件需要空间与生命周期管理；
- 文件系统不支持原子替换或外部持续写入时，恢复能力存在边界；
- 多进程锁、进程崩溃清理和锁租约需要谨慎设计，避免误释放仍在运行的事务。

## 验收标准

1. 所有原生功能与 Addition 的实例写入均经过 Engine 事务 API。
2. 同一实例的冲突写事务不会同时进入 Apply 阶段。
3. 读取操作不会把事务中间态缓存为稳定 Inventory 结果。
4. 多页面、Addition、重复请求和多进程竞争测试不会造成未检测的并发覆盖。
5. 事务阶段与状态持久化，进程异常退出后能够识别未完成事务。
6. 关键文件在 Apply 前执行前态验证，外部修改导致计划失效时中止而非盲目覆盖。
7. 失败、取消和恢复结果准确区分完整成功、部分变更、已回滚和需要人工恢复。
8. 事务提交后相关 Inventory 与缓存正确失效或增量更新。
9. 破坏性操作遵循 ADR 0021，未知影响不会被显示为无影响。
10. 无法保证自动恢复时明确进入 NeedsRecovery，不伪称成功或完整回滚。
