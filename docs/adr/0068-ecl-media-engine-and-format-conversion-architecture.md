# ADR 0068: ECL Media Engine and Standard Media Format Conversion Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-09
- Scope: ECL Media Engine Addition、图片/音频/视频标准格式识别与转换、媒体处理后端治理、许可与技术保护措施边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0039](0039-application-runtime-lifecycle-and-graceful-shutdown.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0067](0067-ecl-music-player-and-minecraft-audio-bridge-architecture.md)

## 背景

ECL 的多个功能可能需要处理用户本地的图片、音频和视频，例如格式转换、格式识别、元数据读取及后续媒体相关工具。若每个 Addition 分别引入不同的编解码库、原生二进制、运行时和许可证，容易造成重复依赖、包体膨胀、平台差异、语言运行时混杂和维护责任分散。

FFmpeg 等成熟媒体工具覆盖面广，但将某一套大型媒体框架直接设为 ECL 的架构核心或强制分发依赖，会把其原生库、构建方式、编解码器组合、平台支持和许可证治理一并带入 ECL。反过来，从零实现通用图片、音频和视频编解码器也不现实。

此外，普通媒体格式处理与绕过第三方平台的加密封装或技术保护措施不是同一类能力。ECL 需要明确支持边界，避免把平台专有解密误包装成普通格式兼容。

## 决策

### 1. 建立独立的 ECL Media Engine Addition

登记唯一 Addition：`ecl.media-engine`，类型为 `Feature`，类别为 `Media Processing`，当前状态为 `Proposed`。

Media Engine 面向用户提供通用媒体处理能力，并为其他 Addition 提供可选的媒体处理服务。它不是 ECL Core 的启动依赖，也不属于 Minecraft 启动链。

- Core 负责 Addition 生命周期、权限裁决、受控资源访问、任务生命周期及必要的宿主隔离。
- Media Engine 负责媒体能力发现、格式识别、转换任务协调、处理后端选择和结果交付。
- 具体编解码器、容器解析器及平台媒体 API 由可替换的处理后端提供。
- 其他 Addition 可以按需复用已安装的 Media Engine 能力，但不得因此形成未经确认的强制依赖。
- Media Engine 不取代各 Addition 自身的领域逻辑；例如 Resource Pack Studio、Map Art Studio 仍负责各自资源语义和业务规则。

### 2. 支持普通、公开且可合法处理的媒体格式

目标范围包括常见图片、音频和视频格式的识别、读取、元数据提取及格式转换。具体格式、编码配置、容器组合和平台覆盖范围必须以实际后端能力及验证结果为准，不在本 ADR 中承诺全格式兼容。

格式支持应区分容器与编码格式；扩展名不能作为内容真实性或可解码性的唯一依据。对损坏、截断、未知、仅部分支持或后端不支持的输入，应提供准确的能力状态，不得将 Unsupported 等同于 Invalid 或 Malicious。

格式转换应明确源格式、目标格式、实际编码参数及可能的质量损失。对有损转换不得暗示无损；不得静默覆盖源文件。原始文件默认保留，输出位置与覆盖行为由用户明确决定。

### 3. 不将 FFmpeg 或任何单一媒体框架设为架构核心

ECL 自己定义稳定的媒体处理能力边界和后端治理方式，不把 FFmpeg 设为不可替换的核心依赖，也不要求所有用户安装完整 FFmpeg 环境。

- FFmpeg 可以作为未来经独立许可、安全、包体和平台评估后选择的可选后端候选；本 ADR 不批准当前捆绑或依赖它。
- 其他成熟库、平台原生媒体 API 或 ECL 当前技术栈可用的实现也可作为候选，必须按能力和许可逐项评估。
- 不从零重写通用编解码器；自研重点是统一能力抽象、后端治理、任务协调、资源边界和用户体验。
- 后端应声明其支持的容器、编码格式、读写能力、平台范围、依赖、许可证和限制；运行时只能选择已声明且经过校验的能力。
- 不为单一功能无必要地引入额外语言运行时。优先评估与 ECL 现有技术栈兼容的实现；确需原生库、独立进程或其他语言组件时，必须说明其收益、部署、调试、签名、升级和故障隔离成本。
- 后端实现语言不应成为 Addition 对外能力契约的一部分。

### 4. 能力按需安装和按需加载

图片、音频、视频能力及其后端依赖应支持按需交付或加载，避免用户只使用音频能力却被迫安装完整视频处理环境。

- 普通 ECL 启动和 Minecraft 启动不得等待 Media Engine。
- 未使用媒体功能时，不应初始化不必要的媒体后端。
- 缺少某一后端或某种格式支持时，应明确报告该能力不可用，不影响其他已安装能力。
- Media Engine 故障不得导致 ECL Core 或 Minecraft 进程被终止。
- 任务应具备取消、超时、资源预算、临时文件清理和失败收敛能力；具体机制由实现设计确定。

### 5. 媒体处理的资源与安全边界

媒体文件及其元数据均视为不可信输入。解码器和媒体解析器可能存在内存安全、资源耗尽及恶意文件风险。

- 媒体处理必须通过 Core 授权的资源访问路径，不得绕过 Resource Broker 或直接扫描未授权目录。
- 处理过程应限制 CPU、内存、临时磁盘和并发占用，并允许用户取消。
- 不得因为文件扩展名或 MIME 声明就信任其内容。
- 后端若运行原生代码或外部进程，应明确其实际权限边界；不得将普通进程隔离描述为完整 OS 沙箱。
- 不得在转换过程中默认上传媒体内容、元数据或缩略图到远程服务。
- 不得静默安装系统级编解码器、修改系统媒体关联或更改用户环境。

### 6. 明确排除绕过平台保护措施的解密能力

Media Engine 仅处理普通公开格式、标准媒体容器，以及用户或 ECL 已获得合法处理授权的内容。

- 不开发、内置、捆绑或自动下载以绕过第三方平台访问控制、DRM 或其他技术保护措施为目的的专用解密器。
- 不将 NCM 等平台专有加密封装的解密列为普通格式转换能力。
- 不因某种专有格式在技术上可解析，就推断 ECL 获得了相关平台或内容权利人的授权。
- 第三方代码的开源许可证只解决代码许可问题，不替代媒体内容、平台技术措施或相关数据的权利授权。
- 对不支持或不在授权范围内的受保护格式，应明确标记为 Unsupported / Not Supported；不得尝试静默绕过保护。
- 本条不限制用户导入已合法取得的普通标准媒体文件，也不要求 ECL 对用户本地文件来源作无依据的违法判断。

### 7. 与其他 Addition 的关系

Media Engine 是独立可选 Addition，不是所有媒体消费者的强制依赖。

- ECL Music Player 可在未来评估复用其音频格式识别、解码或转换能力，但不得要求用户为了基本音乐播放而必须安装完整 Media Engine。
- Resource Pack Studio、Map Art Studio、Shader Studio 等可按实际需要选择性复用图片或视频能力；领域资源解析和渲染逻辑仍由各自 Addition 负责。
- Addition 之间不得直接 IPC、共享内部对象或绕过 Core 建立依赖；协作遵循 ADR 0055 的宿主受控机制。
- 不因某个 Addition 选择某一媒体后端，就把该后端提升为 ECL 全局强制依赖。

## 备选方案

### 方案 A：每个 Addition 各自集成媒体库

不作为长期方向。短期接入简单，但会造成依赖重复、许可审查分散、格式能力不一致和维护成本叠加。

### 方案 B：直接将 FFmpeg 作为 ECL 全局强制依赖

不采用。其覆盖面虽广，但会引入较大的原生依赖、平台构建差异、编解码器与许可证治理负担，也会让不需要视频能力的用户承担额外下载和维护成本。

### 方案 C：完全从零实现图片、音频和视频编解码器

不采用。通用编解码器开发范围巨大，难以达到成熟实现的兼容性、安全性和性能；这不是 ECL 的合理投入方向。

### 方案 D：建立独立 Media Engine 与可替换后端

作为当前 Proposed 方向。ECL 自主掌握能力抽象、任务治理和依赖边界，具体格式支持由经过许可与安全审查的后端提供；后端可替换，且能力按需交付。

## 后果

### 正面影响

- 图片、音频和视频处理能力可以被多个 Addition 复用。
- 不必让每个 Addition 重复集成和维护媒体依赖。
- 不把 FFmpeg 或某个特定语言运行时变成 ECL 的永久架构负担。
- 可以按需安装和加载具体能力，降低无关依赖和包体成本。
- 普通格式转换与平台专有保护措施绕过之间有明确边界。

### 代价与风险

- ECL 需要维护媒体能力模型、后端适配、格式能力声明和兼容性验证。
- 不同平台的原生媒体 API 和第三方库能力可能不一致，格式覆盖范围需要逐项验证。
- 原生解码器和容器解析器仍可能存在安全漏洞；抽象层不能消除底层风险。
- 后端许可证、专利、编解码器构建选项和分发义务可能随版本变化，发布前必须重新审核。
- 若过度追求完全不引入外部依赖，可能导致格式支持不足；应避免把“自研引擎”误解为“自研全部编解码器”。

## 验收标准

本 ADR 当前为 Proposed。以下为后续原型和实现验收方向，不表示功能已经实现：

1. Registry 中存在唯一 `ecl.media-engine` Feature Addition，ADR、README、Manifest 的 ID 和状态一致。
2. Media Engine 不成为 ECL Core、普通启动或 Minecraft 启动的强制依赖。
3. 能力声明区分图片、音频、视频的识别、读取、元数据提取和转换能力，不以单一“支持媒体”标志掩盖能力差异。
4. 对每种正式声明支持的容器/编码组合，均有对应平台和后端的可复核测试；未验证组合不得宣称支持。
5. 转换结果明确目标格式、编码参数和有损/无损属性；失败、取消或空间不足时不破坏源文件。
6. 用户可以明确选择输出位置；未经用户确认不得静默覆盖源文件。
7. 不支持、损坏、截断和格式声明不匹配的输入能够被区分报告。
8. 媒体处理受 Core 授权资源访问、资源预算、取消和临时文件清理约束。
9. 未安装或不可用的单一后端不会阻断其他独立媒体能力或普通 ECL/Minecraft 启动。
10. 不会为仅使用单一媒体类别的用户无条件下载全部图片、音频和视频后端。
11. 所有随包或动态分发的后端均完成代码许可、编解码器许可、来源、签名/完整性及平台分发义务审查。
12. 不包含以绕过第三方平台 DRM、访问控制或技术保护措施为目的的专用解密器；不支持 NCM 等平台专有加密格式解密。
13. 不默认上传用户媒体文件、元数据或缩略图；任何未来远程处理均须单独披露并取得适当授权。
14. 后端语言和实现方式不会强迫 ECL Core 引入无必要的语言运行时；若引入独立进程或额外运行时，必须有独立安全和部署评审。

## 修订记录

- 2026-11-09：首次提出 ECL Media Engine，确定以独立 Addition 提供普通图片、音频和视频格式处理与转换能力；不将 FFmpeg 设为强制架构依赖，采用可替换后端和按需能力交付，并明确排除平台专有加密格式解密及绕过技术保护措施的能力。Decision 保持 Proposed，Implementation 保持 Not Started。
