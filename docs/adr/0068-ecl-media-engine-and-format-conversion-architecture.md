# ADR 0068: ECL Media Processing and Editing Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-09
- Scope: ECL Media Engine Addition、图片/音频/视频读取、转换、编辑、预览与可视化、临时工作区及安全提交、媒体处理后端治理、许可与技术保护措施边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0039](0039-application-runtime-lifecycle-and-graceful-shutdown.md)、[ADR 0047](0047-instance-transactions-and-concurrency-control.md)、[ADR 0048](0048-instance-snapshots-and-recovery.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0067](0067-ecl-music-player-and-minecraft-audio-bridge-architecture.md)

## 背景

ECL 的多个功能可能需要处理用户本地的图片、音频和视频。若将 Media Engine 限定为格式转换工具，将无法覆盖常见的媒体编辑需求，例如图片缩放、裁剪与拼接，音频裁剪、分段、合并与波形查看，以及视频尺寸调整、片段裁剪、合并和预览。

媒体处理还需要可靠的文件安全模型。仅要求“默认不覆盖源文件”仍不足以保护用户：编辑过程可能产生多个中间文件，预览必须反映编辑后的真实结果，拆分任务可能输出多个文件，异常退出也可能留下未完成数据。若编辑器直接操作源文件，用户一次误操作或处理失败就可能破坏原始素材。

若每个 Addition 分别引入不同的编解码库、原生二进制、运行时和许可证，也容易造成重复依赖、包体膨胀、平台差异和维护责任分散。FFmpeg 等成熟媒体工具覆盖面广，但将某一套大型媒体框架直接设为架构核心或强制分发依赖，会把其原生库、构建方式、编解码器组合、平台支持和许可证治理一并带入 ECL；从零实现通用编解码器同样不现实。

此外，普通媒体格式处理与绕过第三方平台的加密封装或技术保护措施不是同一类能力。ECL 需要明确支持边界，避免把平台专有解密误包装成普通格式兼容。

## 决策

### 1. 建立独立的 ECL Media Engine Addition

登记唯一 Addition：`ecl.media-engine`，类型为 `Feature`，类别为 `Media Processing`，当前状态为 `Proposed`。

Media Engine 是通用媒体处理能力提供者，范围包括媒体识别、读取、元数据提取、格式转换、基础编辑、处理结果预览和必要的可视化。它不是 ECL Core 的启动依赖，也不属于 Minecraft 启动链。

- Core 负责 Addition 生命周期、权限裁决、受控资源访问、任务生命周期、临时工作区管理及最终文件提交。
- Media Engine 负责媒体能力发现、编辑/转换任务协调、处理后端选择、预览数据生成和结果交付。
- 具体编解码器、容器解析器及平台媒体 API 由可替换的处理后端提供。
- Media Engine 不取代各 Addition 自身的领域逻辑；例如 Resource Pack Studio、Map Art Studio 仍负责各自资源语义和业务规则。
- 其他 Addition 可以按需复用已安装的媒体能力，但不得因此形成未经确认的强制依赖。

### 2. 图片、音频与视频处理能力

目标能力按媒体类别区分，具体格式、编码配置、容器组合和平台覆盖范围以实际后端能力及验证结果为准，不承诺全格式兼容。

**图片处理：**
- 格式识别、读取、元数据提取和格式转换。
- 尺寸/分辨率调整、裁剪、旋转、翻转。
- 多图片拼接或合并，以及批量处理。
- 保留并正确处理透明通道、色彩信息及相关元数据；具体能力以格式和后端支持为准。

**音频处理：**
- 格式识别、读取、元数据提取和格式转换。
- 裁剪、分段、合并、音量调整及基础淡入淡出。
- 提供音频试听和波形可视化，以支持定位片段、识别静音区间和辅助编辑。
- 多音轨组合或基础混音可作为能力方向，具体范围由后续原型和 Feature Spec 确定；本 ADR 不要求实现专业级数字音频工作站（DAW）。

**视频处理：**
- 容器/编码识别、读取、元数据提取和格式转换。
- 视频尺寸/分辨率调整、画面裁剪、片段截取和多个片段合并。
- 提供处理素材及结果的播放预览、时间定位、关键帧/缩略图提取。
- 基础时间轴和音视频轨道操作可作为能力方向；不以此承诺专业级非线性视频编辑系统（NLE）。

视频播放预览是媒体编辑与检查能力的一部分，不因此创建独立的通用视频播放器 Addition。独立播放器产品（媒体库、播放列表、播放历史、字幕生态等）不属于当前决策范围。

音频波形、视频时间轴、图片预览等属于媒体可视化能力。频谱分析、多轨专业混音、复杂转场、特效和专业后期制作不作为首期承诺。

格式支持应区分容器与编码格式；扩展名不能作为内容真实性或可解码性的唯一依据。对损坏、截断、未知、仅部分支持或后端不支持的输入，应提供准确的能力状态，不得将 Unsupported 等同于 Invalid 或 Malicious。格式转换应明确源格式、目标格式、实际编码参数及可能的质量损失。

### 3. 以临时工作区保护源文件

所有媒体编辑均应在独立于源文件的临时工作区中进行。源文件在编辑、拆分、合并、转换和预览期间保持不变，不作为处理后端的直接写入目标。

- 用户导入源文件后，由 Core 在受控工作区中创建独立工作副本；工作副本应与源文件具有独立存储身份，不能使用可能让写入穿透到源文件的硬链接或其他共享可变存储方式。
- 后续编辑操作基于工作区中的副本及其派生结果执行。编辑器可以生成中间文件、多个片段和预览产物，但不得因此修改源文件。
- 预览应读取当前编辑状态对应的工作区产物，或由相同处理任务生成的预览结果；不得为了预览而提前覆盖源文件。
- 编辑失败、取消或用户放弃时，源文件保持原样。放弃后可清理工作区；若用户选择保留未完成工作，则按明确的恢复/保留流程处理。
- 临时工作区应有任务归属、生命周期、空间预算和清理策略。异常退出后应能识别残留工作区，并为用户提供恢复、导出或放弃选择；不得在未确认用户未完成工作的情况下无条件清除。
- 工作区文件的访问、创建、读取、写入和清理均受 Core 授权及资源边界约束。

该工作区是由 Core 管理的任务级临时文件空间，不是新的 Addition，也不等同于玩家长期资料 Workspace。是否将其抽象为其他 Addition 可复用的通用 Core Workspace/Transaction 能力，应遵循 ADR 0055 及相关事务架构评估；Media Engine 不得自行建立绕过 Core 的文件管理体系。

### 4. 明确区分导出与破坏性替换

编辑完成后的交付必须区分两种不同操作：

- **导出为新文件：** 将工作区中的最终结果写入用户指定的新目标位置，源文件继续保留。
- **替换源文件：** 只有用户在最终提交阶段明确选择并确认破坏性更改后，Core 才能尝试用编辑结果替换源文件。

不得把普通“保存/导出”默认为覆盖源文件。若用户不同意破坏性更改，应放弃替换并按用户选择清理或保留工作区，源文件不得发生任何变化。

破坏性替换必须具备冲突检测和失败恢复能力：

- 在提交前重新核对源文件身份及版本状态。至少应结合文件身份、大小/时间等元数据，并使用内容指纹或等效机制识别源文件是否在编辑期间被外部修改；具体策略由实现确定。
- 若源文件在编辑期间发生变化、被移动、被替换或无法确认仍是最初对象，应中止自动覆盖并要求用户重新决策，不得以旧工作副本静默覆盖新内容。
- 提交应尽可能采用同一文件系统内的安全替换/原子替换方式，并保留必要的恢复材料。平台或文件系统无法提供相应保证时，必须采用经过验证的回退策略；不能保证安全时应拒绝破坏性提交，仍允许导出为新文件。
- 替换失败时不得删除唯一可用的源文件或最终结果；必须报告真实提交状态，并保留可恢复材料。
- 对文件权限、只读属性、占用锁、磁盘空间不足和目标路径冲突等情况，应在提交前或提交过程中安全失败。

拆分、批量转换或多文件导出应视为一个有明确结果清单的输出集合。系统应避免任务部分失败却报告整体成功；在目标文件系统无法提供真正的多文件原子事务时，应使用暂存目录、冲突检查、回滚/清理策略和明确的部分成功报告。不得将多文件导出伪称为原子事务。

### 5. 不将 FFmpeg 或任何单一媒体框架设为架构核心

ECL 自己定义稳定的媒体处理能力边界和后端治理方式，不把 FFmpeg 设为不可替换的核心依赖，也不要求所有用户安装完整 FFmpeg 环境。

- FFmpeg 可以作为未来经独立许可、安全、包体和平台评估后选择的可选后端候选；本 ADR 不批准当前捆绑或依赖它。
- 其他成熟库、平台原生媒体 API 或 ECL 当前技术栈可用的实现也可作为候选，必须按能力和许可逐项评估。
- 不从零重写通用编解码器；自研重点是统一能力抽象、后端治理、编辑/转换任务协调、预览与可视化集成、资源边界和用户体验。
- 后端应声明其支持的容器、编码格式、读写/编辑能力、平台范围、依赖、许可证和限制；运行时只能选择已声明且经过校验的能力。
- 不为单一功能无必要地引入额外语言运行时。优先评估与 ECL 现有技术栈兼容的实现；确需原生库、独立进程或其他语言组件时，必须说明其收益、部署、调试、签名、升级和故障隔离成本。
- 后端实现语言不应成为 Addition 对外能力契约的一部分。

### 6. 能力按需安装和按需加载

图片、音频、视频能力及其后端依赖应支持按需交付或加载，避免用户只使用图片能力却被迫安装完整音视频处理环境。

- 普通 ECL 启动和 Minecraft 启动不得等待 Media Engine。
- 未使用媒体功能时，不应初始化不必要的媒体后端。
- 缺少某一后端或某种格式支持时，应明确报告该能力不可用，不影响其他已安装能力。
- Media Engine 故障不得导致 ECL Core 或 Minecraft 进程被终止。
- 编辑与转换任务应具备取消、超时、资源预算、磁盘空间检查、工作区恢复/清理和失败收敛能力。
- 预览能力可以按媒体类别和实际任务按需加载；不要求仅为图片处理而初始化视频播放环境。

### 7. 媒体处理的资源、安全与隐私边界

媒体文件及其元数据均视为不可信输入。解码器和媒体解析器可能存在内存安全、资源耗尽及恶意文件风险。

- 媒体处理必须通过 Core 授权的资源访问路径，不得绕过 Resource Broker 或直接扫描未授权目录。
- Core 管理工作区文件访问和最终提交；Media Engine 后端只能操作被明确授予的工作区输入与输出，不得直接写入源文件。
- 处理过程应限制 CPU、内存、临时磁盘、解码时长和并发占用，并允许用户取消。
- 不得因为文件扩展名或 MIME 声明就信任其内容。
- 后端若运行原生代码或外部进程，应明确其实际权限边界；不得将普通进程隔离描述为完整 OS 沙箱。
- 不得在处理过程中默认上传媒体内容、元数据、波形数据或缩略图到远程服务。
- 不得静默安装系统级编解码器、修改系统媒体关联或更改用户环境。

### 8. 明确排除绕过平台保护措施的解密能力

Media Engine 仅处理普通公开格式、标准媒体容器，以及用户或 ECL 已获得合法处理授权的内容。

- 不开发、内置、捆绑或自动下载以绕过第三方平台访问控制、DRM 或其他技术保护措施为目的的专用解密器。
- 不将 NCM 等平台专有加密封装的解密列为普通格式转换能力。
- 不因某种专有格式在技术上可解析，就推断 ECL 获得了相关平台或内容权利人的授权。
- 第三方代码的开源许可证只解决代码许可问题，不替代媒体内容、平台技术措施或相关数据的权利授权。
- 对不支持或不在授权范围内的受保护格式，应明确标记为 Unsupported / Not Supported；不得尝试静默绕过保护。
- 本条不限制用户导入已合法取得的普通标准媒体文件，也不要求 ECL 对用户本地文件来源作无依据的违法判断。

### 9. 与其他 Addition 的关系

Media Engine 是独立可选 Addition，不是所有媒体消费者的强制依赖。

- ECL Music Player 可在未来评估复用其音频格式识别、解码或转换能力，但不得要求用户为了基本音乐播放而必须安装完整 Media Engine。
- Resource Pack Studio、Map Art Studio、Shader Studio 等可按实际需要选择性复用图片或视频能力；领域资源解析和渲染逻辑仍由各自 Addition 负责。
- Addition 之间不得直接 IPC、共享内部对象或绕过 Core 建立依赖；协作遵循 ADR 0055 的宿主受控机制。
- 不因某个 Addition 选择某一媒体后端，就把该后端提升为 ECL 全局强制依赖。

## 备选方案

### 方案 A：每个 Addition 各自集成媒体库

不作为长期方向。短期接入简单，但会造成依赖重复、许可审查分散、格式能力不一致和维护成本叠加。

### 方案 B：直接将 FFmpeg 作为 ECL 全局强制依赖

不采用。其覆盖面虽广，但会引入较大的原生依赖、平台构建差异、编解码器与许可证治理负担，也会让不需要视频能力的用户承担额外下载和维护成本。

### 方案 C：直接在源文件上进行编辑

不采用。虽然可以减少工作副本和临时磁盘占用，但编辑失败、误操作、进程崩溃或多输出任务部分失败都可能破坏用户原始素材，无法满足源文件默认不变的安全要求。

### 方案 D：仅生成编辑指令，预览时实时重放全部操作

不作为唯一方案。编辑指令/参数可以用于记录操作历史和重建结果，但复杂处理链的实时重放可能增加预览延迟、后端差异和恢复复杂度；实际预览仍应基于工作区中的处理结果或可复用缓存。

### 方案 E：建立独立 Media Engine、临时工作区和安全提交机制

作为当前 Proposed 方向。ECL 自主掌握媒体能力抽象、编辑任务治理、源文件保护和后端边界；具体格式支持由经过许可与安全审查的可替换后端提供，能力按需交付。

## 后果

### 正面影响

- 图片、音频和视频的读取、转换、基础编辑及预览能力可以由一个 Addition 统一提供。
- 编辑和预览过程不会直接破坏源文件；用户可以先自由尝试，再决定导出、替换或放弃。
- 临时工作区与安全提交机制可以减少误覆盖、异常退出和多文件任务部分失败造成的数据损失。
- 音频波形、视频预览和图片处理可以共享任务与资源治理机制。
- 不必让每个 Addition 重复集成和维护媒体依赖。
- 不把 FFmpeg 或某个特定语言运行时变成 ECL 的永久架构负担。
- 普通格式处理与平台专有保护措施绕过之间有明确边界。

### 代价与风险

- ECL 需要维护媒体能力模型、后端适配、编辑任务协调、预览管线、工作区生命周期和安全提交逻辑。
- 工作副本、预览产物和多输出任务会增加临时磁盘占用；必须提供空间预算与清理/恢复策略。
- 跨平台文件替换语义存在差异；无法保证安全提交的平台必须限制破坏性替换，而不能降低源文件保护要求。
- 多文件导出通常无法依赖文件系统提供真正的整体原子事务，需要明确部分成功和回滚语义。
- 不同平台的原生媒体 API 和第三方库能力可能不一致，格式覆盖范围需要逐项验证。
- 原生解码器和容器解析器仍可能存在安全漏洞；抽象层不能消除底层风险。
- 后端许可证、专利、编解码器构建选项和分发义务可能随版本变化，发布前必须重新审核。
- 若过度追求完全不引入外部依赖，可能导致格式支持不足；应避免把“自研引擎”误解为“自研全部编解码器”。

## 验收标准

本 ADR 当前为 Proposed。以下为后续原型和实现验收方向，不表示功能已经实现：

1. Registry 中存在唯一 `ecl.media-engine` Feature Addition，ADR、README、Manifest 的 ID 和状态一致。
2. Media Engine 不成为 ECL Core、普通启动或 Minecraft 启动的强制依赖。
3. 能力声明区分图片、音频、视频的识别、读取、元数据提取、转换、编辑和预览能力，不以单一“支持媒体”标志掩盖能力差异。
4. 对每种正式声明支持的容器/编码组合及编辑操作，均有对应平台和后端的可复核测试；未验证组合不得宣称支持。
5. 图片至少验证尺寸调整、裁剪和多图合并；音频至少验证裁剪、分段、合并、波形生成与试听；视频至少验证尺寸调整、片段裁剪、合并和播放预览。具体格式与平台范围以实际验证结果为准。
6. 转换/编辑结果明确呈现输出格式、编码参数及可能的有损/无损属性。
7. 导入后创建独立工作副本；编辑、拆分、合并、预览、取消和处理失败均不得修改源文件。工作副本不得使用写入会影响源文件的共享可变存储方式。
8. 预览读取当前编辑状态对应的工作区产物或同一处理任务生成的预览结果，不要求提前覆盖源文件。
9. 导出为新文件与替换源文件是两个明确区分的操作；未经用户明确确认不得执行破坏性替换。
10. 破坏性替换前检测源文件是否被外部修改；发生冲突或无法确认源文件身份时中止自动覆盖并要求用户重新决策。
11. 破坏性替换具备安全替换/回退策略和失败恢复材料；无法提供足够安全保证的平台不得开放替换操作，但仍可导出新文件。
12. 多文件拆分/批量导出有明确输出清单、冲突处理和失败报告；不得将非原子多文件写入宣称为整体原子事务。
13. 异常退出后可以识别未完成工作区，并提供恢复、导出或放弃选择；清理策略不得无条件删除用户可能仍需恢复的未完成工作。
14. 媒体处理受 Core 授权资源访问、资源预算、取消、磁盘空间检查和工作区生命周期管理约束。
15. 未安装或不可用的单一后端不会阻断其他独立媒体能力或普通 ECL/Minecraft 启动。
16. 不会为仅使用单一媒体类别的用户无条件下载全部图片、音频和视频后端。
17. 所有随包或动态分发的后端均完成代码许可、编解码器许可、来源、签名/完整性及平台分发义务审查。
18. 不包含以绕过第三方平台 DRM、访问控制或技术保护措施为目的的专用解密器；不支持 NCM 等平台专有加密格式解密。
19. 不默认上传用户媒体文件、元数据、波形数据或缩略图；任何未来远程处理均须单独披露并取得适当授权。
20. 后端语言和实现方式不会强迫 ECL Core 引入无必要的语言运行时；若引入独立进程或额外运行时，必须有独立安全和部署评审。
