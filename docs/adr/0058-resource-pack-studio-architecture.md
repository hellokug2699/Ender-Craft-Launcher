# ADR 0058: Resource Pack Studio Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-07
- Scope: Resource Pack Studio Addition 的产品与架构边界、资源发现与解析、状态变体预览、渲染资源管理、安全能力复用及兼容性
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0043](0043-minecraft-threat-protection-and-security-analysis.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0012](0012-modpack-archive-extraction-boundary.md)

## 背景

ECL 已有资源包识别与实例资源包管理能力，可以读取资源包元数据并处理 ZIP 归档；但这些能力不等于完整的资源包内容预览。用户希望在不启动 Minecraft、不将资源包安装到实例的情况下，查看资源包中的材质、模型、动画和资源状态变体。

资源包的组织方式并不总是统一。标准 Minecraft 资源包可能使用已知目录、元数据、模型继承和状态定义；其他资源包可能采用自定义目录层级、命名约定、元数据结构或资源关联方式。即使遵循标准格式，不同 Minecraft 版本之间也可能存在格式和语义差异。因此，预览器不能把某一种目录布局或状态属性集合假设为所有资源包的强制结构。

此外，资源包可能包含大量图片、模型和状态组合。若在打开时完整解析、构建并上传所有资源，会造成不必要的 CPU、内存、磁盘和 GPU 开销。预览器还需要处理不可信归档和复杂文件，不能绕过 ECL 已有的安全边界。

Resource Pack Studio 属于可选的专业预览能力。将其解析、模型构建和渲染工作放入主程序，会扩大普通启动器的代码体积、依赖和运行负担，与 ECL 保持 Core 轻量、专业能力按需安装的 Additions 方向不符。

## 决策

### 1. 将 Resource Pack Studio 定位为独立 Feature Addition

建立独立 Addition：

- Name：Resource Pack Studio
- Addition ID：`ecl.resource-pack-studio`
- Type：`Feature`
- Registry Status：`Proposed`
- Implementation：尚未开始
- Release Assets：暂无

Resource Pack Studio 负责资源包内容浏览、视觉预览和资源结构分析。ECL 原生页面可以提供入口、状态展示和未安装提示；专业解析、模型构建、动画处理和预览渲染由 Addition 提供。

该 Addition 不属于 ECL 普通启动、实例管理或游戏启动的必需依赖。未安装、禁用、损坏或不兼容时，不得影响 ECL 主程序及普通游戏启动。

### 2. 明确预览范围，不实现 Minecraft 世界模拟

Resource Pack Studio 是资源包预览与检查工具，不是 Minecraft 客户端、世界编辑器或游戏模拟器。

范围包括：

- 浏览资源包文件和目录；
- 预览图片、材质及透明通道；
- 解析并预览受支持的方块、物品等静态模型；
- 播放受支持的材质动画；
- 根据资源定义展示状态变体；
- 查看资源引用、模型继承和缺失依赖；
- 对照原版资源或其他资源包中的对应资源；
- 展示资源包元数据、解析覆盖情况和分析结果。

预览交互限于资源展示本身，例如旋转、缩放、平移、展示视角切换、动画播放控制、状态选择和资源对照。

明确不包含：

- 放置、破坏或编辑方块；
- 玩家移动、第一人称操作或游戏世界漫游；
- 方块更新、邻居更新、红石信号传播或其他游戏逻辑模拟；
- 建筑场景搭建、投影编辑或世界模拟；
- 为预览而实现完整 Minecraft 客户端或完整游戏渲染管线。

模型预览可以呈现资源定义中声明的几何与视觉状态，但不得将视觉状态展示误称为游戏行为模拟。

### 3. 不假定所有资源包采用同一种组织结构

解析体系必须区分标准格式解析与通用资源发现：

- 对目标 Minecraft 版本中已知的标准资源格式提供一等支持，包括适用的元数据、目录、模型、材质、动画和状态定义。
- 标准格式解析规则必须与目标版本关联；不得把某一版本的规则无条件套用到所有版本。
- 对非标准或自定义组织结构，尽可能通过文件类型、目录、命名、元数据和可识别引用进行资源发现。
- 允许未来通过独立解析适配器扩展对特定自定义格式的支持；适配器不得改变 Core 的基础资源访问与安全边界。
- 保留原始目录结构和文件访问路径。无法建立语义关系时，仍应允许用户查看可安全读取的原始文件。
- 未知结构、未知字段或当前不支持的格式不得仅因解析器不认识就判定为损坏或恶意。

解析结果至少在语义上区分完整解析、部分解析、仅原始资源可读、不支持和确实无效。具体状态编码与 UI 表现由 Feature Spec 和实现规范确定。Unsupported 不等于 Invalid；解析置信度不得被包装成确定结论。

### 4. 状态变体必须从资源定义中发现，不得写死 Minecraft 方块状态表

预览器应能识别标准资源格式中描述的状态属性、取值和视觉映射，并展示这些定义对应的模型、材质、方向或变换。

例如，红石线等具有多个视觉状态的资源，应能够根据目标版本的资源定义发现可用状态并逐项预览，而不是在程序中硬编码 `power=0..15` 或固定的连接形态列表。

约束如下：

- 状态属性及取值来源于资源包及目标版本适用的资源定义。
- 不得假定所有资源都存在相同属性，也不得假定状态组合可以简单笛卡尔积展开。
- 应尊重格式定义中的变体选择、组合规则、模型引用和变换关系。
- 自定义状态结构只有在对应解析适配器能够理解时才提供语义化状态预览；否则保留原始数据并明确标记未支持。
- 状态预览只展示资源定义映射到的视觉结果，不计算状态在游戏中如何产生或传播。

### 5. 采用按需解析与有预算的资源生命周期

预览器不得在打开资源包时默认完整解析所有模型、解码所有图片或将全部纹理上传 GPU。

应遵循以下架构原则：

- 初始阶段优先读取归档目录索引和必要元数据。
- 用户打开资源或请求某组状态时，再解析其直接依赖。
- 模型继承、材质引用和状态映射按需解析，并对循环引用、深度和总工作量设置限制。
- 图片解码、模型构建、动画帧处理和 GPU 资源创建应按实际预览需求进行。
- 对可安全复用的解析结果、解码图片和渲染资源进行有界缓存。
- 工作区关闭、资源替换或缓存淘汰时，及时释放文件句柄、临时数据和 GPU 资源。
- 长时间任务必须支持取消；用户切换资源后，不再需要的任务应能停止或尽快失效。
- 批量缩略图或状态网格生成应受并发数、内存、CPU、GPU 和处理时长预算约束。
- 具体预算阈值由实现阶段通过代表性资源包基准测试确定，不在本 ADR 中虚构固定数值。

不得因资源包条目数或状态组合数量较大，就无条件生成所有预览结果。需要提供渐进加载或有限批次处理的能力。

### 6. 复用 ECL 原版资源和受控资源访问能力

当预览需要未被资源包覆盖的原版材质、模型或其他基准资源时，应优先复用 ECL 已有且版本匹配的本地游戏资源缓存。

- 不得为预览而默认重新下载完整 Minecraft 客户端或重复保存同一份原版资源。
- 只有在确实缺少必要资源且用户发起相关预览时，才考虑通过 ECL 既有下载与资源管理能力获取。
- 目标版本不明确、缓存缺失或版本不匹配时，必须说明预览所使用的资源来源及其不完整性。
- 文件和资源访问遵循 ADR 0055 的 Resource Broker / Document Service 边界；Addition 不得因此获得任意文件系统访问权。
- 原版资源缓存的查找、读取与引用不得绕过 Core 的资源身份和访问控制。

### 7. 复用既有安全中心能力，不在 Addition 内重复建立安全检测系统

资源包是外部输入。Resource Pack Studio 必须在解析前遵循 ECL 既有安全检测与归档处理边界。

- ZIP 炸弹、条目数量、解压尺寸、压缩比、路径安全和其他归档风险检测应复用 ECL 已有的安全能力或由 Core 提供的统一受控能力入口。
- 不得在 Resource Pack Studio 内复制一套独立且可能与 Security Center 不一致的归档安全规则。
- 安全检测能力的调用必须经过 ECL 授权和受控 API；Addition 不得直接调用 Security Center 内部对象或绕过其策略。
- 若现有安全检测尚未提供适合按需读取 ZIP 条目的受控接口，应先由 Core 明确能力边界，再接入预览流程；不得把现有解包工具的存在等同于预览场景已经自动获得完整扫描覆盖。
- 检测通过只表示已完成的检查未发现对应风险，不代表资源包绝对安全。
- 检测拒绝、检测不完整或安全服务不可用时，必须按 ECL 安全策略阻止或限制后续处理，并准确呈现原因；不得静默跳过必要检查。
- 所有解析器仍需实施自身的输入健壮性约束，例如文件尺寸、图像尺寸、JSON 深度、模型继承深度、引用循环、解码工作量和资源预算。安全扫描不能替代解析器的资源消耗防护。

具体安全能力 API、扫描结果模型和权限声明由 Core 与 Security Center 的架构/实现规范确定，本 ADR 不规定未经验证的接口名称或协议字段。

### 8. 通过 Addition Runtime 运行专业解析与渲染工作负载

Resource Pack Studio 的专业解析、模型构建和渲染代码不得加载到 ECL 主进程。

- 通过 ADR 0055 定义的 Addition Runtime、Workspace Host、Native UI Host、IPC 和 Resource Broker 提供运行环境。
- 由于其处理外部归档、图片、JSON 和模型数据，Runtime Policy 应将复杂不可信数据解析风险纳入隔离决策，并评估 Dedicated Workspace Runtime。
- 最终隔离粒度由 ECL Runtime Policy 决定，Addition 不得自行降低隔离要求。
- 进程隔离不等于完整 OS 沙箱；在平台级限制实现并验证前，不得宣称已获得完整沙箱保护。
- Addition 不得通过任意 UI 注入、任意本机代码或不受控图形上下文访问绕过 Native UI Host。
- 渲染实现应使用经 ECL 平台与 Native UI 能力评审允许的机制；具体图形 API、渲染后端和跨平台策略由原型与性能验证决定，本 ADR 不预先锁定技术栈。

### 9. 明确版本兼容与解析能力边界

资源格式和模型语义可能随 Minecraft 版本变化。预览结果必须关联目标 Minecraft 版本及解析器能力。

- 优先从资源包元数据和用户选择中确定目标版本；推断结果必须标记为推断，不得伪装成确定值。
- 对无法确定版本的资源包，可以提供原始资源浏览；语义化模型和状态预览应说明版本不确定带来的限制。
- 对已知版本提供明确的格式支持范围；不支持的格式应标记 Unsupported，而不是默认套用其他版本规则。
- 解析结果应能说明缺失引用、未知字段、部分支持和资源来源。
- 预览器不得承诺与游戏内最终渲染完全一致；目标是对已支持资源语义提供可解释的近似视觉预览。
- 具体支持的 Minecraft 版本、格式覆盖矩阵和回归样本由实现阶段维护。

### 10. 保留原始资源访问与可解释性

语义解析不是访问资源包内容的唯一入口。

用户应能够在安全策略允许的前提下查看原始目录、文件路径、图片、文本/JSON 内容以及解析诊断。解析器必须保留足够的来源信息，使用户能够从预览结果定位到对应文件及引用关系。

不得静默丢弃无法理解的资源，也不得把推断分类、部分解析或未知内容显示为已被完整识别。

## 备选方案

### 方案 A：将解析与渲染直接集成到 ECL Core

可以减少 Addition 与宿主之间的调用边界，但会把专业解析依赖、图形资源和持续维护成本带入主程序，增加普通用户的下载体积和运行负担。与 ECL Core 轻量化及按需扩展方向不符，不采用。

### 方案 B：只做 ZIP 图片查看器

实现简单、资源消耗低，但无法呈现模型、材质引用、动画和状态变体，不能满足资源包视觉预览的主要价值。可作为原始资源浏览的基础能力，但不足以作为完整方案。

### 方案 C：假设所有资源包遵循单一标准目录和固定状态模型

对标准资源包实现较直接，但会错误处理自定义组织结构、版本差异和未知格式，并将“不支持”误判为“无效”。不采用。

### 方案 D：完整模拟 Minecraft 资源与世界运行环境

可能覆盖更多游戏内行为，但需要实现大量游戏逻辑、世界状态和运行时系统，复杂度、资源成本和兼容性负担远超预览需求，也违背本 Addition 的明确范围。不采用。

### 方案 E：独立 Addition、标准解析优先、通用发现兜底、按需视觉预览

将专业能力独立交付；对标准格式提供版本化解析，对非标准结构保留原始资源并尽力发现；按需构建视觉预览和状态变体，并复用 Core 的资源、安全与 Runtime 能力。该方案符合 ECL 的轻量 Core 与可选专业扩展方向，作为当前提议。

## 后果

### 正面影响

- 主程序不承担专业模型解析、动画和渲染依赖，普通启动路径保持轻量。
- 用户无需启动 Minecraft 或安装资源包到实例即可查看支持的资源内容。
- 标准资源包可以获得语义化模型、动画和状态变体预览。
- 非标准资源包不会因目录结构不同而被直接判定为无效，原始资源仍可访问。
- 按需解析和有界缓存降低大型资源包造成的 CPU、内存和 GPU 浪费。
- 安全检测、资源访问和运行时隔离复用 ECL 已有架构边界，避免 Addition 私自建立旁路。
- 预览功能与游戏模拟明确分离，避免范围膨胀为 Minecraft 引擎。

### 代价与风险

- 需要维护版本化的资源格式解析器和测试样本。
- 自定义资源格式无法保证自动获得完整语义预览；需要适配器或退回原始资源查看。
- 模型继承、引用关系和状态组合可能复杂，需要限制解析深度和资源消耗。
- 图形渲染后端、Native UI Host 与 Addition Runtime 的集成需要原型验证。
- 安全中心必须提供适合归档预览场景的受控检测能力；现有归档提取逻辑不能未经验证直接视为完整扫描 API。
- 资源缓存和 GPU 生命周期增加实现与诊断复杂度。
- 不同 Minecraft 版本的资源语义可能导致预览结果与游戏实际渲染存在差异。

## 验收标准

本 ADR 当前为 Proposed。以下为后续实现评审与验收基线，不表示功能已经实现：

- Resource Pack Studio 作为独立 Feature Addition 登记，具有独立版本和发布生命周期。
- 未安装、禁用、损坏或不兼容该 Addition 时，ECL 普通启动、实例管理和游戏启动不受影响。
- 专业解析和渲染业务代码不加载到 ECL 主进程。
- 不启动 Minecraft、不安装资源包到实例，也能浏览安全检查允许访问的资源包内容。
- 支持原始目录与文件访问；未知目录布局或未知字段不会仅因不符合标准解析器预期而被判定为无效。
- 标准格式解析与 Minecraft 目标版本关联；版本不确定时明确标记推断或限制。
- 能够从资源定义中发现并展示受支持的状态变体，不依赖硬编码的红石状态列表或固定属性组合。
- 状态预览展示视觉映射，不执行红石传播、方块更新或其他游戏逻辑。
- 模型预览支持约定范围内的观察交互，但不包含方块放置/破坏、玩家移动、世界漫游或场景搭建。
- 图片、模型、动画和状态预览按需加载；不因打开资源包而默认解码或上传全部资源。
- 解析、缓存、批量缩略图和 GPU 资源具有可配置或经测试确定的资源预算，并支持取消和释放。
- 模型继承循环、引用循环、异常 JSON 深度、超大图片和异常模型数据不会导致无限递归或无界资源消耗。
- 安全检查通过 ECL 受控能力执行；必要检查不可用或结果不完整时，不会静默绕过策略。
- 不在 Addition 内复制独立 ZIP 炸弹/归档安全检测规则。
- 需要原版资源时优先复用目标版本匹配的本地缓存；缺失或不匹配时明确说明。
- 解析结果可追溯到原始文件路径，并区分完整解析、部分解析、仅原始可读、不支持和无效。
- 对标准资源包与至少一组非标准组织结构样本进行测试；不支持内容能够安全回退到原始资源浏览。
- 兼容性、性能、安全和渲染回归有可复核的自动化测试或实验记录。
