# ADR 0034：ECL 自身完整性与可恢复安装架构

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-02
- Scope: ECL Bootstrapper、启动器自身文件完整性、更新事务、故障恢复与本地恢复材料
- Related: [ADR 0016：独立 Bootstrapper 与安全部署边界](0016-independent-bootstrapper-and-safe-deployment-boundaries.md)、[ADR 0024：用户授权的自签名代码证书信任](0024-user-authorized-self-signed-code-signing.md)、[ADR 0025：Installer 首次启动完整性确认向导](0025-installer-first-launch-integrity-confirmation.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)

## 背景

ECL 已经需要对 Minecraft 实例、游戏文件和可选 Additions 进行完整性管理，但启动器自身同样可能被用户误删、第三方软件修改、更新中断或磁盘故障破坏。

如果 ECL 只具备“检查游戏并修复游戏”的能力，而 ECL 自身缺少独立的完整性与恢复路径，那么用户误删一个关键 DLL、更新过程中断电或文件被篡改后，启动器可能直接失去启动和修复能力。这会形成一个基础架构上的单点故障：负责修复其他内容的工具本身无法修复自己。

因此 ECL 需要把自身视为一种需要可验证、可部署、可回滚和可恢复的软件资产。该机制必须与 Bootstrapper 生命周期边界结合，并且不能把修复 ECL 与重置用户 Minecraft 数据混为一谈。

## 决策

### 1. Bootstrapper 作为 ECL 自身完整性检查和恢复的独立入口

ECL 的完整性恢复不得依赖已经损坏的 ECL 主程序本身。Bootstrapper 保持独立的最小职责，至少能够：

- 定位当前 ECL 安装；
- 读取并验证 ECL 安装 manifest；
- 检查关键文件是否存在、内容是否匹配预期；
- 在主程序损坏或缺失时进入 Repair Mode；
- 使用可信的本地恢复材料或发布源恢复 ECL；
- 在恢复成功后启动正确版本的 ECL。

Bootstrapper 不承担完整的 ECL UI，也不应把诊断、游戏启动和其他大型功能重新复制一遍。

### 2. ECL 自身采用 Manifest + Hash + Signature 的完整性模型

每个可恢复的 ECL 版本应有对应的安装 manifest，描述版本、文件路径、文件完整性信息以及必要的组件关系。

关键文件至少应进行内容哈希校验。发布包、关键组件或恢复材料应结合现有代码签名与信任模型进行来源验证。

完整性状态至少需要区分：

- 文件缺失；
- 文件存在但内容不匹配；
- 文件存在且哈希正确但来源/签名不可信；
- 文件完整且可信；
- 当前版本与 manifest 不一致。

不能只用“文件存在”作为完整性判断。

### 3. 完整性检查应优先保证本地可恢复，网络不是正常启动前提

ECL 正常启动不应因为无法访问网络而失败。完整性检查首先验证本地安装，并优先使用已经验证过的本地恢复材料进行修复。

当本地材料不足时，Repair Mode 可以从受信任的发布源重新获取对应版本。下载得到的内容必须在替换前完成完整性和信任验证。

修复源必须遵循 ECL 现有的发布、下载和信任边界，不得因为“这是修复过程”而跳过校验。

### 4. 更新必须采用可回滚的事务式部署

ECL 更新不得采用“先删除旧文件，再直接写入新文件”的不可恢复方式。更新原则上遵循：

1. 下载到临时位置；
2. 验证 manifest、hash 和签名/信任信息；
3. 将新版本准备到 staging 位置；
4. 在可安全替换时执行原子或等价的提交操作；
5. 记录当前活动版本；
6. 启动新版本并确认部署成功；
7. 若提交或启动失败，回滚到最后一个可用版本。

具体文件替换方式可根据 Windows 文件锁和部署环境选择实现，但架构上必须保持“旧版本不会在新版本确认可用前被不可逆地破坏”。

### 5. 支持本地 Recovery Cache，但不把它当作唯一恢复来源

ECL 可以保留经过验证的本地恢复材料、历史版本或必要组件，以便在离线情况下恢复被误删或损坏的文件。

Recovery Cache 应受到空间上限、版本淘汰策略和完整性保护约束，不能无限增长。恢复材料本身也必须验证，不能因为位于本地缓存目录就被视为可信。

如果本地恢复材料不足，系统应明确进入联网修复路径，而不是假装可以离线完成恢复。

### 6. Repair Mode 必须区分“修复 ECL”与“重置用户环境”

ECL 自身损坏时，默认只恢复 ECL 安装所拥有的文件，不删除、不覆盖、不重置用户 Minecraft 数据。

除非用户明确执行其他清理或重置操作，Repair Mode 不得因为修复以下文件而自动处理：

- Minecraft 实例；
- 世界与存档；
- 用户配置；
- Mod、资源包和 Shader；
- 日志与诊断历史；
- 用户下载的数据；
- Additions 的用户数据。

“修复启动器”与“恢复用户环境”必须是两个不同的操作语义。

### 7. 完整性检查、更新和恢复应复用统一的信任边界

ECL 自身完整性机制应与 ADR 0024、ADR 0025 的代码签名、用户授权和首次安装完整性确认机制保持一致，不创建一套绕过现有信任模型的特殊修复通道。

尤其禁止因为文件属于 ECL 自身，就在 Repair Mode 中无条件信任任意下载内容或本地替换文件。

### 8. 普通启动路径必须保持轻量且容错

完整性检查可以在启动前执行，但不应让每次正常启动都进行不必要的大规模全量扫描。架构应允许根据版本、manifest、文件时间/大小等安全元数据判断是否需要进一步验证，并在高风险操作、更新后或检测到异常时进行更完整的检查。

完整性检查失败时应进入明确的 Repair Mode，而不是循环启动失败、反复弹出相同错误或静默覆盖用户文件。

### 9. ECL 的版本结构必须允许“当前版本”和“最后可用版本”同时存在

只要部署模型允许，ECL 应保留一个明确的最后已知可用版本或可恢复状态，使更新失败时能够快速回退。

Bootstrapper 应维护最小的部署状态，例如当前版本、候选版本、上一次启动是否成功以及是否存在待完成的回滚操作。该状态本身也应采用安全写入方式，避免更新中断后进入无法判断当前状态的情况。

### 10. 完整性系统不等同于反病毒系统

该机制的目标是确认 ECL 安装是否符合 ECL 自己的发布预期，并提供可验证的恢复路径；它不是通用恶意软件检测器，也不能声称能够发现所有第三方篡改或系统级攻击。

如果检测到文件与发布 manifest 不符，应报告“完整性异常”，而不是直接断言攻击或恶意软件行为。

## 备选方案

### 方案 A：只校验 Minecraft，不校验 ECL 自身

不采用。会留下启动器自身损坏后的单点故障，用户可能连修复入口都无法使用。

### 方案 B：由 ECL 主程序自己修复自己

不采用。主程序可能正是损坏对象，无法可靠承担最后一道恢复职责。

### 方案 C：每次更新直接覆盖旧版本

不采用。更新过程中断电、磁盘错误或新版本启动失败都可能导致旧版本不可恢复。

### 方案 D：独立 Bootstrapper + Manifest/Hash/Signature + Staging/Rollback + 本地 Recovery Cache

采用。该方案与现有 Bootstrapper、安全部署、代码信任和 Additions 完整性体系兼容，并能覆盖误删、损坏、更新失败和离线恢复等场景。

## 后果

### 正面影响

- 用户误删 ECL DLL 后仍有明确的恢复路径。
- 更新失败不会天然把启动器变成不可启动状态。
- ECL 自身、Minecraft 和 Additions 可以形成统一的完整性治理模型。
- 修复启动器不会默认影响用户实例、存档和配置。
- 本地 Recovery Cache 可以降低对网络修复的依赖。
- Bootstrapper 与主程序职责更清晰，符合现有安全部署边界。

### 代价与限制

- 需要维护 ECL 自身 manifest、版本状态和恢复材料。
- 更新与回滚流程比简单文件覆盖复杂，需要处理 Windows 文件锁、崩溃和断电等情况。
- Recovery Cache 会占用额外磁盘空间。
- 完整性校验不能证明系统绝对安全，只能确认是否符合 ECL 定义的发布状态。
- Bootstrapper 本身成为更高信任级别的组件，因此其代码量、依赖和更新机制必须保持足够小且可审计。

## 验收标准

1. 删除或损坏一个关键 ECL DLL 后，重新启动 ECL 可以被 Bootstrapper 检测并进入 Repair Mode。
2. Repair Mode 可以在不删除用户实例、世界、配置、日志和其他用户数据的情况下恢复 ECL。
3. 恢复得到的文件在进入使用前必须通过 manifest、hash 和适用的签名/信任验证。
4. 模拟更新下载失败、校验失败、替换失败、启动失败和进程中断后，最后一个已知可用版本仍可恢复。
5. 模拟断电/强制终止发生在 staging、提交和首次启动确认附近时，不得产生不可识别的半更新状态。
6. 在无网络环境下，若本地 Recovery Cache 包含完整且可信的恢复材料，关键 ECL 文件可以完成本地恢复。
7. 在无网络且本地恢复材料不足时，ECL 应明确报告无法完成离线修复，而不是使用未经验证的文件继续启动。
8. 完整性异常能够区分缺失、哈希不匹配、来源/签名异常和版本不一致等主要原因。
9. 正常启动路径不会因为 Repair/Recovery 服务不可用而把普通启动变成必然失败；只有检测到实际完整性问题时才进入修复路径。
10. Repair Mode 不会因为 ECL 自身损坏而自动删除或重置 Minecraft 用户环境。
11. Bootstrapper 的恢复流程与现有 ADR 0016、0024、0025 的部署和信任边界一致，不存在绕过验证的特殊修复入口。
12. 在文档和日志中明确记录恢复使用的 ECL 版本、manifest 版本以及恢复来源，便于后续诊断。
