# ADR 0013：用户授权的自签名代码证书信任

- Status: Accepted (implementation pending)
- Date: 2026-11-02
- Scope: Windows 安装、代码签名与更新信任

## 背景

ECL 已有独立的更新签名机制：发布流程使用 RSA-PSS-SHA256 对 `update-manifest.json` 签名，客户端通过公开的 `update-trust.json` 验证签名，再校验更新包及文件的 SHA-256。该机制保护更新内容与更新来源，但它不等同于 Windows Authenticode：Windows 资源管理器、系统安装提示及其他依赖 Authenticode 的工具仍无法据此识别 ECL 的代码签名者。

公开受信任 CA 签发的代码签名证书目前不可作为 ECL 的前置条件。项目维护者没有可用的境外支付途径，因此不能把依赖境外付费服务的证书申请或基础设施作为当前方案的必要条件。

自签名代码证书可以提供稳定的签名身份和文件完整性验证，但默认不会被其他 Windows 设备信任。若安装程序静默导入证书，会在用户不知情的情况下改变系统信任，因此不可接受。另一方面，用户明确知情并主动授权后，可以选择在本机信任 ECL 的特定代码签名证书。

## 决策

1. **采用独立的自签名 Authenticode 代码签名证书作为当前可行方案。** 证书仅用于签署 ECL 发布产物，不将其描述为公开 CA 认证，也不宣称它证明了开发者的现实身份。
2. **证书信任必须由用户明确选择。** 在安装完成后的首次运行或适当的信任设置入口中，向用户解释导入目的、影响范围、管理员权限要求及拒绝后的行为。不得静默导入、不得把导入隐藏在普通安装步骤中，也不得因用户拒绝而阻止 ECL 基本使用。
3. **用户选择信任后，才请求管理员权限并导入证书。** 目标是信任指定的代码签名叶证书，而不是将 ECL 证书安装为系统根 CA。优先评估 `LocalMachine\\TrustedPeople` 对 Authenticode 的适用性；实现前必须通过 Windows 实机验证证书存储位置、链构建、签名验证结果和系统 UI 表现。若 Windows 的实际验证行为要求不同的存储组合，必须在实现前记录其最小权限与信任范围，不得直接退回到无条件安装根证书。
4. **验证证书指纹，而不是只验证 Subject。** ECL 必须固定预期证书指纹/公钥身份；证书显示名称（Subject）、组织字段和文件名都不能作为信任依据。证书导入前展示可核对的指纹，并允许用户从独立的官方发布信息核对。
5. **拒绝导入不影响基本使用。** 用户拒绝、取消 UAC 或没有管理员权限时，ECL 继续使用现有 RSA-PSS 更新 Manifest 验证机制。不得静默降级为“只检查 SHA-256”或跳过签名验证。
6. **保留两套相互独立的验证机制。**
   - Windows Authenticode：用于验证被签署的 Windows 可执行文件及其签名者证书。
   - ECL 更新 Manifest（RSA-PSS-SHA256）：由 ECL Bootstrapper 按 `update-trust.json` 验证更新清单，并由 Manifest 中的 SHA-256 校验发布包及文件。
   两套机制互补，不互相替代。Authenticode 签名不能取代 Manifest 验签；Manifest 验签也不会让 Windows 自动信任代码签名者。
7. **签署发布链中的可执行文件。** 在实现阶段明确签名覆盖范围，至少评估 Installer、ECL.Bootstrapper、ECL 主程序及随包发布的辅助 EXE。签名必须在最终构建产物确定后执行；签名后的文件不得再被修改。
8. **私钥严格留在 private Core / 受保护的发布环境。** 自签名证书及私钥不得进入 public 仓库、客户端、安装包或普通构建产物。public 仓库只保存公开证书/指纹及验证所需的公开信息。私钥应限制访问并备份；泄漏时立即停止使用并执行证书轮换。
9. **提供可撤销和可轮换的信任。** ECL 应允许用户查看当前证书指纹、有效期和信任状态，并提供撤销本机信任的操作。证书轮换时，旧版客户端不得自动信任未知的新证书；必须通过已建立的信任链、更新 Manifest 或再次取得用户明确授权完成迁移。
10. **不把首次安装描述为已获得强身份认证。** 首次下载的 Installer 尚未被用户预先信任的 ECL 证书验证。自签名证书的用户导入只能建立后续本机信任，不能证明首次 Installer 确实来自官方 GitHub Release，也不能抵御 GitHub 账号、仓库权限或发布链被攻陷。用户可通过独立渠道核对证书指纹以降低风险，但这仍依赖首次获取信息的渠道安全。

## 用户交互要求

信任提示至少应清楚说明：

- 这是 ECL 自行生成的代码签名证书，不是公开 CA 对开发者身份的背书；
- 导入后，Windows 将在指定信任范围内信任由该证书签署的代码；
- 导入需要管理员权限（若采用本机级证书存储）；
- 用户可以拒绝，ECL 仍可运行，更新继续使用 ECL 自身的 Manifest 签名验证；
- 用户可以稍后在设置中查看并撤销信任。

不得使用“绝对安全”“Windows 已认证开发者”等误导性文案。信任提示应展示证书指纹，并链接到 public 仓库中的独立证书信息。

## 后果

### 正面影响

- 不依赖境外付费服务即可建立稳定的 ECL 代码签名身份。
- 用户主动授权后，Windows 可以基于本机信任存储验证指定证书签署的文件（具体存储与系统 UI 行为须经实机验证）。
- 后续版本可持续使用同一签名身份；文件被修改后 Authenticode 签名验证将失败。
- 不愿导入证书的用户仍可使用 ECL 现有的更新签名验证链。

### 代价与限制

- 自签名证书不会天然获得其他 Windows 设备的信任；每台设备都需要单独授权。
- 证书导入需要提升权限（本机级信任存储）。
- 这不会自动获得 SmartScreen 声誉，也不保证消除所有“未知发布者”、下载警告或安全软件提示；具体表现取决于 Windows 的信任策略与声誉系统。
- 证书私钥保护、备份、轮换和泄漏响应成为长期维护责任。
- 首次安装仍依赖用户获取安装程序及核对证书信息的渠道安全。

## 实施前验证

在实现安装器 UI 和证书导入逻辑前，必须在干净 Windows 环境完成原型验证：

1. 生成专用自签名代码签名证书，并确认 EKU 包含 Code Signing。
2. 对测试 EXE 签名，验证签名后修改文件会导致 Authenticode 验证失败。
3. 分别测试 `LocalMachine\\TrustedPeople`、必要时的最小附加存储，以及未导入证书时的验证状态；确认不需要将证书加入 Trusted Root。
4. 使用 SignTool（`/pa`）和 Windows API/系统属性页验证签名状态、签名者显示及证书链结果；单独记录 SmartScreen 行为，不将其与 Authenticode 结果混为一谈。
5. 验证非管理员、拒绝 UAC、取消导入、证书已存在、证书指纹不匹配、证书过期、证书轮换和撤销等路径。
6. 验证现有 RSA-PSS Manifest 验签在未导入 Authenticode 证书时仍正常工作，且证书导入失败不会改变更新 fail-closed 行为。
