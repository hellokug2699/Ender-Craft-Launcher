# ADR 0050: ECL UI Architecture and Design System Overhaul

- Decision: Accepted
- Implementation: Not Started
- Date: 2026-11-03
- Scope: ECL 桌面应用的视觉设计系统、主窗口 Shell、主导航与工具入口、页面信息架构、排版、DPI/分辨率适配及所有原生页面的交互呈现
- Related: [ADR 0021：WPF 交互反馈与轻量动效系统](0021-wpf-interaction-and-motion-system.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0040：原版工具集作为独立官方 Addition](0040-vanilla-toolkit-addition.md)、[ADR 0045：原生 Instance Engine 架构与能力边界](0045-native-instance-engine-architecture.md)

## 背景

ECL 当前 UI 的问题不是单纯缺少视觉装饰，而是缺少统一且可执行的设计系统与信息架构约束。现有页面逐渐形成以圆角卡片、密集文本和局部 Tab 为主的呈现方式，导致页面具有演示文稿式的割裂感；功能入口分散在不符合用户工作流程的位置；工具页承担了过多不相干的功能；Regular 字体与小字号文本的可读性不足；不同页面的布局密度、滚动方式和响应行为不一致。

用户最初设想的工具入口是窗口右侧可折叠的工具栏，折叠时显示应用图标，展开后以图标化方式展示工具。该设想尚未成为当前主窗口架构的一部分。与此同时，当前应用虽已声明 PerMonitorV2 DPI awareness，但这不代表所有布局、字体和像素对齐行为均已在多显示器、多缩放比例下得到验证。

继续以单页修补方式处理这些问题，会让各页面继续复制局部规则，最终形成更多不一致。本 ADR 因此将 UI 设计系统、应用 Shell 与信息架构作为一个整体进行重构。

## 决策

### 1. 本 ADR 是 ECL UI 领域的最高优先级约束

本 ADR 经维护者批准后，成为 ECL UI 全局架构与设计系统的最高优先级约束。后续 UI 设计与页面实现必须遵循本 ADR 的全局规则；具体页面布局、交互流程和用户可见行为由已确认的页面规划定义。

当既有 ADR、Feature Spec、页面实现或历史设计与本 ADR 在**全局视觉系统、Application Shell、全局导航职责、工具栏定位、统一排版原则或 DPI/分辨率适配**方面发生冲突时，以本 ADR 为准，并记录需要调整的旧约束。具体页面的布局细节、页面内信息组织和交互流程不属于本条的全局裁决范围，以已确认的页面规划为准。

本优先级不意味着可以违反或削弱其他领域的安全、隐私、数据完整性、权限、业务规则、模块边界和兼容性约束。若 UI 重构触及这些领域，仍必须遵守对应 ADR；不得以视觉一致性为由绕过领域约束。

本 ADR 不自动将其他 ADR 标记为 Superseded。只有当后续决策确实替代某项 ADR 的全部或明确范围时，才按 ADR 生命周期规则更新其状态。

### 1.1 UI 页面规划与领域 ADR 的职责

本 ADR 规定 UI 全局架构与设计系统；已确认的 UI 页面规划（Feature Spec）规定具体页面的产品行为。两者职责不同，不应机械地采用“所有 ADR 永远高于页面规划”的单一排序。

- **页面规划是具体 UI 产品行为的基准**：页面布局、信息组织、功能入口、页面内导航、交互流程、用户可见状态、文案及页面级验收，以对应已确认的页面规划为准。
- **本 ADR 是 UI 全局规则的基准**：Design System、Application Shell、全局导航职责、工具栏定位、统一排版原则及 DPI/分辨率适配，以本 ADR 为准。
- **领域 ADR 是领域架构约束的基准**：安全、隐私、权限、数据完整性、业务规则、领域模型、模块边界、事务、并发、兼容性及持久化语义，继续遵循对应 Accepted ADR。

页面规划可以细化 UI，也可以取代其他 ADR 中已经过时的局部布局、交互或入口假设；不得因此改变该 ADR 中仍然有效的领域架构约束。

### 1.2 冲突裁决

1. 具体页面布局、交互或用户可见行为冲突时，以已确认的页面规划为准，但仍须符合本 ADR 的全局 UI 规则。
2. 页面规划与本 ADR 的全局 Design System、Application Shell 或导航职责冲突时，以本 ADR 为准。确需改变全局规则，必须先修订本 ADR 或另行批准架构决策。
3. 页面规划与其他 Accepted ADR 的安全、权限、数据完整性、事务、模块边界、兼容性或持久化约束冲突时，以对应领域 ADR 为准。
4. Proposed ADR 不构成已批准的强制约束。页面规划不必仅因 Proposed 内容而退让；如涉及潜在安全或数据风险，应先澄清。
5. 跨领域或边界不清的冲突必须交由维护者评审，明确决定后再继续。

### 1.3 旧 UI 假设的取代

当页面规划取代某 ADR 中的旧 UI 描述时，应在页面规划中引用该 ADR，并说明仍需遵守的领域约束；同时在 ADR 中将过时部分标记为历史 UI 假设，注明具体页面行为以对应页面规划为准。不得仅因局部 UI 描述过时，就将仍包含有效领域决策的整份 ADR 标记为 Superseded。

若页面规划实际改变了领域架构决策，必须单独修订或取代对应领域 ADR，不能将其包装成单纯 UI 更新。


### 2. 建立统一 Design System，禁止继续以局部装饰代替设计

ECL 必须建立集中管理、可复用且有明确语义的设计系统，至少覆盖：

- 颜色角色：应用背景、内容表面、浮层、边界、正文、次级文本、强调、状态色；\n- ECL 品牌主题：品牌紫色是固定且不可由用户更改的产品身份色；复选框与开关的开启状态统一使用亮紫色，原有用于品牌强调/选中状态的浅紫色统一迁移为该亮紫色语义令牌；\n- 主题模式：ECL 仅提供固定的品牌主题呈现，不提供浅色模式，也不提供用户自定义主题色；外观设置不得暴露与此决策冲突的主题切换或颜色选择控件；
- 字体角色：页面标题、区块标题、卡片/列表标题、正文、辅助信息、代码与等宽内容；
- 字体字面：Regular、Medium、Bold 必须映射到真实且可验证的字体文件，不得依赖未经验证的合成字重；
- 尺寸与间距：统一定义控件高度、图标尺寸、内容宽度、布局间距和密度等级；
- 控件规范：按钮、输入框、选择器、列表、导航项、菜单、提示、空状态、错误状态和加载状态；
- 图标规范：优先使用一致的图标体系，图标必须具有明确语义，不以 emoji 或随意字符替代常规功能图标；
- 状态与动效：交互反馈、焦点、悬停、按下、禁用、展开/收起和页面切换遵循统一规则。

圆角、阴影和边框只能用于表达层级或交互边界，不得成为页面组织内容的默认方式。页面应优先使用背景层次、留白、排版、分组和明确的导航关系组织内容，避免将每个信息区块都包装成独立卡片。

设计系统应采用语义化资源与组件，不允许各页面长期保留相互冲突的局部字号、颜色、间距和控件模板。确有特殊场景时，必须说明原因并保持语义一致。\n\n品牌主题色规则是全局强制约束：亮紫色作为 ECL 唯一品牌强调色，由 Design System 提供单一语义令牌。复选框和开关的开启状态必须使用该亮紫色；既有界面中用于品牌强调、选中态的浅紫色应统一替换为该亮紫色，不得保留浅紫色作为第二套品牌强调色。颜色角色中具有独立语义的成功、警告、错误、危险等状态色仍按各自语义使用，不应被误替换。品牌紫色不可由用户修改，ECL 不提供浅色模式。外观设置可以管理字体、缩放、语言和动效等偏好，但不得提供主题色选择器或浅色/深色模式切换。具体 RGB/HEX 值应集中定义在 Design System 资源中，不得由页面自行硬编码。

### 3. 重构 Application Shell，建立稳定的主导航、内容区与右侧工具栏

主窗口采用清晰分工的应用 Shell：

- **主导航**负责用户高频、跨实例的主要工作区域，例如主页、实例、下载、内容库和设置。最终入口名称与归属通过信息架构盘点确定。
- **主内容区**负责呈现当前导航目标的完整工作流，不应被工具快捷入口或无关状态卡片挤占。
- **右侧工具栏**是独立于主导航的辅助工具入口，默认折叠为窄图标栏；展开后以图标化网格或列表展示工具图标与名称。工具入口应支持清晰的选中态、键盘访问和可理解的提示。
- 工具栏的展开状态、工具面板与主内容区之间的关系必须明确，不得通过在主内容区内嵌套大型 TabControl 模拟工具导航。
- 工具可以打开独立工作区、侧边面板或上下文面板；具体承载方式应按工具的任务复杂度决定，不强制所有工具采用同一种窗口形式。
- 工具栏不得成为不相关功能的收容所。工具的可发现性、使用频率、上下文依赖和任务规模必须参与入口归属决策。

工具栏必须支持折叠与展开，并在窄窗口、较高 DPI 和键盘导航场景下保持可用。是否记忆用户上次展开状态、是否允许固定展开等行为由后续 Feature Spec 明确。

### 4. 按用户工作流程重建信息架构，功能必须出现在合理位置

所有现有功能必须进行完整盘点，并按用户目标、使用频率、上下文依赖和任务连续性重新归类。不得仅因某功能已经实现在哪个 View 或 ViewModel 中，就继续保留其当前入口位置。

至少遵循以下归属原则：

- 启动、当前实例状态和最近活动属于主页的核心信息，但主页不得退化为功能入口卡片陈列页。
- 实例创建、实例选择、实例配置、Java 运行时选择和实例生命周期管理应围绕实例工作流组织；全局 Java 策略与实例级覆盖必须区分。
- Mod、整合包、资源包、光影包等内容的发现、下载和安装属于内容获取工作流。
- 已安装内容的检查、启用/禁用、依赖与冲突管理应与目标实例上下文紧密关联，避免用户在不明确当前实例的情况下修改内容。
- 日志、启动诊断和性能信息应关联到对应实例或进程会话；全局诊断入口可以提供聚合视图，但不能丢失上下文。
- 世界、存档和多人游戏管理应从对应实例工作区自然进入。
- 账户外观、衣柜、知识浏览、网络诊断、原版工具、扩展提供的工具等，应根据其实际任务定位在主导航、实例工作区或右侧工具栏；不得预先假设所有 Addition 都属于工具。
- 扩展管理与扩展所提供的具体功能必须区分。未安装扩展时可以保留功能入口和安装提示，但不得让普通用户在主工作流中承受扩展管理复杂度。

以上是归类约束而非不可调整的固定菜单清单。最终导航树必须由完整功能盘点和用户任务流确定，并形成可审查的页面/功能映射表。

### 5. 排版以可读性为底线，禁止常规信息使用极小字号

建立全局排版层级，正文与辅助信息必须在常见显示缩放比例下清晰可读。

- 常规正文建议基准为 14px；高密度列表可在经过实测后采用 13px。
- 辅助信息建议 12–13px；11px 仅用于低优先级、短小且非关键的注释。
- 10px 及以下不得用于常规正文、状态说明、路径以外的关键元数据或需要持续阅读的信息。
- 页面标题、区块标题、项目标题、正文和辅助信息之间必须形成稳定的字号与字重层级，不得出现标题很大而普通文字异常细小的断层。
- 颜色对比、字重、行高、文本截断、换行和可访问性必须一并验证；不得只通过增大 FontSize 解决可读性问题。
- Regular、Medium、Bold 字体资源必须逐一验证内部家族名、实际字形和 WPF 加载结果。资源缺失或字面映射错误时应明确失败或回退，不得静默制造不可预测的合成字重。

具体字号可以根据字体实际视觉尺寸和目标 DPI 校准，但不得突破上述可读性底线。

### 6. DPI、分辨率与布局响应属于基础质量要求

DPI awareness 声明只是必要条件，不等同于界面已完成 DPI 适配。ECL 必须同时验证窗口尺寸响应、Per-Monitor DPI、字体渲染、布局取整和跨显示器行为。

- 禁止将固定像素宽度、固定边距或固定列数作为所有窗口尺寸下的唯一布局方案。
- 主要页面必须定义最小可用尺寸与布局收缩策略；空间不足时应调整排列、折叠次要区域或启用适当的滚动，而不是裁切主要内容。
- 避免无意义的多层嵌套 ScrollViewer；每个页面应明确滚动所有权和滚轮路由。
- WPF 布局应检查 UseLayoutRounding、SnapsToDevicePixels、TextFormattingMode、字体 hinting 与缩放行为，按实测结果选择，不得把某个属性视为通用修复。
- 必须覆盖不同 DPI 的多显示器移动场景，窗口从一个缩放比例的显示器移动到另一个显示器后，文字、图标、边界和命中区域仍应保持清晰与正确。
- 响应式布局应基于可用内容尺寸，而不是仅依赖物理屏幕分辨率。

### 7. 先建立系统与 Shell，再重做页面

实施顺序固定为：

1. 盘点现有页面、功能入口、控件资源和 ViewModel 导航关系，建立当前功能映射。
2. 定义 Design System，包括字体验证、语义颜色、字号层级、间距、图标与基础控件。
3. 重构 Application Shell，落地主导航、主内容区和右侧可折叠工具栏。
4. 根据批准的信息架构迁移功能入口，明确主导航、实例上下文、工具和扩展之间的边界。
5. 按统一规范逐页重构主页、实例、下载、内容库、设置及工具承载页面。
6. 完成 DPI、分辨率、键盘访问、滚动和视觉回归验证。

不得在 Shell 与 Design System 尚未稳定时，对所有页面进行一次性大规模视觉改造，以免重复返工。页面迁移期间允许短期兼容旧页面，但新页面不得引入第二套设计规则。

## 备选方案

### 方案 A：继续逐页修补现有 UI

优点是短期改动范围小，能快速处理单个明显问题。

缺点是无法解决导航、工具归属、排版层级和布局行为不一致的问题；每次修补都可能引入新的局部规则，长期返工成本最高。

### 方案 B：只重做主题与控件样式

优点是可以较快改善字体、颜色、圆角和按钮外观。

缺点是无法改变工具页过载、功能入口错位、页面结构割裂和 DPI 下固定布局的问题，容易得到“换皮但仍然难用”的结果。

### 方案 C：整体重构 Design System、Application Shell 与信息架构（采用）

该方案前期需要进行完整盘点和基础设施改造，但能从根本上统一视觉、导航、页面布局与功能归属，并为后续页面重构提供稳定约束。因此采用该方案。

## 后果

### 正面影响

- UI 全局架构与具体页面产品行为各有明确基准；页面规划可取代过时的局部 UI 假设，同时保留领域 ADR 的有效约束。
- 主导航、右侧工具栏和主内容区职责清楚，工具不再挤占主工作流。
- 功能入口围绕用户任务组织，降低功能发现成本。
- 统一排版、字体和控件规范，改善长期可读性与一致性。
- 将 DPI 与窗口响应纳入验收，减少不同设备上的模糊、裁切和布局失衡。
- 新页面可以复用稳定的设计系统，减少重复实现。

### 代价与风险

- 主窗口 Shell 和导航关系调整可能影响现有路由、快捷键、页面生命周期及窗口状态恢复。
- 页面迁移会产生一段时间的新旧 UI 并存，需要控制兼容层和迁移顺序。
- 右侧工具栏会占用横向空间，必须在窄窗口下设计折叠和内容区收缩策略。
- 字体文件、字体回退和 WPF 渲染差异需要在真实 Windows 环境中验证。
- 大规模重构可能影响现有用户习惯，因此不得随意删除功能；功能迁移必须保持可发现性并记录入口变化。
- 不能以 UI 重构为由改变领域服务、持久化格式、安全边界或业务行为；需要改变时应单独评审对应 ADR。

## 验收标准

本 ADR 的 Implementation 只有在以下项目全部完成后才能标记为 Verified：

1. 已建立完整的页面与功能盘点表，所有现有功能都有明确的新归属；不存在因重构而无故丢失的功能。
2. Design System 已覆盖颜色、字体、字号、间距、图标、控件和交互状态；页面不再依赖大量互相冲突的局部样式。
3. Regular、Medium、Bold 字体均已验证实际加载的字面、内部家族名与显示效果；常规正文不存在 10px 及以下字号。\n4. 品牌主题色由单一语义令牌统一提供；复选框与开关开启状态使用亮紫色；不存在用于品牌强调/选中状态的浅紫色分叉；用户无法更改主题色，且 UI 不提供浅色模式。
