# ADR 0065: Official Account Authentication Security Warning and Authorization Verification

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: ECL Microsoft 正版账户登录前的安全提示、外部浏览器身份验证、OAuth 应用身份与权限核对、授权异常处理及令牌接收边界
- Related: [ADR 0037: Account Appearance and Local Wardrobe Architecture](0037-account-appearance-and-local-wardrobe.md)、[ADR 0052: Unified Dialog Engine and Incremental Migration](0052-unified-dialog-engine-and-incremental-migration.md)、[ADR 0053: Additions 能力权限模型与用户授权流程](0053-addition-capability-permission-and-user-consent.md)、[ADR 0055: ECL 混合工作区与原生工具平台架构](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)

## 背景

ECL 的 Microsoft 正版账户登录需要用户在身份提供商页面完成身份验证，并在适用流程中向 ECL 授予访问 Minecraft 服务所需的授权。现有认证流程使用 OAuth Authorization Code + PKCE，并涉及后续 Xbox Live、XSTS 与 Minecraft Services 等服务令牌交换。用户在浏览器中输入的 Microsoft 账户密码，与 ECL 最终接收和管理的 OAuth 授权结果，是两个不同的安全对象。

如果用户无法区分身份验证和应用授权，就可能把“在 Microsoft 页面输入密码”误解为“ECL 会读取密码”，也可能在授权页面未核对应用身份和权限的情况下，向名称相似或伪装成 ECL 的应用授予访问权限。

单纯展示“ECL 不会获取密码”不足以解决应用冒名和过度授权风险。反过来，要求用户仅凭浏览器页面中的显示名称判断应用真伪也不可靠：应用显示名称可以被其他应用仿冒，发布者验证状态也不能单独证明某个 OAuth Client ID 属于 ECL。

因此，ECL 需要在启动正版登录前提供清晰的安全说明，并在应用自身能够验证的范围内检查授权请求与授权结果。用户可见的核对提示是纵深防御的一部分，不能替代 OAuth 协议校验、应用身份固定、最小权限和令牌安全管理。

## 决策

### 1. 在正版登录前提供专用安全提示

ECL 在用户发起 Microsoft 正版账户登录时，应先展示安全提示，说明：

- 身份验证将在系统外部浏览器中完成；
- 用户应只在可信的 Microsoft 官方身份验证页面输入账户密码；
- ECL 不会接收或读取用户在该外部页面输入的密码；
- 身份验证成功后，浏览器可能继续显示应用授权页面，用户需要核对应用身份和申请权限；
- ECL 仍会接收认证流程所必需的授权结果和令牌，并按现有凭据管理机制处理。不得将“ECL 不接触密码”表述成“ECL 不会获得任何账户信息或令牌”。

提示应明确区分“账户身份验证”与“向应用授予权限”两个阶段。不得将 Microsoft 登录页面、ECL 自身的应用授权请求和后续游戏服务令牌交换描述为同一件事。

提示属于登录流程中的安全措施，不是 Security Center 的恶意文件扫描，也不应扩展为通用账户安全中心。

### 2. 使用外部浏览器完成密码验证

Microsoft 账户密码必须由 Microsoft 的外部身份验证页面处理。ECL 不得自行创建密码输入框、嵌入自有页面收集密码、读取浏览器密码字段，或通过其他方式截获用户输入。

ECL 应使用受支持的系统浏览器授权流程。浏览器地址和 TLS 身份由浏览器及身份提供商负责验证；ECL 不得仅凭页面标题、图标、页面文字或用户复制的名称宣称浏览器页面真实可信。

ECL 不得将账户密码写入日志、普通配置、崩溃报告、剪贴板或诊断数据。ECL 也不得要求用户把密码复制回 ECL。

### 3. 在应用内部固定预期 OAuth 应用身份

ECL 必须在受信任的应用配置中维护正版登录所使用的预期 OAuth 应用身份。至少应能明确识别预期的 OAuth Client ID，以及与该客户端配置绑定的身份提供商和适用授权流程。

不得仅凭授权页面显示的应用名称判断是否为 ECL。显示名称属于用户可读提示，不是应用身份的唯一标识，也不得作为 OAuth Client ID 的替代品。

登录流程应使用预期的 Client ID，并在可行范围内验证授权响应与请求上下文的一致性。不得接受由非预期客户端发起、发往非预期身份提供商或不符合预期回调配置的授权结果。

对于 OAuth Authorization Code + PKCE 流程，必须正确使用并验证一次性 state 与 PKCE 关联；适用协议要求的 nonce、issuer、audience、redirect URI、授权码绑定及令牌受众等校验也不得省略。具体校验项目以实际使用的 Microsoft 协议和端点要求为准，不得把某一协议中不存在的字段伪装成通用要求。

OAuth Client ID、身份提供商、回调配置或授权范围发生变更时，应作为认证安全配置变更审查，不得通过普通 UI 文案修改悄悄改变。

### 4. 对授权权限实施最小权限和明确边界

ECL 只申请完成 Microsoft 正版登录、读取必要账户身份以及访问 Minecraft Java Edition 服务所必需的权限。

权限策略应区分：
- **必要权限**：当前认证链实际依赖且经过验证的权限；
- **可选权限**：有明确独立功能需求、可在用户选择后申请的权限；
- **禁止权限**：与 ECL 登录和 Minecraft 服务访问无关，或会授予账户编辑、安全信息管理等高风险能力的权限。

具体权限清单必须以实现阶段核实的 Microsoft 官方文档、实际 OAuth 请求和授权结果为依据；不得在未经验证时编造权限名称，也不得因某个权限出现在历史令牌或其他服务流程中就默认它是必要权限。

授权范围发生变化时，应重新进行安全评审。新增权限不得静默并入既有登录流程。若出现不属于当前允许集合的权限，ECL 应拒绝继续使用该授权结果，并向用户说明原因；不能把“用户点击继续”作为接受程序已判定为越界权限的替代方式。

### 5. 将发布者验证状态作为辅助信息，而非真实性判据

ECL 可以指导用户核对授权页面显示的应用名称和发布者信息。预期显示名称可使用 Ender Craft Launcher，且应明确提示用户警惕额外符号、近似字符或其他冒名文本。

发布者验证状态应使用准确、可理解的标签，并以 Microsoft 当前授权页面实际提供的字段为准。不得将“未验证”误称为“账户未认证”，也不得假定所有 Microsoft 授权流程都会显示相同字段。

发布者验证状态无论显示为已验证或未验证，都不能单独证明 OAuth Client ID 属于 ECL，也不能代替客户端身份固定和授权范围校验。若当前应用尚未完成 Microsoft Publisher Verification，提示可以如实说明这一状态，但不得将其包装成安全保证或将其与用户账户身份验证状态混淆。

### 6. 提供用户可选的名称核对，但不以此代替程序验证

ECL 可以提供文本输入入口，允许用户将授权页面显示的提供者名称复制到 ECL 中进行核对。

核对至少应采用明确的完整字符串比较，并对前后空白、Unicode 相似字符及其他可能造成视觉混淆的输入给出保守处理。不得使用模糊匹配后显示“验证通过”。

名称核对只用于帮助用户发现明显不一致。即使名称完全匹配，也不得向用户承诺应用身份已被密码学验证；名称不匹配时，应建议用户取消授权并检查页面。

ECL 不应为了完成名称核对而读取、注入或控制外部浏览器页面，也不应要求用户复制密码、授权码、访问令牌或刷新令牌。

### 7. 区分可跳过的人工核对与不可跳过的安全校验

用户可以选择跳过手动复制名称的辅助核对，但必须明确看到风险说明，并再次主动确认是否继续。

此选项不得跳过 ECL 自身能够执行的协议校验、OAuth Client ID 固定、回调验证、权限边界检查、令牌校验或其他强制安全检查。程序检测到客户端身份、请求上下文、权限范围或授权结果不符合预期时，必须拒绝该授权结果，不得提供“忽略风险继续”的普通用户选项。

取消登录应始终可用。任何跳过人工核对的行为都不得被记录为用户同意扩大 OAuth 权限或接受协议校验失败。

### 8. 浏览器启动前保留明确的阅读与取消机会

登录提示可以采用短暂倒计时，例如 10 秒，以确保用户有机会阅读安全说明。倒计时仅控制浏览器启动时机，不构成用户授权，也不能自动确认任何应用权限。

如果采用倒计时后自动打开浏览器，必须满足：登录由用户主动发起；倒计时在界面中清楚可见；倒计时期间始终允许取消；取消后不得继续启动浏览器或在后台保留待完成的登录操作。倒计时结束不得自动同意浏览器中的授权请求。

浏览器是否打开、登录是否成功和用户是否在 Microsoft 页面完成授权是不同状态。ECL 不得仅因浏览器已打开就报告登录成功。

### 9. 安全接收和管理授权结果

授权结果应继续交由现有账户认证与凭据管理机制处理，不应由安全提示 UI 自行管理令牌。

ECL 必须验证授权响应与本次登录请求的关联，并在适用范围内验证令牌签发方、受众、有效期、权限范围及后续服务要求。不得将未经验证的授权码、令牌或浏览器回调参数直接视为有效账户会话。

访问令牌、刷新令牌及其他敏感凭据不得出现在日志、普通账户 JSON、剪贴板、UI 调试输出或诊断附件中。凭据存储、刷新、撤销和失效处理继续遵循现有账户服务与安全凭据存储边界。

### 10. 不扩大普通启动的依赖

安全提示和正版登录流程只在用户主动选择 Microsoft 正版登录时触发。它们不得成为 ECL 启动、离线账户使用、第三方认证账户使用或普通 Minecraft 实例启动的前置条件。

Microsoft 身份服务、浏览器、网络或授权页面不可用时，应明确报告正版登录失败或暂不可用，不得阻塞与该登录无关的本地功能。

## 备选方案

### 方案 A：只显示“ECL 不会获取密码”的普通提示

优点是实现简单、对用户打扰较少。

缺点是没有说明身份验证与应用授权的区别，也无法帮助用户发现冒名应用和过度授权。用户容易把密码安全误解为整个授权流程都可信。

不采用作为完整方案。密码隔离说明仍然保留，但必须配合应用身份和权限核对。

### 方案 B：完全依赖用户核对应用显示名称

优点是无需维护客户端身份和权限策略，用户也能直观看到授权页面信息。

缺点是显示名称可以被仿冒，用户容易忽略近似字符或额外符号，且人工核对无法验证 OAuth 请求和令牌上下文。

不采用。名称核对只作为辅助措施。

### 方案 C：完全由程序验证，不向用户展示安全提示

优点是减少登录流程中的用户操作，并能对可机器验证的协议字段实施强制校验。

缺点是用户仍然不了解密码输入位置、应用授权含义和异常页面的处理方式，也无法形成必要的安全认知。

不采用作为完整方案。程序验证与用户教育应当同时存在。

### 方案 D：程序强制验证 + 用户可见安全说明 + 可选人工核对

采用作为提案方向。程序负责其能够可靠验证的客户端身份、请求上下文、权限与令牌边界；用户提示负责解释外部浏览器登录和授权页面风险；名称核对提供额外的人工检查。三者互补，但不相互替代。

## 后果

### 正面影响

- 用户能够理解 ECL 不接触浏览器密码，但仍会接收登录所必需的授权结果和令牌。
- 应用显示名称不再被误当成唯一真实性依据。
- OAuth Client ID、请求上下文和权限范围成为可审查的认证安全边界。
- 用户可以通过人工核对发现明显的冒名页面或权限异常。
- 权限扩张、认证配置变更和异常授权结果有明确处理原则。
- 登录安全提示不会成为离线账户、第三方账户或普通游戏启动的依赖。

### 代价与风险

- 需要维护预期 OAuth 客户端身份、权限清单和协议校验规则，并在认证配置变更时进行审查。
- Microsoft 授权页面可能随账号类型、租户、应用状态和流程变化，用户提示必须避免依赖未经确认的固定页面布局或字段。
- 人工复制名称增加少量登录步骤，但不能保证用户识别所有仿冒页面。
- 发布者验证、应用显示名称和 OAuth Client ID 是不同概念，文案必须避免混淆。
- 认证安全校验需要与现有账户服务集成，不能由弹窗 UI 独立实现或绕过现有凭据管理。

### 待验证事项

- 当前 ECL Microsoft OAuth 应用的 Client ID、发布者信息及 Publisher Verification 实际状态。
- 当前登录流程实际请求的 scope、资源受众及各项权限的必要性。
- 当前 Microsoft 授权页面对应用名称、发布者验证和权限的实际展示字段及不同账户场景差异。
- 当前 OAuth 回调实现对 state、PKCE、redirect URI 及适用令牌字段的校验覆盖。
- 是否存在需要重新同意授权的权限变化，以及如何在不破坏现有账户会话的情况下处理。

## 验收标准

本 ADR 当前为 Proposed。以下是未来实现评审的架构验收方向，不表示功能已经实现：

1. 用户主动发起 Microsoft 正版登录时，ECL 在打开外部浏览器前展示专用安全提示。
2. 提示明确说明密码由外部 Microsoft 身份验证页面处理，ECL 不接触该密码；同时准确说明 ECL 会接收登录所需的授权结果和令牌。
3. ECL 不提供收集 Microsoft 密码的自有输入框，不嵌入或控制密码输入页面。
4. 正版登录使用受信任配置中固定的预期 OAuth Client ID 和身份提供商配置。
5. OAuth 回调能验证本次请求关联性及适用的 PKCE、state、redirect URI、issuer、audience、nonce 等协议要求；不适用的字段不被伪造为通用检查项。
6. 实际请求权限有经过审查的必要权限清单；新增权限需要重新评审，不得静默扩大。
7. 超出允许权限范围或客户端身份不匹配的授权结果会被拒绝，用户不能通过跳过人工核对绕过强制校验。
8. 提示中的应用名称和发布者状态与当前实际 Microsoft 应用配置及授权页面相符；不把发布者验证状态描述成用户账户认证状态。
9. 用户可以进行完整名称人工核对；名称不匹配时得到明确警告，名称匹配也不会被宣称为密码学身份验证。
10. 跳过人工名称核对需要明确风险提示和用户主动确认，但不影响程序强制安全检查。
11. 若使用浏览器启动倒计时，用户可以随时取消；倒计时不会自动同意授权，也不会在取消后继续打开浏览器。
12. 授权结果经现有账户服务验证和处理；敏感令牌不进入普通日志、配置、剪贴板或诊断输出。
13. 浏览器、网络或 Microsoft 服务不可用不会阻塞离线账户、第三方认证账户或普通本地功能。
14. 登录失败、用户取消、授权被拒绝、协议校验失败和令牌交换失败能够被区分，不会错误报告为登录成功。
