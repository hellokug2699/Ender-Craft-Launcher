# ADR 0028：世界种子与生成规则分析功能提议

- Status: Proposed
- Date: 2026-11-02
- Scope: Minecraft 世界种子分析、群系定位、结构预测与生成地图
- Related: ADR 0026（实例工作台的存档、多人游戏与最近访问）、ADR 0027（原生 C# 世界分析与编辑引擎）

## 背景

ADR 0027 规划了基于已生成 Chunk 数据的 Native World Engine，用于读取、分析、渲染和有限编辑现有世界。除此之外，玩家还经常需要在不实际探索世界的情况下，根据世界种子查找生物群系、结构和特定地点。

这类能力与现有世界分析相关，但并不相同：

- **已生成世界分析**回答“磁盘上已经生成的世界实际是什么样子”，数据来源是 Region、Chunk、NBT 和世界资源。
- **世界生成分析**回答“给定种子、Minecraft 版本和生成配置，游戏规则预计会在什么位置生成什么内容”，数据来源是种子、版本规则、维度配置和世界生成算法。

Chunkbase 一类工具证明了种子地图、群系查找和结构定位对玩家具有实际价值。ECL 可以考虑提供同类能力，但不应依赖在线网站、外部 Java 工具或要求用户离开 ECL 才能完成常见查询。

本提议希望在 Native World Engine 的整体技术方向下，增加一个边界独立的世界生成分析子系统。它不应与现有 Chunk 读取器混为一谈，也不意味着 ECL 要在首期重写完整 Minecraft 世界生成器。

## 提议

### 1. 增加独立的 World Generation Analysis 子系统

在 Native World Engine 中规划独立的 World Generation Analysis 能力，负责基于种子和生成配置进行可解释的预测与定位。

建议职责包括：

- 世界种子与 Minecraft 版本配置；
- 维度和世界生成参数；
- 生物群系分布查询与定位；
- 结构候选位置计算；
- 生成地图瓦片与图层；
- 预测结果与现有世界实际 Chunk 数据的对照。

该子系统与 ADR 0027 的已生成世界分析共享地图坐标、渲染模型、群系定义和注册表解析能力，但必须保留不同的数据来源和结果类型。不得把预测结果伪装成从存档中读取的事实。

核心实现继续采用 C# / .NET，不要求 Java Runtime，不通过启动 Minecraft 或执行模组 JAR 代码完成查询。

### 2. 支持种子、版本和维度作为明确输入

世界生成预测至少依赖以下上下文：

- 世界 Seed；
- Minecraft Java Edition 版本；
- 目标维度；
- 可识别的世界类型、生成设置和相关配置；
- 在适用版本中影响生成的 Data Pack 内容。

用户可以手动输入 Seed，也可以在打开现有世界时读取存档中可获得的 Seed 和生成设置。自动读取失败或信息不完整时，应允许用户补充或修正。

ECL 不得仅凭 Seed 推断版本、维度或完整生成配置。输入上下文不完整时，应在结果中明确显示缺失项和预测精度限制。

种子属于用户本地世界数据。默认在本地处理，不上传给 ECL 服务或第三方网站；若未来引入任何在线计算服务，必须另行明确告知并取得用户主动授权。

### 3. 分阶段提供查询能力

建议按可验证程度分阶段实现：

**第一阶段：原版生物群系定位**

- 在指定版本和维度下查询目标生物群系；
- 在地图上展示已知或预测的生物群系分布；
- 支持按名称、命名空间或类别搜索；
- 支持坐标定位、地图平移和缩放；
- 显示 Seed、版本、维度和当前查询条件。

**第二阶段：原版结构定位**

- 查询受支持结构的候选生成位置；
- 支持村庄、要塞、神殿、古代城市等结构类型，具体列表按版本和实现成熟度确定；
- 展示结构候选坐标及其适用版本、维度和限制；
- 区分“算法预测的候选位置”和“已在存档中确认存在的结构”。

**第三阶段：生成地图与实际世界叠加**

- 在同一地图中叠加预测的生物群系/结构与实际已生成 Chunk；
- 对比预测与存档中的实际数据；
- 清楚区分已生成、未生成、预测区域、未知区域和不一致区域；
- 支持从预测位置跳转到现有世界地图或坐标。

上述阶段是建议顺序，不代表所有功能都必须同时交付。每种 Minecraft 版本和结构类型都应单独定义支持状态。

### 4. 版本准确性是核心要求

Minecraft 世界生成算法会随版本变化。生物群系分布、结构放置规则、随机数算法、维度配置和生成参数都可能改变。

因此：

- 预测必须绑定明确的 Minecraft 版本，不能使用“最新规则”代替用户目标版本。
- 版本适配应显式管理算法差异，不得把某个版本的结果无条件套用到其他版本。
- 不支持的版本应显示不支持或有限支持，不得给出看似精确的错误坐标。
- 结构定位应区分候选位置计算与结构实际生成条件；候选点不一定最终生成结构。
- 算法实现应使用公开可验证的规则和测试样本，并记录参考版本与测试依据。
- 需要为 Seed、版本、维度和配置建立回归测试集，避免算法重构后产生静默偏移。

对于结果，应尽可能提供“精确支持”“有限支持”“不支持”等明确状态。不能仅以地图看起来合理作为算法正确的证据。

### 5. 模组和数据包世界采用能力分级，不承诺任意兼容

模组和数据包可能修改生物群系、维度、结构注册、放置规则、随机数调用和完整世界生成流程。

ECL 可以静态解析可识别的数据包定义、注册表和模组资源，并在规则完整且已实现的情况下提供相应预测。但不得为了兼容而执行任意模组 Java 代码，也不得把静态资源解析等同于完整复现模组生成逻辑。

能力应分级表达：

- **原版规则已支持：** 对应版本、维度和查询类型通过测试，可提供受支持范围内的预测。
- **数据驱动规则可解析：** 相关 Data Pack 配置可静态解析，且 ECL 已实现对应规则。
- **部分识别：** 能识别内容 ID 或部分配置，但缺少完整算法；只展示已确认的信息，不输出未经验证的精确预测。
- **动态模组规则不支持：** 依赖模组代码运行时行为或未知算法，明确提示无法预测。

Biomes O' Plenty 等模组可以作为群系识别与配置解析的测试对象，但不能因为成功识别其群系名称就声称能够准确预测其世界生成分布。对模组结构和自定义维度也采用同样原则。

### 6. 预测地图与存档地图必须区分

预测结果不是存档事实。UI 必须让用户能够识别当前查看的是哪种数据：

- **实际世界图层：** 来自现有 Region / Chunk 的真实保存数据。
- **预测生物群系图层：** 根据 Seed 和已支持的世界生成规则计算。
- **预测结构图层：** 根据结构放置算法得到的候选位置。
- **未知/不支持图层：** 因版本、数据包或模组规则缺失而无法可靠判断的区域或内容。

预测图层不得覆盖或篡改实际 Chunk 数据。预测结果与存档不一致时，应保留两者并提示可能原因，例如版本/配置不匹配、算法支持范围不足或存档经过外部修改。

### 7. 性能和计算边界

种子地图可能涉及大范围空间查询。实现应支持按视口或查询区域计算，避免打开页面时无界扫描整个世界。

- 计算应异步执行，可取消，并限制并发与任务资源消耗。
- 对可复用的版本规则、配置解析结果和地图瓦片进行有界缓存。
- 缓存键必须包含 Seed、Minecraft 版本、维度、世界生成配置及算法版本；上下文变化时不得复用不匹配结果。
- 对用户输入坐标、范围和查询密度设置合理边界。
- 不得为了生成预测地图而自动创建或修改真实世界 Chunk。
- 预测计算失败不得影响现有世界浏览、实例管理或游戏启动。

### 8. 与现有世界工作流集成

入口可以放在实例工作台的世界/存档相关页面，并允许用户：

- 从现有世界读取可用 Seed 和版本信息；
- 打开独立的种子地图查询；
- 搜索群系或结构并定位坐标；
- 将预测图层与已生成世界地图叠加；
- 将坐标复制或作为游戏内导航参考。

该功能是辅助分析工具，不应自动修改世界、自动传送玩家或改变游戏规则。任何未来涉及存档写入的能力仍须遵循 ADR 0027 的编辑安全边界。

## 当前不纳入承诺的范围

本提议不意味着：

- ECL 首期实现完整 Minecraft 世界生成器；
- 能够预测任意模组、整合包或数据包的世界生成结果；
- 仅凭 Seed 就能准确还原缺失的世界生成配置；
- 所有结构候选位置都必然生成真实结构；
- 预测地图可以替代已生成世界的实际 Chunk 数据；
- ECL 会执行模组代码或依赖 Java Runtime；
- ECL 必须提供在线地图服务或上传用户 Seed。

## 后果

### 潜在收益

- 玩家可以在 ECL 内查询生物群系和结构位置，无需切换到外部网站。
- 种子预测与已生成世界分析可以共享地图交互、坐标和部分注册表/资源解析能力。
- 预测结果与实际 Chunk 叠加后，可以更方便地探索、核对和规划世界。
- 原版版本支持可以逐步建立明确的算法测试和兼容性边界。

### 成本与风险

- 世界生成算法比读取已生成 Chunk 更复杂，且版本差异显著。
- 结构候选位置和结构实际生成之间存在差异，错误表达会误导玩家。
- 模组和数据包的动态生成逻辑难以通过静态解析完整复现。
- 需要持续维护版本适配、测试样本和算法回归测试。
- 如果过早追求模组全兼容，会显著扩大开发范围并拖延 ADR 0027 的基础能力。

## 实施建议

本 ADR 当前为提议，不要求立即开始完整实现。

建议先完成 ADR 0027 的 Region / NBT / Chunk 基础解析和地图渲染，再独立评估原版世界生成算法的实现范围。随后以一个明确的 Minecraft 版本为起点，先验证生物群系查询，再验证少量结构定位；通过坐标样本和真实世界对照后，才扩大版本与结构覆盖范围。

每次增加一个版本或查询类型，都应有可复现的测试 Seed、预期结果和明确支持声明。模组支持应按实际实现能力逐项开放，不以模组名称识别成功作为生成算法兼容的证明。

## 验收要求

若未来批准实施，至少应满足：

- 核心计算在没有 Java Runtime 的环境中运行。
- Seed、版本、维度和生成配置均明确参与查询上下文。
- 不支持的版本或规则不会静默输出伪精确结果。
- 生物群系查询与结构候选定位具有可复现的测试 Seed 和坐标样本。
- 结构候选位置与实际已确认结构在 UI 和数据模型中明确区分。
- 预测图层与存档实际数据图层分离，能够叠加但不会互相覆盖。
- 未知模组/数据包生成逻辑明确标记为不支持或有限支持。
- 查询任务异步、可取消且有资源上限。
- 默认不上传 Seed，不修改存档，不自动生成 Chunk。
- 预测功能失败不影响 ECL 的常规启动和现有世界管理功能。
