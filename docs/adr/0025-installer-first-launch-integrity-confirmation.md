# ADR 0025：Installer 首次启动完整性确认向导

> 生命周期迁移说明：本次仅拆分决策与实施状态，不改变既有技术决策；尚未开始实施的提案保持原有阶段。

- Decision: Accepted
- Implementation: Not Started
- Date: 2026-11-02
- Scope: Windows Installer 首次启动、安装前完整性验证与用户知情授权

## 背景

ECL 的首次安装存在一个信任引导问题：用户运行 Installer 时，尚未建立对 ECL Authenticode 自签名证书的本机信任。后续的代码签名和更新 Manifest 验证无法反向证明当前正在运行的首次安装程序本身未被替换。

为了让用户在安装前获得一个可自行执行、可理解的完整性检查步骤，Installer 应在首次启动时提供文件 SHA-256 核对向导。用户可以使用 Windows 自带 PowerShell 计算当前 Installer 文件的哈希，并与 ECL 官方 GitHub Release 为该安装资产公布的 SHA-256 值进行比对。

该步骤增加了首次安装的操作成本，但允许用户在建立本机证书信任之前，先检查实际下载的文件是否与官方发布记录中的文件一致。

ECL 希望建立一套范围有限、边界明确、可由个人维护者实际执行的 **ECL-ZeroTrust** 安全模型。这里的 ZeroTrust 不是对绝对安全或完整零信任架构的宣称，而是指 ECL 不应要求用户无条件信任单个程序、单次下载或某个未经核验的状态；每个可由 ECL 控制的关键环节，都应尽可能提供独立验证、明确授权和失败时安全默认行为。

ECL 无法控制 GitHub 平台本身的安全性，也无法保证 GitHub 账号、仓库权限或 Release 发布链永远不会遭到入侵。维护者能做的是尽可能保护账号与凭据（包括启用双因素认证、妥善保管恢复方式、限制账号与仓库权限），并在 ECL 自身可控的范围内增加验证与权限边界。ECL-ZeroTrust 必须诚实声明这些外部信任依赖，不得把它们包装成已经解决的问题。

## 决策

1. **Installer 首次启动必须展示完整性确认向导。** 在执行安装、写入系统位置或导入代码签名证书之前，先展示当前 Installer 的文件名、官方发布版本及 SHA-256 核对说明。该步骤属于首次安装信任引导的一部分，不得静默跳过。
2. **提供使用 Windows PowerShell 计算本地文件哈希的方法。** 向导展示可复制的命令模板：
   ```powershell
   Get-FileHash -LiteralPath "Installer文件完整路径" -Algorithm SHA256
   ```
   用户将路径替换为当前下载的 Installer 实际路径，在 PowerShell 中执行，并读取输出中的 Hash 字段。路径必须使用引号，避免空格等字符造成解析错误。
3. **同时展示官方预期 SHA-256。** 预期值必须对应当前 Installer 的确切 Release 版本和资产文件，来源为 ECL 公有仓库官方 GitHub Release 中发布的资产 SHA-256 摘要或专门的校验和记录。不得拿其他版本、其他架构或其他安装包的哈希进行比较。若官方记录暂时不可用或无法确认资产对应关系，向导不得显示“验证通过”。
4. **由用户确认比对结果。** 向导要求用户将 PowerShell 输出的完整 SHA-256 值与官方预期值逐字符比较，并明确选择是否一致。不得仅凭用户打开了 PowerShell、复制了命令或点击了“下一步”就声称验证成功。
5. **哈希一致后才显示该项检查通过。** 只有用户明确确认两者完全一致，向导才可将“本地文件哈希与官方发布摘要一致”标记为通过，并允许进入后续安装步骤。界面应提供复制官方哈希和重新查看 PowerShell 命令的能力。
6. **允许用户不验证而继续，但必须明确告知风险。** 用户可以选择“跳过并继续”，不得被强制阻止安装；但该路径必须显示显著、明确的安全提示，说明用户尚未核对安装文件与官方发布摘要，无法排除下载损坏、传输替换或文件被篡改等风险。用户必须主动确认后才能继续，不能把跳过设计成默认选项或与正常通过状态混淆。
7. **不得将哈希核对夸大为身份认证或完整的零信任证明。** SHA-256 比对只能证明本地文件与所使用的预期摘要一致。若 GitHub 账号、仓库权限、Release 发布链或摘要来源遭到攻陷，攻击者可能同时替换文件和摘要。因此该步骤是首次安装完整性检查，不是独立的开发者身份认证，也不能替代 Authenticode、ECL RSA-PSS 更新 Manifest 验签或对发布渠道的安全保护。
8. **保留检查证据的可解释性。** 向导应明确展示当前文件名、目标版本、官方摘要来源和完整 SHA-256 值；验证结果应区分“用户确认一致”“用户跳过”“官方摘要不可用”及“用户确认不一致”。不得把用户跳过或摘要不可用记录为验证成功。
9. **发现哈希不一致时采取安全默认行为。** 用户确认本地哈希与官方摘要不一致时，不得继续标记为可信或自动修复该结果。应建议用户取消安装、删除当前文件并从官方 Release 重新下载；如用户仍选择继续，必须走与跳过验证同等级或更高等级的显式风险确认路径，且结果必须记录为未验证/不匹配，绝不可显示为通过。
10. **向导本身不得引入额外提权。** 计算哈希和展示比对信息不需要管理员权限。该向导不得为执行 PowerShell 或读取当前 Installer 路径而申请管理员权限；管理员权限仍受 ADR 0024 的严格边界约束。
11. **将 ECL-ZeroTrust 定义为有限、可执行的项目安全原则。** ECL 应在自身控制范围内尽可能采用显式验证、最小权限、用户知情授权和失败关闭；不得以“零信任”为由承诺消除所有风险，也不得要求个人维护者建立无法持续维护的复杂安全基础设施。

## ECL-ZeroTrust 的范围与边界

ECL-ZeroTrust 是 ECL 项目内部的有限安全模型，不是对 GitHub、Windows、网络服务或用户设备的全面安全背书。其目标是在可控范围内减少隐式信任，并让信任决策可见、可验证、可撤销。

### ECL 可控范围内的承诺

- **发布账号与仓库访问：** 维护者应尽可能启用双因素认证（2FA），妥善保管恢复凭据，限制仓库写入权限和发布权限，并避免不必要的凭据暴露。2FA 能降低账号被盗风险，但不能保证账号绝不会被接管。
- **首次安装：** 提供本 ADR 定义的 Installer SHA-256 人工核对流程；跳过、无法验证和不匹配必须与验证通过明确区分。
- **代码身份：** 按 ADR 0024 使用用户主动授权的 Authenticode 自签名证书建立本机信任，不静默安装证书，不把自签名证书冒充公开 CA 身份背书。
- **更新完整性：** 保留 ECL RSA-PSS-SHA256 Manifest 验签和文件摘要校验；验证失败时不得静默降级或继续安装未经验证的更新。
- **权限边界：** 遵循 ADR 0024 的管理员权限约束。常规启动、更新和游戏管理不得请求管理员权限；提权仅限用户明确发起的首次证书导入等已记录操作。
- **用户知情与可撤销性：** 对信任导入、跳过完整性检查等安全相关选择说明影响；在能力允许时提供查看、撤销和重新授权入口。

### 明确不在 ECL 保证范围内的事项

- GitHub 平台、DNS、互联网路由、下载镜像及其他第三方服务始终安全可用。
- GitHub 账号即使启用 2FA 也绝不会被盗，或仓库权限、组织设置、Token、设备会话永远不会泄漏。
- GitHub Release、文件和校验摘要不会被拥有相应仓库权限的攻击者同时替换。
- 首次安装时展示的 GitHub 摘要天然构成独立于 GitHub 的信任来源。
- 用户设备、Windows、PowerShell、杀毒软件或本地管理员环境没有遭到入侵。
- ECL 的任何验证机制能够抵御所有供应链攻击、零日漏洞或维护者操作失误。

若未来引入独立于 GitHub 账号控制的发布摘要公告渠道或离线签名证明，可以作为增强措施评估；但不得在尚未部署和验证前将其描述为现有安全能力。

## 用户交互要求

向导至少应包含：

- 当前 Installer 文件名和对应的 ECL Release 版本；
- 官方发布的完整 SHA-256 摘要及其来源；
- 可复制的 PowerShell 命令：
  ```powershell
  Get-FileHash -LiteralPath "Installer文件完整路径" -Algorithm SHA256
  ```
- 简明步骤：打开 PowerShell、执行命令、比较 Hash 字段、确认是否完全一致；
- “哈希一致，继续”操作；
- “跳过并继续”操作及明确的安全风险确认；
- 哈希不一致、官方摘要不可用时的警告和取消安装建议。

建议使用清晰、无歧义的状态文案：

- **已确认一致**：用户确认本地 SHA-256 与官方发布摘要逐字符一致。
- **未验证**：用户主动跳过核对。
- **无法验证**：官方摘要缺失、来源不可用或资产对应关系无法确认。
- **不匹配**：用户确认本地 SHA-256 与官方摘要不同。

不得把“未验证”“无法验证”或“不匹配”显示为绿色成功状态，也不得使用“绝对安全”“已证明来自开发者本人”等文案。

## 后果

### 正面影响

- 用户可以在首次安装时独立计算本地文件 SHA-256，不必完全依赖 Installer 自身的自检逻辑。
- 在官方摘要可信且未被同时篡改的前提下，可以发现下载损坏、传输错误或本地文件被替换。
- 用户在导入 Authenticode 信任证书之前，就能获得一次明确的完整性检查机会。
- 用户仍保留跳过能力，不会因为无法使用 PowerShell 或暂时无法访问 GitHub 而被永久阻止安装。
- ECL-ZeroTrust 为项目提供了清晰的安全边界：对自己能控制的部分负责，对外部平台和基础设施的风险如实披露。

### 代价与限制

- 首次安装多出人工操作步骤，对不熟悉 PowerShell 的用户不够友好。
- 用户可能复制错误路径、比较错误版本或误读哈希；向导必须尽可能降低这些操作错误。
- 如果本地文件和预期摘要都来自同一个已被攻陷的发布渠道，哈希匹配无法识别恶意替换。
- 用户跳过后，首次安装文件仍缺少这项额外完整性核对；不能将其视为已验证安装。
- 该检查不提供 SmartScreen 声誉，不保证消除 Windows 下载警告，也不替代代码签名和更新签名验证。
- ECL-ZeroTrust 不意味着零风险；它要求维护者持续执行账号保护、发布权限管理和验证流程，带来一定维护成本。

## 实施前验证

1. 验证 Installer 能准确识别当前正在运行的文件路径、文件名和 Release 版本。
2. 确认官方 SHA-256 摘要与 Release 资产一一对应，并验证摘要读取失败、资产缺失、版本不匹配时不会误报通过。
3. 使用 PowerShell 的 `Get-FileHash -LiteralPath ... -Algorithm SHA256` 对真实安装包进行测试，确认结果与发布流程生成的 SHA-256 一致。
4. 测试本地文件被修改、下载不完整、路径包含空格及非 ASCII 字符等情况。
5. 测试用户确认一致、跳过、确认不一致、官方摘要不可用及取消安装等全部分支，确认状态不会混淆。
6. 确认哈希计算和向导展示不请求管理员权限，并符合 ADR 0024 的提权边界。
7. 确认向导文案准确说明哈希来源的信任限制，不把同一 GitHub 发布渠道中的文件与摘要匹配描述为独立身份认证。
8. 检查 ECL-ZeroTrust 的文档承诺与实际发布、账号保护、签名和更新流程一致；未实现的增强措施必须明确标记为计划或建议，不得写成既有能力。
