# ADR 0035: Offline Minecraft Knowledge Library as an Optional Addition

- Decision: Superseded
- Implementation: N/A
- Date: 2026-11-02
- Scope: ECL 内置知识中心、Minecraft Wiki 类内容、模组资料索引与离线知识包
- Related: [ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0033：本地 Minecraft 全面诊断与知识引擎](0033-local-minecraft-diagnostic-and-knowledge-engine.md)
- Superseded by: [ADR 0036：内置浏览器与 Minecraft 知识访问](0036-embedded-browser-for-minecraft-knowledge.md)

## 状态说明

本 ADR 的原始方向是以可选离线知识包作为 Minecraft 与模组资料的主要交付方式。该方向现由 ADR 0036 的内置浏览器访问方式取代，因此本 ADR 标记为 Superseded。被取代的是“以大规模离线知识包作为主要知识入口”的整体方案，不代表禁止所有离线知识数据。明确授权、范围较小且具有独立价值的离线资料仍可作为补充，并继续遵循本文关于来源、许可、版本和数据质量的约束。

## 背景

ECL 希望为玩家提供不离开启动器即可查阅 Minecraft 相关知识的能力，内容范围不仅包括原版 Minecraft，还必须考虑模组生态。目标体验接近内置百科：玩家可以搜索、浏览条目、查看版本差异与关联内容；在安装相应扩展和知识数据后，即使设备完全离线，也能够继续查阅已安装的内容。

该能力不能简单等同于嵌入一个在线 Wiki 页面。在线网页在断网时不可用，也无法保证内容长期可访问；将第三方 Wiki 或模组资料站整体抓取、镜像并重新分发，又会引入版权许可、网站条款、来源归属、更新负担和服务压力等问题。尤其是模组资料分散在大量作者、项目平台、Wiki 和社区站点中，单一来源无法覆盖整个生态。

本 ADR 记录长期架构方向和不可越过的约束，不代表 ECL 已经取得任何第三方内容的复制、改编或再分发授权，也不承诺短期内实现全量 Minecraft 百科。

## 决策

### 1. 知识中心是 ECL 原生入口，完整内容以可选 Addition 提供

ECL 主程序可以提供原生知识中心入口、搜索界面、分类导航、条目阅读器、收藏与历史记录等基础 UI。知识引擎和大规模知识数据不强制编译进启动器主程序，而是遵循 ADR 0032 的 Additions 体系独立分发。

建议至少区分：

- **Knowledge Engine（Feature Addition）**：负责本地索引查询、条目读取、版本筛选、关联跳转和内容渲染。
- **Knowledge Pack（Data Addition）**：提供具体领域的数据、文章、结构化记录、资源和索引。
- **Source Connector（可选 Feature Addition）**：在用户主动联网时，从允许使用的数据源发现或更新资料；它不是离线阅读的依赖。

知识中心页面在未安装扩展时仍应存在，并说明缺少哪些组件。未安装、未启用或加载失败时，不得影响 ECL 普通启动、实例管理和 Minecraft 启动。

### 2. 安装完成的知识包必须支持真正离线阅读

用户安装某个 Knowledge Pack 后，该知识包声明包含的内容必须在无网络环境下可搜索、可打开和可浏览。离线能力不能只依赖网页缓存、Service Worker、远程图片、在线 API 或原站 iframe。

知识包应携带离线阅读所需的正文、必要资源、元数据和本地索引，或携带可在安装时确定性生成这些内容的文件。条目必须明确标记未随包提供的外部链接、远程媒体或动态功能；不能将在线资源缺失伪装为离线内容完整。

“离线可用”的承诺仅覆盖已成功安装且通过完整性校验的内容范围，不意味着整个 Minecraft 或全部模组知识都已离线收录。

### 3. 内容来源、许可证和再分发权限必须逐项可追溯

ECL 不得假定公开可访问的网页、API、Git 仓库或模组页面就允许复制、改编、缓存或随 ECL 再分发。

每个知识包及其可独立识别的内容来源，应尽可能记录：

- 原始来源、作者或权利人；
- 内容许可证及其版本，或明确记录“授权状态未知 / 不允许再分发”；
- 允许的使用方式，例如链接、引用、缓存、改编、离线分发；
- 必须履行的署名、相同方式共享、非商业或其他条件；
- 内容版本、获取时间、修订记录和维护者；
- 对应的第三方商标、图片、美术、截图及其他媒体权利状态。

许可证不明确、来源无法确认或再分发权限不足的内容，不得进入官方离线知识包。可以在合规前提下只保留条目名称、简短事实性索引和原始链接，但是否允许这些处理仍须依据具体来源规则判断，不能把“只抓元数据”视为自动免责。

对于具有不同许可证的文章、图片、图标、截图、配方数据和其他素材，必须分别判断，不得用页面整体的一个许可证覆盖所有嵌入内容。

### 4. 不以全量爬取第三方 Wiki 或模组站点作为知识库建设策略

ECL 不建立以全站抓取、绕过访问限制、规避反爬机制或持续高频请求为基础的数据采集系统。

第三方站点可以成为资料发现和外部引用来源，但只有在其条款、许可和技术规则允许的范围内，才可以自动获取数据。采集必须遵守速率限制、缓存要求、robots 规则及站点明确规定的访问约束；遇到禁止、拒绝或不明确的情况，应停止自动采集并寻求授权或改用其他来源。

尤其是模组生态，不得将单一中文资料站视为全部模组知识的唯一来源，也不得把全量镜像某个社区站点作为首期目标。

### 5. 模组知识必须作为核心领域，而不是未来可选的边缘补充

知识中心的数据模型必须从一开始支持模组资料，不能只围绕原版 Minecraft 设计后再通过不兼容字段勉强扩展。

模组条目可以包含：

- 项目标识、名称、别名、作者和原始项目主页；
- 支持的 Minecraft 版本与 Loader；
- 文件版本、依赖、前置组件和冲突声明；
- 模组简介、功能分类和经过授权的说明内容；
- 物品、方块、实体、维度、配方、机制等关联条目（在数据可得且授权允许时）；
- 配置说明、常见问题、兼容性经验和已验证故障案例；
- 内容来源、许可证、验证状态和更新时间。

模组项目 ID、Mod ID、平台项目 ID 和文件 ID 必须分开建模。名称不能作为唯一标识；同名模组、分支项目、重制版本、不同平台镜像和同一项目的多个 Loader 构建都必须能够区分。

模组作者和平台拥有各自的权利与发布规则。一个平台允许获取项目元数据，不代表允许复制模组说明、图片、文档或模组本体；知识中心不负责重新分发模组文件。

### 6. 采用分层、按需积累的数据策略

知识库不追求首发即全量覆盖。应先建立可维护的基础索引，再逐步增加经过授权的详细内容。

建议数据层级：

1. **基础索引**：名称、别名、标识、分类、版本范围、作者和外部链接。
2. **结构化知识**：方块、物品、实体、维度、配方、机制、Loader 与依赖关系。
3. **说明性内容**：经过授权或独立撰写的介绍、教程、机制解释和使用说明。
4. **经验与诊断知识**：兼容性、冲突、故障案例及经过验证的解决方法。

可优先从 ECL 用户实际安装的实例和整合包中发现待补充项目，建立本地待收录队列。对于尚未收录的模组，知识中心应明确显示资料缺失或仅有基础索引，不得生成虚构介绍或暗示已经覆盖。

### 7. 离线包应支持独立版本、完整性验证和增量更新

Knowledge Pack 应具有独立版本、内容清单、兼容性声明和完整性信息。安装前应验证清单、文件哈希、包结构、大小限制和来源信任；如果采用签名分发，还应遵循 ADR 0032 的信任模型。

更新可以采用完整包或增量包，但必须保证更新中断、磁盘空间不足、包损坏或版本不兼容时，不会破坏当前可用版本。更新完成前应保留旧版本或可恢复副本，并在验证成功后再切换。

本地索引应与内容版本绑定。安装、更新、卸载和回滚后，索引必须保持一致；索引损坏时应能够重建，且不能因此删除原始知识数据。

### 8. 内容阅读器必须限制主动内容和外部资源

知识包优先使用受控、可离线渲染的内容格式，例如受限 Markdown 和结构化数据。不得默认执行知识包中的任意脚本、动态 HTML、插件代码或外部可执行内容。

图片、字体和其他媒体资源必须随包提供或明确标记为在线资源，并分别校验授权和完整性。阅读器不得在用户仅打开本地条目时隐式请求远程资源；外链跳转应由用户主动触发。

### 9. 与诊断知识库共享基础设施，但保持内容域独立

知识中心可以与 ADR 0033 共享搜索索引技术、版本管理、来源追踪、许可证元数据、包安装和本地缓存基础设施，但百科内容与诊断规则必须是不同的数据域和包类型。

百科文章不得自动成为诊断规则；未经验证的社区经验不得被诊断引擎当作确定性结论。诊断规则需要额外的适用条件、证据模型、置信度和验证流程。

### 10. 普通游戏启动不得依赖知识中心

知识引擎、知识包、搜索索引和来源连接器均为可选能力。缺少、损坏、过期或无法更新知识包时，ECL 仍必须正常启动并运行 Minecraft。

知识中心不得在普通启动路径中自动执行大规模索引、网络爬取或数据库更新。安装和更新应由用户主动发起，或遵循明确可配置的更新策略。

## 备选方案

### 方案 A：直接内嵌在线 Wiki 网页

不作为主要方案。该方式实现成本较低，但依赖网络和原站服务，无法保证离线阅读，也无法提供稳定的本地搜索、版本化内容和跨来源知识关联。可以保留为外部资料入口。

### 方案 B：全量抓取并镜像 Minecraft Wiki 与模组资料站

不采用。内容许可可能限制商业使用、改编或再分发；页面中的图片和嵌入素材可能有独立权利；站点服务条款和访问策略也可能限制自动采集。全量数据体积、请求量、增量同步、页面结构变化和内容纠错都会形成持续维护负担。技术上可抓取不代表法律上可分发，也不代表项目有能力长期维护。

### 方案 C：只做外部链接目录

不作为最终目标。它合规和维护成本较低，但无法满足用户在 ECL 内离线查阅的核心需求，也难以形成统一搜索和版本关联体验。可作为初期的基础功能。

### 方案 D：授权内容 + 自主编写 + 结构化公开数据组成可离线知识包

作为目标方向。它能逐步建立真正可离线使用的知识库，同时把内容授权、来源追踪和维护成本纳入架构。但该方案并不意味着内容获取容易，也不能保证短期覆盖大量模组。

## 后果

### 正面影响

- 用户安装知识包后，可以在无网络环境下访问已收录内容。
- 知识中心不依赖某个第三方 Wiki 永久在线或保持页面结构稳定。
- 原版与模组知识从一开始就在统一数据模型中得到考虑。
- 知识数据可以独立更新、回滚和卸载，不增加普通用户的启动器基础体积。
- 可以逐步积累 ECL 用户实际使用的模组知识，并与本地诊断能力形成关联。
- 来源、许可证和版本信息可追溯，降低未来更换来源或处理侵权请求时的混乱程度。

### 困难、成本与难以执行的因素

本项目必须明确承认：**“安装后离线可读”是可以设计的技术目标，但“获得足够全面、准确、合法且持续更新的 Minecraft 与模组知识”才是主要瓶颈。**

1. **版权与再分发许可难以统一。** Minecraft Wiki 的不同内容、第三方模组 Wiki、模组项目页面、图片和社区文章可能适用不同许可证或权利安排。即使某些文字使用开放许可证，也不能推定页面中的所有图片、商标、美术或引用内容采用相同许可。部分许可可能附带署名、相同方式共享或非商业条件；这些条件可能与 ECL 未来的分发、商业化或内容混编方式冲突。必须逐来源核验，必要时取得明确授权并接受法律审查。此 ADR 不构成法律意见。
2. **模组生态高度分散且变化快。** 模组作者、平台、独立 Wiki、Git 仓库和社区文档分布广泛，命名和标识不统一。模组可能停更、改名、分叉、迁移平台或更换维护者。没有单一数据源能够完整覆盖所有模组。
3. **全量采集的网络和运营成本不可控。** 全站爬取可能产生大量请求、带宽和存储开销，触发站点限流或封禁；页面结构变化还会使采集器持续失效。ECL 不应把维护爬虫和对抗反爬机制变成长期核心工作。
4. **离线数据包可能非常庞大。** 若包含多语言文章、图片、历史版本、模组介绍和关联索引，包体积可能迅速增长。首次下载、增量更新、磁盘占用、解压时间、索引构建和低速网络体验都需要实测，不能预先承诺统一包体大小。
5. **内容新鲜度与离线稳定性存在冲突。** 离线包越稳定，内容越可能落后于模组更新；更新越频繁，用户下载量和维护成本越高。必须定义内容快照、更新频率、过期提示和历史版本策略。
6. **数据质量比数据数量更难保证。** 自动抽取可能丢失表格、模板、脚注、版本条件和页面关系；模组介绍可能过期、重复或由用户生成。错误的依赖、配方或兼容性信息可能误导玩家，甚至影响诊断结论。
7. **多语言维护需要持续投入。** 中文资料丰富度、英文原始资料和其他语言内容并不一致。翻译会产生维护和授权问题，机器翻译也可能错误处理游戏术语、版本差异和技术条件。
8. **知识引擎和阅读器本身也不是零成本。** 需要处理全文搜索、分词、模糊匹配、版本筛选、跨条目链接、索引重建、媒体资源、安全渲染和数据库迁移。中文搜索尤其需要验证分词、同义词、别名和中英文混合检索效果。
9. **需要长期内容维护者。** 即使首批知识包成功建立，仍需有人审核来源、处理授权变化、修正错误、更新过期条目、回应删除请求和维护采集/转换工具。不能假设自动化能够替代所有人工审核。
10. **外部平台策略和接口可能变化。** API 配额、认证要求、许可条款、域名、页面结构和下载策略都可能改变。任何单一外部平台都不应成为离线知识库唯一的上游依赖。

因此，首期不得承诺“全量 Minecraft Wiki”“全量 mcmod.cn”或“所有模组百科”。应以可授权、可维护、可验证的小范围内容集开始，并通过实际包体、请求量、解析质量和人工维护工时决定是否扩大范围。

### 需要在实施前验证的关键假设

- 至少存在一批能够明确授权离线再分发的原版和模组知识内容。
- 选定的结构化数据来源允许 ECL 按计划获取、转换和分发。
- 目标设备能够在可接受的时间和磁盘成本内安装、索引和搜索知识包。
- 知识包增量更新能显著降低相较完整下载的流量和时间。
- 内容模型能够表达不同 Minecraft 版本、Loader、模组分支和多语言条目，而不依赖名称作为唯一身份。
- 项目有可持续的内容审核和维护能力；如果没有，应主动缩小内容范围，而不是降低授权和质量要求。

## 实施顺序建议

1. 先制作数据来源与许可证清单，逐项区分允许链接、引用、缓存、改编和离线再分发的权限。
2. 调研 Minecraft Wiki、mcmod.cn、Modrinth、CurseForge、官方文档及模组作者资料的具体许可和访问规则；不得在调查完成前启用全量采集。
3. 定义知识条目 schema、稳定标识、版本范围、来源和许可证字段。
4. 选择少量明确可再分发的数据，制作离线 Knowledge Pack 原型。
5. 实测压缩体积、安装耗时、索引构建耗时、磁盘占用、搜索质量和离线阅读完整度。
6. 实现 Knowledge Engine 的本地搜索、条目阅读和版本筛选。
7. 实现包清单、哈希校验、原子安装、回滚和索引重建。
8. 增加模组基础索引，优先覆盖 ECL 用户实际安装的项目；对无授权的详细内容只保留合规允许的引用或外链。
9. 建立人工审核、社区贡献、内容纠错、撤回和授权变更处理流程。
10. 只有在来源许可、维护能力和技术成本得到验证后，才扩大语言、模组和历史版本覆盖范围。

## 验收标准

- 知识中心作为 ECL 原生页面存在；未安装知识扩展时能够说明缺失组件，且不影响普通游戏启动。
- 安装一个有效 Knowledge Pack 后，在完全断网状态下仍可搜索和阅读该包声明包含的内容。
- 离线验收不得依赖浏览器缓存、远程 API、原站 iframe 或未随包提供的远程媒体。
- 每个官方离线包具有清单、版本、兼容性声明和完整性校验信息。
- 知识包安装、更新失败或回滚不会破坏当前可用版本；索引可重建。
- 阅读器不执行知识包提供的任意脚本或可执行代码，打开本地条目不会隐式请求远程资源。
- 内容条目能够追溯来源、许可证状态、版本和维护信息；授权不明或不允许再分发的内容不会进入官方离线包。
- 模组数据模型能够区分项目 ID、Mod ID、平台 ID、文件 ID、版本和 Loader，不以显示名称作为唯一键。
- 知识中心能够明确区分完整内容、基础索引、外部链接和未收录内容，不伪造覆盖程度。
- 知识库与 ADR 0033 的诊断规则保持数据域隔离；未经验证的百科内容不能直接成为确定性诊断规则。
- 没有知识扩展、知识包损坏或目录服务不可用时，ECL 普通启动和 Minecraft 启动不受影响。
- 在扩大数据范围前，必须提供真实测量的包体积、安装时间、索引时间、搜索质量和内容维护成本记录。
