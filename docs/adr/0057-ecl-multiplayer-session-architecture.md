## 背景

Minecraft 多人联机对非专业用户而言，通常涉及网络连通性、NAT 穿透、会话建立、房主与加入者状态、游戏版本和模组环境一致性等多个环节。仅提供一个网络隧道开关不足以形成完整的启动器体验；用户需要在 ECL 内完成创建会话、邀请加入、检查联机环境、处理差异、连接、查看状态和结束会话等连续操作。

ECL 希望提供自有的联机产品体验，而不是把一个第三方联机工具简单嵌入界面。此前评估过的方案存在生态或技术栈适配问题；EasyTier 是可考虑的底层网络能力候选，但其具体集成方式、许可、分发、进程生命周期和 API 适配仍需验证。底层网络实现不应决定 ECL 的会话领域模型，也不应成为用户必须理解的产品概念。

产品方向明确不建设公共联机大厅、公开房间目录或依赖广告/流量运营的匹配服务。联机以用户主动发起的私人会话和邀请为中心，避免将 ECL 变成公共服务器平台。

多人联机还会带来模组环境不一致问题。缺少模组、版本不匹配、无法识别的文件和来源不可信是不同问题，不能用一个“模组不一致”提示概括。文件哈希只能确认文件内容是否一致，不能证明文件来源可信；房主提供的恶意文件同样可以具有稳定且一致的 SHA-256。Security Center 可以进行静态检查和风险提示，但不能保证未知模组绝对安全。

## 决策

> 本 ADR 已获批准，确定 ECL Multiplayer 的产品边界、Addition 定位、可替换网络层原则、兼容性与安全职责边界。批准不代表已经实施或发布；具体 UI、会话交互、网络协议、适配器接口及实现策略由本机开发阶段根据兼容性验证自主确定，不由本 ADR 预先限定。EasyTier 仍只是待验证的底层能力候选。

### 1. Multiplayer 作为独立 Feature Addition

1. ECL Multiplayer 以独立 Feature Addition 交付，正式 ID 为 `ecl.multiplayer`。
2. ECL 原生界面负责入口、Addition 缺失提示和安装引导；Addition 负责联机产品流程、会话编排和受控网络能力调用。
3. 未安装、禁用或启动失败时，不得影响 ECL 普通启动、单人游戏、实例管理或其他下载功能。
4. 联机能力不得成为 Minecraft 普通启动链的强制依赖。
5. 联机相关界面和流程必须形成完整的会话体验，不应退化为仅暴露底层网络工具参数的设置页。

### 2. 私人会话优先，不建设公共大厅

1. 产品以用户主动创建或加入的私人会话为中心。
2. 不建设公共房间大厅、公开服务器列表、自动匹配、广告位或依赖流量运营的联机社区。
3. 邀请信息应由房主主动生成并分享；加入者通过邀请信息进入指定会话。
4. 邀请信息应具备足够随机性和可撤销/失效机制；不得将长期固定的网络地址或可枚举会话 ID 当作访问凭据。
5. 不应默认将房间信息、玩家列表、游戏状态或邀请关系上传到 ECL 自有服务。
6. 如果未来确实需要信令或辅助协调服务，必须单独说明其必要性、数据字段、保留时间、访问控制和服务可用性；不得借此演变为公共大厅。

### 3. 自有会话抽象与可替换网络传输层

1. ECL 定义自己的会话领域模型，包括会话身份、房主/加入者角色、生命周期、连接状态、邀请凭据、参与者状态、失败原因和清理状态。
2. 网络传输层通过受控适配接口接入，不得将第三方网络工具的配置对象、内部状态或命令行参数泄漏为 ECL 的公共领域模型。
3. EasyTier 可以作为底层网络能力候选进行原型验证，但在完成许可、分发、平台兼容、进程隔离、升级、故障恢复和安全评估前，不视为已选定依赖。
4. 若采用 EasyTier 或其他网络组件，应明确其版本、许可证、来源、签名/完整性验证、运行权限、进程生命周期和退出清理策略。
5. 网络组件异常退出、连接中断或 Addition 被关闭时，必须释放其创建的网络资源，不得遗留后台进程、虚拟网络配置或系统代理/DNS 修改。
6. 不得未经用户明确授权修改系统网络配置、安装驱动、创建持久化服务或开放不必要的入站端口。
7. 具体 NAT 穿透、Relay、直连优先级和传输协议由实现阶段的技术验证确定；不得在尚未验证前承诺所有网络环境均可连接。

### 4. 会话生命周期与用户可理解的状态

会话至少应覆盖以下生命周期阶段，具体状态名称可在 Feature Spec 中细化：

- 创建准备：选择实例/世界、检查当前实例状态和联机前置条件。
- 网络建立：启动传输适配器并等待网络路径就绪。
- 邀请待加入：生成并展示邀请信息，允许房主撤销或结束邀请。
- 加入验证：解析邀请、验证会话有效性并检查本地环境。
- 环境协调：展示本机与房主的 Minecraft、Loader 和模组差异。
- 连接中：呈现网络连接与 Minecraft 启动/加入进度，避免将隧道已建立误报为游戏已加入。
- 已连接：显示参与者、会话持续状态和必要的连接质量信息。
- 中断/恢复：区分网络暂时中断、房主离线、会话失效、游戏进程退出和本地传输组件故障。
- 结束清理：关闭会话、撤销邀请、停止传输组件并释放资源。

必须区分“网络隧道已建立”“Minecraft 进程已启动”和“玩家已进入同一游戏世界”三个状态。任一状态不得被当作另一状态的充分证明。

### 5. 联机环境兼容性检查

1. 加入会话前，应比较双方 Minecraft 版本、Loader 类型及版本、必要的启动环境信息，以及可获得的模组清单。
2. 检查结果应区分硬性不兼容、可能不兼容和仅供参考的信息；不得把所有差异都直接判定为无法连接。
3. 房主提供的环境清单应被视为不可信输入。解析过程必须限制大小、数量、深度和处理时间，防止恶意清单造成资源耗尽或路径注入。
4. 环境检查不得自动执行房主提供的脚本、安装器、命令或任意文件。
5. 版本信息应明确显示本机版本与房主要求版本；允许用户在受控流程中选择升级/降级或在风险说明后跳过非强制警告。
6. 对可能影响存档、实例或现有模组环境的变更，必须先展示影响并使用 ECL 现有实例事务、快照/恢复与用户确认机制；不得静默覆盖现有实例。
7. 若无法可靠读取对端清单，应明确显示“无法验证”，不得伪造为一致或不一致。

### 6. 模组差异分类与处理

模组差异至少按以下维度分类，最终文案、交互和自动化范围由 Feature Spec 细化：

**A. 本机缺少，且能够识别并找到经过审核的可靠分发来源**

- 显示模组名称、版本、来源和目标文件信息。
- 可以提供自动安装选项，但必须显示来源、版本、许可/分发信息和将要变更的文件。
- 下载资产必须经过来源策略、签名/哈希完整性校验及安全中心允许的检查。
- 不得仅凭房主给出的下载 URL 就认定来源可靠。

**B. 本机缺少，能够识别，但没有可确认的可靠下载来源**

- 明确提示无法提供可信自动下载。
- 建议用户自行寻找可信来源或向房主索取文件，并展示可验证的项目/发布信息（若有）。
- 不得为了“自动补齐”而从任意镜像、网盘或房主提供的未知 URL 下载。

**C. 本机缺少，且无法可靠识别**

- 标记为未知文件/未知模组，不将“未知”直接等同于“恶意”，也不得描述为安全。
- 不提供未经验证的自动下载。
- 提醒用户只从可信渠道获取，并可交由 Security Center 进行静态检查。
- 若安全中心发现达到既定阻断策略的风险，应遵循安全中心的阻断决策；不能由 Multiplayer 自行绕过或覆盖。
- 若检查无法得出结论，应明确显示风险未知，交由用户按安全策略决定是否继续；不得承诺扫描能证明安全。

**D. 双方存在同名模组但版本不匹配**

- 同时显示本机与房主版本，避免只显示一个含糊的“版本冲突”。
- 在有可靠来源且兼容性信息明确时，可提供升级/降级建议。
- 对实例文件的修改必须遵循备份、事务和确认机制。
- 对非强制差异，允许用户在充分提示后跳过；对明确的硬性加载器/协议不兼容，应说明无法保证连接成功，不得虚报兼容。

**E. 本机存在而房主缺少，或双方额外模组不同**

- 区分客户端可选模组、服务端必需模组和双方必须一致的模组；若无法判断模组侧别或必需性，应显示未知，不得自行猜测。
- 说明差异可能导致连接失败、功能缺失或游戏行为不一致。
- 不得自动删除本机模组。任何移除或隔离操作必须由用户明确确认，并提供可恢复方案。

### 7. 安全中心与完整性校验的职责边界

1. Multiplayer 负责发现差异、展示兼容性信息和编排用户确认流程；Security Center 负责文件风险分析、扫描结果和安全策略。
2. Multiplayer 不得自行实现一套与 Security Center 冲突的恶意软件判定或安全等级体系。
3. SHA-256 等哈希用于确认文件内容完整性/一致性，不证明发布者身份、来源可信或文件无恶意行为。
4. 即使房主提供的文件与其清单哈希完全一致，也只能说明收到的文件与清单中的字节摘要一致，不能证明该文件安全。
5. 未知模组不能仅因未知而被断言为恶意，也不能仅因扫描未发现问题而被宣称绝对安全。
6. Security Center 的静态扫描能力存在边界；扫描结果、规则覆盖范围和无法判定的情况必须如实展示。
7. 对达到 ECL 安全策略阻断条件的文件，Multiplayer 不得提供“忽略并强制启动”等绕过入口。对未达到阻断条件但风险未知的情况，按 Security Center 已批准的风险接受流程处理。
8. 不得把房主身份、会话邀请或对端哈希视为可信发布者凭据。

### 8. 会话安全与隐私

1. 邀请凭据必须随机生成、具备有限有效期，并可撤销；凭据不得写入公开日志或遥测。
2. 参与者加入前应明确知道房主可见的身份/连接信息，以及加入会话后会发生的网络连接行为。
3. 会话默认只交换建立连接和必要环境检查所需的数据；不上传本地日志、账户令牌、诊断历史或与联机无关的文件。
4. 不自动上传世界存档、玩家文件或完整实例目录。任何主动文件传输能力必须另行设计、明确展示文件范围、方向、大小和授权。
5. 房主提供的名称、描述、模组清单、版本字段和邀请内容均按不可信数据处理，进行长度限制、编码处理和安全展示。
6. 不将会话数据用于广告、行为分析或用户画像；本地会话历史遵循 ECL 本地数据主权原则。
7. 连接质量检测应低频、按需且有明确边界，不建立持续遥测或隐蔽网络监控。

### 9. 实例与世界数据保护

1. Multiplayer 不得直接绕过 Native Instance Engine 对实例文件进行并发写入。
2. 启动多人游戏前，应确认所选实例与世界的使用状态；同一世界不得因 ECL 会话流程而被两个本地游戏进程无保护地同时写入。
3. 若需要为联机创建临时副本或隔离环境，必须明确数据来源、复制范围、存储位置、清理策略和用户可恢复性。
4. 会话结束不得自动删除用户原始世界、实例或模组。
5. 自动安装/调整模组前应使用现有事务和快照能力，确保失败时可恢复。

### 10. 玩家通讯与社交功能边界

1. ECL Multiplayer 是联机连接与会话管理功能，不是独立的玩家通讯或社交平台。
2. ECL 不提供独立于 Minecraft 游戏内聊天机制之外的玩家即时通讯能力，包括但不限于私聊、群聊、独立文字消息、语音通话和视频通话；也不建设玩家动态、社交关系流或类似社区功能。
3. Minecraft 游戏内聊天仍由 Minecraft 及其游戏/服务端机制负责。ECL 不建立自己的聊天内容中继、托管、消息历史或独立聊天服务，也不应为了提供通讯体验而截获或转发游戏聊天内容。
4. 为创建、邀请、加入、维护和结束联机连接所必需的控制消息，不属于玩家通讯功能。此类消息应限于会话控制所需的最小信息，不得扩展为通用消息通道或借机承载玩家聊天。
5. 邀请分享、加入通知、连接状态和会话生命周期提示属于联机流程，不构成社交功能；不得因此引入常驻好友关系、私信收件箱或公共社交图谱。
6. 本边界限制 ECL 自身提供的产品能力，不限制 Minecraft、服务端、模组或用户自行选择的外部通讯工具。

## 备选方案

### 方案 A：直接嵌入第三方联机工具

优点是可以复用已有网络能力，减少底层网络开发。

缺点是产品体验、会话状态、错误语义和生命周期容易受第三方工具约束；还可能引入不匹配的运行时依赖、许可和 UI 生态问题。即使复用底层组件，也不应直接把第三方工具作为 ECL 的产品层。

### 方案 B：自研完整网络协议和 NAT 穿透体系

优点是协议、生命周期和产品体验完全可控。

缺点是工程投入巨大，需要长期维护 NAT 穿透、Relay、网络兼容和安全协议，不适合作为首期目标。

### 方案 C：ECL 自有会话架构 + 可替换网络传输适配器

由 ECL 自主定义会话、邀请、环境检查、模组差异和 UI；底层通过适配器复用经过验证的网络能力。EasyTier 可作为候选进行验证，但不预先锁定。该方案兼顾产品控制权与网络实现成本，作为拟议方向。

### 方案 D：建设公共联机大厅或匹配服务

优点是用户发现房间和寻找玩家更方便。

缺点是需要长期运营服务、审核、反滥用、内容治理和隐私处理，与私人邀请优先、避免广告和公共平台运营的产品边界冲突。不采用。

## 后果

### 预期收益

- ECL 可以提供从创建到结束的完整私人联机体验，而不是单一网络隧道控制页。
- 会话领域模型独立于底层网络组件，便于替换或升级传输实现。
- 不运营公共大厅，降低服务端、内容审核、广告和滥用治理负担。
- 模组差异被拆分为来源可验证性、识别程度、版本兼容和安全风险，用户能理解每种处理方式。
- 安全中心保持统一的文件风险判断职责，避免 Multiplayer 以哈希或房主身份错误背书。
- 实例事务、快照和本地数据原则可保护用户现有环境。

### 代价与风险

- 需要设计和维护会话状态机、邀请凭据、连接恢复、网络适配器和资源清理。
- 不同 NAT、运营商网络、防火墙和系统权限会造成连接成功率差异；不能承诺所有网络环境均可用。
- EasyTier 或其他候选组件的许可、平台支持、分发、升级和安全性仍需验证。
- Minecraft 模组元数据来源分散，模组侧别和必需性并非总能可靠判断。
- 自动补齐模组涉及第三方下载来源、版本选择、许可证、实例修改和安全扫描，必须限制自动化范围。
- 未知模组无法被静态扫描完全证明安全，产品必须接受“无法判定”的状态并向用户解释。
- 不提供公共大厅意味着用户需要通过外部渠道交换邀请信息。

## 验收标准

以下标准作为架构验收方向；具体数值、UI 文案、逐页交互、协议字段和实现细节由后续 Feature Spec 与本机实现验证确定。

1. Multiplayer 作为独立 Addition 安装/禁用/卸载；缺失或故障不影响普通启动和单人游戏。
2. 不存在公共房间大厅、公开房间目录或自动匹配服务。
3. 会话模型不依赖某个第三方网络组件的内部对象或命令行语义。
4. 底层网络组件可独立启动、监控、停止和清理；异常退出后不遗留未授权系统网络修改或后台进程。
5. 创建、邀请、加入、环境检查、连接、断开、恢复和结束等阶段具有可区分状态与明确错误原因。
6. UI 不把隧道建立误报为 Minecraft 已启动或玩家已加入世界。
7. 加入前可比较 Minecraft、Loader 和可识别的模组环境差异；无法获取的信息明确标记为未知。
8. 模组差异至少覆盖可识别且有可信来源、可识别但无可信来源、无法识别、版本不匹配及本机额外模组等类别。
9. 未经可信来源验证，不会仅凭房主提供的 URL 自动下载模组。
10. 哈希只用于完整性/一致性，不被用于证明来源可信或文件安全。
11. 未知模组的扫描结果不会被表述为绝对安全；达到安全中心阻断策略的文件不能被 Multiplayer 绕过。
12. 任何实例/模组变更均经过用户确认，并使用事务/快照等可恢复机制；不会自动删除原始文件。
13. 不自动上传世界、实例、日志、账户令牌或本地诊断数据；不建设广告或行为分析遥测。
14. 邀请凭据具有随机性、有限有效期和撤销机制，不会写入公开日志。
15. 所有网络组件、许可、平台兼容和分发方式均经过审查后，才可确定正式运行时依赖。
16. ECL 不提供独立玩家私聊、群聊、文字消息、语音/视频通话或社交关系功能；Minecraft 游戏内聊天由 Minecraft 自身机制负责，ECL 不托管或中继聊天内容。
17. 联机邀请、加入通知、连接状态及会话控制消息仅用于建立和管理会话，不形成通用玩家通讯通道。
