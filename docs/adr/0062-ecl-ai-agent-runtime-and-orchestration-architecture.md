# ADR 0062: ECL AI Agent Runtime and Orchestration Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-08
- Scope: ECL AI Agent Runtime Addition 的目标管理、计划与任务编排、受控执行、变更管理、验证恢复及 Core 安全边界
- Related: [ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0045](0045-native-instance-engine-architecture.md)、[ADR 0047](0047-instance-transactions-and-concurrency-control.md)、[ADR 0048](0048-instance-snapshots-and-recovery.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)、[ADR 0061](0061-ecl-ai-conversation-and-capability-architecture.md)

## 背景

ADR 0061 已确定 ECL AI 提供 Chat、Knowledge 和 Diagnostic 三种工作模式，并允许模型通过受控工具获取资料、读取日志与实例资源。随着 AI 能力从单轮问答扩展到多步骤任务，单纯依赖 Prompt 约束和分散的工具调用实现不足以形成一致、可审计的执行边界。

ECL 需要独立的 AI Agent Runtime，统一承载目标管理、计划与任务调度、模型请求、上下文组装、工具调用分发、执行循环、变更集合管理、验证恢复、证据关联、预算控制和安全交互。Agent Runtime 按维护者决定作为独立 Feature Addition 交付，而不是隐藏在 ECL AI 内部，也不是 ECL Core 的推理组件。ECL AI 是面向用户的 AI 产品与工作模式；Agent Runtime 是其Agent 编排与受控执行运行时，二者拥有独立 Addition 身份和生命周期。

模型不是可信执行主体。模型输出可能忽略指令、受到提示注入影响、误判资源范围或提出危险操作。ECL 必须遵循自身安全规范：权限由 Core 强制执行，用户同意由 ECL 授权流程表达，资源访问由宿主中介，文件写入遵循 Instance Engine 的事务、并发与恢复约束。Agent Runtime 不得建立与这些机制竞争的第二套权限体系。

## 决策

### 1. 将 ECL AI Agent Runtime 注册为独立 Feature Addition

- Addition ID：`ecl.ai-agent-runtime`
- Name：ECL AI Agent Runtime
- Type：`Feature`
- Category：AI & Assistance
- Registry Status：`Proposed`
- `ecl.ai` 使用 Agent Runtime 执行模型工具任务时，将 `ecl.ai-agent-runtime` 作为必需 Addition。
- Agent Runtime 不替代 ECL AI，不提供第二套 Chat、Knowledge 或 Diagnostic 产品入口。
- Agent Runtime 不属于 ECL Core，也不进入普通启动或游戏启动链。未安装、禁用、崩溃或版本不兼容时，不得影响 ECL 普通功能。
- Agent Runtime 可供未来经审核的 AI Addition 复用，但不得因此默认授予其他 Addition 工具权限或跨 Addition 直接访问能力。

将 Agent Runtime 登记为 Addition 是为了隔离 AI 执行依赖、生命周期和安全能力，不意味着把 Core 的权限执行器、Resource Broker、Instance Engine 或用户确认权交给扩展。

### 2. 明确 ECL AI、Agent Runtime 与 Core 的职责边界

**ECL AI（`ecl.ai`）负责：** Chat、Knowledge、Diagnostic 工作模式及用户体验；对话、消息、历史、附件和 Shared Knowledge 的产品语义；模型与 Provider 选择、任务意图；向 Agent Runtime 提交最小上下文和任务范围。

**ECL AI Agent Runtime（`ecl.ai-agent-runtime`）负责：** Target、Plan、Task Graph 与 Task Scheduler；模型请求与 System Prompt 编排；Context Assembly 和来源关联；工具目录、请求校验、Tool Dispatcher 与受限执行循环；任务预算、超时、取消和故障收敛；Change Set 与变更审查语义；工具结果、验证结果与证据追踪；向 Core 提交权限请求并呈现 Core 返回的授权结果；将工具副作用限制在已授权范围内。

**ECL Core 负责：** Addition 身份和调用者校验；Capability 声明、授权记录、权限判定、撤销和每次调用的强制执行；可信用户授权入口；Resource Broker、受控网络、凭据代理；文件访问、实例身份、事务、并发、快照和恢复等原生能力。

Agent Runtime 是安全策略的集成与执行编排层，不是安全授权的最终权威。模型、ECL AI 和 Agent Runtime 均不能自行批准权限。


### 2.1 Target：显式任务目标与范围

每个可执行任务必须关联一个明确的 Target。Target 描述“要达成什么”以及“任务涉及哪些对象”，不代表权限授予，也不能替代 Core 的 Capability 与用户授权检查。

- Target 可以指向一个或多个受支持的资源对象，例如 ECL 项目、Minecraft 实例、日志会话、文件集合、配置对象或知识检索范围。
- Target 应表达预期结果、目标对象身份、适用版本/环境、用户给定约束、排除范围和可验证的完成条件；具体字段由实现阶段定义。
- Target 必须具有稳定身份和可追踪的修订历史。目标对象发生变化、身份失效或任务范围实质改变时，关联计划与证据必须重新评估。
- Target 可以由用户直接指定，也可以由模型提出候选；模型推断的目标必须在产生有副作用的操作前得到用户确认或由既有授权明确覆盖。
- Target 的资源范围不得被解释为访问许可。Core 仍须在每次受保护访问时独立执行权限裁决。
- 不明确、相互矛盾或无法解析的 Target 不得被模型自行扩张为更宽范围；应请求澄清或停止相关操作。

### 2.2 Plan：可审查的执行计划

对于需要多步骤执行的任务，Agent Runtime 应维护与 Target 关联的 Plan。Plan 将目标转化为可执行、可验证的工作安排。

- Plan 应包含任务步骤、依赖关系、预期产物、风险/副作用说明、验证条件和已知限制。
- Plan 应区分只读调查、分析、拟议变更、实际写入和验证等不同阶段。
- Plan 必须保留版本。目标、任务依赖、资源范围或验收条件发生实质变化时，应形成新的计划修订，并保留与既有执行记录的关联。
- 模型可以提出或修改计划，但不能借计划变更扩大已授权的资源或操作范围。
- 对影响范围较大、涉及破坏性操作、跨多个资源或明显改变用户原始目标的计划，应在执行前请求用户审查。
- 计划不是执行证据；任务只有在实际执行并满足适用验收条件后才能标记完成。

### 2.3 Task Graph 与 Task Scheduler：依赖驱动的任务调度

Agent Runtime 应将 Plan 表达为可调度的任务集合及其依赖关系。调度器负责确定何时、以何种顺序执行任务，而不是让模型通过连续工具调用隐式控制全部流程。

- 任务应具有稳定身份、所属 Target/Plan、输入输出、依赖、执行状态、资源需求、风险等级和可追溯证据。
- 应支持顺序任务、可并行任务、依赖等待、失败阻断、重试条件、暂停、恢复和取消。
- 只有依赖满足且资源/权限条件有效的任务才能进入可执行状态。
- 并行执行必须检查共享资源冲突。可能同时修改同一文件、实例状态或其他互斥资源的任务应串行化、协调或拒绝并行。
- 调度器不得因任务排队、重试或并行而复用已失效的读取证据或过期授权。
- 重试必须区分幂等操作与可能产生副作用的操作。结果不确定时先检查实际状态，不得盲目重复执行。
- 模型可以提出任务拆分、依赖和优先级建议；调度器负责校验依赖完整性、循环依赖、资源冲突和预算。不能安全调度时应停止并说明原因。
- 任务状态至少应能区分待处理、就绪、执行中、等待用户、阻塞、成功、失败、已取消和结果不确定等语义；具体状态机与持久化格式留给实现设计。
- 调度器必须支持任务级和计划级预算，并受全局预算、并发上限、超时及用户取消约束。

### 2.4 Change Set 与 Changes Review：变更集合及审查入口

Agent Runtime 必须提供统一的变更集合语义，使用户能够集中查看 AI 任务拟议、已执行和验证过的变更。用户可见的 Changes/Changed Files 审查入口是该能力的产品组成部分，不应退化为普通工具日志。

- 每项变更应关联 Target、Plan、Task、原始请求、授权记录、目标资源身份、执行结果和验证证据。
- 至少区分拟议变更、等待授权、已应用、验证通过、验证失败、存在冲突、已恢复/撤销及状态不确定等结果；不能将“生成了 patch”描述为“文件已修改”。
- 对可展示差异的文本资源，应提供修改前后差异及新增、修改、删除等变更类型；对二进制或无法生成文本差异的资源，应提供准确的变更摘要和可用元数据，不得伪造 diff。
- 用户应能够按任务或资源查看变更，并识别变更来源、影响范围、当前状态和验证结果。
- 多个 Task 产生的变更应汇总到对应 Change Set，同时保留每项变更的独立来源和状态；不得把不同任务的变更合并到无法追溯的单一结果。
- 用户审查、批准或拒绝变更必须与实际写入权限区分。Changes 面板中的可见或勾选状态本身不构成 Core 授权；任何写入仍经过既有授权与写入安全门。
- 已应用变更的恢复/撤销必须使用 Core 支持的事务、快照或恢复能力，并再次检查当前资源状态；不得承诺所有变更都可无条件回滚。
- 用户手动修改导致基线变化时，应检测冲突并保留用户的新内容，不得静默覆盖。
- Changes 记录应在任务结束后仍可追溯，具体保留周期和清理策略由数据生命周期设计确定。

### 2.5 Checkpoint、暂停与恢复

Agent Runtime 应支持可恢复的长任务执行，而不是只在单次模型请求期间维持隐式状态。

- 在适当的任务边界记录计划修订、已完成任务、待处理依赖、执行证据、Change Set 状态和必要的恢复信息。
- 用户关闭对话、切换页面或应用重启后，若底层能力支持，应能恢复任务状态；恢复时必须重新验证目标身份、资源状态、权限和授权有效性。
- 不得将内存中的旧上下文、旧读取证据或模型摘要当作当前资源状态。恢复后按需重新读取关键资源。
- 对无法安全恢复的操作，应标记为结果不确定或需要用户介入，不得假装任务从未执行。
- 暂停与恢复不得绕过预算、授权过期、用户取消或资源冲突检查。


### 3. 所有模型工具调用必须经过 Agent Runtime 与 Core 双重边界

模型只能提出结构化工具请求。工具调用必须经过 Agent Runtime 校验和调度，再由 Core 对每次受保护能力调用进行最终授权检查。

- 模型不能直接访问文件系统、进程、凭据、网络套接字或任意宿主对象。
- 模型输出、工具参数、网页、搜索结果、日志、模组说明和附件均是不可信数据，不能成为系统指令或授权凭证。
- Agent Runtime 只能调用明确登记、具备稳定能力声明且当前版本支持的工具。
- 每次调用绑定当前 Addition 身份、任务、会话、工具能力、资源范围和授权状态。
- Core 独立校验调用者、Capability ID、资源目标、操作类型和当前授权；不能信任 Agent Runtime 自报“已批准”。
- 未知工具、未知能力、参数越界、资源范围不匹配、授权过期或权限已撤销时，必须失败关闭。
- 不得通过模型重试、工具别名、路径变体或自动降级绕过拒绝结果。

Agent Runtime 可以维护执行策略和预算，但不得复制一套能够独立授予宿主资源访问权的权限数据库。

### 4. 用户授权必须发生在受保护操作之前

Agent Runtime 必须直接集成 ADR 0053 的能力声明、用户授权、宿主授予和运行时强制执行模型。用户确认不是模型请求的一部分，而是由 ECL Core 控制的独立授权决策。

授权请求应向用户说明发起主体、准确资源或范围、操作类型、用途、关联任务、授权范围，以及读取内容是否会发送给远程 Provider。用户拒绝、取消、授权超时或授权状态不明确时，不得执行对应操作。

授权必须限定资源、操作和适用范围。新增目标、操作类型或数据范围时重新评估，必要时重新请求授权。仍在有效范围内的授权可以按 ADR 0053 复用，避免同一任务内重复打扰；但只读授权不得升级为写入授权，单实例授权不得扩展为全局文件系统授权。

### 5. 明确区分读取、远程传输与文件修改

Agent Runtime 必须区分目录枚举、文件读取、远程传输、文件创建、修改/覆盖、删除/移动/重命名和批量操作，不得使用笼统的“访问文件”权限覆盖全部行为。

读取授权不自动包含远程上传授权。配置远程 Provider 或 API Key 不代表允许上传完整目录、全部日志、聊天历史或其他实例数据。远程请求遵循 ADR 0061 的数据最小化和 Request Inspector 要求。

模型请求修改文件时，Agent Runtime 必须将拟执行操作转化为用户可理解的变更说明，并在写入前取得适用的明确授权。应展示目标文件、操作性质、任务目的和可识别的变更范围；能够安全生成差异时应提供差异预览。无法准确说明影响范围的操作不得以宽泛描述请求批准。

### 6. 文件状态追踪必须依赖 Core 原生资源与事务机制

Agent Runtime 必须集成 Core 的 Resource Broker、Instance Engine、事务、并发控制和快照/恢复能力；不得绕过这些设施直接写入实例目录。

对于获准的文件修改：
- 修改前记录可用的目标基线状态，例如规范化资源标识、文件存在状态、大小、修改时间和内容哈希；
- 真正写入前重新检查目标，识别授权后发生的外部修改、替换或路径解析变化；
- 检测到状态冲突时暂停，不得覆盖用户或其他进程的新变更；继续执行必须重新取得适用授权；
- 写入通过 Core 支持的事务或受控写入能力执行；
- 完成后记录实际结果和新的文件状态，并关联原始请求、用户授权与执行记录；
- 在适用情况下使用 Instance Engine 的事务恢复材料或快照能力。

状态追踪用于证明执行前后发生了什么，不等于自动回滚、备份保证或完整防篡改审计。若 Core 无法提供所需保护，Agent Runtime 必须拒绝相应高风险操作或明确限制能力。

路径检查必须考虑规范化、路径穿越、符号链接/重解析点和检查后目标被替换等风险。资源标识与最终操作目标必须由 Core 在实际访问边界重新验证，不能只依赖 Agent Runtime 的字符串路径检查。


### 6.1 Read-Before-Write、状态一致性与读取覆盖充分性

文件修改必须同时满足读取先行、读取状态一致和读取覆盖充分三个条件。三者是 Core 写入边界上的强制安全条件，不是仅依赖 System Prompt 或模型自我承诺的行为规范。

**Read-Before-Write Enforcement：**
- 每次文件写入必须有与当前任务、会话、目标资源和操作范围关联的有效读取证据。模型不能仅凭记忆、历史摘要、旧对话或其他文件的内容修改目标文件。
- 没有读取证据时，Core 必须拒绝写入并要求先读取目标文件。
- 读取证据至少应能关联规范化资源身份、实际读取内容或版本标识、读取时文件状态、任务/会话、拟写入范围及操作类型。具体证据格式由实现阶段确定。

**Read-State Consistency：**
- 读取后若目标文件内容、身份或相关状态发生变化，原读取证据立即失效；基于旧内容生成的修改结果也必须废弃。
- Agent Runtime 必须重新读取当前文件，并基于新读取结果重新分析、重新生成修改，不得直接重放旧 patch、旧替换文本或旧决策。
- 在真正提交写入时，Core 必须在实际资源访问边界再次验证目标状态，并确保验证与写入之间不存在可被利用的竞态。若无法保证，应拒绝写入或使用 Core 提供的原子事务机制。
- 不得提供忽略冲突、强制覆盖、沿用旧读取结果等绕过路径。

**Read-Coverage Sufficiency（Incomplete Context Rejection）：**
- 读取部分内容本身不构成拒绝写入的理由；关键是实际读取证据是否覆盖了本次修改所需的上下文。
- Agent Runtime 必须识别本次修改目标及其可识别的关联约束，并基于实际读取记录判断覆盖是否充分。仅由模型声称“已经读够”不能作为充分性证明。
- 当目标范围、关联定义、调用点、配置关系、文件结构约束或其他必要上下文尚未读取，且现有证据不足以排除对修改正确性有实质影响时，必须拒绝写入并要求补充读取。
- 补充读取可以是目标区间、相邻上下文、相关定义/引用、结构信息或完整文件；不得把“读取不完整”机械等同于“必须读取整个文件”。
- 对于跨文件或跨模块影响，Agent Runtime 应在可用工具能力范围内扩展检查相关依赖和调用关系。若无法可靠识别或验证必要关联，必须扩大读取范围；仍无法建立足够上下文时，停止修改并说明限制。
- 读取范围应与任务风险和修改性质相称。局部、边界清晰的修改可以使用定向读取；结构性修改、全局重构、格式迁移、整体替换或影响范围不明确的修改通常需要结构性检查或完整读取。
- Agent Runtime 应优先使用低成本方式建立足够上下文，避免为局部修改无差别读取超大文件；但不得为了节省 Token 而降低安全覆盖要求。结构摘要、索引或搜索结果只能作为定位和补充证据，不能冒充目标内容已被完整读取。
- 读取证据应具有明确生命周期，并在任务结束、授权撤销、目标状态变化或资源身份变化时失效；不得跨任务无限复用。

**读取策略与失败提示：**

实现可以采用按需扩展的读取策略，而不要求固定的读取等级或固定工具协议：
1. 定向读取：读取修改目标、必要的邻近上下文及已识别的直接关联内容。
2. 结构性读取：在局部边界不足以判断影响时，读取文件结构、符号/章节关系、相关定义与引用，并按需展开。
3. 完整读取：在整体重构、全文件转换、全局一致性修改，或无法通过局部与结构性证据建立充分覆盖时读取完整文件。

上述策略是成本与覆盖范围的指导，不是对具体实现的强制分级接口。Agent Runtime 应按需逐步扩大读取范围，并在上下文充分后停止扩展。

当拒绝写入时，错误应说明缺少哪类前置条件，例如：
- `Cannot edit config.json, read the file, then edit.`
- `Cannot edit config.json, file has changed, read the file, then edit.`
- `Cannot edit config.json, read coverage is insufficient, read the required context, then edit.`
- `File verified. Edit permitted.`

最后一条仅表示读取与状态前置条件通过，不代表用户授权、Capability 检查或其他写入安全检查已自动通过。读取覆盖充分也不等于模型结论必然正确。

### 7. 工具执行受预算、取消和故障策略约束

Agent Runtime 应对每个任务维护可审查的执行边界，包括最大工具调用次数、循环深度、耗时、并发任务、响应体积和资源预算。具体阈值由实现阶段依据模型、工具和宿主能力验证确定。

- 模型不能无限循环调用工具。
- 工具超时、取消或失败后，不得自动扩大权限或无限重试。
- 用户取消任务时，Agent Runtime 应停止后续模型请求和新工具调用，并通过 Core 对正在执行的可取消操作发出取消请求。
- 对无法安全中断的事务操作，由 Core 决定完成、回滚或进入可恢复状态；Agent Runtime 不得伪称已取消或已回滚。
- 工具结果关联任务和来源，避免不同对话、任务或实例的证据串用。
- Agent Runtime 崩溃或失去 Core 授权状态时，后续受保护操作必须停止。


### 7.1 Execution Feedback、Self-Correction 与 Verification

Agent Runtime 必须为多步骤工具任务提供可观察、可反馈、可验证的执行闭环。工具调用成功只表示该工具操作按其契约完成，不代表更高层任务目标已经实现，也不代表修改正确。

**Execution Feedback：**
- 每次工具调用必须向模型返回真实执行结果，包括成功、失败、部分完成、取消、超时和结果不确定等状态；不得将异常或不确定状态伪装成成功。
- 在可获得时，反馈应包含结构化错误类别、诊断信息、资源/文件位置、相关输出和可追溯的执行标识。
- 编译器、解释器、测试运行器、格式检查器和其他验证工具的输出均作为执行证据返回模型，并保留其来源与适用环境。
- 工具输出和诊断内容是不可信输入，不能覆盖 System Prompt、改变权限或直接触发未授权操作。

**Error Classification 与 Diagnostic Context：**
- Agent Runtime 应尽可能区分语法/解析错误、类型或编译错误、测试失败、运行时错误、环境/依赖错误、权限拒绝、资源冲突、超时和基础设施故障。
- 错误分类应保留原始诊断，不得只依赖模型推断；无法可靠分类时标记为未知或未分类，不得伪造确定性。
- Agent Runtime 可以提供错误位置、相关上下文和定位线索，但不得把未经读取验证的猜测当作文件事实。
- 当诊断指向文件内容时，后续修复仍必须遵守 Read-Before-Write、Read-State Consistency 和 Read-Coverage Sufficiency；验证器给出的行号或片段不能自动替代有效读取证据。

**Self-Correction Loop：**
- Agent Runtime 应允许模型根据工具反馈分析失败原因、提出修正方案并发起下一轮受控工具调用。
- 修正操作仍受原有 Capability、用户授权、资源范围、读取证据、事务和写入前检查约束。验证失败不得自动扩大权限、扩大资源范围或推定用户同意。
- 如果修正需要超出原授权范围的操作，必须重新进入 Core 授权流程；用户拒绝或授权不可用时停止。
- 对文件修改引起的失败，模型必须基于当前文件状态重新读取并生成新的修改，不得盲目重放上一次写入内容。
- Agent Runtime 必须限制自动修正轮数、工具调用次数、总耗时和资源预算。达到上限、重复相同失败、错误原因不明或无法安全恢复时，应停止循环并向用户报告。
- 取消、超时、部分执行或结果不确定时，Agent Runtime 必须先确认可观察的实际状态，再决定是否继续；不得假定操作未发生而重复执行可能产生副作用的操作。

**Verification 与 Honest Completion：**
- 任务完成状态必须基于实际执行和验证证据，而不是模型的主观判断或工具调用意图。
- Agent Runtime 应区分“工具操作成功”“文件已写入”“静态/语法检查通过”“编译通过”“指定测试通过”和“目标应用实际运行验证通过”等不同证据等级。
- 验证范围必须明确，包括使用的工具、目标、版本/环境、执行结果和未覆盖部分。某一编译目标或测试集通过，不得表述为整个项目或应用已完全验证。
- 未执行的检查必须标记为未执行；不可用的验证器必须标记为不可用；部分通过、跳过和失败必须如实呈现。
- 模型不得将写入成功等同于任务成功，也不得声称已验证未实际运行或检查的目标环境。
- 验证失败时，Agent Runtime 应将诊断反馈给模型进入受限修正循环，或在无法安全继续时明确结束为失败/未完成，而不是静默忽略。

上述闭环不保证模型必然找到正确修复，也不要求每次普通工具调用都执行编译或测试。验证深度应依据任务性质、可用工具和风险选择；但凡对外声称某项验证已通过，必须存在对应的实际执行证据。


### 8. System Prompt 强制应用，但不构成权限

Agent Runtime 必须确保每次模型推理请求使用 ADR 0061 定义的适用 ECL System Prompt，并追溯实际使用的 Prompt 版本和组成。不得静默省略、绕过或替换 Prompt；后端无法可靠传递系统指令时应标记不兼容或能力受限，不得无 Prompt 降级。

工具结果、网页、日志、附件和模型生成内容不得提升为 System Prompt 或宿主授权。Prompt 不能批准权限、扩大资源范围或代替 Core 检查。用户应能查看实际生效的 ECL 控制指令，不得暗中追加未披露的 ECL 行为指令。

### 9. 保持 Addition 隔离与宿主资源中介

Agent Runtime 与 ECL AI、其他 Addition 之间遵循 ADR 0055 的隔离约束。不得通过进程内共享对象、任意 IPC 或直接访问彼此内部实现绕过宿主边界。Addition 间协作必须经过 Core 受控机制；Agent Runtime 不向其他 Addition 暴露 Core 权限令牌、原始凭据或可转授的宿主句柄。

进程隔离不等于完整 OS 沙箱，也不等于 GPU 沙箱。本 ADR 不宣称 Agent Runtime 已获得操作系统级安全隔离。具体进程布局由实现阶段验证，但不能削弱权限边界。

### 10. 不在本 ADR 范围内

本 ADR 定义 Target、Plan、Task Schedule 和 Changes 审查入口必须具备的产品语义，但不规定具体 UI 页面布局、弹窗视觉样式、工具协议字段、SDK、Provider/模型名单、数据库、目录结构、预算数值、具体 IPC/API 签名或进程部署拓扑。具体交互以经确认的 UI 页面规划为准；接口和执行细节由实现设计确定，但不得改变 Core 是最终授权权威、用户授权先于受保护操作、资源读取与远程传输分离、文件变更受 Core 事务与状态检查保护等约束。

### 2.6 Agent Runtime 的职责边界与不应承担的能力

Agent Runtime 管理任务编排和受控执行，但不取代 ECL AI 的产品层，也不取代 Core 的原生资源、安全和事务能力。

- ECL AI 继续负责 Chat、Knowledge、Diagnostic 的产品语义、对话历史、Provider/Model 选择和用户交互入口。
- Agent Runtime 负责任务执行生命周期、Target/Plan/Task、调度、工具执行、变更集合、验证反馈和恢复协调。
- Core 继续拥有最终权限裁决、用户授权入口、Resource Broker、实例身份、事务、并发、快照和恢复能力。
- Agent Runtime 不应把每个 Task、Target 或 Change Set 拆成独立 Addition；这些是同一运行时内部的协调对象。
- 本 ADR 不要求采用特定 Agent 框架，也不要求实现多 Agent/子 Agent。并行任务是调度能力，不代表不同模型代理可以绕过共享权限与资源约束。

## 备选方案

### 方案 A：将 Agent Runtime 作为 ECL AI 内部模块

初期结构简单，但执行环境与产品功能共享同一 Addition 生命周期，未来其他 AI 能力难以复用，也容易使工具执行边界与对话产品逻辑耦合。与维护者明确要求 Agent Runtime 独立作为 Addition 的方向不符，不采用。

### 方案 B：独立 Agent Runtime Addition，但自行管理权限和文件访问

会形成与 ADR 0053、0055 和 Core 资源机制竞争的第二套授权体系，并可能绕过 Instance Engine，安全边界不可接受，不采用。

### 方案 C：独立 Agent Runtime Addition + Core 强制权限与资源执行

Agent Runtime 独立管理 AI 执行编排、工具循环和证据追踪；Core 保留身份校验、权限裁决、用户授权、资源访问和文件事务的最终控制权。该方案兼顾 Addition 生命周期隔离、可复用性和 ECL 统一安全规范，作为本 ADR 的 Proposed 方向。

## 后果

### 正面影响

- ECL AI 的工具调用、上下文和执行循环具有统一 Agent Runtime 边界。
- Agent Runtime 可独立安装、更新、禁用和验证，不把 AI 执行依赖塞入 Core。
- 用户授权、权限撤销和资源访问继续使用 ECL 已有安全规范。
- 模型不能自行批准请求，也不能借助 Prompt 或工具结果扩大权限。
- 文件读取、远程传输和文件修改被明确区分。
- 文件变更能够关联修改前状态、用户授权、实际写入结果和修改后状态。
- 实例事务、并发控制、快照和恢复继续由原生 Core 负责。

### 代价与风险

- 新增 Addition 带来独立版本、兼容性、生命周期和依赖治理成本。
- Core 必须提供覆盖完整且不可绕过的能力执行入口。
- 权限请求和变更确认可能增加交互步骤，需要按任务范围复用有效授权以避免授权疲劳。
- 文件状态追踪与并发冲突处理需要和 Instance Engine 深度协调。
- 对任意本机代码或 GPU 执行的安全性不能仅凭 Agent Runtime 或进程隔离保证。
- 模型输出仍可能错误；Agent Runtime 只能限制副作用和保留证据，不能保证模型结论正确。

## 验收标准

本 ADR 当前为 Proposed，以下为评审与未来实现基线，不表示功能已经实现：

本 ADR 当前为 Proposed，以下为评审与未来实现基线，不表示功能已经实现：

- Registry 中存在独立 Addition `ecl.ai-agent-runtime`，类型为 Feature，登记状态与本 ADR 生命周期一致。
- `ecl.ai` 执行模型工具任务时声明对 `ecl.ai-agent-runtime` 的必需依赖；缺失时明确显示能力不可用，不得静默绕过 Agent Runtime。
- Agent Runtime 不提供重复的 Chat、Knowledge 或 Diagnostic 产品入口。
- 模型工具调用只能经过 Agent Runtime 调度和 Core 能力执行边界；模型不能直接访问宿主文件系统或系统资源。
- 多步骤任务具有明确 Target，且 Target 与权限授予分离；目标范围不明确或发生实质变化时必须重新确认和评估。
- 多步骤任务具有可追溯、可修订的 Plan，包含任务步骤、依赖、产物和验收条件。
- Task Scheduler 支持依赖驱动的任务调度、顺序/安全并行、暂停、恢复、取消和失败阻断；共享资源冲突不会被并行执行掩盖。
- 任务状态、预算、重试和结果不确定状态可追溯；非幂等操作不会在状态不明时盲目重试。
- 存在统一 Change Set / Changes 审查入口，可查看拟议和已应用变更、差异或准确摘要、来源任务、授权与验证状态。
- Changes 面板的查看、勾选或审查状态不代替 Core 授权；所有写入仍经过既有授权、读取证据和事务安全门。
- 多任务变更能够汇总查看，同时保留每项变更的独立来源、状态和验证证据。
- 任务暂停、应用重启或恢复后会重新验证目标、资源状态和授权；不能安全恢复的操作明确标记为不确定并请求介入。
- Core 对每次受保护调用重新验证调用者、能力、目标资源、操作类型和当前授权。
- 用户拒绝、取消、授权失效或权限撤销后，相关操作不会发生或继续发起。
- 目录枚举、文件读取、远程传输、创建、修改、覆盖、删除和批量操作具有可区分的能力语义。
- 本地读取不自动授权远程上传；远程传输范围能够被检查和取消。
- 文件修改前执行目标状态复核；检测到外部变更或路径目标变化时停止并进入冲突处理。
- 每次文件写入均具备与当前任务和目标资源关联的读取证据；未读取、读取状态已变化或读取覆盖不足时，Core 拒绝写入。
- 读取覆盖不足时按需补充定向、结构性或完整读取；不得将局部修改一律强制为全文件读取，也不得以节省 Token 为由跳过必要上下文。
- 读取后目标状态变化时，旧读取证据和基于旧内容生成的修改结果失效；必须重新读取并重新生成修改，且由 Core 在实际写入边界再次验证状态。
- 读取覆盖充分性不能仅由模型自我声明；必须结合实际读取证据和可用的结构/关联信息判断，无法建立可靠覆盖时停止写入。
- 文件写入经过 Core 受控资源与事务能力，完成后记录可追溯结果状态。
- Agent Runtime 不绕过 ADR 0045、0047、0048 的实例所有权、事务、并发和恢复约束。
- System Prompt 在每次推理中强制应用且可追溯；Prompt 和外部内容均不能授予权限。
- 工具循环、耗时、并发和资源预算具备限制；取消、超时和失败不会导致权限扩大。
- 工具调用真实返回成功、失败、部分完成、取消、超时或不确定状态；诊断输出保留来源，不伪装成功。
- Agent Runtime 能将可识别的执行/验证错误反馈给模型，并支持受预算限制的自我修正循环；修正仍遵循原有授权、读取和写入安全门。
- 修正达到预算上限、重复失败、无法确认副作用状态或需要扩大授权时，Agent Runtime 停止自动循环并如实报告。
- 任务完成状态区分工具执行、写入、语法/静态检查、编译、测试和实际运行验证；未执行或不可用的验证不得声称通过。
- Addition 间协作遵循 ADR 0055，不共享内部对象或直接互相访问。
- Agent Runtime 不可用或崩溃不影响 ECL 普通启动、实例管理和游戏启动。
- 对路径穿越、符号链接/重解析点、TOCTOU、权限撤销竞态、提示注入、跨任务证据串用、远程数据最小化、文件冲突和失败恢复具备可复核测试。
