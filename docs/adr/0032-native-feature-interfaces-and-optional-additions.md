# ADR 0032：原生功能入口与按需 Additions 扩展体系

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-02
- Scope: ECL 原生功能页面、官方扩展包、数据扩展包、扩展目录与分发、扩展生命周期及 Core API 边界
- Related: [ADR 0024：用户授权的自签名代码证书信任](0024-user-authorized-self-signed-code-signing.md)、[ADR 0027：原生 C# 世界分析与编辑引擎](0027-native-world-engine.md)、[ADR 0030：世界诊断与区块异常定位联动](0030-world-diagnostics-and-chunk-fault-workflow.md)、[ADR 0031：多维度世界架构与存储解析](0031-multi-dimension-world-architecture.md)

## 背景

ECL 正在规划多项大型能力，包括 Minecraft 日志与环境诊断、世界种子和生成规则分析、世界地图分析与编辑。这些能力可能需要较大的知识库、版本化算法资料或独立的执行引擎。如果将所有功能代码和数据直接集成进启动器，普通用户会承担不必要的下载体积、依赖、启动开销和维护复杂度；如果把完整功能页面也放进可选扩展，用户又必须先安装扩展才能理解功能、找到入口或知道应该下载什么。

项目也不希望为扩展分发再维护一个独立 Git 仓库，更不希望为了提供这些能力而引入必须在线运行的自有服务端。

因此，ECL 需要将用户界面、基础设施、功能执行能力和大型数据内容分开交付：启动器原生提供统一的功能入口和完整的未安装状态，具体能力与数据按需下载。扩展体系应复用现有 ECL 公有仓库及其发布渠道，不改变普通用户启动游戏的基本路径。

## 决策

### 1. 采用“原生功能入口、可选功能能力”的产品模型

功能页面、导航入口、介绍、安装提示、进度状态、错误反馈和扩展管理界面由 ECL 原生实现，并随启动器交付。

当某项功能所需的 Addition 未安装时，页面仍然存在，展示功能说明、所需扩展、下载大小（若目录提供）、依赖和安装入口。用户明确选择安装后，ECL 才下载并安装对应组件。安装完成后，原生页面通过受控 Core API 调用该能力。

未安装扩展时，页面不得显示为已经具备完整功能；如果只安装了部分能力或数据，应明确展示当前可用范围、缺失依赖及受限能力。

### 2. 不新增仓库，复用 ECL 公有仓库作为唯一官方分发项目

官方 Additions 的目录、清单、发布说明和相关元数据保存在现有 ECL 公有仓库中。扩展包和大型数据包可作为该仓库 GitHub Releases 的独立 Release Assets 发布，并使用独立的标签或版本命名规则管理，不要求每次扩展更新都重新发布启动器。

仓库中的目录文件只保存索引和必要元数据，不把大型数据库或所有扩展二进制文件直接提交到 Git 历史。具体目录布局、标签命名和包格式属于后续实现设计，但不得以新增专用仓库作为前置条件。

第一阶段不建设自有在线服务端。目录和包分发依赖现有静态仓库及发布资产；未来若增加镜像或其他分发源，也必须保持相同的包身份、校验和信任规则。

### 3. 区分 Feature Additions 与 Data Additions

Additions 至少分为两种逻辑类型：

- **Feature Addition**：提供可执行的功能实现，例如诊断引擎、世界生成分析引擎、世界编辑能力。
- **Data Addition**：提供可独立更新的数据，例如已知故障知识库、模组元数据、版本兼容资料、世界生成算法参数或索引。

一个 Feature Addition 可以声明所需的 Data Additions，也可以声明其他 Feature Addition 或 Core API 依赖。数据包可以独立更新，不应要求为了更新知识库而重新下载整个功能引擎。

功能可以在基础数据缺失时提供有限能力，但必须显式声明能力边界；如果某项操作必须依赖特定数据，则在执行前阻止该操作并解释缺失项，不得静默使用过期或不完整数据给出确定结论。

### 4. Core 保留通用基础设施，Addition 提供可选的领域能力

ECL Core 负责启动器不可缺少或跨功能共享的基础能力，包括扩展目录读取、依赖解析、包下载与校验、安装事务、版本兼容检查、文件路径边界、权限控制、日志和受控 API。

通用数据格式与基础设施不应被某个 Addition 独占。例如，实例管理、世界文件安全访问、基础 Region/Anvil/NBT 解析能力及共享诊断事件模型，应按其跨功能价值留在 Core 或共享引擎层；高级诊断规则、完整知识库、世界生成预测、地图分析与编辑工作流等可选产品能力则通过 Additions 提供。

不得为了将功能做成 Addition 而复制一套已有 Core 能力，也不得让卸载某个 Addition 破坏实例管理、普通游戏启动或其他 Addition 的基础能力。

### 5. 原生页面通过受控接口调用扩展，不开放任意 UI 注入

Additions 不负责向 ECL 动态注入导航项、页面、任意 WPF 控件或任意界面脚本。功能入口、页面结构、交互风格和用户确认流程由 ECL 原生维护。

Feature Addition 通过 ECL 定义并版本化的能力接口提供服务。接口应围绕明确的领域能力设计，例如诊断提供器、世界分析提供器和世界编辑提供器；不得让扩展直接访问启动器内部对象、任意 ViewModel 或不受约束的 UI 线程。

初期只支持 ECL 官方构建和签发的受控扩展，不承诺任意第三方代码插件、脚本执行或运行时 UI 注入。未来若考虑第三方扩展，必须另行评估隔离、权限、审核、撤销和兼容性模型。

### 6. 建立可版本化的扩展目录与依赖描述

官方目录至少应描述：

- 稳定且全局唯一的 Addition ID；
- 名称、说明、类型和功能分类；
- 独立的组件版本；
- 包下载地址、包大小及 SHA-256；
- 发布者签名或可验证的签名信息；
- 支持的 ECL Core API 范围；
- 依赖、可选依赖和冲突声明；
- 数据 schema 或格式版本（适用于 Data Addition）；
- 适用的 Minecraft、Loader、平台或其他环境范围（适用时）；
- 撤回、停止分发或替代版本信息。

目录、包清单和包内容必须相互一致。依赖解析应在下载前给出将安装、更新或移除的组件清单，并拒绝循环依赖、不可满足依赖和不兼容组合。不得仅因版本号较新就推断兼容。

### 7. 扩展拥有独立版本与生命周期

ECL Core、Feature Addition 和 Data Addition 分别版本化。扩展不要求与启动器使用相同版本号，也不要求每次 ECL 更新都同步更新全部扩展。

扩展至少区分以下状态：

- Available：目录中可获取；
- Downloading：正在下载；
- Installed：已安装在本地；
- Enabled：用户允许该功能被调用；
- Loaded / In Use：当前操作正在使用该能力；
- Disabled：已安装但不允许调用；
- Update Available：存在兼容的新版本；
- Incompatible：与当前 Core API 或依赖不兼容；
- Broken：安装内容缺失、损坏或校验失败。

Installed、Enabled 和 Loaded / In Use 是不同概念。安装扩展不意味着启动 ECL 时自动加载它；只有用户进入对应功能或明确发起操作时，才按需初始化所需能力。未被使用的扩展不得进入普通游戏启动链。

更新应保留已知可用版本或可恢复状态。卸载扩展前检查依赖关系，并明确说明将受影响的功能。卸载功能代码或数据包不得删除用户的 Minecraft 实例、世界、日志或其他用户数据。

### 8. 扩展下载、安装和更新不得影响普通启动路径

普通启动器启动、实例管理和游戏启动不得要求访问扩展目录、下载扩展或等待扩展初始化。

扩展目录应在用户打开 Additions 管理页面、对应功能页面，或主动检查扩展更新时按需读取。远程目录不可用、网络离线、下载失败或扩展服务器（静态托管）不可访问时，ECL 必须继续正常启动和运行游戏；可使用最近一次成功获取且通过校验的目录缓存，并明确标记其可能不是最新状态。

扩展包下载到临时位置，完成长度、哈希、签名、清单和兼容性校验后再安装。安装应采用可恢复的事务或暂存目录切换，避免中断后留下半安装状态。更新失败时保留原有可用版本；校验失败时不得加载或执行包内容。

### 9. 安全模型复用 ECL 既有信任边界

Additions 的包校验必须同时验证内容完整性和发布者信任。SHA-256 只能验证内容是否匹配已取得的摘要，不能单独证明发布者身份。官方扩展应使用可验证的签名机制；签名者身份、密钥轮换、撤销和首次信任必须遵循 ECL 既有代码签名与更新信任决策，不得因扩展分发而降低 ADR 0024 的安全要求。

目录和下载地址不得成为任意代码执行入口。包身份、签名、哈希、版本、目标路径和依赖都必须在安装前验证。扩展不得通过安装过程静默请求管理员权限；安装目录应遵守 ECL 既有普通用户权限边界。任何未来需要更高权限的扩展操作都必须单独设计、明确告知并取得用户授权，不能继承启动器权限或绕过用户确认。

### 10. 数据隐私与本地优先

诊断日志、崩溃报告、世界存档、Seed、服务器地址和用户配置默认只在本地分析。下载知识库或扩展不代表允许上传用户数据。任何未来的远程分析、社区案例提交或遥测必须是独立、明确、自愿的功能，并在上传前提供内容预览和脱敏能力。

Data Addition 应声明数据来源、更新时间、适用范围和许可信息。来自公开项目的元数据或问题记录必须尊重其许可与使用条款；未经核实的社区报告不得被包装成确定事实。

### 11. Additions 不应成为普通用户的必经概念

ECL 可以在功能页面中展示可选能力和安装提示，但不得在首次安装、普通启动、创建实例或启动游戏流程中强制用户选择或下载 Additions。用户不使用高级功能时，可以完全忽略扩展体系。

## 后果

### 正面影响

- 启动器原生页面始终提供一致的功能入口、说明和安装体验。
- 大型功能代码与数据按需下载，普通游戏用户不承担无关的下载体积和运行开销。
- 诊断知识库、世界生成资料和其他数据可以独立更新。
- 不需要新增仓库或自有服务端，即可建立官方扩展分发能力。
- 统一的目录、依赖、校验和 Core API 可以服务多个未来功能。
- 功能页面与执行实现分离，UI 可以先行完善，具体引擎可以独立开发和交付。

### 代价与限制

- ECL 需要维护扩展目录格式、包格式、依赖解析、安装事务和兼容性策略。
- Core API 必须保持稳定并有明确的兼容策略，否则扩展会随启动器更新频繁失效。
- 官方扩展发布需要额外的签名、校验、版本管理和撤回流程。
- 用户可能安装了功能代码但未安装完整数据，UI 必须准确表达能力缺口。
- 依赖和版本组合会增加测试矩阵；不能仅测试启动器本身。
- GitHub Releases 仍受平台可用性、访问速度、资产限制和账号安全影响；本决策不承诺无限制分发或永久可用。

## 实施顺序建议

1. 先定义 Addition ID、类型、版本、清单、目录 schema 和 Core API 兼容策略。
2. 明确官方目录与 Release Assets 在现有 ECL 仓库中的组织方式，不创建新仓库。
3. 实现只读目录解析、依赖解析和安装计划预览。
4. 实现下载、哈希与签名验证、暂存安装、失败恢复、更新和卸载。
5. 实现原生 Additions 管理页面及功能页的未安装、部分安装、不兼容、下载中和可用状态。
6. 定义受控 Feature API，并验证扩展不会注入任意 UI 或影响普通启动链。
7. 选择一个小型 Data Addition 验证独立下载、更新和回滚。
8. 选择一个 Feature Addition 验证原生页面与可选执行能力的完整生命周期。
9. 再将诊断中心、世界分析和世界编辑逐步迁移到该交付模式。

## 验收标准

- 不新增专用 Git 仓库，官方目录和扩展发布资产均可从现有 ECL 公有仓库获取。
- 未安装任何 Addition 时，所有规划中的功能入口仍由 ECL 原生展示，并能说明所需扩展及安装方式。
- 未安装或禁用扩展时，ECL 普通启动、实例管理和游戏启动不受影响。
- 普通启动路径不因远程目录不可用、离线或扩展损坏而失败或等待网络超时。
- Feature Addition 与 Data Addition 可独立版本化、下载、更新和卸载。
- 依赖、冲突、Core API 兼容性和数据 schema 版本在安装前完成检查。
- 安装前验证包身份、签名、哈希和目标路径；不完整或校验失败的包不会被加载。
- 安装或更新中断不会破坏原有可用版本；失败后能够恢复。
- Installed、Enabled 和 Loaded / In Use 状态清晰区分；未被调用的扩展不进入普通游戏启动链。
- 扩展只能通过受控 API 提供能力，不能任意注入或替换原生 UI。
- 扩展卸载不会删除实例、世界或其他用户数据，也不会破坏其他扩展。
- 不因扩展安装而静默请求管理员权限，不降低 ADR 0024 的信任和签名要求。
- 用户日志、Seed、存档及其他诊断输入默认不上传。
- 数据来源、许可、适用范围和更新时间可以被识别；不可信数据不会被呈现为确定结论。
