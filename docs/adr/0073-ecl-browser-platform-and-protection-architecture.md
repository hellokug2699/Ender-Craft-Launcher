# ADR 0073: ECL Browser Platform and Protection Architecture

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-26
- Scope: ECL Browser 产品定位、浏览器运行时边界、用户会话与配置隔离、网络内容过滤、恶意网站防护、下载安全、浏览器更新及宿主进程隔离

## 背景

ADR 0036 将浏览器定义为只访问 Minecraft Wiki 中文站和 mcmod.cn 的受限知识浏览器，并以域名白名单作为主要网络边界。该方案虽然形成了可复用的 URL 规范化、域名策略、重定向判断、本地错误页和地址栏状态逻辑，但其产品边界无法覆盖实际知识获取场景：用户可能需要访问 Bilibili、小黑盒、CSDN、YouTube、Fandom、模组作者主页、代码仓库及其他正常网站。持续增加白名单会把网站维护责任转嫁给 ECL，也会将安全目标错误地简化为“只允许访问少数网站”。

新的目标是提供一个真正可用的浏览器产品：允许用户访问正常互联网，同时由浏览器宿主、Chromium 沙箱、网络过滤、威胁情报、下载管理和 Profile 隔离共同保护用户设备、账户和隐私。Minecraft 知识获取仍是重要使用场景，但不再是网络访问范围的限制条件。

本 ADR 是新的架构提案。它定义产品目标、安全不变量和 PoC 验证方向；CEF 具体版本、CEF 封装方式、窗口托管方式、过滤引擎及其语法兼容范围，在完成验证前均不视为已批准的最终实现选型。

## 决策

### 1. 将 ECL Browser 定位为通用浏览器 Addition

ECL Browser 是 ECL 管理的通用网页浏览器能力，而不是只访问指定 Minecraft 资料站的 WebView 页面。

产品目标包括：

- 多标签浏览、前进/后退、刷新、地址栏和搜索；
- 书签、历史记录、阅读列表及下载管理；
- 多个浏览器 Profile、持久化 Cookie 和网站会话；
- 临时浏览会话及按站点清理数据；
- 站点权限、弹窗控制、下载确认和安全提示；
- 广告过滤、隐私过滤和恶意网站防护；
- 在 ECL 内访问 Minecraft Wiki、模组平台、视频站、社区、文档和其他正常互联网内容。

浏览器由 ECL 安装、更新和管理。浏览器宿主进程与 ECL 主 UI 分离；是否支持脱离 ECL 独立启动属于后续产品决策，本 ADR 不预先承诺。

浏览器不得以“安全”为由恢复 ADR 0036 的固定站点白名单。正常互联网访问是产品目标；安全控制应主要约束网页对本机资源、浏览器会话、下载、权限和宿主能力的访问。

### 2. 浏览器运行时必须保留 Chromium 安全边界

优先评估 Chromium Embedded Framework（CEF），但在 PoC 完成前不锁定 CEF 封装库或宿主实现。

候选路线至少包括：

- Native CEF Host：使用 CEF 原生 API，由独立进程承载浏览器运行时；
- .NET CEF Binding：评估 CefGlue 等封装，但必须证明其能够满足当前 CEF 版本的 Windows Sandbox Bootstrap 要求；
- WebView2：作为对照方案，验证其网络拦截、响应处理、Profile、下载和进程隔离能力是否足以支持完整浏览器产品。

Windows 上 Chromium Sandbox 是发布门槛，不是可选优化。对于 CEF M138 及之后版本，必须遵循对应的 Bootstrap 部署模型，包括客户端 DLL、CEF Bootstrap 可执行文件、Sandbox Info 传递及同版本二进制配套要求。不得以关闭 Sandbox、传入 no-sandbox 或降低 Renderer 隔离作为绕过封装问题的解决办法。

如果候选运行时不能提供可验证的沙箱能力、及时安全更新和必要的请求控制能力，则不得作为正式浏览器运行时发布。

### 3. 使用独立 Browser Host 和最小 IPC

浏览器运行时不得与 ECL 主 UI 共享一个不受隔离的网页执行环境。

目标边界为：

- ECL WPF UI：负责浏览器外壳、标签、地址栏、用户交互和状态呈现；
- Browser Host：负责 CEF 生命周期、浏览器实例、Profile、导航、网络回调和宿主级权限；
- Chromium 子进程：按 Chromium 进程模型运行 Renderer、Network、GPU 等服务，并保留适用的操作系统沙箱；
- Protection Service：为 Browser Host 提供规则判定、威胁情报、拦截决策和解释信息；
- IPC：只开放浏览器 UI 必需的有限命令和事件，不提供任意 .NET 对象、任意文件访问或任意进程执行接口。

网页内容、Renderer 和普通脚本不得直接访问 ECL IPC。IPC 调用必须由宿主验证来源、操作类型、目标范围和当前会话状态。浏览器崩溃、Renderer 崩溃或恶意网页不得导致 ECL 主程序、实例管理或 Minecraft 启动路径崩溃。

### 4. 采用 Profile 隔离与本地会话持久化

浏览器支持独立 Profile。每个 Profile 的 Cookie、Local Storage、Cache、IndexedDB、权限和站点数据必须处于明确的数据目录边界内。

至少支持：

- Default Profile：用户主动选择的常规持久化浏览会话；
- Temporary Profile：关闭会话后按明确策略清理的临时会话；
- Additional Profiles：用户主动创建的独立身份与数据空间。

用户可以在网站正常登录，并在持久化 Profile 中保留会话；ECL 不读取网页密码，不上传 Cookie，不将网站会话同步到 ECL 服务器，也不把一个 Profile 的会话自动共享给另一个 Profile。

ECL 不得把网页登录密码、Cookie 或网站访问令牌作为普通浏览器诊断日志记录。浏览器数据清理必须明确区分 Cookie、缓存、历史记录、下载记录和书签，不得以“清理浏览数据”为名误删用户保存的内容。

密码管理器、跨设备浏览器同步和 Google/其他第三方账户专用集成不属于首期必需能力。任何未来凭据管理功能都必须单独定义秘密存储、自动填充授权和账户隔离边界。

### 5. 建立本地优先的 Content Protection

浏览器应提供统一的内容过滤与威胁防护服务，至少区分以下规则类别：

- Advertisement：广告请求、广告脚本和广告资源；
- Privacy：已知跟踪器、追踪像素及部分第三方分析请求；
- Annoyances：弹窗、遮挡元素、Cookie 提示和其他烦扰元素；
- Malicious Content：已知钓鱼网站、恶意域名、诈骗页面和危险资源；
- User Rules：用户主动添加的规则、例外和自定义订阅。

广告过滤与恶意威胁判定必须分离。广告命中不等于网站恶意；某网站存在广告不得直接导致整个网站被列入恶意站点名单。不同类别具有独立来源、启停、更新和误报处理机制。

过滤优先在本地执行。浏览器不得默认将完整 URL、查询参数、页面内容、Cookie 或浏览历史发送给远程过滤服务器。未来可选的在线威胁查询必须单独说明数据范围、目的、保留策略和隐私保护机制；网络不可用时应保留本地规则能力，并明确区分“本地检查完成”和“在线信誉未知”。

### 6. 过滤引擎与规则列表采用可替换设计

优先评估 Brave 的 adblock-rust 作为网络过滤与 Cosmetic Filtering 引擎候选。其网络请求判定、元素隐藏、资源替换和 Scriptlet 能力需要分别验证，不得将项目宣称支持的能力等同于完整兼容 AdGuard、uBlock Origin 或所有 ABP 扩展语法。

过滤服务必须通过稳定适配层向 Browser Host 提供请求判定与规则解释能力。不得让 CEF 回调直接依赖某个过滤引擎的内部数据结构。未来替换过滤引擎时，浏览器请求处理接口和用户规则数据格式应尽量保持稳定。

规则来源可以评估 EasyList、EasyPrivacy、AdGuard Filters 及其他经过审查的社区列表。引入或再分发每个列表前必须记录来源、许可证、更新地址、用途和兼容性。不得假设所有列表具有相同许可证或允许任意再分发。

规则更新必须具备版本管理、内容完整性校验、原子替换、失败回滚和可追溯来源。第三方规则不得直接获得修改 ECL 安全策略、读取用户数据或执行任意宿主代码的权限。用户自定义规则与官方安全威胁情报应保持来源和信任等级区分。

### 7. 恶意网站防护采用独立 Threat Intelligence Provider

恶意网站防护不应只是广告过滤规则的一个标签。它需要独立的威胁情报接口和数据模型。

至少区分：

- URL/域名命中；
- 钓鱼与凭据窃取；
- 恶意下载和已知恶意文件来源；
- 已知诈骗或仿冒站点；
- 情报来源、更新时间、置信度和误报状态。

本地情报优先。在线查询为可选增强，必须遵循最小数据披露原则。未知目标不能被伪装成“已验证安全”；情报服务不可用时应明确显示检查范围和状态。

恶意站点拦截必须允许用户查看具体原因、规则来源和目标地址。例外应尽量限制在具体站点、规则或资源范围，并记录用户主动创建的例外；不得把广告过滤的普通开关与恶意威胁防护的关闭合并为一个模糊按钮。

### 8. 拦截响应由本地宿主生成，不依赖远程代理

正常网页访问应由用户设备直接访问目标站点。ECL 不要求所有浏览流量经由 ECL 或第三方远程代理转发，也不默认部署 HTTPS 中间人解密。

Browser Host 应在 Chromium 请求处理边界执行过滤决策。被阻止的顶层文档导航应由本地拦截页面解释原因；对于子资源请求，应按资源类型安全取消或返回适当的空/替代响应，不得把 HTML 拦截页面错误地作为图片、脚本或字体响应。

重定向必须逐跳检查。浏览器应在跟随下一跳前评估目标；若阻止，应记录原始响应状态、原始 URL 和拒绝目标，并导航到 ECL 本地拦截页面。页面可以显示原始 301/302/303/307/308 状态和 ECL 的拦截决定。具体是否能让 Chromium 将本地合成响应表现为真实 HTTP 403，必须通过所选运行时的实测确认；在验证前不得把 UI 显示的“403”描述成远端服务器真实返回的状态码。

本地拦截页面不得加载被拦截站点的资源，不得执行来自不可信页面的脚本，也不得将原始 URL 未经编码地插入 HTML。拦截日志应记录必要的决策证据，但避免保存完整浏览内容或敏感查询参数。

### 9. 下载、权限和外部协议采用明确控制

浏览器下载由宿主统一管理，不允许网页绕过下载管理器直接静默写入任意目录或自动执行文件。

下载流程至少需要：

- 显示文件名、来源 URL、文件类型和大小（可获得时）；
- 用户明确确认保存位置或使用用户配置的默认目录；
- 防止路径穿越、危险文件名和覆盖用户文件；
- 支持取消、失败清理及必要的完整性检查；
- 下载完成后不得自动执行文件；
- 对可疑来源和危险文件类型显示明确风险信息。

弹窗、通知、摄像头、麦克风、地理位置、剪贴板读取、文件选择器和外部协议应由站点权限模型管理，默认拒绝或在首次使用时向用户请求明确授权。网页不得直接启动 ECL、修改 Minecraft 实例或调用启动器内部管理能力。

### 10. Chromium Runtime 必须持续更新

浏览器内核是安全关键依赖。ECL 必须建立 CEF/Chromium 版本跟踪、漏洞评估、构建与分发、完整性校验、更新失败回滚和最低安全版本策略。

浏览器 Runtime、Browser Host、过滤引擎和规则列表应有可独立更新的边界，但更新兼容性必须由版本清单明确约束。不能因为规则列表仍能更新就长期运行存在已知高危漏洞的 Chromium 内核。

当 Runtime 版本低于项目定义的安全下限、完整性校验失败或更新状态无法确认时，应限制浏览器启动并给出可理解的恢复提示；不得静默降级到关闭沙箱的旧版本。

### 11. 保留 Minecraft 知识场景，但不再限制互联网范围

Minecraft Wiki、Modrinth、CurseForge、mcmod.cn、视频站、论坛、文档和代码仓库都是浏览器的正常访问场景。ECL 可以在浏览器中提供 Minecraft 知识入口、站点快捷方式、页面收藏和未来的受控内容识别能力。

这些入口是产品导航与便利功能，不是安全白名单。是否允许访问某个网站由通用浏览策略、威胁情报和用户权限决定，不由固定的 Minecraft 域名列表决定。

## 备选方案

### 方案 A：保留 ADR 0036 的受限知识浏览器

不采用。固定站点白名单无法覆盖真实知识获取来源，持续维护白名单会损害正常浏览体验，也不能代替浏览器沙箱、下载控制和威胁防护。

### 方案 B：继续使用 WebView2，仅增加站点白名单与广告过滤

作为对照 PoC 保留，但不预先认定足够。必须验证其网络拦截、重定向、合成响应、Profile、下载和宿主隔离能力能否满足完整浏览器目标。

### 方案 C：直接使用 CefSharp 嵌入 WPF

不作为默认方案。其集成便利性不能抵消 Windows Chromium Sandbox 支持问题。除非能够提供可信且可维护的沙箱方案，否则不得采用。

### 方案 D：Native CEF Host + ECL UI + 独立 Protection Service

作为优先验证方向。它增加进程、窗口托管和 IPC 的复杂度，但为保留 Chromium 沙箱、请求控制和独立生命周期提供更明确的边界。最终选型仍以 PoC 结果为准。

### 方案 E：自行 Fork Chromium 并维护完整浏览器

暂不采用。维护 Chromium 分支、安全补丁、构建工具链和平台适配的成本过高。除非未来 CEF 等嵌入方案无法满足不可妥协的需求，才重新评估。

## 后果

### 正面影响

- 浏览器从单一 Minecraft 资料入口升级为通用浏览能力，不再需要持续维护网站白名单。
- 用户可以正常登录网站并在独立 Profile 中保留会话。
- 安全边界从“允许哪些网站”转向“网页能做什么、访问哪些本地能力以及下载如何处理”。
- 广告过滤、隐私保护和恶意威胁情报各自拥有明确的规则来源与信任等级。
- 本地过滤和拦截页面减少对远程代理的依赖，也降低完整浏览 URL 外泄风险。
- 浏览器宿主、过滤引擎和规则数据可独立演进。

### 代价与风险

- 完整浏览器的实现、维护和测试成本显著高于 WebView 控件。
- CEF Windows Sandbox Bootstrap、Native Host、WPF 窗口集成和 IPC 需要专门 PoC。
- 不同规则列表的语法兼容性不一致，可能需要明确支持子集和规则诊断工具。
- 威胁情报存在过期和误报风险，需要来源治理与用户可理解的解释。
- Profile、Cookie、历史、下载和权限数据需要长期维护与迁移策略。
- Chromium 安全更新会形成持续的版本跟踪和发布负担。
- 浏览器允许访问任意互联网内容后，必须依靠沙箱、权限、下载与更新策略控制风险，不能再依赖站点白名单作为主要防护。

## 验收标准

本 ADR 在 Proposed 阶段不代表任何实现已经通过验收。批准前至少需要完成以下 PoC 并记录可复核证据：

- 在受支持的 Windows 版本上运行候选 CEF Runtime，证明 Chromium Sandbox 已启用；验证 Renderer 崩溃或受控测试进程不能直接访问不应开放的宿主资源。
- 验证 CEF M138+ Windows Bootstrap 部署模型、客户端 DLL 入口、Sandbox Info 生命周期、Browser/Renderer 子进程启动和关闭。
- 验证 ECL WPF UI 与 Browser Host 之间的 IPC 只暴露最小操作，网页内容不能直接调用该 IPC。
- 验证请求拦截能够覆盖顶层文档、iframe、脚本、样式、图片、字体、XHR/fetch、媒体和重定向；对 Service Worker、WebSocket、WebRTC、预连接和缓存命中等特殊路径形成明确测试结论。
- 验证 301、302、303、307、308 重定向在下一跳请求发出前得到检查；阻止时保留原始状态和拒绝目标，并展示本地拦截页。
- 验证本地拦截响应的状态码、MIME、编码、CSP、缓存策略和页面资源隔离；分别测试主文档和子资源阻止行为。
- 验证 adblock-rust 对选定 EasyList、EasyPrivacy、AdGuard 规则样本的解析和匹配；记录不支持语法、Cosmetic Filtering 和 Scriptlet 的兼容性边界。
- 验证规则更新的完整性、原子切换、失败回滚、来源展示和用户自定义规则隔离。
- 验证恶意网址情报与广告过滤规则相互独立，能够展示来源、时间、置信度和误报处理状态。
- 验证持久化 Profile、Temporary Profile、Cookie/Local Storage 隔离、会话清理和多 Profile 切换。
- 验证下载确认、保存路径约束、取消、失败清理和禁止自动执行。
- 验证浏览器 Runtime 可独立于 ECL 主程序更新，更新失败能够回滚；低于安全版本时不会静默继续运行。
- 验证浏览器运行时崩溃、规则损坏、威胁情报不可用或网络离线不会影响 ECL 普通启动、实例管理和 Minecraft 启动。
