# ADR 0038: Authlib-Injector Texture Upload Protocol Support

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-02
- Scope: Authlib-Injector / Yggdrasil 第三方账户的皮肤与披风上传、清除及能力识别
- Related: [ADR 0037：账户外观与本地衣柜架构](0037-account-appearance-and-local-wardrobe.md)

## 背景

ADR 0037 确立了本地衣柜、账户外观 Provider 和实例外观边界。其中，第三方账户不能仅凭 Authlib-Injector / Yggdrasil 认证兼容性就被视为支持外观管理：认证协议解决身份验证和角色资料读取，外观写入能力仍需由服务端提供相应接口。

Authlib-Injector 的 Yggdrasil 服务端扩展规范定义了材质上传能力声明及对应的上传/清除接口。服务端可通过角色资料中的 `uploadableTextures` 属性声明可上传的材质类型，例如 `skin`、`cape`。规范还约定了按角色 UUID 定位的皮肤与披风接口。

这为 ECL 提供了一个重要机会：对于遵循该规范的第三方验证服务，可以实现一次通用 Provider，而不必为每个兼容皮肤站分别开发一套上传适配。与此同时，不能把“服务商网页端允许上传”或“服务商使用 Authlib-Injector”直接等同于其部署实例一定开放并正确实现协议端点。

## 决策

### 1. 将 Authlib-Injector Texture Upload Protocol 作为第三方上传能力的首选通用适配

ECL 应优先实现 Authlib-Injector 定义的材质上传协议，作为第三方 Yggdrasil 账户皮肤与披风写入能力的通用适配方式。

该 Provider 属于第三方账户外观 Provider 的一种标准协议实现，不取代 ADR 0037 定义的 Provider 抽象，也不意味着所有 Yggdrasil 服务均支持材质上传。

### 2. 通过能力声明分别识别皮肤和披风

Provider 应解析角色资料中服务端返回的 `uploadableTextures` 属性，并将其转换为独立能力：

- `skin`：服务端声明支持皮肤上传；
- `cape`：服务端声明支持披风上传；
- 同时包含两项：分别开放皮肤与披风操作；
- 属性缺失、为空或不包含对应值：不得向用户宣称对应材质可上传。

能力识别必须按具体账户和角色资料进行，不得仅根据验证服务器类型、名称、域名或网页介绍推断。

该属性是服务端能力声明，不是端点健康检查或成功保证。实际操作仍必须处理端点不存在、权限拒绝、请求格式不兼容、账户失效和服务端错误等情况。服务端声明与实际响应冲突时，应将能力标记为不可用或待确认，并保留可诊断的错误信息。

### 3. 使用规范定义的角色材质接口

对于确认兼容的服务端，Provider 按 Authlib-Injector 规范使用以下接口：

| 操作 | HTTP 请求 |
|---|---|
| 上传/设置皮肤 | `PUT /api/user/profile/{uuid}/skin` |
| 清除皮肤 | `DELETE /api/user/profile/{uuid}/skin` |
| 上传/设置披风 | `PUT /api/user/profile/{uuid}/cape` |
| 清除披风 | `DELETE /api/user/profile/{uuid}/cape` |

其中 `{uuid}` 为当前已认证账户对应的角色 UUID。上传请求按规范使用 `multipart/form-data` 传递 PNG 文件，并使用当前第三方账户的有效访问令牌进行 Bearer 认证。皮肤模型参数（例如 `slim`）仅在协议及服务端实现支持时发送；不得将皮肤模型参数错误地应用于披风操作。

实现必须以 Authlib-Injector 当前正式技术规范为准，明确处理路径拼接、UUID 格式、请求字段、响应状态及错误响应。不得通过尝试猜测端点或遍历其他路径来探测服务商接口。

### 4. 严格复用第三方账户的认证上下文

Provider 必须复用 ECL 已有第三方 Yggdrasil 账户会话及其凭据管理，不得再次要求用户输入密码，也不得创建与账户系统相互独立的长期令牌副本。

发送请求前必须确认目标服务器与当前账户认证服务器属于同一可信配置上下文。访问令牌不得发送到用户未配置或未经验证的其他主机；不得因 HTTP 重定向将 Bearer 凭据转发到其他来源。请求应遵循现有第三方认证的 HTTPS、安全重定向和凭据保护规则。

令牌过期、权限不足或账户会话失效时，应返回明确的认证状态并引导用户通过既有账户流程重新认证，不得在 Provider 内私自实现另一套登录或刷新协议。

### 5. 上传成功后重新读取角色资料

上传接口返回成功只代表服务端接受了该次请求，不足以证明新材质已经正确写入角色资料或能够在游戏中显示。

操作完成后，Provider 应重新读取角色资料，并核对材质属性/签名数据是否发生预期变化。界面应分别表达：

- 上传请求已被服务端接受；
- 角色资料已反映新的材质；
- 游戏客户端或服务器中已实际验证显示。

ECL 不得将这三个状态合并成一个含义模糊的“更换成功”。

### 6. 区分上传、清除与衣柜切换

协议中的 PUT/DELETE 操作用于设置或清除当前角色的皮肤、披风，不构成服务端多套衣柜、收藏夹或历史版本管理协议。

ECL 本地衣柜可以保存多份资源。用户选择本地资源并执行上传时，Provider 将资源设置为当前角色材质；服务端是否保留历史版本、是否提供多披风选择或其他资源管理能力，必须由服务商自己的 API 明确提供，不能从本协议推断。

披风上传能力与选择账户已有披风的能力也应分别建模。若服务端仅支持选择已有披风而不支持上传自定义披风，Provider 不得将其报告为 `cape` 上传能力。

### 7. 对不兼容服务端提供安全降级

以下情况均不得阻塞第三方账户登录、实例管理或 Minecraft 启动：

- 服务端未声明 `uploadableTextures`；
- 服务端只支持皮肤或只支持披风；
- 服务端声明能力但对应端点不可用；
- 服务端仅提供网页端上传或自定义 API；
- 用户未登录、令牌失效或网络不可用。

在标准协议不适用时，ECL 仍提供本地衣柜与预览。若未来支持服务商专用 API，应通过独立 Provider 实现，并明确标识其服务商范围；不得把专用 API 混入通用 Authlib-Injector Provider。

### 8. 文件校验、隐私与安全

上传前应在本地验证资源确为可解码的 PNG，并检查尺寸、像素总量及文件大小上限，防止异常文件或解压后占用过大的图像造成资源耗尽。皮肤模型参数应与实际资源类型和用户选择一致。

ECL 不应将皮肤、披风或账户资料上传到除当前账户配置的验证服务端以外的第三方。上传前应明确显示目标账户/服务端及操作类型。日志不得记录访问令牌、完整授权头或不必要的材质二进制内容。

## 备选方案

### 方案 A：每个皮肤站单独开发 Provider

不作为默认方案。它会造成重复实现、维护成本和行为差异，也使新增兼容服务商需要依赖 ECL 发版。对于确实使用专用 API 的服务商，可在通用协议之外增加独立适配。

### 方案 B：只提供网页端跳转

不作为唯一方案。网页端可以作为不兼容服务端的后备入口，但无法提供统一的启动器内上传体验，也无法充分利用 Authlib-Injector 已定义的通用接口。

### 方案 C：根据 `uploadableTextures` 声明直接认定上传可用

不采用。该属性只能表达服务端声明的能力，不能保证端点可访问、权限有效或实现符合规范。仍需处理真实请求结果并在操作后复查角色资料。

### 方案 D：实现 Authlib-Injector 通用上传 Provider，并允许专用 Provider 补充

采用。优先覆盖遵循标准的服务端，同时保留对非标准服务商的扩展空间。代价是需要维护协议兼容性、能力状态和安全请求处理。

## 后果

### 正面影响

- 对遵循 Authlib-Injector 材质上传规范的服务端，ECL 可以复用一套通用实现。
- 不必为每个采用相同协议的皮肤站重复开发上传逻辑。
- 皮肤与披风能力独立识别，避免把部分支持误报为全部支持。
- 本地衣柜可以直接向当前账户服务端应用资源，同时保持本地资源管理与服务端状态分离。
- 不兼容服务端仍可使用本地衣柜，不影响普通游戏启动。

### 代价与限制

- 服务端实现可能存在版本差异、配置限制或协议偏差，能力声明不能替代实际请求验证。
- ECL 需要维护协议请求、响应、令牌生命周期和角色资料复查逻辑。
- 服务商专用 API 仍可能需要额外 Provider，通用协议无法覆盖所有网页端功能。
- 服务端接受材质不代表所有客户端、服务器或模组环境都会显示该材质。

## 验收标准

- 对符合规范的测试服务端，ECL 能正确解析 `uploadableTextures`，并分别识别皮肤和披风上传能力。
- 属性缺失、为空或不包含某项能力时，ECL 不显示该项上传操作为可用。
- ECL 能按规范完成皮肤 PUT、皮肤 DELETE、披风 PUT 和披风 DELETE；每项能力均有独立测试覆盖。
- 上传请求使用当前账户的有效 Bearer 凭据，且不会向其他来源或重定向目标泄露凭据。
- 上传文件在发送前通过 PNG 解码、文件大小和图像尺寸/像素总量校验。
- 上传成功后重新读取角色资料，并区分请求接受、资料更新和游戏内显示验证状态。
- 服务端只支持皮肤或只支持披风时，界面仅开放对应能力。
- 服务端声明能力但端点不可用、权限不足或响应异常时，ECL 显示准确错误，不伪报成功。
- 不兼容服务端仍可使用本地衣柜；Provider 故障不会阻塞账户登录或游戏启动。
- 日志、普通配置和错误报告不包含访问令牌、完整授权头或不必要的材质二进制数据。
