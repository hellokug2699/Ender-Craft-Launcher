# ADR 0039：应用运行时生命周期与优雅关闭

- Decision: Accepted
- Implementation: Implemented
- Date: 2026-11-02
- Scope: ECL 桌面应用进程内的服务初始化、后台工作协调、关闭流程与资源释放
- Related: [ADR 0015](0015-process-scoped-game-log-sessions-and-diagnostics.md)、[ADR 0019](0019-memory-pressure-process-survival-and-diagnostic-continuity.md)、[ADR 0020](0020-download-artifact-lifecycle-and-cleanup.md)、[ADR 0029](0029-installer-bootstrapper-uninstaller-lifecycle.md)、[ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)

## 背景

ECL 已经在多个领域建立了局部生命周期管理：应用组合根负责 DI 容器创建和启动初始化；Operations 提供业务操作状态、取消与作用域；下载、HTTP 客户端、内存压力监控等模块各自释放其拥有的资源；游戏进程监控负责等待进程退出、排空日志管道、完成会话收尾并释放 Process；Additions 体系定义了安装、启用、加载和使用等不同状态。ADR 0015、0019、0020、0029 分别约束游戏会话、内存压力、下载产物和安装组件的局部生命周期。

这些设计解决了各自领域的问题，但它们并不自动组成应用级的运行时生命周期协议。依赖注入容器的 Dispose 不等于所有异步后台工作已经停止；CancellationToken 可用也不代表任务已被登记、取消、等待并完成资源收尾。

若应用关闭时只同步释放 ServiceProvider，仍可能存在未被统一追踪的后台任务、异步 I/O、事件订阅或外部资源。反过来，应用级关闭协调也不能擅自终止应独立于 UI 存活的 Minecraft 游戏进程或破坏诊断证据收尾。

本 ADR 定义跨模块的最小协调契约，不取代各模块自身的资源所有权和领域生命周期规则。

## 决策

### 1. 应用运行时生命周期

应用运行时采用明确的单向生命周期：
1. **Starting**：建立组合根、注册服务并执行必要初始化。
2. **Running**：正常接收用户操作和应用级后台工作。
3. **Stopping**：停止接收新的应用级工作，通知受管理工作取消，并等待其在限定时间内收尾。
4. **Disposing**：按依赖关系释放应用拥有的服务和资源。
5. **Stopped**：关闭流程完成。

启动失败应进入受控清理路径；清理失败不得掩盖最初的启动异常。关闭流程应具备幂等性，重复触发不得重复释放资源或重新接收工作。状态模型是协调契约，不要求所有业务服务复制一套相同状态字段。

### 2. 应用级关闭协调器

应用组合根应提供一个应用级生命周期协调入口，负责停止接收新工作、按登记的工作类别发出取消请求、等待受管理工作完成或达到关闭时限、执行模块级异步停止步骤、最后释放 DI 容器及剩余同步资源，并汇总关闭期间的失败、超时和未完成工作，留下可诊断记录。

协调器只负责编排，不应直接拥有所有业务资源，也不应把领域逻辑集中到全局管理器中。模块仍然负责停止并释放自己创建或拥有的资源。

### 3. 后台工作登记与所有权

需要跨越当前调用栈、长期运行或可能影响应用关闭的后台工作，必须有明确的所有者和生命周期策略。适用对象包括长期监控、后台队列、周期任务、持续 I/O 和脱离 UI 生命周期继续运行的工作。

登记信息至少应能表达工作标识及所属模块、工作类别或关闭策略、启动/取消/完成状态、协作取消令牌、可等待的完成句柄，以及失败与超时的诊断信息。

短生命周期、由调用方直接 await 且不会逃逸其所有者作用域的普通异步调用，不必为了形式统一而全部登记。Fire-and-forget 不作为默认后台工作模式。确实无法由调用方等待的工作，必须由明确的所有者捕获其任务、观察异常，并负责完成清理；不得仅因任务被丢弃就视为已获得生命周期管理。

### 4. 取消、等待与超时

关闭顺序必须区分“请求取消”和“工作已经结束”：停止接收新的相关工作；发出协作式取消信号；等待任务退出并执行自身 finally/DisposeAsync 收尾；达到时限后记录超时及剩余工作；按资源类型执行安全的最后处理，然后继续关闭。

不得假定 CancellationToken 能强制终止任意任务。不得无限等待不响应取消的第三方代码、网络请求或外部组件。关闭时限应可配置或由工作类别定义，并为系统关机、用户退出和故障退出保留合理边界。超时策略不得通过无条件终止整个进程来伪装成优雅关闭。

### 5. 资源所有权与释放

- 创建资源的模块或明确接收所有权的模块负责释放资源。
- 一个资源只能有一个明确的释放责任方；借用方不得擅自释放共享资源。
- 异步资源优先通过其真实所有者的异步停止/释放流程完成收尾。
- 依赖其他服务的资源应先于其依赖项释放；释放顺序应由模块依赖关系决定，而非依赖容器内部未声明的偶然顺序。
- 事件订阅、Timer、CancellationTokenSource、SemaphoreSlim、Stream、Process、WebView2 及原生句柄等，必须具有清晰的创建、停止和释放边界。
- Dispose/DisposeAsync 应尽可能幂等；释放异常应记录并继续清理其他独立资源。

不得为了统一而把所有资源转移给一个全局容器，也不得同时让 DI 容器和业务所有者释放同一资源。

### 6. 与现有子系统的边界

**Operations**：Operations 继续负责业务操作状态、进度、取消和作用域语义。它不是后台任务注册表，也不自动承担应用关闭时终止所有业务任务的职责。应用级协调器可以协调受管理的 Operation，但不得破坏其领域状态语义。

**Minecraft 游戏进程与诊断会话**：游戏进程及其日志采集、会话收尾遵循 ADR 0015 和 ADR 0019。普通 UI 退出不得默认终止用户启动的 Minecraft 进程，也不得因 UI 关闭而提前丢弃日志缓冲或诊断证据。是否继续采集、由哪个宿主持有进程监控以及宿主退出策略，必须由游戏会话/采集子系统明确决定。应用级协调器只能调用该子系统提供的生命周期接口，不能直接接管或强制结束游戏进程。

**下载与安装更新**：下载临时产物清理遵循 ADR 0020；Installer、Bootstrapper 和 Uninstaller 的边界遵循 ADR 0029。应用关闭时是否取消下载、允许下载收尾还是保留可恢复状态，应由对应模块声明策略，不能统一粗暴删除临时文件。

**Additions**：Additions 遵循 ADR 0032 的按需加载与功能边界。被加载的 Addition 必须明确其后台工作和资源所有权，并提供可协调的停止/释放入口。卸载或升级前必须确认其工作已停止且资源已释放；无法安全卸载时应拒绝或延迟操作，而不是假装卸载成功。

### 7. UI 与宿主技术约束

WPF 关闭事件本身不能被当作异步任务等待机制。实现时应在真正退出前启动可等待的关闭流程，并防止重复关闭触发；同步退出回调只承担有限的兜底清理，不得在 UI 线程无限阻塞等待。

具体实现可以使用 .NET Generic Host、Hosted Service、DI 生命周期接口或项目现有抽象，但本 ADR 不强制所有模块迁移到某一种框架。选型应服从现有模块化单体结构和清晰的资源所有权。

## 备选方案

### 1. 继续只依赖 ServiceProvider.Dispose

优点是实现简单，符合当前部分模块的做法。缺点是无法表达异步停止、取消后等待、关闭超时和跨模块收尾顺序；容易把“容器已释放”误认为“后台工作已结束”。

### 2. 所有后台工作统一改为 IHostedService

优点是 .NET Host 提供成熟的启动和停止抽象。缺点是会强迫不同生命周期的工作采用相同宿主模型；短任务、领域任务、游戏进程监控和可选扩展未必适合统一托管。该方案可以作为局部实现手段，但不作为全项目强制规则。

### 3. 每个模块完全独立关闭，不设应用级协调

优点是模块自治、全局抽象较少。缺点是无法保证停止顺序、统一关闭时限和整体诊断，也难以发现遗漏登记的长期任务。

### 4. 由全局管理器直接持有并释放所有资源

优点是表面上集中、容易列举。缺点是破坏模块封装和资源所有权，导致全局管理器了解过多领域细节，并增加重复释放和依赖环风险。

## 后果

### 正面影响

- 应用退出不再仅依赖 DI 容器同步 Dispose；
- 长期后台工作有明确所有者、取消方式和完成观察；
- 异步资源能够在容器销毁前完成收尾；
- 关闭超时和清理失败可以被记录、诊断；
- 游戏进程、下载、诊断和 Additions 保留各自领域生命周期，不被应用级机制错误接管；
- 为未来的 WebView2、可选扩展和更多后台服务提供一致的协调边界。

### 成本与风险

- 需要为部分现有 fire-and-forget 工作补充任务持有、异常观察和停止接口；
- WPF 关闭流程需要处理异步关闭、防重入和 UI 响应；
- 模块必须明确资源所有权和关闭策略；
- 关闭时限设置不合理可能导致退出过慢或收尾不足；
- 对不可取消的第三方工作，只能记录超时并执行安全降级，无法保证其优雅结束。

### 明确不在本 ADR 范围内

- 不定义通用内存泄漏检测器、对象池或 GC 调优策略；
- 不引入内核驱动、内核隔离或强制沙箱；
- 不要求所有异步方法和短任务都登记到全局调度器；
- 不要求所有模块统一使用 IHostedService；
- 不改变 Minecraft 游戏进程默认独立于 UI 的生命周期；
- 不替代 ADR 0015、0019、0020、0029、0032 中的领域规则；
- 不保证进程被强制终止、断电或系统崩溃时仍能完成清理。

## 验收标准

1. 应用正常退出时，能够观察到明确的停止接收工作、取消、等待、释放和完成阶段。
2. 关闭协调流程可重复调用，不会重复释放资源或产生未处理异常。
3. 受管理后台工作均有明确所有者；关闭时能够请求取消、等待完成，并记录超时或失败。
4. 关键后台任务的异常不会因 fire-and-forget 而丢失或成为未观察异常。
5. 异步资源在其依赖服务被释放前完成必要收尾；释放顺序有明确依据。
6. 启动失败能够执行有界清理，同时保留原始启动异常。
7. 关闭超时不会无限阻塞 UI 或系统关机；超时工作及采取的后续策略有日志记录。
8. 普通 UI 退出不会无条件终止 Minecraft 游戏进程，也不会破坏其日志与诊断收尾。
9. 下载、安装更新和 Additions 按各自领域策略停止或收尾，不发生无条件删除仍在使用的产物。
10. 至少提供自动化测试覆盖：正常关闭、重复关闭、取消后完成、取消不响应时超时、停止步骤抛异常、启动失败清理及依赖顺序。
11. 通过代码审查确认没有把所有资源所有权集中到单一全局管理器，也没有强制所有模块迁移到同一种托管框架。
