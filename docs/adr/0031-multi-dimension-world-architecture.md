# ADR 0031：多维度世界架构与存储解析

- Status: Accepted (implementation pending)
- Date: 2026-11-02
- Scope: Minecraft 世界维度身份、维度发现、维度存储映射、跨维度数据隔离
- Related: ADR 0026（实例工作台的存档、多人游戏与最近访问）、ADR 0027（原生 C# 世界分析与编辑引擎）、ADR 0030（世界诊断与区块异常定位联动）

## 背景

Minecraft 世界并不只有主世界。下界、末地，以及由模组或数据包定义的自定义维度，都可能拥有独立的区块、实体和 POI 数据。ECL 的存档工作台、Native World Engine 和 World Diagnostics Service 必须以一致的方式发现、识别和访问这些维度。

如果系统把维度等同于固定目录名，或默认所有坐标都属于主世界，就可能漏掉维度、把数据映射到错误位置，甚至将一个维度的诊断结果应用到另一个维度。不同版本的 Minecraft、存档迁移、模组和数据包也会带来存储布局差异。

因此，维度必须成为 ECL 世界领域模型的基础层级，而不是后续附加的兼容性功能。

## 决策

### 1. 统一世界对象层级

ECL 的世界数据模型采用以下逻辑层级：

**World → Dimension → Region → Chunk**

Block、Section、Entity、Block Entity、POI 等对象必须归属于明确的维度上下文。并非所有维度都一定包含每一种存储类型；缺失的数据应表达为不可用或不存在，不得伪造。

维度是世界模型中的一等对象。任何读取、分析、渲染、缓存、诊断或编辑操作，都必须携带明确的 World 与 Dimension 上下文。

### 2. 维度身份与磁盘存储位置分离

Dimension ID 是逻辑身份，不是目录名。至少识别常见原版维度：

- `minecraft:overworld`
- `minecraft:the_nether`
- `minecraft:the_end`

同时允许带命名空间的自定义 ID，例如 `example:moon`。不得将自定义维度强行归类为原版维度。

磁盘路径是某个维度数据的存储映射，必须由存储解析器根据 Minecraft 版本、存档结构和可用元数据确定。传统布局中可能出现 `region/`、`DIM-1/`、`DIM1/` 或 `dimensions/<namespace>/<path>/` 等路径，但这些示例不是跨版本、跨世界的唯一规范，也不能单凭目录名认定维度身份。

逻辑 Dimension ID、规范化后的存储位置和数据来源应分别记录。一个维度可关联多个存储类别（如 Region、Entities、POI），各类别的映射状态独立表达。

### 3. 建立 Dimension Discovery & Storage Resolver

Native World Engine 应提供独立的维度发现与存储解析能力，至少负责：

- 枚举存档中可识别的维度；
- 从可靠元数据、版本规则及存档布局建立 Dimension ID 与存储位置的映射；
- 分别发现 Region、Entities、POI 等可用数据；
- 标记维度来源、解析依据、支持状态和缺失的数据类别；
- 处理不完整、未知、冲突或损坏的布局；
- 在无法可靠确认映射时保留未知状态，不猜测、不回退映射到主世界。

发现目录不等于确认其逻辑维度身份；识别 Dimension ID 也不代表该维度的所有存储数据都存在。解析结果应保留证据与不确定性。

发现与解析必须只读，不执行模组代码，不启动 Minecraft，也不因单个维度解析失败而使整个存档不可用。

### 4. 跨维度数据严格隔离

以下数据的稳定身份或缓存键必须包含 World 身份和 Dimension ID，并在适用时包含数据类别及定位粒度：

- Region、Chunk、Section、Block；
- Entity、Block Entity、POI；
- 地图瓦片、分析结果和资源解析上下文；
- 诊断事件及其目标；
- 编辑目标、备份和恢复记录。

不同维度中相同的 Chunk 坐标是不同对象。不得仅使用 X/Z 坐标作为跨模块对象标识，也不得将某维度缺失的数据自动替换为另一维度的数据。

维度存储映射发生变化、存档移动或重新发现时，应通过稳定身份和重新验证更新映射；不能仅凭旧路径继续写入。

### 5. 世界编辑器以维度为独立工作上下文

ADR 0027 的世界编辑器应提供维度选择与状态展示。切换维度时，Chunk/Region、Biome、Heightmap、实体、Block Entity、诊断叠加层和地图视图必须切换到对应维度的数据上下文。

缓存、异步任务和选择状态必须隔离，避免切换维度后旧任务结果覆盖当前视图。编辑器应显示维度 ID、可读名称（若可解析）、数据来源和支持状态。

自定义维度可先支持基础 Region/NBT/Chunk 读取。若其注册表、生成规则或动态模组行为无法解析，相关图层应标记为未知或近似；不得将其伪装成原版维度或给出虚假的生物群系/生成结果。

### 6. 实例工作台展示维度概览

ADR 0026 的存档详情可展示已发现维度、Dimension ID、可用数据类别及解析状态。维度级诊断摘要应按 World 与 Dimension 分组，并提供进入对应维度编辑器视图的入口。

维度发现失败或某个维度数据损坏时，应局部显示失败状态，不得隐藏其他可正常读取的维度，也不得影响实例启动和普通存档管理。

### 7. 诊断事件必须绑定维度身份

ADR 0030 的诊断目标必须包含世界身份、Dimension ID、定位粒度和坐标/对象标识。日志明确提供维度时应使用该值；缺少维度信息时，不得默认主世界。

通过玩家位置、游戏上下文或相邻日志推断维度时，必须标记为推断并保留依据。无法确认维度时，事件可以保留为未定位或候选关联，但不得产生确定的维度地图标记，也不得用于自动修复。

维度身份不确定、存储映射冲突或目标维度无法重新验证时，必须拒绝破坏性操作。

### 8. 版本兼容与未知维度降级

维度目录布局、元数据来源和 Chunk schema 可能随 Minecraft 版本变化。Resolver 应采用版本化规则和真实存档样本测试，不将某一版本的目录约定推广为所有版本的事实。

对于模组和数据包自定义维度：

- 能可靠发现并识别时，按真实 Dimension ID 管理；
- 只能发现候选目录但无法确认身份时，显示未确认候选，不冒充已识别维度；
- 能读取基础 Chunk 数据但无法解析语义时，提供有限的原始/结构视图；
- 无法安全解析的数据保持只读或不可用；
- 不执行模组代码来补齐动态注册表或生成行为。

## 后果

### 正面影响

- 主世界、下界、末地和自定义维度拥有统一且明确的数据模型。
- 工作台、世界引擎和诊断服务共享同一维度身份语义。
- 相同坐标不会在不同维度之间发生误关联。
- 未知维度和不完整存储能够安全降级，而不是被错误解释。

### 代价与限制

- 必须维护按 Minecraft 版本区分的存储发现与映射规则。
- 自定义维度的完整语义支持受限于静态资源解析能力。
- 缓存、诊断、编辑和持久化模型需要升级为维度感知。
- 旧诊断记录或旧缓存若缺少维度身份，迁移时必须标记为未知，不能猜测为主世界。

## 实施顺序建议

1. 定义版本化 Dimension Descriptor、Dimension ID 和存储映射模型。
2. 收集不同 Minecraft 版本的原版世界样本，验证主世界、下界和末地的发现规则。
3. 实现只读 Dimension Discovery & Storage Resolver，覆盖 Region、Entities、POI 的独立映射。
4. 将 World Engine 的对象身份、缓存键和异步任务改为维度感知。
5. 在编辑器中加入维度选择器和维度状态展示。
6. 将维度概览接入实例工作台。
7. 将 Dimension ID 纳入诊断事件模型，并对缺失/推断维度建立明确降级状态。
8. 扩展到模组与数据包自定义维度，并以真实整合包存档验证。

## 验收要求

- 能在受支持版本的真实存档中分别发现主世界、下界和末地。
- Dimension ID 与磁盘路径分开存储和展示，不依赖单一固定目录名。
- Region、Entities、POI 的映射状态可以独立表达。
- 未知或冲突布局不会被错误映射到主世界。
- 同坐标不同维度的数据、缓存、诊断和编辑目标严格隔离。
- 切换维度不会显示其他维度的异步旧结果或诊断标记。
- 自定义维度能按支持程度降级，未知内容不伪装成原版内容。
- 维度发现和解析为只读，不执行模组代码。
- 单个维度损坏或不可用不影响其他维度及 ECL 常规功能。
- 缺少维度身份的旧诊断记录不会被自动归入主世界。
- 对维度身份或存储映射无法确认的目标拒绝破坏性编辑。
