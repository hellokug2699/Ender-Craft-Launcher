# ADR 0053：Additions 能力权限模型与用户授权流程

- Decision: Proposed
- Implementation: Not Started
- Date: 2026-11-04
- Scope: Additions 权限声明、宿主能力授予、安装前用户知情授权、权限撤销与运行时访问控制
- Related: [ADR 0024：用户授权的自签名代码证书信任](0024-user-authorized-self-signed-code-signing.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0045：原生 Instance Engine 架构与能力边界](0045-native-instance-engine-architecture.md)、[ADR 0052：统一弹窗引擎与渐进迁移](0052-unified-dialog-engine-and-incremental-migration.md)

## 背景

ADR 0032 已确定 Additions 通过版本化 Core API 使用宿主能力，并禁止任意 UI 注入及绕过宿主边界。但仅在扩展目录或管理列表中展示“所需权限”，不足以让用户在安装前理解扩展将接触哪些数据、能够执行哪些操作，也不足以表达用户授权与宿主实际执行限制之间的关系。

扩展可能需要读取实例元数据、访问用户选定的实例文件、读取日志、写入特定文件或访问网络。这些能力的风险并不相同；“访问实例数据”之类的笼统标签无法让用户作出有意义的决定。

ECL 需要一个明确的权限声明、授权、执行和撤销模型。用户体验可以借鉴 OAuth Consent Screen：在安装确认阶段集中说明扩展身份及其申请的访问范围，由用户明确允许或拒绝。但这只是交互模式参考，不意味着 ECL 使用 OAuth 协议，也不意味着一次点击即可授予任意代码访问系统的能力。

## 决策

### 1. 将扩展权限拆分为声明、授予和执行三个层次

权限模型必须区分：

- **声明能力（Declared Capabilities）**：扩展清单请求的能力、访问范围及用途。
- **宿主授予能力（Granted Capabilities）**：用户授权后，宿主根据策略、扩展身份、版本、兼容性及能力支持情况实际授予的能力。
- **运行时执行（Runtime Enforcement）**：每次能力调用由宿主 API 检查调用者身份、当前授权、目标资源和操作范围，并在允许范围内执行。

扩展自行声明某项能力不代表已经获得该能力。UI 中显示用户已同意，也不能代替 Core 对每次调用进行检查。三层信息必须可分别审计和呈现。

### 2. 使用最小权限原则和明确的能力标识

每项能力必须拥有稳定、版本化、可机器校验的 Capability ID，并由宿主定义其语义。能力定义至少包含：

- 稳定标识及版本；
- 用户可读名称和说明；
- 访问对象及数据范围；
- 允许的操作类型，例如读取、创建、修改、删除或网络通信；
- 是否为扩展核心功能所必需；
- 可选的触发条件或使用场景；
- 宿主执行端点及适用的 API 版本。

能力应尽可能细分，避免将只读与写入、单实例与全局、读取日志与读取任意文件合并成一个权限。扩展不得自行定义宿主权限语义，也不得通过未知 Capability ID 获得访问能力。

宿主只授予当前版本明确支持且能够强制执行的能力。未知能力、无法解释的权限声明、超出宿主策略的范围或不兼容的能力请求应导致安装计划失败或相应能力不可用，不得静默降级为宽泛权限。

### 3. 安装前展示 OAuth 风格的授权确认界面

安装流程应分为安装计划预览和最终确认两个阶段。最终确认使用清晰、独立的授权弹窗，交互上参考 OAuth Consent Screen，但不实现 OAuth 协议。

授权弹窗至少展示：

- 扩展名称、图标、版本、发布者和来源；
- 签名与内容完整性验证结果；
- 扩展用途及依赖；
- 申请的每项能力；
- 每项能力的访问对象、数据范围、读写性质、用途及触发时机；
- 必需能力与可选能力的区别；
- 未授权可选能力可能导致的功能限制；
- 安装后是否需要重启及其他重要影响。

用户必须在看到完整授权信息后明确选择允许或拒绝。拒绝即取消安装，不得在用户拒绝后继续静默安装，也不得通过默认勾选、误导性按钮、模糊描述或把授权藏在普通安装确认中取得同意。

最终授权按钮必须设置 **5 秒阅读缓冲期**。授权弹窗完整呈现全部权限信息后才开始倒计时；倒计时期间主确认按钮保持禁用，并依次显示“允许并安装（5s）”至“允许并安装（1s）”，结束后显示可点击的“允许并安装”。倒计时结束不会自动授予权限，仍须用户主动点击确认。

缓冲期必须确保用户确实有机会阅读授权内容：弹窗不可见或权限清单发生变化时，倒计时应暂停或重新开始。用户可以随时拒绝或取消，无须等待倒计时结束。该机制只延迟肯定授权，不得延迟安全验证失败、拒绝操作或其他安全阻断。

签名/来源验证、完整性验证、兼容性检查和权限授权是相互独立的门槛。用户同意权限不代表信任签名者，也不能覆盖签名失败、哈希不匹配、来源不明或包内容异常等验证失败。

### 4. 支持必要能力与可选能力的区分

扩展清单应明确标记能力是运行其核心功能所必需，还是增强功能所可选。

- 必需能力未获授权时，不得启用依赖该能力的功能；若扩展没有可运行的剩余能力，则不得将其标记为可正常启用。
- 可选能力未获授权时，允许安装或启用其他不依赖该能力的功能，并向用户说明受限功能。
- 不得为了让扩展“正常工作”而在运行时自行扩大权限。
- 当用户主动使用一个需要额外能力的功能时，可以再次显示针对该能力的授权请求；必须在访问发生前取得同意。

如未来实现细粒度授权，默认只选择核心功能所必需的能力。任何默认选择都必须准确对应清单中的必要性声明，不能由 UI 自行推断。

### 5. 权限授权应绑定扩展身份、版本和权限清单

授权记录至少应绑定 Addition ID、发布者身份、扩展版本、权限清单摘要/版本、Capability ID、授权范围和授权时间。

出现以下情况时必须重新评估授权：

- 扩展请求新增能力；
- 已有能力扩大数据范围或操作类型；
- 发布者身份发生变化；
- 权限清单语义版本发生不兼容变化；
- 更新后的扩展无法证明仍遵循原授权范围。

纯修复或不改变权限范围的更新不应无故重复打扰用户，但宿主仍须校验更新包身份、签名、完整性和权限清单。不得仅凭 Addition ID 相同就继承不同发布者或不同权限范围的授权。

### 6. 提供权限查看与撤销机制

扩展管理页面应分别展示声明能力、实际授予能力和当前能力状态。用户可以查看每项能力的范围、用途、授权时间及对应扩展版本，并对支持撤销的能力执行撤销或重新授权。

撤销后，宿主必须拒绝后续相关能力调用。对于正在执行的操作，宿主应依据操作类型安全取消、等待安全边界或拒绝新请求；不得假称撤销能够收回已经读取的数据、已经写入的文件或已经发出的网络请求。

禁用或卸载扩展时，应撤销其后续运行能力，并释放其运行时资源。卸载扩展不应擅自删除独立的用户数据；授权记录可按安全审计与隐私策略保留最小必要信息。

### 7. 能力检查必须由 Core 强制执行

所有受保护资源访问都必须通过宿主控制的能力接口。Core 应在调用边界验证：

- 调用者是否为已验证的扩展实例；
- 当前扩展身份和版本是否与授权记录一致；
- 请求的 Capability ID 是否已授予；
- 请求目标是否位于授权范围内；
- 操作类型是否被允许；
- 相关实例、文件或任务是否仍处于有效状态。

Instance 文件访问继续遵循 ADR 0045 和 Instance Engine 的所有权、事务与并发约束。权限系统不得成为绕过 Instance Engine 的替代通道。扩展不得直接访问任意 WPF 对象、主导航、进程内任意对象或未受控制的文件系统接口。

权限清单和授权弹窗只负责表达与记录决策，不构成安全边界。若底层无法强制限制某项能力，就不得向用户宣称该能力已被隔离或可安全细粒度授权。

### 8. 网络与敏感数据能力必须明确区分

网络访问不能仅以“需要联网”概括。若宿主支持网络能力，应至少能够表达目标范围、用途和请求发起主体；无法可靠限制目标范围时，不得声称具备域名级或端点级隔离。

登录令牌、Refresh Token、Access Token、API Key、私钥及其他认证秘密默认不属于普通扩展可读取数据。若某个官方功能确实需要代表用户访问外部服务，应通过 Core 提供的受控凭据代理或专用操作接口完成，不向扩展暴露原始凭据。此类专用授权需要独立、明确的用途说明和最小权限设计。

### 9. 不把 UI 授权误认为操作系统级沙箱

本 ADR 定义的是 ECL 宿主 API 的能力授权和访问控制，不自动提供进程隔离、操作系统沙箱或对任意本机代码的完整约束。

在扩展代码与 ECL 处于同一进程且可直接调用任意 .NET/系统 API 的情况下，仅靠接口约定或 UI 权限列表无法阻止扩展绕过宿主 API。因此，在实际隔离机制得到验证前，ECL 不得宣称扩展受到完整沙箱保护，也不得把未受控的第三方代码当作低风险代码加载。

未来若开放任意第三方扩展，必须单独评估进程隔离、IPC、操作系统权限、资源限制、签名身份和撤销机制；不得默认认为本 ADR 已解决这些问题。

## 备选方案

### 方案 A：只在扩展详情中展示权限说明

优点是实现简单，缺点是用户可能在安装时没有看到权限信息；也无法清晰表达用户授权与宿主实际授予的差异。不能满足安装前知情同意要求。

### 方案 B：安装时只显示一个“信任此扩展”开关

该方案把不同范围、不同风险的能力压缩成单一判断，用户无法知道实际允许了什么，也无法对可选能力进行选择或后续撤销。因此不采用。

### 方案 C：安装时展示细粒度能力授权，并由宿主强制执行

该方案增加清单设计、授权存储、API 检查和 UI 复杂度，但能够将用户可理解的授权决策与实际访问边界对应起来，且为未来第三方扩展留下明确安全边界。作为本 ADR 提案方向。

## 后果

### 正面影响

- 用户在安装前能理解扩展将访问的数据和执行的操作。
- 扩展声明、用户同意和宿主实际授予不会再被混为一谈。
- 可以拒绝可选能力而保留扩展的其他功能。
- 权限变化可以触发重新授权，避免更新后静默扩大访问范围。
- Core 能在能力调用边界统一执行授权检查。
- 为未来评估第三方扩展隔离提供清晰的权限模型基础。

### 代价与风险

- 需要设计稳定的 Capability ID、权限清单 schema 和兼容策略。
- 授权记录需要可靠持久化，并与扩展身份和权限清单绑定。
- Core API 必须覆盖所有受保护访问入口；遗漏任何旁路都可能使 UI 授权失去意义。
- 细粒度授权会增加扩展作者的清单维护和测试成本。
- 同进程任意代码执行无法仅靠本 ADR 中的 API 授权完全隔离，必须避免过度承诺。
- 权限撤销不能逆转已经发生的数据访问或外部副作用。

## 验收标准

- 扩展清单能够声明稳定的能力标识、用途、访问范围、操作类型和必要性。
- 安装前授权界面逐项展示真实能力请求及其数据范围、读写性质、用途和触发时机。
- 用户拒绝授权后安装流程取消，且在授权前没有安装或启用副作用。
- 签名验证、完整性验证、兼容性检查和权限授权彼此独立。
- 未知或宿主不支持的能力请求不会被静默授予。
- 必需能力未获授权时，依赖功能不可用；可选能力未获授权时，其他独立功能仍可工作。
- 授权记录绑定扩展身份、版本和权限清单；权限范围扩大时要求重新授权。
- 扩展详情可分别查看声明能力、宿主实际授予能力及其状态。
- 撤销授权后，宿主拒绝后续对应能力调用。
- 所有受保护访问由 Core 在调用边界执行授权检查，且不能绕过 Instance Engine。
- 凭据秘密不会通过普通文件或通用 API 暴露给扩展。
- 在未实现并验证操作系统级隔离前，产品文档和 UI 不宣称具备完整沙箱。
- 权限系统不会影响未安装扩展时的普通启动、实例管理和游戏启动路径。
