# ADR 0037: Account Appearance and Local Wardrobe Architecture

- Decision: Accepted
- Implementation: In Progress
- Date: 2026-11-02
- Scope: 玩家皮肤、披风资源管理，账户外观 Provider，以及实例外观应用边界
- Related: [ADR 0018：Minecraft 工作区与实例存储位置](0018-minecraft-workspace-and-instance-storage.md)、[ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)

## 背景

皮肤与披风是 Minecraft 玩家身份表达和日常游戏体验的一部分。ECL 已支持 Microsoft 正版账户、离线账户，以及基于 Authlib-Injector / Yggdrasil 的第三方认证账户，但不同账户类型能够访问和修改的外观能力并不相同。

当前 Microsoft 正版认证链已经完成实机验证，包括 OAuth Authorization Code + PKCE、Xbox Live、XSTS、Minecraft Services、Java Edition entitlement、Minecraft profile，以及凭据安全存储和静默刷新。外观功能应复用现有账户与凭据生命周期，不应重新实现登录流程，也不应让外观模块自行维护另一套 Microsoft 登录状态。

离线账户没有 Mojang/Microsoft 账户侧的外观服务；其本地皮肤资源能否在游戏中显示，取决于客户端、服务端或兼容模组/加载器提供的实现。第三方 Yggdrasil 服务的外观接口、上传权限、披风能力和数据格式则由具体服务商决定，不能假设所有服务器都提供统一能力。

因此，ECL 需要区分三个不同问题：

1. 用户有哪些本地皮肤和披风资源可供整理；
2. 当前账户的服务端外观支持哪些读取、上传或切换操作；
3. 某个 Minecraft 实例能否以及如何显示选定的外观。

将这三者混为一个“更换皮肤”操作，会导致界面承诺超出账户或游戏环境的实际能力。

## 决策

### 1. 提供本地衣柜，作为外观资源的统一管理入口

ECL 提供本地外观资源管理能力，负责导入、导出、整理、收藏、预览和校验用户拥有的皮肤及披风资源。

本地资源至少应记录：

- 资源类型（Skin / Cape）；
- 文件格式、尺寸及必要的结构校验结果；
- 皮肤模型类型（Classic / Slim），以及可识别时的来源信息；
- 用户自定义名称、收藏和创建/导入时间；
- 资源内容哈希，用于去重和完整性检查。

衣柜是资源管理能力，不等同于账户管理器，也不意味着其中的资源已经上传到账户或能在所有游戏环境中显示。ECL 不应把第三方网络资源的临时 URL 当作本地资源的永久身份。

### 2. 账户外观操作通过可选 Provider 能力提供

账户系统可以为不同账户类型关联外观 Provider。Provider 应声明自身实际支持的能力，而不是要求所有账户实现相同操作。

能力至少需要区分：

- 读取当前账户外观；
- 读取账户可用皮肤或披风列表；
- 上传或设置皮肤；
- 选择账户已拥有的披风；
- 删除或取消账户外观（仅在服务端明确支持时）。

能力应以运行时结果或明确的 Provider 元数据呈现。未实现、服务端不支持、权限不足、网络失败和账户凭据失效必须是不同状态；不得把“不支持”伪装成暂时网络错误，也不得在操作失败后显示成功状态。

### 3. Microsoft Provider 复用现有正版认证链

Microsoft Provider 应复用 ECL 已有 Microsoft 账户会话和 Minecraft Services 凭据，不得重复打开 OAuth 登录，不得自行持久化另一份 refresh token，也不得绕过账户服务管理凭据生命周期。

Provider 通过账户服务取得执行 Minecraft Services 请求所需的有效凭据；令牌刷新、轮换、安全存储和失效处理继续由现有认证模块负责。外观模块不得记录或展示完整令牌。

在实现前，应逐项验证 Minecraft Services 当前可用的皮肤和披风接口、请求格式、账户权限要求及服务端行为。只有服务端明确提供且实测可用的操作才能声明为支持。账户已拥有的披风选择与上传自定义披风是不同能力，不得混为一谈。

### 4. 离线 Provider 只承诺本地资源能力

离线账户可以使用本地衣柜，并可为实例选择本地外观配置。但离线账户本身不存在可供 ECL 调用的 Mojang/Microsoft 账户外观 API。

ECL 必须区分“已为实例选择资源”和“游戏内已实际显示资源”。只有在当前实例的客户端、服务端或兼容模组方案能够承载该外观时，才可以报告已应用或已验证生效。

ECL 不应仅修改账户名称、UUID、启动参数或本地文件，就宣称原版离线客户端能够自动获得官方皮肤/披风显示能力。若需要额外服务端或客户端组件，应明确说明依赖、适用范围和安装/移除影响。

### 5. 第三方 Provider 按认证服务商能力适配

Authlib-Injector / Yggdrasil 账户只代表认证协议兼容，不代表外观 API 也完全兼容。

第三方 Provider 必须基于具体认证服务器公开且可验证的 API、元数据或明确配置实现。每个 Provider 应独立声明读取、上传、披风和实例显示相关能力。没有可用 API 时，账户仍可使用本地衣柜，但不能声称能够同步到账户。

不得通过猜测端点、向不可信服务器发送账户凭据，或把一个服务商的私有扩展当作 Yggdrasil 通用标准来实现外观同步。服务器地址和凭据仍遵循现有第三方认证安全约束。

### 6. 区分账户外观与实例外观

账户外观是服务端账户档案中的状态；实例外观是某个 Minecraft 实例在运行时实际使用或显示的外观。两者必须分别建模和反馈。

实例可以保存本地外观选择或覆盖配置，但实例级选择不应在用户不知情时修改 Microsoft 或第三方账户的全局外观。反之，修改账户外观也不应悄悄改写其他实例的本地配置。

当用户执行可能修改账户全局外观的操作时，界面必须明确说明影响范围。对于实例本地覆盖，应显示其依赖的客户端/服务端兼容条件。

### 7. 资源和凭据分离存储

皮肤、披风等资源文件及其元数据应存放在 ECL 管理的本地资源目录中；账户外观快照、实例选择配置和认证凭据应分别管理。

不得把资源二进制内容或敏感令牌塞入普通账户 JSON。账户凭据继续由现有安全凭据存储负责；衣柜索引只保存必要的资源引用和非敏感元数据。

删除账户不应默认删除用户导入的本地资源；删除实例也不应误删被其他实例引用的衣柜资源。清理行为应遵循明确的引用关系和用户确认。

### 8. 外观功能不得成为普通启动的前置条件

衣柜、本地预览、账户外观同步和 Provider 初始化均属于可选能力。外观服务不可用、第三方 API 变更、预览组件故障或用户没有导入资源时，不得阻塞账户登录、实例管理或 Minecraft 启动。

外观同步应由用户主动触发或由明确的用户设置授权，不应在后台静默修改账户外观。ECL 不需要为此建立自有外观托管、代理或用户资源云同步服务。

## 备选方案

### 方案 A：只做离线皮肤更换

不采用作为整体方案。它能覆盖本地资源的一部分用途，却无法统一管理正版账户外观，也没有为第三方服务留下清晰的能力边界。离线本地应用仍作为 Provider 的一种能力保留。

### 方案 B：所有账户使用同一套皮肤/披风 API

不采用。Yggdrasil 兼容认证不等于外观 API 兼容；Microsoft 服务能力和第三方服务商扩展也不相同。强制统一会造成虚假的能力承诺，或诱导实现不安全的协议猜测。

### 方案 C：只提供账户外观同步，不提供本地衣柜

不采用。没有 API 的离线和第三方账户将失去资源整理、预览和实例本地配置能力；用户也无法在账户服务不可用时管理已有资源。

### 方案 D：本地衣柜 + 能力声明式 Provider + 实例应用边界

采用。它把本地资源管理、账户服务能力和游戏运行时显示分离，同时允许不同账户类型按真实能力逐步接入。代价是需要维护 Provider 能力模型，并向用户解释不同账户之间的能力差异。

## 后果

### 正面影响

- 用户拥有统一的皮肤与披风资源管理入口，不必依赖某一种账户类型。
- Microsoft 正版账户复用已经验证的认证链和凭据生命周期。
- 离线账户即使没有账户外观 API，仍可使用本地衣柜。
- 第三方认证服务可以按各自 API 独立接入，不会把服务商扩展误认为通用协议。
- 账户全局外观与实例本地外观互不意外覆盖。
- 外观能力故障不会影响普通登录和游戏启动。

### 代价与限制

- Provider 能力需要逐服务商验证和维护，第三方服务的 API 变更可能导致部分能力失效。
- Microsoft Minecraft Services 的具体外观接口、权限和披风操作需要在实现阶段重新核实，不能仅凭登录链完整就推断全部外观操作可用。
- 离线皮肤和披风的实际显示依赖游戏客户端、服务端或兼容组件，ECL 无法仅凭本地资源保证所有环境生效。
- 本地衣柜、实例引用和账户外观快照需要明确的数据生命周期与迁移策略。
- 预览、模型识别和不同皮肤格式兼容会增加客户端实现与测试工作。

## 验收标准

- ECL 能在不登录任何账户的情况下导入、导出、整理和预览本地皮肤资源。
- 皮肤资源能够识别并展示 Classic / Slim 模型；无法识别或格式错误时给出明确结果。
- 衣柜资源、账户凭据、账户外观状态和实例外观配置分开存储。
- Microsoft Provider 复用现有账户服务，不重复实现 OAuth，不在日志或普通配置中泄露令牌。
- Microsoft 的每项外观操作均有对应接口依据、权限说明和真实账户测试记录；未验证的能力不显示为已支持。
- 第三方 Provider 只有在具体服务商 API 已验证时才启用对应能力；缺少 API 时仍可使用本地衣柜。
- 离线账户选择本地外观时，ECL 明确区分“已选择”“已配置”和“游戏内已验证显示”。
- 修改账户全局外观前明确告知影响范围；实例本地外观选择不会未经确认修改账户全局外观。
- 删除账户或实例不会意外删除仍被衣柜或其他实例引用的资源。
- 外观 Provider 不可用、网络中断或预览失败不会阻塞普通登录、实例管理和 Minecraft 启动。
- ECL 不建立强制的外观代理或云托管服务，不静默上传用户皮肤、披风或账户外观数据。
