# ADR 0070: Account Appearance and Appearance Enhance Addition Architecture

- Decision: Accepted
- Implementation: Not Started
- Date: 2026-11-15
- Scope: Core 基础账户外观读取与 2D 展示、Appearance Enhance Addition、3D 外观查看、本地衣柜、账户外观管理及不同账户类型的能力边界
- Related: [ADR 0032：原生功能入口与按需 Additions 扩展体系](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0053：Additions 能力权限模型与用户授权流程](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054：Addition 注册表、清单与生命周期治理](0054-addition-registry-and-manifest-governance.md)
- Supersedes: [ADR 0037: Account Appearance and Local Wardrobe Architecture](0037-account-appearance-and-local-wardrobe.md)、[ADR 0038: Authlib-Injector Texture Upload Protocol Support](0038-authlib-injector-texture-upload-protocol.md)

## 背景

ECL 已经形成账户外观读取、本地皮肤资源管理和 Provider 能力模型的初步实现，但原有 ADR 0037 将本地衣柜、账户外观管理和实例外观应用放在同一套基础架构中；ADR 0038 又进一步规划了通过 Authlib-Injector 扩展协议向第三方 Yggdrasil 服务上传皮肤与披风。

后续产品边界讨论表明，这种组织方式会让基础启动器承担过多非必要的外观功能，也容易让用户误以为所有 Yggdrasil 账户都能通过统一协议管理外观。实际情况是：第三方服务通常只提供读取角色资料和材质的基础能力；上传通道由服务商自行配置，可能默认关闭，还可能受到账户权限、站点积分或其他业务规则限制。uploadableTextures 之类的协议声明不能保证服务商业务层允许操作，更不能保证操作成功。

另一方面，账户当前皮肤的读取和基础展示具有普遍价值。只要账户服务提供可用的外观读取接口，ECL 就不应因为某种账户不允许管理外观而一并关闭读取。主页等原生界面仍应能够展示当前账户的 2D 皮肤预览。

ECL 的 Additions 体系已经明确采用“原生功能入口、可选功能能力”的模型。3D 模型查看、完整衣柜和外观管理属于增强型领域能力，适合由独立 Feature Addition 提供，而不是成为普通启动路径的必需组成部分。

因此，需要重新划分 Core 的基础外观能力与可选增强能力，并明确 Offline、Microsoft 和第三方 Yggdrasil 账户之间的产品权限边界。

## 决策

> 本 ADR 已 Accepted。以下决策作为后续架构与实施的约束；Implementation 状态仍为 Not Started，不代表相关代码已经完成。

### 1. Core 只提供基础外观读取与 2D 当前皮肤展示

ECL Core 保留账户当前外观的基础读取能力，并为原生界面提供轻量级 2D 皮肤展示。

Core 的职责限于：

- 根据当前账户类型和既有认证上下文，读取可获得的当前皮肤外观数据；
- 提供统一、受控的外观读取结果，包含必要的来源、模型类型和读取状态；
- 在主页等原生位置展示当前账户的 2D 皮肤预览；
- 在读取尚未完成、账户不提供外观、资源无效或读取失败时展示明确的占位/状态，不以空白或虚构外观代替；
- 向可选 Addition 提供受控的基础外观读取接口，避免扩展重复实现认证上下文和基础资料读取。

Core 不提供完整衣柜、皮肤资源收藏管理、皮肤上传/切换界面、披风管理界面或 3D 人物查看器。基础 2D 展示不得依赖 Appearance Enhance Addition；未安装、禁用、损坏或不兼容该 Addition 时，Core 的基础展示仍应可用。

外观读取必须复用现有账户和认证模块。不得为外观读取另建登录流程、复制长期令牌或绕过现有凭据管理。读取失败不得影响账户登录、实例管理或游戏启动。

### 2. 完整衣柜由 Appearance Enhance Addition 提供

建立官方 Feature Addition，建议 ID 为 ecl.appearance-enhance。

该 Addition 承担完整的外观增强体验，包括：

- 3D 玩家模型查看器：人物模型渲染、旋转、缩放，以及 Classic / Slim 模型呈现；
- 完整本地衣柜：皮肤资源导入、校验、整理、命名、收藏、预览和删除；
- 外观管理界面：根据账户类型和 Provider 实际能力呈现可用操作；
- 皮肤/披风资源与账户当前外观的关联和应用流程；
- 后续可扩展的外观展示能力，但不得将未实现能力显示为可用。

衣柜整体属于 Addition，而不是 Core 中一个仅隐藏入口的原生功能。未安装该 Addition 时，Core 不提供衣柜的部分管理入口或降级衣柜；原生扩展页面应按 ADR 0032 展示该功能的介绍、依赖和安装状态。

Addition 应复用 Core 的账户身份、认证会话、基础外观读取和受控 API，不得复制认证实现或自行持有第二份凭据。Addition 的安装、启用、加载、禁用和卸载遵循 ADR 0032、0053、0054 及后续适用的扩展治理决策。

### 3. Offline 账户由 Addition 提供本地衣柜和本地外观管理

Offline 账户没有 Mojang/Microsoft 账户侧的外观服务。Appearance Enhance Addition 可以为 Offline 账户提供本地皮肤资源管理，并在明确支持的游戏环境中提供本地外观选择或应用能力。

必须区分以下状态：

- 资源已导入衣柜；
- 用户已为某个目标选择该资源；
- ECL 已完成相应本地配置；
- 游戏客户端/服务端已实际显示该外观。

不得仅凭修改账户名称、UUID、启动参数或本地文件，就宣称原版离线客户端必然能够显示官方皮肤或披风。若应用依赖客户端、服务端或兼容组件，必须明确说明依赖和适用范围。

本地资源属于用户数据。Addition 卸载、账户删除或实例删除不得未经明确授权删除仍被用户或其他实例引用的资源。

### 4. Microsoft 账户管理由 Addition 按已验证接口提供

Appearance Enhance Addition 可以为 Microsoft 账户提供外观管理能力，但必须复用 ECL 现有 Microsoft 认证链和 Minecraft Services 凭据生命周期。

具体管理操作（例如上传/重置皮肤、披风操作）只有在对应接口、请求格式、权限要求、账户限制和真实服务端行为经过逐项验证后，才能作为可用能力开放。不能仅因存在某个 API 端点或当前账户能够读取皮肤，就推断上传、重置和披风管理均已支持。

Microsoft Provider 不得重复实现 OAuth，不得自行保存另一份 refresh token，不得在日志或普通配置中记录访问令牌。未验证或暂不支持的操作必须如实显示为不可用，并提供明确原因。

### 5. 第三方 Yggdrasil 账户仅保留基础外观读取，不提供衣柜和外观管理

第三方 Yggdrasil 账户可以通过其认证服务提供的现有角色资料/材质读取接口读取当前外观。Core 可以将读取结果用于原生 2D 当前皮肤展示；Appearance Enhance Addition 的 3D 查看器在安装后也可以消费这份只读外观数据。

但是，第三方 Yggdrasil 账户不开放以下产品能力：

- 将第三方账户当前皮肤关联到 ECL 衣柜；
- 为第三方账户提供衣柜资源选择、切换或应用入口；
- 通过 ECL 上传、替换或删除第三方账户皮肤；
- 通过 ECL 上传、选择或删除第三方账户披风；
- 根据服务端 uploadableTextures 声明动态开放上述衣柜或管理功能。

该限制是 ECL 的明确产品策略，不根据某个服务端声明的协议能力、站点类型或端点响应动态解除。第三方账户仍可正常认证、读取当前外观（在服务端提供且读取成功时）并启动游戏。

本决策不禁止读取协议中出现的能力元数据，也不代表 ECL 必须删除已有 Authlib-Injector 协议解析代码；但这些信息不得用于向第三方账户开放衣柜或外观写入产品入口。

### 6. 区分基础读取、3D 查看与外观管理

这三类能力必须在模块和接口上明确分离：

- **基础读取**：Core 负责从当前账户上下文获取当前外观数据，并供原生 2D 展示使用；
- **3D 查看**：Appearance Enhance Addition 将可用的皮肤/披风数据呈现为交互式 3D 人物模型，不负责重新认证或绕过账户读取策略；
- **外观管理**：Appearance Enhance Addition 通过按账户类型隔离的 Provider 执行本地资源管理或经验证的账户操作。

Addition 不应为了实现 3D 查看而把账户写入权限作为必需依赖。只读账户仍可在 Addition 中使用 3D 查看器，但不能因此获得衣柜管理能力。Provider 应按能力声明和账户类型返回真实状态，不得暴露虚假的通用写入接口。

### 7. 不改变认证与普通游戏启动边界

外观系统不得成为登录或游戏启动的前置条件。

- Core 外观读取失败不得阻塞登录或启动；
- Addition 未安装、禁用、损坏或加载失败不得影响普通启动；
- 3D 渲染失败不得影响 Core 的 2D 皮肤展示；
- 外观管理操作只能在用户明确发起后执行，不得静默修改账户全局外观；
- 对账户全局外观有影响的操作，必须在执行前明确展示目标账户、目标服务和影响范围；
- 外观数据、衣柜资源、账户凭据和实例配置应分离存储。

ECL 不因本决策建设自有皮肤托管、外观代理或用户资源云同步服务。

### 8. 与旧 ADR 及既有实现的关系

本 ADR 已 Accepted，并整体取代 ADR 0037 和 ADR 0038 的产品架构决策：

- ADR 0037 原先将统一本地衣柜、所有账户 Provider 和实例外观应用纳入基础外观架构；新方案改为 Core 基础读取/2D 展示与 Appearance Enhance Addition 分层，并明确第三方账户只读。
- ADR 0038 原先将 Authlib-Injector Texture Upload Protocol 作为第三方账户通用上传适配；新方案不再将第三方上传作为 ECL 产品能力。协议知识和已有代码可以作为历史技术资产保留，但不得继续作为第三方账户衣柜或上传功能的接线依据。

将旧 ADR 标记为 Superseded 不代表删除历史实现、测试或技术资料。维护者已选择重写旧衣柜实现，不将旧 Core 衣柜作为整体迁移或复用目标。旧本地衣柜、PNG 校验、Provider 和 Authlib 协议代码可供行为审计与兼容性研究；具体底层通用组件是否复用，必须逐项证明不携带旧产品边界或安全语义。不得整体迁移旧衣柜 UI/领域实现，也不得因旧代码仍存在而将新方案视为已实现。

## 备选方案

### 方案 A：所有外观能力继续留在 Core

不采用。完整衣柜、3D 渲染和账户管理并非普通启动器的必要能力，会扩大 Core 的职责、依赖和维护成本，也让不需要外观管理的用户承担不必要的功能复杂度。

### 方案 B：将所有外观能力（包括基础读取和 2D 展示）全部放入 Addition

不采用。主页当前皮肤展示是轻量级基础体验，且读取接口并不等于管理权限。若将读取也完全依赖扩展，未安装 Addition 的用户将失去基础外观展示，账户类型之间也更容易出现不必要的体验差异。

### 方案 C：所有账户统一使用衣柜，只根据 Provider 能力隐藏写入按钮

不采用。第三方 Yggdrasil 服务的业务规则和上传通道不可统一保证；即使协议声明上传能力，也不意味着站点业务允许上传。保留第三方衣柜会形成用户可选择但无法可靠完成的产品流程，因此对第三方账户明确禁用衣柜与管理入口。

### 方案 D：Core 基础读取/2D 展示 + Appearance Enhance Addition

已选择并批准。它在基础体验、可选增强能力、账户权限边界和普通启动可靠性之间取得平衡。代价是需要维护 Core 与 Addition 之间稳定的外观读取契约，并将账户 Provider 的管理能力限制在明确允许的账户类型中。

## 后果

### 正面影响

- 未安装任何 Addition 的用户仍可在原生界面看到当前账户的 2D 皮肤预览。
- 3D 模型查看、衣柜和管理界面按需安装，不增加普通启动路径的必要依赖。
- Offline、Microsoft 与第三方 Yggdrasil 的能力边界清晰，避免将协议兼容误解为账户写入授权。
- 第三方账户仍保留基础外观读取体验，但不会出现上传通道关闭、积分不足或业务规则不透明导致的衣柜失败流程。
- Core 与 Addition 分工明确，扩展可以复用基础读取能力而不重复实现认证。
- 外观模块故障不会影响账户登录和 Minecraft 启动。

### 代价与风险

- Core 需要维护稳定且安全的基础外观读取契约，并处理不同账户服务的读取差异。
- 3D 查看器与完整衣柜必须作为 Addition 独立设计、发布、测试和维护。
- Microsoft 外观管理能力必须逐项真实验证，未验证前不能向用户承诺完整管理。
- Offline 外观应用仍受 Minecraft 客户端、服务端及兼容组件限制。
- 原有衣柜页面与实现必须按新边界重写；历史协议代码不得继续驱动第三方账户的衣柜或写入入口。
- Core 2D 展示与 Addition 3D 展示需要共享资源读取契约，避免重复下载、缓存冲突或显示状态不一致。

## 验收标准

以下标准用于未来评审通过后的实施验收；当前 Implementation: Not Started，以下验收标准均尚待实施与验证。

- 未安装、禁用或损坏 Appearance Enhance Addition 时，Core 仍可读取并展示当前账户的 2D 皮肤；读取失败时显示明确占位状态。
- Core 的基础外观读取复用现有账户认证上下文，不重复登录、不另存长期令牌。
- Core 不包含完整衣柜管理、3D 人物查看器、皮肤上传/切换或披风管理 UI。
- 官方 Addition 以独立 Feature Addition 发布，建议 ID 为 ecl.appearance-enhance，并遵循 ADR 0032 等扩展治理决策。
- 安装 Addition 后可使用 3D 人物查看器；渲染失败或 Addition 不可用不影响 Core 2D 展示和普通启动。
- 完整衣柜的导入、校验、收藏、整理、预览和删除由 Addition 提供，资源删除遵循引用保护和用户数据安全规则。
- Offline 账户的本地外观流程明确区分资源导入、选择、配置和游戏内实际显示，不作超出环境能力的承诺。
- Microsoft Provider 复用既有认证链；每项账户管理操作在开放前均有接口依据、权限验证、真实账户测试和可复核结果。
- 第三方 Yggdrasil 账户在 Core 中可读取当前外观并进行 2D 展示（以服务端实际提供数据为前提）。
- 第三方 Yggdrasil 账户不出现衣柜关联、衣柜选择、皮肤/披风上传、替换、删除或其他账户外观管理入口；uploadableTextures 不得解除该限制。
- Addition 的 3D 查看器可以读取第三方账户当前外观，但仅限只读展示，不提供写入能力。
- 外观读取、渲染、Addition 加载或管理操作失败均不会阻塞账户登录、实例管理或 Minecraft 启动。
- 账户凭据、外观快照、本地衣柜资源和实例配置分离存储；日志不泄露令牌或不必要的用户材质数据。
- 实施记录明确区分历史代码仍存在、已迁移、已隔离、已移除和真实验收状态，不以 ADR 状态变更代替代码审查。
