## 背景

ECL 的首次安装、版本部署、更新、完整性检查和故障恢复原本由 ADR 0016、0017、0034 分别描述。三份决策分别从 Bootstrapper、图形化安装器和自身完整性切入，但它们共同构成同一条生命周期：获取安装介质、建立安装、启动、检查、更新、失败回滚、修复以及在必要时离线重建恢复环境。

分散描述造成了职责交叉和决策缺口。例如，Bootstrapper 的安全部署边界、Installer 携带的安装材料、Repair Mode 的恢复来源分别写在不同 ADR 中；更新源默认指向 GitHub，但中国大陆等网络环境可能无法稳定访问 GitHub。若 GitHub 不可达、本地 Recovery Cache 又缺少材料，当前设计没有完整说明如何切换来源、导入离线介质或恢复 Bootstrapper 自身。

此外，Installer 与 Bootstrapper 不只是后台部署组件：它们都需要面向用户的独立图形界面。首次安装不能依赖尚未安装的 ECL 主程序提供交互；更新与恢复也不能假设主程序始终可运行。因此，两者的 UI 入口、运行边界与主程序 UI 的关系必须纳入统一生命周期架构。

本 ADR 将这条生命周期统一为一个架构，并保留现有已实现能力。它不表示所有新机制已经实现；当前实现状态和待完成事项以部署文档及实施记录为准。

## 决策

### 1. 统一生命周期与组件职责

安装、更新和恢复共享同一套发布信任模型、Manifest 协议、内容验证和部署引擎，但由不同组件承担明确职责：

- **Installer**：提供首次安装与用户交互，检查安装介质是否齐备，将部署工作委托给 Bootstrapper；不得实现第二套签名验证、归档解包或版本提交逻辑。
- **Bootstrapper**：独立于 ECL 主程序，负责安装根目录管理、启动当前版本、部署、版本切换、回滚、完整性检查和 Repair Mode。不得依赖主程序正常运行才能执行恢复。
- **Update Source Resolver**：解析并按策略尝试可用更新来源，只负责传输来源选择和故障切换，不授予来源信任。
- **Trust Verifier / Package Verifier**：验证发布者签名、Manifest 语义、包大小、包哈希及逐文件完整性。所有网络来源和用户导入介质均经过相同验证。
- **Deployment Engine**：将已验证输入放入 staging，执行安全解包、逐文件校验、版本目录提交和原子指针切换。
- **Recovery Engine**：优先使用已验证的本地恢复材料；材料不足时尝试受信任网络来源；仍不可用时支持导入完整离线恢复介质并给出人工恢复指引。

组件可以在实现上共享程序集或服务，但不得因此混淆信任边界。Installer 不得绕过 Bootstrapper 部署；Update Source Resolver 不得决定文件是否可信；恢复流程不得绕过正常部署验证。

#### 1.1 Installer 与 Bootstrapper 的独立 UI

Installer 与 Bootstrapper 均提供自己的图形化用户界面，并作为独立于 ECL 主程序的用户交互入口：

- **Installer UI**：承载首次安装所需的用户交互与流程状态。它必须能够在 ECL 尚未安装、主程序尚不存在或无法启动时独立运行；安装前完整性确认继续遵循 ADR 0025。
- **Bootstrapper UI**：承载启动前检查、版本部署、更新、回滚、Repair Mode 与离线恢复等需要用户参与的操作及其状态反馈。它必须在 ECL 主程序缺失、损坏或无法启动时仍可独立呈现相应恢复入口。
- 两者拥有各自的窗口/页面与生命周期，不作为 ECL 主窗口内部页面，也不得依赖 ECL 主程序启动后才能显示。
- 两者在视觉语言、排版、控件反馈和可访问性方面遵循 [ADR 0050](0050-ecl-ui-architecture-and-design-system-overhaul.md) 的全局 UI 设计系统；但不因此要求复用 ECL 主窗口 Shell、主导航或运行时。
- Installer 与 Bootstrapper 的 UI 只负责呈现状态、收集必要输入并发起受控操作。签名验证、内容校验、部署、回滚和恢复仍由本 ADR 定义的对应引擎执行，UI 不得复制或绕过这些逻辑。
- 本节只确定独立 UI 的架构边界，不规定具体页面布局、文案、控件排列或完整交互步骤；这些细节由后续独立 UI 页面规划定义。

### 2. 安装目录、用户数据与版本部署边界

- 程序安装目录与用户数据目录、Minecraft 工作区完全分离。
- 安装目录保存 Bootstrapper、公开信任材料、部署状态、版本目录、staging 和必要恢复材料。
- 每个版本部署到独立版本目录；新版本先在 staging 中准备，验证完成后才可提交。
- 当前版本通过安全写入的指针记录；切换失败时旧指针和旧版本保持可用。
- 保留最后已知可用版本，回滚通过指针切换完成，不依赖重新下载。
- 安装、更新、修复和回滚不得清理 Minecraft 实例、世界、账户凭据、配置、日志或用户导入内容。
- 卸载时程序移除与用户数据清理必须是不同操作；数据删除需明确展示范围并取得用户确认。

### 3. 发布输入与统一信任模型

所有发布输入都视为不可信数据，包括 GitHub 直连、代理、镜像、缓存和用户手动导入的文件。

统一验证顺序至少包括：

1. 使用安装介质或客户端预置的受信任公钥验证 detached Manifest signature。
2. 严格验证 Manifest schema、产品、频道、版本、平台、架构、最低 Bootstrapper 版本及资源路径。
3. 验证完整包大小与 SHA-256。
4. 安全解包，拒绝路径穿越、绝对路径、符号链接、重复条目及超限内容。
5. 按 Manifest 逐文件验证大小与 SHA-256，并拒绝未声明文件。
6. 验证当前版本策略、版本回退限制及部署前置条件。
7. 全部通过后才允许写入正式版本目录或修复现有文件。

SHA-256 用于内容完整性，发布者身份由签名和受信任密钥建立。HTTPS 保护传输，但不能替代签名。来源地址、TLS 证书或代理服务本身均不能成为发布者信任根。

信任公钥不得由未经验证的网络响应替换或自动加入。密钥轮换必须遵循独立、可审计的信任更新策略；不能通过普通代理或普通更新 Manifest 静默更换信任根。

### 4. 多来源更新与故障切换

更新源不得被设计为单一 GitHub URL。Resolver 应支持多个有序候选来源，并允许按产品、发布频道、平台和架构解析相同的发布资源。

候选来源类别包括：

1. **官方 GitHub 直连**：默认首选来源。
2. **GitHub 代理 / gh-proxy 类来源**：作为可选的传输路径，用于改善 GitHub 在特定网络环境中的可达性。
3. **独立镜像**：可选的官方发布资产副本，必须提供与原始发布完全一致、可由客户端独立验证的 Manifest、签名和包内容。
4. **本地来源**：Recovery Cache、安装介质或用户手动选择的离线恢复包。

网络来源的具体顺序、超时、重试和健康状态策略由部署文档及实现配置细化。来源健康记录只影响尝试顺序，不改变信任级别；应有过期机制，避免一次失败永久屏蔽某来源。失败切换必须有界，避免无限重试和长时间阻塞。

代理只允许访问明确允许的 GitHub 发布资源。代理目标与逐跳重定向目标必须经过主机和协议策略检查；禁止把任意 URL 当作可信代理配置。不得向代理发送 GitHub Token、访问令牌、签名私钥或其他秘密。代理可以观察请求元数据、拒绝服务或返回过期内容，因此必须视为不可信传输渠道。

无论使用何种网络来源，客户端都必须对最终取得的原始 Manifest 字节执行签名验证，再验证 Manifest 指定的包哈希和逐文件哈希。代理返回签名错误、哈希错误、Manifest 语义错误或可疑降级内容时，不得将其简单视为普通网络超时；必须拒绝该输入、记录来源与失败类别，并按安全策略决定是否继续尝试其他来源。切换来源不能降低验证要求。

### 5. 版本新鲜度与防回退

签名有效只能证明内容由受信任发布者签署，不能单独证明它是当前最新版本。客户端必须结合当前已知版本、频道策略、已验证发布元数据和本地持久化状态防止意外回退。

- 不得因代理或镜像返回缓存的旧 Manifest 而静默降级。
- 允许的显式回滚必须由用户或受控恢复策略触发，并清楚说明目标版本及影响。
- 对于缺少可信新鲜度证据的离线环境，客户端应区分“签名有效但新鲜度未知”和“确认是当前版本”，不得伪称已获取最新版本。
- 版本回退保护状态应安全持久化；损坏或状态冲突时采取保守策略并提供诊断，不得自行重置为无约束状态。

### 6. 本地 Recovery Cache

Recovery Cache 用于在网络不可用时恢复已知版本，不是永久归档，也不是独立信任根。

- 缓存内容至少包括可验证的 Manifest、签名及其对应的完整恢复文件或完整包。
- 写入缓存前必须完成验证；读取使用前必须重新验证签名、哈希和目标版本关系。
- 缓存应有明确空间上限、保留数量和淘汰策略。
- 不得淘汰当前版本、最后已知可用版本或仍被恢复事务引用的材料。
- 缓存损坏、缺失或版本不匹配时必须明确报告，并继续评估其他来源。
- 普通缓存清理不得删除恢复所需材料；清理恢复缓存必须遵守独立保留规则。

本地恢复优先于网络下载。若缓存具有完整且可信的目标材料，网络不可用不得阻止本地修复。

### 7. Repair Mode 与 Bootstrapper 自身恢复

Bootstrapper 必须保持足够小且独立，主程序损坏或缺失时仍可执行完整性检查、回滚和 Repair Mode。Repair Mode 只修复 ECL 自身拥有的文件，不得顺带重置用户环境。

Bootstrapper 本身损坏或缺失是独立故障边界：安装目录内的 Bootstrapper 副本不能作为唯一恢复入口。完整安装介质必须携带可独立运行的 Bootstrapper 和恢复所需的公开信任材料，使用户可以从外部介质重新建立恢复入口。不得要求损坏机器先通过网络下载一个新的 Bootstrapper 才能开始恢复。

若 Bootstrapper 自身更新，必须先验证新 Bootstrapper，并保留可启动的旧副本或独立恢复副本；替换操作必须可恢复。任何自更新流程不得先销毁唯一可用的恢复入口。

### 8. 完整离线恢复介质与手动导入

完整安装介质不仅用于首次安装，也必须能够在目标机器完全无法访问网络、安装目录损坏或 Bootstrapper 缺失时重建 ECL。

介质至少应包含：

- 独立 Bootstrapper；
- 与该发布包匹配的 Manifest 及 detached signature；
- 受信任公钥材料（其信任必须来自预置或既有信任链，不能仅因介质同时携带公钥就自动信任）；
- 完整发布包；
- 介质格式/版本说明及必要的恢复入口。

用户可以在另一台设备下载介质，再通过 U 盘或其他本地方式传输到故障机器。Repair Mode 或独立 Bootstrapper 应提供明确的手动导入路径。导入文件与网络下载文件执行相同的签名、Manifest、哈希、路径和部署校验。

不得要求下载介质的设备与目标机器共享信任状态；不得因为文件来自本地磁盘或可移动介质而跳过验证。介质不包含用户 Minecraft 工作区、账户凭据或用户配置。

### 9. 故障分类与最终人工恢复

系统至少区分 DNS/名称解析失败、连接拒绝、连接超时、TLS 错误、HTTP 错误、代理拒绝、资源缺失、签名错误、Manifest 不兼容、哈希不匹配、磁盘空间不足、文件占用、部署失败和恢复材料不足。

- 可重试的网络故障可以触发下一候选来源。
- 签名、信任、哈希和路径安全错误必须被记录为安全验证失败，不得降低校验级别。
- 磁盘、权限或文件占用错误应给出对应诊断和可执行建议，不应盲目切换网络来源。
- 所有网络来源不可用且本地材料不足时，明确告知用户无法自动恢复，并提供官方完整安装介质的获取入口、手动导入步骤、校验结果和切换网络环境的建议。
- 如果故障机器无法访问任何下载站点，允许用户使用另一台设备获取介质；ECL 不承诺在没有网络和没有本地材料时凭空恢复文件。
- 不得无限重试、静默退出、伪造恢复成功或自动删除现有安装以“重新开始”。

### 10. 启动体验与用户数据保护

正常启动不得以更新服务器可用为前提。用户关闭自动更新检查时，不得为了启动而访问网络。普通启动只执行必要的轻量完整性检查；需要全量验证时应基于明确风险或用户操作触发。

Installer 与 Bootstrapper 必须分别提供独立的图形化交互界面，不得将其仅视为无 UI 的后台执行器。Bootstrapper 的恢复界面必须在主程序不可用时仍能启动。

恢复界面必须区分检查、下载、验证、部署、回滚和结果状态。显示当前安装状态、恢复来源、目标版本、失败类别和下一步操作。恢复操作不得隐瞒将要替换的程序版本或清理范围。Installer 与 Bootstrapper 的 UI 遵循 ADR 0050 的全局设计系统，但不依赖主程序 Shell；具体页面行为由独立页面规划定义。

ECL 遵循本地优先原则：不上传用户 Minecraft 实例、世界、账户凭据、配置或日志作为更新/恢复的默认步骤。诊断日志保存在本地；用户主动分享时必须明确展示内容和接收方。

## 备选方案

### 方案 A：继续由三份 ADR 分别定义安装、部署和恢复

不采用。三者共享同一发布信任模型和生命周期，分散维护容易产生重复、遗漏和相互冲突的约束。原 ADR 保留为历史记录，由本 ADR 统一取代。

### 方案 B：只使用 GitHub 直连，失败后提示用户自行处理

不采用。无法充分应对 GitHub 在部分网络环境中的不可达，也没有充分利用可验证代理、独立镜像和离线介质。

### 方案 C：信任代理或镜像提供的文件与元数据

不采用。代理和镜像是传输渠道，不是发布者。信任代理会使中间服务能够替换发布内容或信任根。

### 方案 D：多个传输来源 + 统一客户端验证 + 本地缓存 + 完整离线介质

采用。该方案兼顾可达性、发布者身份验证、网络故障容忍和最终人工恢复；不需要 ECL 自建必须在线的恢复服务器。

## 后果

### 正面影响

- 安装、更新、完整性检查和恢复具有统一的生命周期模型与信任边界。
- GitHub 不再是唯一网络传输路径；可按需增加 gh-proxy 类来源和独立镜像。
- 任意代理或镜像篡改内容都必须通过客户端签名和哈希验证才能进入部署。
- 网络不可用时优先使用本地缓存；缓存不足时可从其他设备导入完整恢复介质。
- Bootstrapper 自身损坏不再只能依赖安装目录内的 Bootstrapper。
- 最终无法自动恢复时，用户能够得到明确、诚实且可操作的人工恢复指引。
- 安装、更新、回滚和修复继续保护 Minecraft 用户数据。

### 代价与风险

- 多来源解析、超时、健康状态、重定向策略和版本新鲜度管理增加实现复杂度。
- 公开 gh-proxy 服务的稳定性、隐私和运营策略不可控；不得将其作为唯一或永久保证的来源。
- 独立镜像需要额外的发布同步与资产一致性验证，但不能拥有独立签名权。
- Recovery Cache 和离线介质增加磁盘占用及发布流程复杂度。
- Bootstrapper 自身更新和外部恢复入口属于高信任路径，需要额外测试与审计。
- Installer 与 Bootstrapper 需要分别维护独立 UI 的启动、状态呈现、可访问性与回归测试；同时必须控制 UI 对部署核心的依赖，避免削弱恢复入口的独立性。
- 旧客户端的信任根轮换和新鲜度状态迁移必须谨慎设计，避免合法更新被锁死或降级保护失效。

## 验收标准

1. 首次安装介质包含 Installer 所需的完整发布输入与可独立运行的 Bootstrapper；安装端不实现第二套部署验证。
2. 正常更新、首次安装、Repair Mode 和手动导入使用相同的 Manifest、签名、哈希和路径安全验证规则。
3. GitHub 直连失败时，Resolver 能按配置尝试其他允许来源；所有重试有界且可诊断。
4. 使用 gh-proxy 类来源时，只能访问允许的 GitHub 发布资源；重定向逐跳受控，不发送任何授权凭据或秘密。
5. 从直连、代理、镜像和本地介质取得的同一发布资产具有相同的签名验证结果；篡改 Manifest、签名、包或单文件均被拒绝。
6. 代理或镜像返回签名有效但过期的 Manifest 时，客户端不会静默降级；新鲜度未知时如实表达。
7. 一个来源失败不会阻止尝试其他来源；来源健康状态过期后可以重新探测，不会永久屏蔽来源。
8. 网络不可用且 Recovery Cache 材料完整时，可以不访问网络完成修复。
9. Recovery Cache 缺失或损坏时，不会被当作可信材料；系统能够继续尝试网络来源或离线介质。
10. Bootstrapper 缺失或损坏时，可使用独立完整安装介质重建恢复入口；该过程不依赖故障安装目录中的 Bootstrapper。
11. 手动导入的完整恢复介质在部署前完成相同的签名、Manifest、哈希和逐文件验证。
12. 所有网络来源不可用且本地材料不足时，系统明确停止自动恢复，展示官方介质获取、跨设备传输、手动导入和网络切换指引。
13. 模拟下载中断、校验失败、磁盘空间不足、文件占用、提交中断和首次启动失败后，最后已知可用版本仍可恢复。
14. 正常启动不因更新源不可达而失败；关闭更新检查时不访问更新源。
15. 安装、更新、回滚和修复不会删除或修改用户 Minecraft 实例、世界、账户、配置及用户导入数据。
16. 恢复日志能够记录阶段、版本、来源类别和失败原因，不包含访问令牌、私钥或不必要的用户数据。
17. Installer 拥有可独立运行的首次安装图形界面；Bootstrapper 拥有可独立运行的启动/更新/恢复交互界面。两者在 ECL 主程序未安装、缺失或无法启动时，仍能分别提供其职责范围内的 UI 入口。
18. Installer 与 Bootstrapper 的 UI 遵循 ADR 0050 的全局设计系统，但不依赖 ECL 主窗口 Shell、主导航或主程序运行时；UI 不实现、不绕过签名验证与部署逻辑。

## 实施阶段

- **P0：统一现有实现与文档**：保持当前 Installer、Bootstrapper、Manifest、签名、staging、指针切换、回滚、Repair Mode 和 Recovery Cache 行为；统一部署文档和验收口径。
- **P1：来源解析与容灾**：实现有界多来源尝试、GitHub 代理候选、重定向约束、来源健康状态及失败分类。
- **P2：完整离线恢复**：定义可独立验证的恢复介质格式、手动导入流程和跨设备恢复 UX。
- **P3：Bootstrapper 自恢复与信任生命周期**：完善 Bootstrapper 独立副本、自更新、信任根轮换、防回退和新鲜度持久化。

实施阶段不代表对应能力已经完成；各阶段必须按验收标准提供测试或实机证据。
