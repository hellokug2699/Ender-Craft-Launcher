# ADR 0061: ECL AI Conversation and Capability Architecture

- Decision: Accepted
- Implementation: Not Started
- Date: 2026-11-08
- Scope: ECL AI Addition 的产品模式、推理后端、Minecraft 知识搜索、诊断增强、对话与上下文生命周期、数据持久化、隐私及安全边界
- Related: [ADR 0015](0015-process-scoped-game-log-sessions-and-diagnostics.md)、[ADR 0032](0032-native-feature-interfaces-and-optional-additions.md)、[ADR 0033](0033-local-minecraft-diagnostic-and-knowledge-engine.md)、[ADR 0044](0044-local-first-network-diagnostics-and-data-sovereignty.md)、[ADR 0053](0053-addition-capability-permission-and-user-consent.md)、[ADR 0054](0054-addition-registry-and-manifest-governance.md)、[ADR 0055](0055-ecl-hybrid-workspace-and-native-tool-platform-architecture.md)

## 背景

ECL 希望提供 AI 能力，帮助玩家理解 Minecraft、模组与相关技术，也帮助玩家分析日志、崩溃和运行环境问题。同时，用户可能只想把 ECL 当作通用聊天入口，并不一定要讨论 Minecraft。产品不应擅自判断或限制用户的聊天主题。

AI 能力涉及模型推理、网络搜索、游戏数据访问、远程数据传输、凭据、对话历史和长期上下文。如果每个用途分别实现聊天、模型配置、存储和权限，会造成重复建设；如果将所有能力直接集成进 ECL 主程序，又会扩大主程序体积、启动依赖和维护范围。

ECL 还需要遵守既有 Addition 架构：专业能力按需安装，普通启动不依赖扩展；Core 提供可信的宿主边界，Addition 在授权范围内使用宿主能力。System Prompt 可以表达 ECL 对模型行为的要求，但不能替代真实权限控制。

## 决策

### 1. 建立一个统一的 ECL AI Feature Addition

官方 AI 能力以一个 Feature Addition 登记：

- Name：ECL AI
- Addition ID：`ecl.ai`
- Type：`Feature`
- Registry Status：`Planned`

ECL AI 内部提供三个工作模式：

| 模式 | 职责 |
|---|---|
| Chat | 通用聊天，不限制用户讨论主题；不要求 Minecraft 专业上下文 |
| Knowledge | 帮助玩家理解 Minecraft、模组、Loader、配置、机制和相关技术；按需搜索外部资料 |
| Diagnostic | 帮助玩家理解日志、崩溃和环境问题；结合可用证据进行原因分析并提出建议 |

Chat、Knowledge 和 Diagnostic 是同一个 Addition 内的产品模式，不分别登记为三个 Addition。它们共享对话系统、上下文管理、模型后端、凭据管理、存储和安全机制，但可以拥有不同的 Prompt、上下文来源、工具权限和专业行为。

不将 AI Runtime、Model Manager、Search Broker 或 Conversation Manager 单独登记为强制依赖的 Addition。它们属于 ECL AI 的内部基础设施能力；Core 仅提供必要的安全宿主原语。未来若出现独立复用需求，应另行评估，不预先拆分。

### 2. 明确 Core 与 ECL AI 的职责边界

Core 负责提供可信且可复用的宿主能力，包括但不限于：

- 安全凭据存储与受控凭据使用；
- 用户授权、权限检查和授权撤销；
- 受控文件、实例日志和其他本地资源访问；
- 受控网络访问及必要的请求安全限制；
- ECL 数据目录和受控持久化能力；
- Addition 生命周期、隔离和宿主故障边界。

ECL AI 负责：

- 对话和工作模式管理；
- 上下文组装、裁剪、摘要和来源追踪；
- 本地模型与远程 Provider 的适配；
- 模型配置、能力信息和本地模型生命周期管理；
- Prompt 管理、工具编排和结果呈现；
- Knowledge 搜索策略与检索结果整理；
- Diagnostic 证据组织、解释和建议；
- 对话历史、附件引用、共享知识和 AI 专属缓存管理。

Core 不因安装 ECL AI 而承担模型推理、模型下载或远程 AI API 费用。ECL AI 不得绕过 Core 直接读取任意用户文件、凭据或系统资源。

### 3. 推理后端保持可替换，用户承担远程 Provider 费用

ECL AI 应支持可插拔推理后端，目标范围包括：

- **Local Model**：在用户设备上运行模型；推理请求和对话内容默认留在本地。
- **Remote Provider**：用户自行配置 Provider、模型和 API Key；请求由用户选择的服务商处理，费用由用户承担。
- **Self-hosted / LAN Provider**：用户使用自行部署或局域网可访问的模型服务。
- **Hybrid Routing**：在用户明确配置和授权后，按任务选择本地或远程后端。

ECL 不提供由 ECL 付费承担的公共 AI 推理 API，不将用户请求默认转发到 ECL 自有服务器，也不绑定单一模型厂商或专有请求格式。

用户可以使用 ECL AI 进行任意主题的普通聊天。ECL 不以“是否与 Minecraft 有关”作为拒绝回答或限制使用的理由。远程 Provider 的实际费用由用户与 Provider 之间的服务关系决定；ECL 可以提供 Token/费用估算、预算提醒或用户自设限制，但这些控制默认不得成为强制聊天配额。Provider 未提供可靠价格或用量数据时，ECL 必须明确显示未知或估算值，不得伪装成准确账单。

本地模型的算力、内存、显存和磁盘需求应在模型选择与使用过程中向用户说明；ECL 不应将“本地运行”宣传为没有设备成本。

### 4. 本地推理与联网搜索相互独立

本地模型可以使用联网搜索。模型推理位置与资料检索位置是两个独立维度：

- 模型可以完全在本地推理；
- 搜索可以通过 ECL 受控网络能力访问外部资料；
- 搜索结果返回后，由本地模型进行理解、归纳和回答；
- 使用远程模型时，也可以使用相同的受控搜索能力，避免每个 Provider 自行建立不受控网络访问。

Knowledge 模式应能按需查询 Minecraft 原版知识、模组资料、Loader 文档、项目仓库、Issue、Wiki 和其他经过治理的来源。Diagnostic 模式也可以查询模组文档、已知问题和修复记录。搜索能力属于 ECL AI 的共享基础设施，不专属于 Knowledge。

搜索请求必须经过受控网络边界。不得因模型提出任意 URL 就自动允许任意网络访问、重定向、文件下载或本地网络探测。请求预算、频率、响应大小、超时、域名/来源策略和异常响应处理应由宿主及搜索能力共同约束。

搜索结果、网页、README、Issue、日志和附件均属于不可信输入。其内容不得覆盖 System Prompt、改变宿主权限或直接触发未授权工具操作。搜索结果应尽可能保留来源链接、检索时间、版本适用范围和证据片段；无法确认的版本或来源信息必须明确标记。

搜索请求本身也可能向服务端暴露查询内容和网络元数据。ECL 应最小化搜索请求，不得为了查询一个简单问题而附带无关日志、用户名、实例目录或其他私人上下文。

### 5. Diagnostic 必须具有不依赖其他 Addition 的基础能力

ECL AI 的 Diagnostic 模式必须在没有安装其他可选 Addition 的情况下提供基础诊断能力。它可以使用用户明确选择的日志、崩溃报告和 Core 已授权提供的运行环境/日志会话信息，完成基础上下文整理、异常解释、原因推断和建议生成。

以下现有 Addition 可以作为可选增强，而不是强制依赖：

- `ecl.diagnostic-engine`：提供更丰富的结构化诊断事件、规则结果和证据关联。
- `ecl.diagnostic-knowledge-base`：提供额外的版本化故障模式、兼容信息和经过审核的解决方案。

缺少、禁用或版本不兼容的增强 Addition 不得阻止 Diagnostic 工作；ECL AI 应说明当前可用的证据范围和能力限制。可选增强不得被静默安装或自动授予权限。

Diagnostic 输出必须区分直接证据、较强推断、一般可能性和未知事项。模型不得仅凭日志末尾、最后一个异常类或某个模组名称就断言根因；不得把模型生成的解释覆盖成原生诊断证据。需要引用具体日志行或堆栈时，应保留原始证据位置，摘要不能替代原始证据。

### 6. 统一对话系统，默认隔离不同对话

Chat、Knowledge 和 Diagnostic 使用统一的对话管理与消息存储能力。用户可以创建多个对话，并为不同任务保留独立历史。

默认情况下，每个对话是独立的安全与上下文边界：

- 当前对话可以读取自身消息和明确关联的附件；
- 一个对话不得自动读取其他对话的消息、附件或摘要；
- 模型不得自行跨对话搜索或拼接历史；
- 更换模型不改变对话归属和历史记录；
- 不同模式可以使用不同的工具权限和上下文策略。

跨对话共享通过独立的 Shared Knowledge 空间实现。用户可以明确选择资料或经确认的摘要加入共享空间，并在之后管理、撤回或删除。用户明确启用的非敏感全局偏好可以作为独立上下文提供，但不得将私人聊天内容自动提升为全局记忆。

本 ADR 不要求具体 UI 布局或对话切换交互；但必须保证默认隔离语义不能被 UI 便利性或模型自主行为绕过。

### 7. 每次请求都按需构建上下文，不等同于完整聊天记录

聊天记录是用户的持久历史；模型上下文是为某一次请求临时构建的输入。两者必须分离。

上下文可由以下来源组成，具体选择由当前模式、任务、模型能力、用户授权和上下文预算共同决定：

- ECL System Prompt 与当前模式 Prompt；
- 当前对话中相关的近期消息；
- 当前对话的历史摘要；
- 用户明确共享的 Shared Knowledge；
- 当前任务所需的日志、实例信息、附件或其他资源；
- 经受控搜索获得的外部资料；
- 必要的结构化诊断证据。

不得默认把所有聊天历史、所有附件、全部实例信息或整个游戏目录发送给模型。只选择完成当前任务所必需的最小数据范围。

长对话可以采用近期原文、历史摘要和按需重新读取原始证据的分层策略。摘要必须能够追溯到来源消息或证据范围，并明确它是摘要而非原始材料。涉及诊断证据、路径、行号、版本或其他需要精确引用的信息时，必须在可用情况下重新读取原始来源，不得把摘要当作原始证据。

上下文裁剪不得静默丢弃会改变结论的重要事实。无法容纳关键上下文时，应说明限制、请求用户缩小任务范围，或在获得授权后采用其他模型/后端。

### 8. 聊天记录默认本地持久化，并提供用户可控生命周期

ECL AI 的对话消息、对话元数据、摘要、附件引用和共享知识默认由 ECL 在本地管理，不默认同步到 ECL 服务器或其他云端。

逻辑上应区分保存区域：

- 对话消息与对话元数据；
- 用户主动添加的附件及其引用；
- 对话摘要与来源索引；
- Shared Knowledge；
- 模型和 Provider 配置；
- 临时检索结果与缓存。

实际文件布局、数据库类型和目录结构由实现阶段决定，不在本 ADR 中指定。

用户应能够选择持久对话或临时对话，并能够删除单个对话、附件、摘要、共享资料或全部 AI 本地数据。删除操作应处理相关派生摘要、索引和缓存；对于无法立即安全清理的底层存储，应明确说明实际清理语义。应提供对话导出能力，以便用户备份和迁移。

删除 ECL 本地记录不等于删除已经发送给远程 Provider 的数据。ECL 必须说明第三方 Provider 的数据保留、日志和训练政策由其自身条款决定，不能承诺 ECL 无法控制的远程删除。

API Key 等凭据必须由 Core 的安全凭据能力管理，不得以明文写入 Addition 普通配置、聊天记录、Prompt、附件或日志。对话内容是否加密存储应结合平台能力与安全评审确定；敏感凭据的保护不得依赖普通聊天记录加密策略。

### 9. System Prompt 必须公开、可查看、可追溯，且不得暗中扩大权限

ECL 制定并注入的 System Prompt 是 ECL 对模型行为提出要求的机制。它必须满足：

- Prompt 的源文本、生成逻辑和版本纳入公开仓库审查；
- 用户能够在 ECL 内查看当前实际使用的完整 ECL 控制指令；
- 如果 Prompt 由基础模板、模式规则和动态上下文组成，应能区分各组成部分，并查看实际发送的 ECL 指令内容；
- 不得在发送请求时偷偷追加未向用户披露的 ECL 行为指令；
- Prompt 变更应有版本或修订记录，用户能够识别当前版本；
- 不得通过 Prompt 诱导模型索取无关数据、秘密上传隐私、绕过权限或隐瞒数据处理行为。

应区分 ECL 提供的 Prompt、Provider Adapter 为满足协议所做的格式转换，以及第三方 Provider 自身可能追加且 ECL 无法控制的系统规则。ECL 不得声称能够公开或控制第三方服务商的内部指令。

Prompt 不是安全边界。模型可能忽略指令或受到提示注入影响，因此文件访问、凭据使用、网络请求、工具调用和数据传输必须由 Core 的实际权限与执行机制控制。Prompt 不得授予权限，也不得扩大用户授权范围。

### 10. 远程数据传输必须独立授权，并提供请求透明度

用户配置 API Key 或选择 Remote Provider，不代表同意上传全部聊天历史、附件、日志、实例信息或其他本地数据。

每次远程请求都必须遵守数据最小化原则，并在适用情况下向用户展示或确认：

- 目标 Provider 与模型；
- 将发送的对话消息和上下文类别；
- 附件、日志、实例信息及搜索结果的具体范围；
- 可能包含的敏感字段；
- 是否会调用外部搜索或其他工具。

用户应能够在发送前检查、删减或取消数据。对于敏感数据、完整日志、凭据、服务器地址或其他高风险内容，不得仅凭 API Key 配置推定用户授权。

应提供 Context Inspector / Request Inspector，使用户能够了解本次请求实际使用的上下文来源、裁剪结果、估算 Token 数量和传输目标。对于纯本地推理，也应能查看本次上下文的主要组成，但不应把本地内容误标为已上传。

### 11. 工具调用必须受宿主控制，外部内容不得成为权限指令

模型可以在受支持的范围内请求搜索或读取任务资料，但工具调用必须经过宿主能力检查。模型输出、网页内容或 Prompt 中的文字不能直接执行任意命令、任意文件写入或未授权网络操作。

- 工具按用途声明最小能力，不向模型暴露通用宿主权限。
- 读取文件和实例数据必须受当前任务与用户授权范围约束。
- 写入、删除、启动程序、修改实例或其他有副作用的操作必须另行经过适当授权和用户确认。
- 搜索结果、模组说明、日志和附件中的指令均视为不可信内容。
- 工具失败、超时或返回不可信内容时，不得通过自动扩大权限来“修复”任务。

### 12. AI 能力失败不得影响 ECL 普通使用

ECL AI 按需安装和使用，不进入普通 Minecraft 启动链。模型未安装、Provider 不可用、网络搜索失败、上下文存储损坏或 AI Addition 崩溃，不得阻塞 ECL 普通启动、实例管理或游戏启动。

Diagnostic 的 AI 能力不可用时，ECL 既有原生诊断能力和独立 Diagnostic Engine 仍按各自边界工作；ECL AI 不应成为既有确定性诊断流程的强制前置条件。

### 13. 明确不在本 ADR 范围内的事项

本 ADR 不规定具体聊天页面布局、消息气泡、导航位置、UI 动效、数据库技术、文件目录、Provider SDK、模型量化格式、具体模型名单、搜索服务商名单、Prompt 的逐字内容或具体 IPC/API 签名。

这些内容由后续 Feature Spec、实现设计和安全评审确定，但不得改变本 ADR 的对话隔离、数据最小化、权限边界、Prompt 透明度和普通启动独立性。

本 ADR 不承诺所有本地模型都能满足复杂诊断或长上下文需求，也不承诺任意 Provider 都支持工具调用、结构化输出、视觉输入或准确用量统计。模型能力应按 Provider 声明与 ECL 实际验证分别记录。

## 备选方案

### 方案 A：Chat、Knowledge、Diagnostic 分别作为独立 Addition

每个功能可以独立安装，但需要重复处理对话、上下文、模型配置、凭据、历史记录和安全策略，并增加跨 Addition 版本兼容与数据共享成本。不采用。

### 方案 B：将 AI Runtime、Model Manager、Search Broker 全部做成独立基础 Addition

可以让多个 AI 功能复用，但会形成额外的强制安装链，并使用户为了使用一个 AI 功能先理解和安装多个基础扩展。当前功能规模不足以证明这种拆分的收益。不采用；相关能力先作为 ECL AI 内部基础设施。

### 方案 C：将 AI 全部集成进 ECL Core

可减少 Addition 边界，但会把模型管理、推理依赖和 AI 专业功能带入主程序，增加体积、维护和故障面，也不符合按需扩展方向。不采用。

### 方案 D：只支持远程 API

设备要求较低，但依赖网络、服务商和用户费用，且会扩大隐私与数据传输风险。不采用为唯一方案。

### 方案 E：只支持本地模型且完全离线

可以避免远程推理费用和数据上传，但设备资源要求高，且 Minecraft 与模组知识可能迅速过时。不采用为唯一方案。

### 方案 F：单一 ECL AI Addition + 多工作模式 + 可替换推理后端

通过一个 Addition 统一管理 Chat、Knowledge、Diagnostic 和共享基础设施；本地/远程推理与受控搜索独立组合；Diagnostic 可选消费既有诊断扩展增强。该方案在复用、可理解性、主程序轻量化和安全边界之间取得较好平衡，予以采用。

## 后果

### 正面影响

- 用户只需安装一个 ECL AI Addition，即可使用 Chat、Knowledge 和 Diagnostic。
- 通用聊天不受 Minecraft 主题限制，用户可以自行决定用途与远程费用。
- 本地模型可以通过受控搜索获取最新 Minecraft 和模组资料。
- Knowledge 与 Diagnostic 共用搜索、上下文、对话、模型和安全设施。
- Diagnostic 在没有其他 Addition 时仍可工作，已有诊断引擎和知识库作为可选增强。
- 多对话默认隔离，跨对话共享有明确的用户控制入口。
- 聊天历史本地优先，模型上下文按任务最小化构建。
- Prompt、上下文和远程请求具有可审查性，权限由宿主机制而非模型指令保证。
- ECL 主程序不承担推理费用，也不因 AI 能力缺失影响普通启动。

### 代价与风险

- ECL AI 自身仍是一个较复杂的 Addition，需要管理模型适配、对话存储、上下文预算和搜索工具。
- 本地模型效果取决于用户硬件、模型能力和配置；复杂诊断不能保证成功。
- 远程 Provider 的隐私、可用性、费用和数据保留政策不受 ECL 完全控制。
- 搜索结果可能过时、错误或包含提示注入，需要来源治理和不可信输入处理。
- 上下文摘要可能丢失信息，必须保留来源和原始证据引用。
- 对话附件、摘要、缓存和共享知识的删除与迁移需要完整生命周期管理。
- Core 必须提供足够的受控文件、凭据、网络和授权能力，但不能因此成为 AI 推理运行时。

## 验收标准

本 ADR 已批准，Implementation 保持 Not Started。以下为实现与验证基线，不表示功能已经实现：

- 官方 Registry 中存在唯一的 ECL AI Feature Addition：`ecl.ai`。
- ECL AI 提供 Chat、Knowledge、Diagnostic 三种模式；三者不要求分别安装。
- Chat 不按 Minecraft 相关性限制用户主题。
- ECL 不提供默认由自己付费的公共推理 API；远程 Provider 由用户配置，费用归用户。
- 本地模型能够在受控网络工具授权下进行搜索，且搜索与推理后端相互独立。
- Knowledge 能够保留可查看的资料来源；搜索结果被视为不可信输入。
- Diagnostic 在未安装 `ecl.diagnostic-engine` 和 `ecl.diagnostic-knowledge-base` 时仍可执行基础分析。
- 上述两个现有 Addition 作为可选增强，不构成 ECL AI 的必需依赖。
- 多对话默认隔离；跨对话共享必须通过用户明确管理的 Shared Knowledge 或明确授权的偏好实现。
- 聊天历史与单次模型上下文分离；上下文按需构建，不默认附加全部历史、附件或实例数据。
- 长对话摘要具有来源追踪；需要精确证据时可以回到原始消息或文件。
- 对话、附件、摘要、共享知识和缓存具有明确的本地存储及删除生命周期。
- API Key 不以明文写入 Addition 普通配置、聊天记录、Prompt 或日志。
- 用户可以查看当前实际使用的 ECL System Prompt 及其版本；不得存在未披露的 ECL 隐藏追加指令。
- Context Inspector / Request Inspector 能够说明本次上下文来源和远程传输范围。
- 配置 API Key 不会自动授予上传全部历史、日志、附件或实例信息的权限。
- 文件、网络、凭据和工具调用由 Core 宿主权限控制；Prompt 不授予权限。
- 模型不可用、搜索失败、AI Addition 损坏或未安装时，不影响 ECL 普通启动和游戏启动。
- 对本地、远程、混合后端，多对话隔离、上下文裁剪、提示注入、权限撤销、数据删除和故障恢复具备可复核测试。
