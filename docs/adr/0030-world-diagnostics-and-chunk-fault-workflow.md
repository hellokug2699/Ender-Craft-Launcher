# ADR 0030：世界诊断与区块异常定位联动

- Status: Accepted (implementation pending)
- Date: 2026-11-02
- Scope: 游戏日志诊断、区块异常关联、实例工作台告警、世界编辑器定位与修复工作流
- Related: ADR 0015（按进程隔离的游戏日志会话与诊断）、ADR 0026（实例工作台的存档、多人游戏与最近访问）、ADR 0027（原生 C# 世界分析与编辑引擎）

## 背景

ADR 0026 已将游戏日志、崩溃分析和诊断导出纳入实例工作台；ADR 0027 规划了原生 C# 世界分析与编辑引擎。两者可以通过一套世界诊断流程形成联动：当游戏日志或崩溃报告中出现疑似与特定区块、实体或世界数据相关的异常时，ECL 尝试定位受影响对象，在实例工作台提示用户，并允许用户将诊断上下文带入世界编辑器进行检查。

典型问题包括区块加载或解析异常、NBT 解码失败、区块数据索引越界、实体 Tick 异常、实体渲染异常，以及模组代码在处理特定区块或实体时抛出的异常。

但日志中的异常并不必然意味着存档数据损坏。例如 Entity Rendering Exception 可能来自渲染器缺陷、模组冲突或版本不兼容；IndexOutOfBoundsException 也可能是模组自身的数据结构错误。日志坐标可能缺失、格式不统一，甚至只是异常发生时玩家所在位置，而不是实际损坏数据的位置。

因此 ECL 必须将原始证据、坐标关联、原因推断和修复建议分开表达，不能把日志异常直接判定为 Chunk 损坏，更不能未经用户确认修改世界。

## 决策

### 1. 建立独立的 World Diagnostics Service

增加独立的 World Diagnostics Service，作为日志诊断来源与实例工作台、Native World Engine 之间的中间层。

它负责：

- 消费指定实例、指定游戏会话的日志和崩溃报告；
- 识别与世界、区块、实体或存档数据相关的异常；
- 提取维度、Chunk 坐标、Block 坐标、实体 UUID、Region 坐标及相关上下文；
- 将异常归类为结构化诊断事件；
- 评估定位可信度和证据完整程度；
- 生成可能原因及建议检查/修复动作；
- 将诊断摘要提供给 ADR 0026 的实例工作台；
- 将完整诊断报告提供给 ADR 0027 的 Native World Engine。

ADR 0026 不直接实现日志解析规则；ADR 0027 不负责扫描游戏日志或猜测错误来源。两个模块通过稳定、版本化的诊断数据模型协作，不直接互相依赖。

World Diagnostics Service 应复用现有按进程隔离的游戏会话和诊断能力，不得把不同实例或不同游戏会话的日志混合归因。

### 2. 诊断来源与支持范围

第一阶段可从以下来源提取诊断信息：

- Minecraft 客户端游戏日志；
- Minecraft 崩溃报告；
- ECL 已有的会话日志与诊断记录；
- 后续由 Native World Engine 产生的 Region / Chunk / NBT 静态校验结果。

诊断解析应优先使用结构化信息和有明确上下文的日志模式。针对不同 Minecraft 版本、加载器和常见模组日志格式，可逐步建立可测试的解析规则。

日志解析器必须将原始文本视为不可信输入，限制单条记录长度、文件读取量、解析耗时和堆栈深度。异常或恶意日志不能导致 ECL 崩溃、无限内存增长或任意文件访问。

日志中出现某个类名、模组名或异常关键词，不足以单独证明世界数据有问题。无法可靠分类的记录可以保留为一般诊断事件，不应强行归类为区块损坏。

### 3. 坐标提取与定位可信度

诊断事件应尽可能提取：

- 实例稳定标识及游戏会话标识；
- 世界存档标识或可验证的存档路径关联；
- 维度 ID；
- Chunk 坐标；
- Block 坐标；
- Region 坐标；
- 实体 UUID 或可识别的实体类型；
- 事件时间、异常类别和原始日志位置；
- 原始异常类型、消息及相关堆栈片段。

定位必须标记来源和可信度，至少区分：

- **明确定位：** 日志或报告明确提供 Chunk 坐标，且能够确认其属于当前世界/维度上下文。
- **坐标推导：** 从明确的 Block 坐标换算得到 Chunk 坐标，保留原始坐标和换算过程。
- **关联推断：** 通过实体 UUID、区块加载上下文或相邻日志关联到候选 Chunk，但不能确认直接因果关系。
- **位置线索：** 仅有玩家位置、当前维度或 Region 等间接信息。
- **无法定位：** 缺少足够信息，不创建虚构坐标。

Minecraft 坐标可能为负数。Block 到 Chunk 的换算必须采用正确的向下取整语义，不得使用对负数不正确的简单整数截断。维度必须作为坐标身份的一部分；不同维度中相同的 Chunk 坐标不是同一个对象。

如果只有 Region 坐标，应标记为 Region 级定位，不能任意选择其中一个 Chunk 进行高亮。如果日志中的位置只是玩家当前坐标，应明确标记为位置线索，而不是故障位置。

### 4. 证据、推断和修复建议必须分离

每个诊断事件至少应包含以下逻辑字段：

- **Observed Evidence：** 日志实际记录的异常类型、消息、堆栈、时间、坐标和来源。
- **Location：** 世界、维度、坐标及定位粒度。
- **Confidence：** 坐标定位可信度和关联可信度。
- **Classification：** 解析异常、区块加载异常、NBT 异常、实体 Tick 异常、实体渲染异常等分类。
- **Hypotheses：** 可能原因及其依据，不得写成已确认事实。
- **Severity：** 对用户的风险提示等级及其判定依据。
- **Suggested Actions：** 只读检查、进一步验证和可选修复操作。
- **References：** 原始日志文件、会话 ID、行号/偏移或崩溃报告引用。
- **Status：** 新发现、待检查、已检查、已修复、已验证、已忽略或无法确认。

UI 必须清楚区分“日志明确记录了什么”和“ECL 推测可能是什么原因”。例如，实体渲染异常只能证明渲染路径发生异常，不能仅凭这一点断言实体 NBT 损坏。

推断应尽可能附带依据和限制。缺少足够证据时，应显示“原因未知”或“需要进一步检查”，不得生成看似确定的解释。

### 5. 危险等级与定位可信度分开表达

危险等级描述潜在影响或建议操作的风险，不等同于定位可信度。两者必须独立显示。

建议的风险等级：

- **信息：** 记录到异常，但没有足够证据表明存档数据受损；建议观察或查看日志。
- **低：** 有局部异常线索，优先进行只读检查。
- **中：** 存在可能影响特定区块或实体的异常，建议备份后进一步检查。
- **高：** 有明确的数据损坏证据，或拟执行的修复可能导致数据丢失；必须清楚警告并提供备份/恢复方案。
- **严重：** 可能影响较大范围世界数据，或当前无法安全恢复；默认不提供一键破坏性修复，要求用户审慎处理。

风险等级应说明是“问题影响风险”还是“所选修复操作风险”。不能因为日志出现 Exception 就自动标为高危，也不能因为坐标明确就降低数据修改风险。

### 6. ADR 0026：实例工作台显示诊断摘要与告警

实例工作台应在对应实例的世界/存档区域展示诊断摘要。

当诊断事件能够关联到某个存档时，可显示：

- 检测到的疑似区块/实体异常数量；
- 相关维度和坐标；
- 异常类型与最近发生时间；
- 定位可信度及风险等级；
- 当前检查/修复状态；
- 打开世界编辑器查看的入口。

示例文案应使用“检测到区块相关异常”或“疑似区块问题”，而不是在未经验证时宣称“某区块已损坏”。

多个事件可能指向同一 Chunk，应支持聚合展示，同时保留每条原始诊断事件。一次游戏会话中的重复日志不应无节制地产生重复告警；聚合时不得丢失事件次数、时间范围和原始证据引用。

无法关联到具体存档或 Chunk 的事件仍可保留在日志/诊断页面，但不得错误挂到当前选中的实例或世界上。

告警入口应将用户带到对应存档、维度和坐标的编辑器视图，并传递诊断报告引用，而不是只传一个裸坐标。

### 7. ADR 0027：世界编辑器消费诊断报告并高亮目标

Native World Engine 应支持从诊断报告打开世界，并根据定位粒度显示对应目标：

- Chunk 级定位：高亮对应 Chunk；
- Block 级定位：可在 Chunk 高亮基础上进一步标记方块坐标；
- Entity 级定位：若存档解析器能够识别对应实体，可定位并标记实体；
- Region 级定位：高亮 Region 范围或提供候选 Chunk 列表；
- 无法定位：打开世界诊断面板和相关证据，不伪造地图位置。

地图应通过独立诊断叠加层展示异常，不得覆盖原有高度图、生物群系图、表面方块图或实际 Chunk 数据。不同诊断事件可以有不同标记，并支持筛选、选择和跳转。

鼠标悬停或选择诊断标记时，应展示：

- 异常类型和摘要；
- 原始错误消息的安全截取；
- 维度及坐标；
- 发生时间和游戏会话；
- 定位可信度；
- 可能原因及推断依据；
- 风险等级；
- 可选检查和修复建议；
- 查看原始日志/崩溃报告的入口。

诊断报告中的文本属于外部输入，应按普通文本安全展示，不得作为 XAML、HTML、脚本或其他可执行内容解释。

### 8. 修复建议按侵入性递增，默认只读

世界编辑器可以依据诊断类别提供分级建议，但建议不等于自动执行。

推荐处理顺序：

1. 查看原始日志和相关堆栈；
2. 只读检查 Chunk / Section / NBT 结构；
3. 查看目标 Chunk 中的方块状态、实体和区块实体；
4. 检查相关模组、加载器和版本兼容性；
5. 在有足够证据时，提供针对单个字段、实体或区块实体的有限修复；
6. 只有在明确说明影响并完成备份后，才考虑重置整个 Chunk；
7. 更大范围的 Region 或世界级操作不属于普通一键修复，应单独评估。

修复方案必须与诊断证据相匹配。例如实体渲染异常应优先检查实体类型、实体 NBT、模组版本和渲染器；不能直接建议删除整个 Chunk。模组代码缺陷或版本冲突可能无法通过修改世界数据解决，UI 应允许给出“更新/回退相关模组”或“向模组维护者报告”的非存档修复建议。

### 9. 所有写入操作遵循 ADR 0027 的编辑安全边界

任何修改世界数据的操作必须：

- 明确展示目标世界、维度、Chunk/实体及具体字段；
- 解释拟修改内容和预计影响；
- 显示修复依据、风险和无法保证的部分；
- 检查 Minecraft 或其他进程是否正在使用世界；
- 在写入前创建可验证备份；
- 使用安全提交策略，避免中断后留下半写入数据；
- 提供可执行的恢复路径；
- 由用户明确确认后执行；
- 修复后重新解析并验证数据结构。

不得仅凭日志推断自动删除实体、重置区块或修改 NBT。若目标数据格式未知、诊断定位不可靠、世界正在使用或备份失败，应拒绝破坏性修复。

默认不自动修改存档。游戏启动、日志读取、告警展示和打开编辑器均不得触发隐式写入。

### 10. 诊断报告生命周期、去重与隐私

诊断报告应在本地保存，并与实例、存档和游戏会话建立稳定关联。建议支持版本化的数据模型，以便未来增加新的诊断来源和字段。

- 保留原始日志引用，不必在每条聚合事件中无限复制完整日志。
- 聚合重复事件时保留计数、首次/最近发生时间及证据引用。
- 用户移动或删除实例、存档时，报告应显示无法访问或待重新关联状态，不得猜测新路径。
- 用户可以清除诊断记录；清除报告不应自动删除原始游戏日志或世界数据。
- 诊断数据默认本地处理，不自动上传给 ECL 维护者。
- 不把完整日志、世界数据、Seed、服务器地址或用户路径发送到远端服务。
- 若用户主动导出诊断包，应沿用现有诊断导出机制，并明确告知可能包含本地路径、用户名、模组信息、服务器地址、聊天文本或其他游戏内容。

诊断记录损坏、版本不兼容或读取失败不得阻止 ECL 启动、实例管理或游戏运行。

### 11. 性能与故障隔离

日志解析、诊断关联和世界扫描均应异步执行、可取消且具有资源上限。

- 不在 UI 线程解析大日志或扫描世界。
- 不为查找单个问题而默认扫描整个世界；只有用户主动发起时才执行有界的深度扫描。
- 日志解析器和 NBT 解析器应隔离处理异常输入。
- 诊断服务不可用时，原始日志查看和游戏启动仍可使用。
- 编辑器不可用时，实例工作台仍可显示诊断摘要和原始证据入口。
- 无法提取坐标时保留诊断事件，不得阻断其他诊断结果。

## 模块边界建议

- **Game Log / Crash Report Sources：** 提供按会话隔离的原始日志和崩溃报告。
- **World Diagnostics Service：** 解析异常、坐标提取、归类、证据关联、可信度和风险建议。
- **Diagnostic Report Store：** 本地持久化、版本迁移、去重和状态管理。
- **ADR 0026 Instance Workbench：** 消费诊断摘要并展示告警、状态和编辑器入口。
- **ADR 0027 Native World Engine：** 消费完整诊断报告，负责存档结构检查、地图高亮和受控修复。
- **Repair Workflow：** 在 World Engine 内或独立领域服务中实现，复用 ADR 0027 的备份、进程占用检查和安全写入机制。

具体程序集/项目名称可在实施阶段按仓库现有结构调整。服务之间应通过明确的数据模型和接口交互，不得形成实例工作台与世界引擎的循环依赖。

## 后果

### 正面影响

- 将游戏日志从被动文本变为可定位、可操作的世界诊断信息。
- 玩家无需手动阅读复杂堆栈，也能找到可能相关的区块。
- ADR 0026 的实例工作台获得明确的异常告警和后续入口。
- ADR 0027 的世界编辑器获得真实诊断上下文，不再只是让用户自己寻找问题。
- 原始证据、推断和修复方案分离，降低误判和误删风险。
- 后续可扩展 Region/NBT 静态扫描、实体检查和其他诊断来源。

### 代价与限制

- 不同 Minecraft 版本、加载器和模组的日志格式差异较大，需要持续维护解析规则。
- 日志不一定提供真实故障坐标，定位准确性无法保证。
- 同一异常可能由模组代码、渲染器、资源包或世界数据共同触发，自动根因分析存在边界。
- 诊断报告需要版本化存储、事件去重和原始证据引用管理。
- 修复能力必须谨慎设计，避免把“看起来像问题”转化为破坏性操作。
- 自动化程度应服从证据质量，不能为了 UI 完整而制造虚假的精确定位。

## 实施顺序建议

1. 梳理现有游戏会话日志、崩溃报告和诊断导出接口，确定可复用的数据来源。
2. 定义版本化诊断事件模型，先支持原始证据引用、异常分类和坐标/维度提取。
3. 建立小规模、可复现的日志样本测试集，覆盖负坐标、不同维度、缺失坐标、实体异常、NBT/Chunk 异常及模组堆栈。
4. 实现定位可信度和风险等级，明确区分明确坐标、推导坐标、关联推断和无法定位。
5. 在 ADR 0026 实例工作台展示诊断摘要和告警，不执行任何世界修改。
6. 在 ADR 0027 编辑器中实现诊断报告导入、Chunk/Region/Entity 高亮和原始证据查看。
7. 实现只读 Chunk / NBT 检查与可解释的修复建议。
8. 在备份、进程占用检测、安全写入和恢复机制通过实机测试后，再开放有限的修复操作。
9. 逐步扩展 Minecraft 版本、加载器和常见模组的日志解析覆盖。

## 验收要求

- 诊断事件始终关联正确的实例和游戏会话，不混合不同世界的日志。
- 明确坐标、推导坐标、间接推断和无法定位具有不同状态。
- 负坐标换算正确，维度参与目标身份判定。
- 仅有玩家位置或 Region 坐标时，不伪造精确 Chunk 定位。
- 原始日志证据与原因推断在数据模型和 UI 中分离。
- Entity Rendering Exception 等非存档错误不会被自动认定为 Chunk 损坏。
- 重复日志可聚合，但保留事件次数、时间范围和原始证据引用。
- ADR 0026 可展示疑似异常摘要，并跳转到正确实例、存档、维度和诊断上下文。
- ADR 0027 能按定位粒度高亮 Chunk、Block、Entity 或 Region；无法定位时不伪造地图标记。
- 悬停/选择诊断标记时能查看错误摘要、推断原因、定位可信度、风险等级和可选处理方案。
- 诊断叠加层不修改或覆盖实际世界数据及其他地图图层。
- 默认诊断和浏览只读，不自动修改世界。
- 任何修复均有目标预览、进程占用检查、可验证备份、用户确认和修复后验证。
- 不支持或无法可靠定位的数据拒绝破坏性修复。
- 日志解析、诊断关联和世界扫描异步、可取消且有资源上限。
- 诊断服务失败不影响 ECL 启动、实例管理、原始日志查看或游戏运行。
- 诊断数据默认保存在本地，不自动上传。
