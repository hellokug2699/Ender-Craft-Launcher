# ECL Roadmap

> 本文同时定义产品交付顺序与工程验收门槛。它不是愿望清单：未满足验收条件的工作不得仅凭“代码已写完”标记完成。

状态：`[x]` 已完成；`[~]` 进行中；`[ ]` 未开始；`[!]` 被外部条件阻塞；`[-]` 已明确不在当前范围。

## 产品目标

ECL 是面向 Windows 的 Minecraft 启动器，长期目标是达到 HMCL / PCL2 的核心使用完整度，同时保持配置元数据驱动、可观测启动流水线、模块化单体与 CLI 可复用能力。

优先顺序：

1. **正确性与数据安全**：安装、启动、文件校验、回滚、凭据和用户数据安全。
2. **可恢复性与可诊断性**：失败原因明确，操作可取消，失败后能安全重试或恢复。
3. **交付能力**：可重复构建、可验证的发布产物、可靠更新和迁移。
4. **核心用户流程完整性**：账户、实例、Mod 与整合包管理。
5. **体验完善**：向导、托盘、细粒度无障碍和其他便利功能。

不得为了完成新功能而破坏现有 CLI、配置继承、实例隔离、安装事务、Dry Run、脱敏诊断或跨平台 Core 测试。

## 当前基线

当前仓库已实现原版安装与启动、Java 管理、Fabric / Forge / NeoForge / Cleanroom、OptiFine 显式安装、Mod 管理、Modrinth / CurseForge 整合包导入导出、CurseForge 搜索与安装、资源包和光影包文件管理及启用状态（写入 `options.txt`）、崩溃分析、脱敏诊断包、下载暂停/恢复、自定义 JVM 预设、WPF 与 CLI、单元测试及 CI。

WPF 外壳已完成第一轮 launcher-first 视觉重构：主窗口采用持久侧栏与内容画布，实例页优先展示选中实例与启动动作，Mod 管理页、设置页与关于页统一到同一套卡片、Hero、状态徽标与操作层级。控件级主题（按钮、输入框、下拉框、复选框、列表选中态、滚动条与提示框）已统一为 ECL 深色视觉，并内嵌 HarmonyOS Sans SC 作为界面字体；浅色模式已移除。该轮 UI 工作只调整呈现层，保留既有 ViewModel 绑定与业务命令。

已知未完成或受限项：

- [!] Microsoft OAuth 及 Xbox / XSTS / Minecraft Services 认证链路：受应用注册 / OAuth 审核条件影响；不能以离线账户模拟替代真实认证。
- [ ] authlib-injector 第三方认证。
- [ ] Mod 更新检查、可选依赖选择及严格依赖版本范围语义。
- [ ] 更完整的键盘导航、焦点与读屏支持。
- [ ] 正式安装包、发布签名验证与自更新。
- [-] Quilt / Legacy Fabric：当前不纳入近期交付范围。
- [-] 首次启动向导：暂缓，待安装、配置和发布链路稳定后再评估。

标记为已完成的现有能力仍须由 CI 和相关回归测试持续保护；本清单不代表所有边界场景均已验证。

## Phase A — v0.8 可靠性与功能闭环

**目标：** 在继续扩大功能面之前，收敛已实现功能的缺口，建立可持续回归的基线。

### A1. 发布前基线与回归保护

- [ ] 在 Windows CI 中验证 Release 构建、完整测试和 WPF 项目构建。
- [ ] 在 Linux CI 中验证 Core / CLI / Tests 可构建、测试可运行。
- [~] 统一执行 `dotnet format` 检查和静态分析；`dotnet format --verify-no-changes` 已修复现存问题并作为 Windows CI 门槛，静态分析（分析器/警告即错误）仍待补齐。
- [ ] 为关键用户流程补充集成级回归测试：创建实例 → 安装原版 → 安装加载器 → Dry Run → 真实启动所需前置条件检查。
- [ ] 记录测试结果、已知限制和可复现的失败步骤；不以测试数量单独衡量覆盖质量。

**验收门槛**
- Release 构建与现有测试通过。
- 关键流程的失败、取消、重试和回滚路径有对应测试或明确记录。
- 没有已知的高严重度数据丢失、路径越界、凭据泄露问题。

### A2. 资源包 / 光影包启用状态

- [x] 明确启用状态的唯一事实来源，以及与 `options.txt`、资源文件缺失和外部修改的同步规则。
- [x] 接入启用 / 禁用选择器，支持缺失文件、无效条目和重复条目的安全处理。
- [x] 在 UI 与 CLI 中提供一致的状态查询与修改能力（如适用）。
- [x] 为配置写入增加备份或原子替换，避免异常中断造成配置损坏。

**验收门槛**
- 启用、禁用、重启启动器后状态一致。
- 不删除资源文件来表达禁用状态。
- 对损坏或未知条目提供可理解的提示，不静默覆盖用户配置。

### A3. Mod 依赖与更新能力

- [ ] 定义 Mod 版本范围匹配规则；不把无法识别的版本范围误判为兼容。
- [ ] 先完成更新检查与差异展示，再实现批量更新。
- [ ] 为 CurseForge 可选依赖设计显式选择流程；必需依赖与可选依赖不可混淆。
- [ ] 下载、替换和元数据更新必须支持校验、取消和失败恢复。

**验收门槛**
- 更新检查不会自动改写或删除现有 Mod。
- 更新安装失败时保留原文件，或能可靠恢复。
- 对作者限制分发的文件明确说明限制，不尝试绕过来源限制。

### A4. 诊断与无障碍收尾

- [ ] 完善键盘焦点顺序、焦点可见性、读屏名称与常用操作键盘可达性。
- [ ] 检查日志和诊断包的令牌、用户名、路径等敏感字段脱敏规则。
- [ ] 为安装 / 启动失败提供稳定错误代码、用户可理解消息和下一步建议。

**验收门槛**
- 常见管理流程可以不依赖鼠标完成。
- 诊断包不包含账户凭据、访问令牌或 API key。
- 错误消息不只暴露异常堆栈，也不伪装失败为成功。

### A5. Launcher UI 第一轮收尾

- [x] 主窗口统一为 launcher-first 外壳：持久侧栏、内容画布、版本 / 数据目录信息和统一主题。
- [x] 实例页重构为“选中实例 → 启动 / 安装 → 实例库 → 配置”的信息层级。
- [x] Mod 管理页重构为实例选择 → 快速操作 → Mod 列表 → CurseForge → 资源包 / 光影包的工作流。
- [x] 关于页统一品牌展示、运行环境信息、数据目录与项目免责声明。
- [x] 控件级主题统一：主 / 次 / 危险 / 幽灵按钮、文本框、下拉框、复选框、列表选中态、滚动条与提示框使用同一套 ECL 深色视觉；下拉框改为自定义弹出面板。
- [x] 修正自定义下拉模板下 `DisplayMemberPath` 不进入选中框的问题（统一改用 `ItemTemplate`），并把主题刷子改为 `DynamicResource`。
- [x] 界面字体替换为内嵌 HarmonyOS Sans SC（Regular / Bold），关于页与 README 保留版权与许可证声明；移除浅色模式。
- [ ] 设置页继续收敛为更清晰的作用域选择 → 状态 → 分类设置结构，并检查长表单的键盘导航与焦点表现。
- [ ] 对全部 WPF 页面执行一次资源键、绑定、可见性转换器和窗口缩放回归检查。

**验收门槛**
- UI 重构不改变既有 ViewModel API、业务命令和文件行为。
- 常用动作在首屏或明确的二级区域可发现。
- Windows WPF Release 构建通过，且不得引入新的 XAML 编译错误。
- 不用“看起来完成”代替实际 CI 验证。

## Phase B — v0.9 账户与核心工作流

**目标：** 补齐影响实际日常使用的核心流程；受外部审核影响的功能单独管理，不阻塞其他可交付工作。

### B1. 账户系统

- [!] Microsoft OAuth：先确认应用注册、授权流程和所需审核条件；条件未满足前不得把该项排入无条件执行队列。
- [ ] 在外部条件满足后实现 Microsoft 登录、Xbox / XSTS / Minecraft Services 链路、令牌刷新与失效处理。
- [ ] 使用 Windows DPAPI 保护需要持久化的敏感令牌；明确退出登录、令牌失效和数据迁移行为。
- [ ] 实现 authlib-injector 第三方认证，并将认证协议适配限制在认证模块内。
- [ ] 完成账户管理 UI、默认账户选择和错误恢复流程。

**验收门槛**
- 真实账号流程经过可重复的端到端验证；不以 Mock 测试冒充线上认证成功。
- 令牌不进入日志、诊断包、命令预览或普通配置文件。
- 登录失败、取消、令牌过期和撤销均有明确状态，不影响离线账户的现有能力。

### B2. 实例与整合包工作流

- [ ] 审核整合包导入 / 导出对 manifest、覆盖文件、缺失远程文件、路径穿越和重复文件的处理。
- [ ] 明确导入整合包时哪些实例设置会被覆盖、保留或提示用户确认。
- [ ] 补齐实例级 Mod、资源包、光影包和诊断入口之间的交互一致性。
- [ ] 根据真实使用反馈决定是否实现首次启动向导；向导不得复制一套独立的安装 / Java / 配置业务逻辑。

**验收门槛**
- 不可信压缩包不能写入实例目录之外。
- 导入失败不会留下被误认为完整安装的半成品实例。
- 已存在实例和用户存档不会在未告知的情况下被覆盖。

## Phase C — v1.0 可分发版本

**目标：** 用户能安全安装、升级、恢复和卸载 ECL；发布过程可重复、可审计。

### C1. 发布与安装包

- [ ] 在 MSIX 与 Inno Setup 之间基于更新方式、权限、卸载和签名要求作出 ADR 决策。
- [ ] 建立版本号、发布通道（稳定 / 测试）和 Release 产物命名规则。
- [ ] 在干净 Windows 环境验证安装、首次运行、升级、卸载和用户数据保留策略。
- [ ] 为构建产物生成校验和、软件物料清单（SBOM）并记录依赖审计结果。
- [ ] 确保公开仓库可在没有私有仓库、签名证书或 API key 的情况下完成普通构建与测试。

### C2. 更新器与恢复机制

- [ ] 先编写更新协议：可信更新清单、版本与通道、下载地址限制、哈希、签名、超时和错误模型。
- [ ] 在执行更新前验证清单与包签名；哈希只能证明文件一致性，不能代替发布者身份验证。
- [ ] 设计独立更新进程或其他可验证的替换策略，避免运行中的文件被直接覆盖。
- [ ] 支持下载失败、签名无效、空间不足、更新中断和重启失败后的恢复。
- [ ] 只有基础更新可靠后，才评估增量更新。
- [ ] 如实现版本公告，明确区分可信的结构化内容与外部文本。

**验收门槛**
- 签名或完整性验证失败时拒绝安装更新。
- 模拟更新中断后，用户仍能启动旧版本或执行明确的恢复流程。
- 稳定与测试通道不会意外交叉升级。
- 不上传遥测；任何未来遥测均须单独设计、明确告知并取得用户同意。

### C3. 正式发布门槛

- [ ] Windows 干净环境安装 / 升级 / 卸载测试通过。
- [ ] 核心安装、启动、Mod 与整合包回归测试通过。
- [ ] 发布产物签名与校验信息可供用户验证。
- [ ] 文档列明系统要求、账户能力、已知限制、数据目录、备份与故障报告方式。
- [ ] 建立可复现的发布检查清单与回滚步骤。

## 跨阶段工程门槛

每个阶段都必须遵守以下规则：

- [ ] **测试**：新行为必须有对应测试；修复缺陷必须添加能复现原问题的回归测试。
- [ ] **接口**：修改公共接口前，先列出调用方、兼容影响与迁移方案。
- [ ] **错误与取消**：异步任务正确传播 `CancellationToken`；取消不能留下假成功状态或损坏的半成品。
- [ ] **文件安全**：对压缩包路径、下载地址、缓存路径和用户输入执行边界校验。
- [ ] **数据安全**：不记录凭据；涉及删除、覆盖、迁移时明确保护用户数据。
- [ ] **文档**：行为、配置、接口或架构变化后同步更新相关文档。
- [ ] **回归**：保留 CLI、Dry Run、配置继承、实例隔离和现有安装 / 启动链路。
- [ ] **完成定义**：代码、测试、文档、错误处理和验收条件全部满足后才能标记 `[x]`。

## AI 辅助开发任务协议

将任务交给任何编码模型前，任务说明必须包含：

1. **目标与背景**：要解决的具体问题，以及为什么现在做。
2. **允许修改范围**：可改文件 / 模块；禁止顺手重构的范围。
3. **依赖与约束**：必须复用的接口、架构规则和既有行为。
4. **验收条件**：可观察、可执行、可判定的结果。
5. **测试要求**：需要新增或运行的测试及构建命令。
6. **非目标**：本任务明确不做什么。
7. **交付报告**：改动文件、设计选择、测试结果、未解决问题与潜在风险。

执行规则：

- 一个任务只解决一个主要问题；跨模块任务应先拆分或先提交接口方案。
- 如果发现现有架构与任务说明冲突，先报告并提出最小决策点，不自行扩大范围。
- 不删除或弱化失败测试来获得绿色构建。
- 不把“编译通过”当作功能验收。
- 先检查现有实现与调用方，再修改；避免重写已经可用的模块。
- 任务完成后由维护者检查 diff、测试结果和回归风险，再决定合并。

## 近期推荐顺序

1. 建立并确认当前 Windows / Linux CI 基线。
2. 完成 Launcher UI 第一轮收尾，并在 Windows WPF CI 中验证全部页面。
3. 完成资源包 / 光影包启用状态闭环（A2 已完成）。
4. 处理 Mod 依赖匹配与更新检查的设计，再分阶段实现。
5. 收敛诊断、无障碍与数据安全缺口。
6. 单独评估 Microsoft OAuth 外部条件；不让它阻塞可独立完成的工作。
7. 决定发布包方案，再实现签名验证与自更新。

不要同时启动多个会修改同一公共接口或同一 UI 页面的大任务。优先交付可独立测试、可审查、可回滚的小变更。
