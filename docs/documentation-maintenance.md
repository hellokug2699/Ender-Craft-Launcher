# 文档维护规则

本文是 ECL 公共仓库文档的维护规范。目标不是让文档看起来完整，而是让读者能区分**当前实现、历史决策、计划事项和未经验证的假设**。

## 1. 事实来源优先级

出现冲突时，按以下顺序确认事实：

1. 当前目标分支的源码、测试与构建配置；
2. 当前目标分支可核验的 CI 结果和实机验收记录；
3. 与当前实现一致的用户界面、CLI 帮助和运行行为；
4. 本仓库文档；
5. 旧提交、旧路线图、讨论记录和个人记忆。

文档不能反过来作为实现已经存在的唯一证据。无法从源码、测试或可复现行为确认的内容，必须标为“待验证”或删除，不得写成既成事实。

## 2. 描述实现状态

- 使用“当前实现”“当前限制”“计划中”“历史行为”等明确措辞，避免把不同时间点混在一起。
- “已完成”必须有实现依据；涉及正确性或用户体验的能力，还应有测试或实机验收依据。
- 单元测试通过不等于真实 Minecraft、真实账户、真实服务器或真实安装包已经验收。
- Mock 测试、CI、Windows 实机、Linux CI 和真实游戏实机应分别描述，不得互相替代。
- 不把路线图中的目标、ADR 中的决策或代码注释当作功能已交付的证明。
- 对功能覆盖范围使用精确边界，例如“下载批次已接入 Operation”不能简写成“所有操作均已接入任务中心”。

## 3. 代码变更必须同步文档

修改以下内容时，必须检查并更新所有受影响文档：

| 代码或行为变更 | 必须检查的文档 |
| --- | --- |
| 公共接口、模块边界、依赖关系 | `architecture.md`、相关 ADR |
| 设置项、默认值、作用域、继承 | `configuration.md`、`adr/0002-*.md` |
| 账户类型、令牌存储、登录/刷新/注销 | `authentication.md`、`architecture.md` |
| 下载源、重试、缓存、下载任务 | `operations.md`、`adr/0005-*.md`、相关服务文档 |
| 加载器、安装器、Java 选择 | `loaders.md`、`java.md`、相关 ADR |
| CLI 命令、参数、退出码 | 对应功能文档及 CLI 帮助示例 |
| 导入、实例目录、文件所有权 | `instance-import.md`、`architecture.md`、`roadmap.md` |
| 安全边界、凭据、代理、发布流程 | `repository-policy.md`、相关 ADR 和功能文档 |
| 新增/删除/改名文档 | 文档索引、相对链接和相关入口 |

不相关的文档不需要为了“同步”而制造无意义改动。

## 4. ADR 规则

- ADR 记录的是决策及其背景，不是当前功能清单。
- 状态必须明确为提议、已采纳、已取代或已废弃等可理解状态。
- 被取代的 ADR 保留历史决策，并链接到取代它的 ADR；不得继续把旧方案描述为当前实现。
- 实现与 ADR 决策发生偏离时，新增/更新 ADR 说明偏离原因；不能静默改写历史背景。
- ADR 日期表示决策日期，不因后续编辑而随意改成当前日期。

## 5. 路线图与验证记录

- 路线图只列当前仍有价值的目标；已经交付的事项移入已完成基线，取消的事项标记为暂不计划并说明原因。
- 每项状态必须与当前代码和测试相符。状态变化时更新图表、正文、优先级和验收条件，不能只改其中一处。
- 验证记录必须包含日期、环境、实际执行命令/测试范围、结果及可核验的 CI 或提交引用。
- 历史测试数量和旧 CI 链接可以保留，但必须明确它们是历史记录；不得将其写成当前 HEAD 的验证结果。
- 不得猜测 CI 状态、真实用户行为、上游服务可用性或发布日期。

## 6. 配置、命令和路径示例

- 配置项名称、默认值、允许值和作用域必须能在当前配置注册/读取实现中找到依据。
- CLI 示例必须与当前命令解析和 `--help` 输出一致；不确定时先运行命令或检查解析代码。
- 路径示例应说明是 Windows、Linux、应用数据目录还是 Minecraft 游戏目录。
- 代码标识符、错误码、文件名和 URL 必须与当前实现一致。
- 不在公开文档中放置 API key、令牌、签名私钥、内部部署凭据或其他秘密。公开客户端端点不应被误称为秘密。

## 7. 文档审查清单

每次文档变更或相关功能合并前，至少检查：

- [ ] 文档描述的是目标分支当前实现，而非其他分支或旧提交。
- [ ] 已区分实现、计划、限制和历史记录。
- [ ] 相关代码标识符、配置项、命令、路径与错误码仍然存在。
- [ ] ADR 状态与当前决策一致，旧决策有明确取代关系。
- [ ] 路线图图表、正文、状态和验收条件彼此一致。
- [ ] 内部 Markdown 链接有效。
- [ ] 没有凭据、密钥或不应公开的部署信息。
- [ ] 对验证结果的表述没有超出实际执行范围。

## 8. 自动检查的边界

CI 会检查 Markdown 相对链接和 ADR 状态字段等结构性问题。自动检查不能判断业务语义是否过时，也不能证明功能真实可用；语义审查仍须对照源码、测试和实际运行结果完成。
