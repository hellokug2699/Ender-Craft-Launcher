# 分支与合并策略

ECL 使用三条长期分支：`nightly`、`dev`、`main`。三者的 README 必须保持**项目级、分支无关**，避免分支状态写进共享文件后产生长期合并冲突。

## 分支职责

### `nightly`

主要活动开发分支。新功能、架构调整和快速修复首先在这里集成。

允许：

- 未完成但可持续推进的功能；
- 界面和内部 API 的快速调整；
- 实验性架构变更。

不代表正式稳定状态。

### `dev`

集成验证分支。用于确认跨模块协作、回归测试和 CI，并作为进入 `main` 前的候选基线。

### `main`

正式稳定基线。优先保证可用性、回归质量和发布质量。

## 推进关系

```text
nightly  ──持续开发──>  dev  ──集成验证与验收──>  main
```

原则上功能按这个方向推进。若需要从 `nightly` 直接同步到 `main`，必须明确确认该变更不绕过必要的 `dev` 验证。

## README 规则

这是最重要的合并约定：

1. **三个长期分支的 `README.md` 内容应保持一致。**
2. README 只描述 ECL 项目本身：功能类别、构建方式、文档入口、安全和许可证等。
3. **禁止把“当前分支已实现什么”写进 README。**
4. 分支定位、工作流和合并规则统一写在本文件。
5. 分支专属的开发状态、实验功能、验收记录和临时注意事项，应放进 Issue、PR、路线图或专门的开发文档，而不是 README。
6. 如果 README 在跨分支合并中产生冲突，应优先恢复为统一版本，而不是让冲突双方各保留一套分支状态。

这样可以把 README 从“随代码版本漂移的分支状态文件”变成“所有分支共享的项目入口文件”。

## 合并前检查

合并前：

- 重新读取源分支和目标分支的最新提交 SHA；
- 确认目标分支没有新的维护者提交；
- 确认相关 CI 已 `completed` 且 `success`；
- 必要时完成真实游戏、账户、安装包或其他实机验收；
- 检查 README 是否仍符合本文件的共享规则。

不要未经确认执行 reset、force-push 或删除他人的新提交。

## 临时集成分支

临时 `integration/*` 分支只用于一次性同步或解决复杂合并问题。

合并完成后：

1. 确认 PR 已 merged；
2. 确认目标分支包含合并提交；
3. 关闭已失效的旧 PR（如有）；
4. **删除临时分支。**

临时分支不应成为长期开发入口。
